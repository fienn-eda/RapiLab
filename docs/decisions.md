## gap #11(강제 재장전/탄약 제거)은 신규 발사-타임라인 프리미티브 없이 해소 — 샷 0개 세그먼트 + 재장전 공식 양방향화 + `burst_anchored_buffs`
- Date: 2026-07-20
- Context: Milk: Blooming Bunny가 마지막 미인코딩 유닛이었고, 2026-07-17 이후 "발사 타임라인 자체를 스킬이 조작(규모 중~대)"으로 적혀 있던 gap #11에 막혀 있었다. 그녀의 Embarrassment는 진입 시 **탄약 100% 제거 + 강제 재장전(속도 50% 감소)**을 건다.
- Alternatives considered: (a) 기록대로 발사 타임라인에 개입하는 재장전 이벤트 프리미티브를 신설. (b) Embarrassment를 통째로 defer하고 버프만 얇게 인코딩 — 그 상태가 킷의 심장이라 정직하지 않고, 재장전 다운타임을 빼면 **낙관 방향**으로 틀린다(ceiling). (c) 상태를 정적 무기 프로필(탄창 1발)로 접기 — 착수 초기에 내가 제안했다가 **Fienn 정정으로 폐기**: 그녀는 상시 루프가 아니라 자기 버스트 사이클과 교대한다. (d) 기존 프리미티브 조합.
- Decision: (d). 세 가지 사실이 확장 규모를 무너뜨렸다. ① 진입 조건이 "상태가 아닐 때"이고 Fienn 판정(2026-07-20)상 **버스트 면역으로만 해제**되므로, 진입은 자기 버스트 1회당 정확히 1회 — 매 풀차지 루프가 아니다. ② `_base_shot_records`가 각 구간을 `window_start`에서 **새 탄창으로 재시작**하므로(무기변형 v1의 resume 시맨틱), "탄약 제거 + 강제 재장전"은 곧 **샷 0개짜리 `weapon_mode_schedules` 세그먼트**다. ③ 재장전 속도 조작은 `reload_speed_percent` 콜러블로 이미 배선돼 있었다.
- 실제로 필요했던 소규모 확장 2건: **`reload_time_with_speed`** — 속도 감소를 시간 증가의 거울로 모델(`speed ≥ 0 → base/(1+s)`, `speed < 0 → base×(1−s)`). 기존 공식은 −50%에서 4초를 줬지만 Fienn 인게임 수치는 그녀의 2초 기본에 대해 **3초**다. 기존 소비자가 전부 +버프뿐이라 이 오류가 드러난 적이 없었다(음수 분기는 관측 한 점에만 앵커돼 있음을 docstring에 명시). **`burst_anchored_buffs`** — 버스트 시각 + 오프셋에 버프를 걸고 지속시간을 `UNTIL_NEXT_OWN_BURST`로 지정할 수 있는 소형 패스. `own_burst_activate` 규칙으로는 불가능한데, 그 규칙이 발동하는 시점엔 버스트 사이클 순회가 진행 중이라 **다음 버스트 시각이 아직 없기 때문**이다. 버스트 시각이 확정된 직후이자 샷 루프 **이전**에 배치해, 여기 놓인 버프가 데미지뿐 아니라 탄창/재장전/케이던스 콜러블에도 보이게 했다.
- Why: 세그먼트 프로필에 `charge_time`이 아니라 `rate_of_fire`를 쓴 것도 의도적이다 — 명시 rate 프로필은 케이던스 버프를 받지 않으므로, 아군 차지속도 버프가 빈 창을 줄여 유령 샷을 흘리는 경로가 구조적으로 막힌다.
- Consequences: **수집된 유닛 전원 인코딩 완료(미인코딩 0명).** E2E 검증: 강제재장 창에 샷 0개, 직전에 끊기고 창 종료 후 차지 1회를 거쳐 새 탄창으로 재개. Elegg·Mihara의 Pattern B 오분류와 같은 교훈이 반복됐다 — "엔진이 못 한다"를 실제 운용 빈도와 기존 프리미티브의 부수 효과에 대조하기 전에 확정하면 확장 규모를 크게 과대평가한다. 보류로 남은 건 Pierce 키워드(엔진에 per-hit pierce 플래그 없음, 기존 관례)뿐.

## "N회 크리티컬 히트 후" 트리거를 기대-크리 누적기(`every_n_critical_hits`)로 해소 — 2026-07-12의 "영구 defer" 판정 철회
- Date: 2026-07-20
- Context: EVE의 주력 딜 Unstable Energy가 "노멀공격으로 크리티컬 44회 적중" 트리거다. 2026-07-12 Julia 시그니처(Crescendo/Marcato) 인코딩 때 이 문구를 **영구 defer**로 판정했었다 — 엔진이 크리를 기대값으로만 다루고(히트마다 `crit_rate` 배율) per-hit RNG를 굴리지 않으므로 "이 샷이 크리였나"라는 이벤트 자체가 없기 때문. 그 판정이 맞다면 EVE는 킷의 심장이 빠진 얇은 인코딩만 가능했다.
- Alternatives considered: (a) 판정 유지, 영구 defer — Unstable Energy(240%×3연타)와 Electric 받댐 라이더를 통째로 누락. (b) 빌드시점 고정 발수 환산 — 44 / 0.75 = 59발마다. 단순하고 확장 불필요하지만 **덱의 크리율 버프를 전부 무시**한다(Miranda·Zwei·Julia 등이 있어도 발동 빈도가 그대로). (c) 샷마다 라이브 크리율을 누적하는 기대-크리 누적기. (d) 실제 per-hit 크리 RNG 도입 — 엔진의 결정론적 기대값 모델을 통째로 갈아엎는 일이라 검토만.
- Decision (Fienn, 2026-07-20): (c). Fienn의 수용 조건이 정확히 "기대값으로 계산하는 건 합리적인데, 덱에 크리율 버프가 적용이 안 되는 건 문제"였고, 이게 (b)를 배제하고 (c)를 규정한다. `per_shot_rules`에 `every_n_critical_hits` 모드 추가(`raid_simulator.py`): 샷마다 `min(1.0, base_crit_rate + registry.total_for("crit_rate", target, shot_time))`을 누적기에 더하고, 임계 N을 넘을 때마다 발동시키며 나머지를 이월한다.
- Why: 이벤트를 새로 만드는 게 아니라 **딜 경로가 이미 하고 있는 기대값 환산을 카운터에도 똑같이 적용**하는 것이라 엔진의 크리 철학과 일관된다. 라이브 조회라 덱 크리 버프가 자연스럽게 발동 케이던스를 바꾼다 — 엔진 테스트로 고정(50%→100% 크리율이 발동 간격을 정확히 절반으로 만든다).
- Consequences: EVE 인코딩 가능. **Julia(시그니처)의 Crescendo/Marcato도 같은 모드로 풀리므로 "영구 defer" 딱지를 떼고 재방문 대상이 됐다**(`docs/insights.md`의 해당 항목도 정정됨 — 그 문서에 남아 있던 "not a to-do for a future extension"은 이제 틀린 서술이었다). 알려진 한계 2건: ① 샷 루프가 유닛별로 돌기 때문에 **나중에 처리되는 아군의 per-shot 규칙이 거는 크리 버프는 안 보인다**(버스트/풀버스트 트리거 크리 버프는 모든 샷 루프보다 먼저 등록되므로 보임 — 통상적인 크리 버퍼는 대부분 여기 해당). ② 누적 비교에 `1e-9` 허용오차가 필요하다 — 0.3을 10번 더하면 2.9999999999999996이 되어 발동이 한 샷 밀린다(`burst_cycle`의 `last + cooldown` 반올림 함정과 같은 계열).

## Phase 7 sub-project 4: the caller-side session comes from the USER's own browser via a bookmarklet, not an operator account; roster storage stays client-side; sub-project 3 (ownership proof) is dissolved
- Date: 2026-07-19
- Context: the Stage 1 reconnaissance entry below established that a caller-side authenticated blablalink session can read any consenting public account's roster, but explicitly deferred "who supplies the caller-side session" for a hosted service. Fienn confirmed the near-term goal IS a public hosted service for other users, so this had to be answered against the project's standing "never store credentials, tokens supplied by Fienn" posture.
- Alternatives considered: (a) **operator session, server-side** — the service holds its own blablalink account and calls the API on every user's behalf. Best UX (paste a share URL, done; works on mobile) but rejected: it means storing operator cookies server-side (violates the credential posture, for the operator rather than the target); whether a game-unlinked burner account even works is UNVERIFIED (anonymous calls are refused with code 300001 "game not login", suggesting a real game-linked account may be required); session expiry stops ALL users at once until Fienn manually re-extracts cookies; one account querying hundreds of distinct open_ids is exactly the traffic shape that reads as scraping; and a ban on that single account kills the entire service — every one of these unknowns is service-fatal and outside our control. (b) **user's own session via a bookmarklet** — CHOSEN. (c) **a browser extension** (the ExiaInvasion precedent) — more capable for repeat sync, but carries store-review and maintenance burden not needed once the bookmarklet was proven to work.
- Decision (Fienn, 2026-07-19): (b). The user pastes their ShiftyPad share URL once; we generate a personalised bookmarklet containing only their own `intl_open_id` (no credential); they click it on a blablalink page, where it calls the three collector endpoints with their OWN session cookies and hands the raw payloads to our app via `window.open` + `postMessage`; our stateless backend assembles them and the result merges into localStorage. Storage model follows from this: the roster lives in the browser only, the assemble endpoint persists nothing, and there is no account system or login. An anonymous client id (localStorage UUID, analytics only, never sent to blablalink, never stored with a roster) was added for product analytics. **Sub-project 3 (ownership proof) is dissolved by this decision** — submitting your own data with your own session leaves nobody to prove ownership to; the previously-planned `profile_team` challenge is unnecessary.
- Why: postMessage rather than a direct POST from the blablalink page to our domain — a direct POST would depend on blablalink's CSP `connect-src` allowing us, which was never verified; postMessage isn't governed by `connect-src`, so this removes the unknown entirely rather than testing it. Empirically verified in a real browser (2026-07-19, not assumed): a bookmarklet runs on blablalink pages without being blocked by CSP; a credentialed fetch from that page context passes CORS and returns code 0 with complete data (the returned `recycle_room_researches` matched the test suite's ground truth exactly); `game_openid` is HttpOnly, so the bookmarklet CANNOT discover the open id itself, which is why it must be baked into the bookmarklet at generation time. Observed error codes: 300001 not logged in, 1303005 malformed/placeholder open id, 1 wrongly-formatted open id.
- Consequences: desktop only — bookmarklet installation is not realistically possible on iOS/Android, so mobile is an explicit non-goal. Changing the bookmarklet's logic forces EVERY user to re-install their bookmark, because loading an external script would be blocked by blablalink's script-src, so the logic is inline — this is why cheap correctness fixes were front-loaded before any user installed it. Storing no credentials and no rosters is a meaningful posture for a public service, at the cost of no cross-device sync and no recovery (re-syncing is two clicks, which is what makes that acceptable). Two implementation facts that corrected the design: React 19 HARD-BLOCKS `javascript:` URLs passed via a JSX `href` prop (verified in react-dom's PRODUCTION bundle, which substitutes a throwing stub), so the bookmarklet link's `href` must be written imperatively via a ref callback during commit; and `window.open` must be called BEFORE the three awaited fetches, or the click's transient user activation can expire and the popup gets blocked. Verified end to end on Fienn's real account: no popup block, 159 units imported, and a second run exercised the merge path (0 added / 159 updated), confirming previously-entered cube data survives a re-sync. Still outstanding, not blockers: a privacy policy document before any public deployment; a routine for refreshing the committed directory snapshot (a Nikke released after it is silently skipped); and deployment infrastructure (no remote exists today). Spec and plan: `docs/superpowers/specs/2026-07-19-roster-sync-bookmarklet-design.md`, `docs/superpowers/plans/2026-07-19-roster-sync-bookmarklet.md`.

## Multi-user preconditions: unknown overload effect types are skipped (with a warning), unobserved overload levels are linearly filled, and missing recycle-room/outpost lookups default to rank 0
- Date: 2026-07-19
- Context: Phase 7 roster sync must assemble OTHER users' rosters (see the Stage 1 reconnaissance entry below — a caller-side session can already read a consenting public account's data), but every reference table in `backend/app/stat_assembly.py` was fitted from Fienn's single roster. Four lookups raised `KeyError` on anything the fitting pass never observed: an overload effect type outside the named set, an overload roll level outside the observed levels for its type, a corporation-research rank row, and an outpost defensive-slot lookup.
- Alternatives considered: (a) fail the sync outright on any unknown input (maximum accuracy per-value, but reproduces the exact "can't sync another user" failure this work exists to fix — any account with even one effect type or level Fienn's roster never rolled can't sync at all); (b) surface an unknown overload line to the user as "unknown effect (type N)" rather than dropping it (visible, but still unusable — the simulator maps overload lines by name, so an unnamed line can't be wired to a stat regardless); (c) skip unknown/unobserved inputs with a warning and a sane default, and assemble the rest of the roster.
- Decision (Fienn, 2026-07-19): (c). Concretely: an overload roll of an unnamed effect type is dropped from that unit's assembled stats, with a warning naming the `(type, level)` so the type/level can be added once observed; an overload roll at a level not directly in the fitted table is filled via the type's own linear fit (see the linearity insight in `docs/insights.md`) rather than raising; a missing recycle-room research row defaults to rank 0; a missing outpost defensive lookup likewise defaults to rank 0.
- Why: the level-fill case loses no accuracy at all — the overload table is provably linear per type (cross-checked, not just curve-fit smooth; see `docs/insights.md`), so any unobserved level within a type's already-named range is mathematically determined, not guessed. The remaining case (a genuinely unnamed effect type) is the only real approximation: those types are most likely DEF/hit-rate-class lines the simulator's damage path doesn't consume anyway (the ones that matter for damage — ATK, elemental damage, crit, etc. — were all named early because they're the rolls players chase), so dropping one unnamed line and warning is cheaper than failing an entire roster's sync over a probably-inert stat. The warning is the safety valve: it names the exact `(type, level)` so the table can be completed from a real observation instead of the assumption being silently load-bearing forever.
- Consequences: another user's roster now assembles instead of crashing on the first unknown value. Residual risk: if an unnamed overload type turns out to be damage-relevant after all, a synced roster silently understates that unit until the warning is investigated and the type is named — this is a known, accepted gap, not a hidden one. Implemented on branch `wip/multiuser-preconditions` (commit `dcf3fc8`); backend suite 812 passed; the existing 77/77 overload-parity check is unchanged (all of Fienn's own observed types/levels still resolve identically, since the fallbacks only engage on genuinely unseen inputs).

## Elegg: Boom and Shock의 버스트를 고스트 캡까지 보류 — `burst_delay`가 `min_interval`을 갖게 됨
- Date: 2026-07-19
- Context: 13 Ghosts는 13스택(캡)에서 13히트, 미만이면 6히트만 나간다. 쿨마다(40초) 발동시키자 시뮬은 전투당 5번 버스트했고 그중 4번이 6히트 분기, 첫 발은 t=2에 고스트 3개뿐이었다. Fienn의 실제 플레이 서술은 "전투 중 2번, 그것도 13스택이 쌓인 후".
- Decision: `not_before = cap × capture_interval`(= 78초, 최초 캡 도달 시각), `min_interval = spend_at_cap × capture_interval`(= 54초, 버스트로 소모된 뒤 다시 캡까지 채워지는 시간)을 그녀 자신의 스킬 값에서 유도해 `burst_delay`에 싣는다(`app/skill_rules/elegg_boom_and_shock.py::build_elegg_burst_delay`, `registry.py`의 `_BURST_DELAY_BUILDERS`). 하드코딩한 측정치가 아니라 빌더 함수 — Diesel의 지연은 고정값(`_DIESEL_BURST_DELAY`)이라 다른 이유로 `get_burst_delay`가 빌더 형태를 취함(값이 유닛 스킬값에서 유도되는 경우까지 커버).
- Why: 54초 재충전이 40초 쿨보다 길어서 **실효 케이던스는 쿨다운이 아니라 재충전**이다. 결과: 78.2초 / 136.2초 2번 버스트, 둘 다 13스택 — Fienn의 서술과 일치.
- 구현 세부(`burst_cycle.py::_ready_at`): `min_interval`은 CDR로 되감기는 `last_used_at`이 아니라 새로 추가한 `last_fired_at`(CDR에 영향받지 않는 실제 발동 시각 사본)에서 잰다 — 고스트는 벽시계로 차고, 아군 쿨감이 그걸 앞당기지 못하기 때문. 이걸 `last_used_at` 기준으로 뒀을 때 54초 간격이 39초로 3번 줄어드는 회귀가 있었다(고쳐서 병합).
- Consequence: "종료 직전 1번" 같은 부가 운용은 모델링하지 않음(Fienn이 먼저 말한 "2번"이 일반형이라 YAGNI). 지연된 유닛이 자기 티어에 혼자면 그 사이클은 아예 안 뜬다(조기 발동으로 credit하는 것보다 정직 — 아래 `burst_delay` 엔진 결정과 공통).

## `burst_cycle`에 유닛별 버스트 지연(`burst_delay`) 도입 — 스킵/보류/최소간격 3형태
- Date: 2026-07-19
- Context: 2026-07-17에 "Diesel은 짝수 사이클 버스트가 강한데 `burst_cycle`이 '한 사이클 거르기'를 표현 못 한다"로 미뤄둔 갭. Diesel 인코딩 시점에 착수하기로 했던 항목이고, 이번에 Diesel과 Elegg 두 소비자가 생겨 구현.
- Decision: `burst_cycle`의 덱 멤버가 선택적 `burst_delay`를 가진다. 세 형태: `{"skip_cycles": N}`(앞 N사이클에서 그 유닛을 제외), `{"not_before": T}`(T초 전 발동 금지), `{"min_interval": S}`(실효 쿨다운을 S로 늘림). 세 형태 모두 멤버별 ready time을 계산하는 한 곳(`burst_cycle.py::_ready_at`)에 접혀 들어가, 티어 선택(`tier_ready_time`)과 eligibility 체크가 지금까지와 동일한 산술을 그대로 쓴다 — 기존 fractional-CDR 반올림 회귀 수정이 그대로 유지됨.
- Why 두 축을 다 두는가: Diesel의 상태는 사이클 카운트가 근거이고(그녀가 첫 풀버스트에 참여했는지), Elegg는 자원(고스트) 충전 시간이 근거다 — 서로 환산 불가능한데, 덱 구성에 따라 사이클 길이 자체가 달라지기 때문이다.

## Deck search now scores every intra-tier ordering per combination, not a canonical order refined for a top-K shortlist — closes a mis-scoring gap measured up to 78%
- Date: 2026-07-19
- Context: `search_best_decks` ranked each shape combination on ONE arbitrary ("canonical") intra-tier order, then only permuted the top 40 combinations by that canonical score (`permutation_top_k`) to find the true best order. This treated order as a tie-break — but `simulate_burst_cycle` fires the FIRST ready member of each burst tier, so order decides which tier member never bursts at all. That is a real strategy, not an artifact: a (1,1,3)'s rightmost Burst 3 commonly runs as a buffer/normal-attack unit that never bursts, Prika must burst before Mint for her Encore to hand Mint the slot, and Velvet / Helm: Aquamarine are usually seated without ever bursting (Fienn, 2026-07-19). The new measurement script `scripts/measure_intra_tier_ordering_impact.py` quantified the damage: of 56 measured (1,1,3) combinations, 9 swing over 10% between canonical and best order (worst case 78%), and the TRUE best deck for that dataset ranked #21 under canonical scoring — outside the top-40 shortlist that ever got permuted, so the old search could not have surfaced it under any budget.
- Decision: `search_best_decks` (`backend/app/deck_search.py`, commit `ed9ef0a`) now scores EVERY intra-tier ordering of EVERY shape combination — `_all_intra_tier_orderings` replaces the canonical-score-then-refine-top-K flow. `permutation_top_k` is removed entirely; `sim_budget` now counts orderings (what actually costs sims) rather than combinations, so the existing pool-pruning fallback (`prune_candidate_pool`) still triggers correctly when the full ordering count would blow the budget.
- Why: intra-tier order is not a tie-break between equivalent decks, it's a role assignment that changes which unit contributes at all — so ranking a combination on a single order can mis-score it by exactly the amount that order differs from the best one, and a fixed top-K shortlist compounds the error by only ever fixing the mistake for the K combinations that happened to look best under the wrong order in the first place. Scoring every ordering is the only way to rank combinations on their true achievable value; the measured 78%-worst-case / rank-#21 result shows this was not a marginal gap.
- Consequences: `permutation_top_k` is gone — any caller that passed it now gets a `TypeError` rather than a silent behavior change (none did outside tests, which were updated in the same commit). Cost is now driven by ordering count, not combination count — a (1,1,3) costs 3! orderings, a (1,2,2) costs 2!×2!, both scored in full whenever they fit inside `sim_budget`, else the roster is pruned first via `prune_candidate_pool`. `scripts/measure_intra_tier_ordering_impact.py` is kept as a reusable tool, not a one-off — rerun it after changing `burst_cycle`, the deck search's scoring, or encoding a unit whose value depends on NOT bursting, to confirm ordering sensitivity is still handled and to re-derive the numbers above. See the companion insight in `docs/insights.md` ("Deck search").

## The outside-Full-Burst per-shot filter is closed on the right (`t <= end`), not half-open like the during-FB filter — a shot exactly at a window's end counts as inside FB
- Date: 2026-07-19
- Context: Laplace: Signature's Hero Bomber trigger uses `every_outside_full_burst` to fire only on Full Charge hits landing outside her own Full Burst window. Her weapon-mode segment's 93rd Buster tick can land exactly at `burst_time + 10.0`, which is precisely the Full Burst window's end — and `_resource_fill_times`'s outside-FB filter (`raid_simulator.py`) previously excluded the window with a half-open `start <= t < end` check (matching the existing during-FB filter), so a shot landing exactly on `end` read as "outside," spuriously firing Hero Bomber on a shot that is still, in every meaningful sense, part of the Full Burst.
- Decision: change the outside-FB filter to a closed interval, `start <= t <= end` — a shot at the window's exact end boundary counts as inside FB (matching "the last instant of Full Burst is still Full Burst," not "Full Burst just ended").
- Why: the alternative reading (end-of-window = already outside) is the one that produced the bug; the fix makes a coincidental float landing on the boundary resolve to the more defensible in-game interpretation, and is pinned by a regression test with a synthetic segment tuned to land exactly on the boundary (`test_raid_simulator.py`).
- Consequences: the during-FB filter (`per_shot_every_during_full_burst`) was deliberately left half-open (`start <= t < end`) rather than also being widened to match — widening it would double-count a boundary shot in BOTH the during and outside tallies for two different callers. The result is a narrow, intentional asymmetry: a shot landing exactly at a Full Burst window's end is caught by neither filter (not "during," per the during filter's still-open check; not "outside," per the outside filter's now-closed check). No current consumer is affected by this gap (Laplace's boundary tick is now correctly excluded from the outside filter, and nothing currently depends on it being counted as "during" either) — recorded as a known conservative asymmetry for the next per-shot-filter consumer to be aware of. ## Summon/stack cadences come from measurement, not from the skill text
- Date: 2026-07-17
- Context: Encoding Ein and Raven, the skill text was actively misleading twice. Ein's Feather Shot reads "Activates when Near Feather is summoned ... ## New engine primitive `scheduled_nukes` for self-computed damage cadences
- Date: 2026-07-17
- Context: Ein's feather attacks and Raven's Shock Wave both land on a cadence `periodic_nukes` (a fixed interval) cannot express — Ein's varies with how many feathers are alive, Raven's with her own Full Charge times. Later the same day, extended so a schedule can read the owner's own firing timeline off `context.shot_times[slug]` (Raven's need) — the engine already kept `shot_times_by_slug`, so this exposed existing data rather than computing anything new, and left Ein's `(context, fight_duration)` signature untouched.
- Why: these schedules are fully deterministic — summons come from battle start plus the owner's burst times, both settled before the damage pass runs — so precomputing is exact, not an approximation. Reach for it only when the cadence genuinely varies — a fixed interval is still `periodic_nukes`. Catalogued in the encoding skill's `engine-capabilities.md`.

## Throughput lever for the 282s five-deck allocation overrun: simulation parallelism (ProcessPool), not a smaller tier cap
- Date: 2026-07-17
- Context: The entry below measured the shipped peeling+swap algorithm at 282.17s against a seconds-to-a-minute budget target and left the throughput-lever choice open between two alternatives: (a) shrink the search's tier cap (trade search breadth/quality for speed), or (b) parallelize the simulation itself via `ProcessPool` (trade implementation complexity for speed at unchanged breadth).

## Swap phase gets its own time budget, anchored after (unbudgeted) peeling completes
- Date: 2026-07-17
- Context: The five-deck allocator (`backend/app/deck_allocation.py`) runs greedy peeling then a same-tier swap hill-climb, both under one nominal `time_budget_sec`. The deadline was originally computed once at entry (`start + time_budget_sec`), before peeling ran. Peeling itself is unbudgeted and took ~100s+ on the real 42-unit roster, so the shared deadline had already passed by the time peeling finished — the swap phase, which is where quality improvements actually come from, never ran a single iteration. The first full-roster measurement (103.92s, 3 decks) was silently swap-free because of this.
- Decision (Fienn): give the swap phase its own budget, always up to the full `time_budget_sec` measured from when peeling completes, not from function entry. Peeling is treated as an unbudgeted prerequisite step whose own cost isn't charged against the swap deadline.
- Why: the swap hill-climb is the actual quality mechanism (peeling alone is a fast but locally greedy first pass); anchoring its deadline before an unbudgeted, unpredictable-length peeling phase meant the phase that mattered most for quality was starved to zero on any roster large enough for peeling to take non-trivial time — exactly the case that matters (the real roster).
- Consequences: `time_budget_sec` now bounds two phases separately rather than one shared window (`docs/roadmap.md` and `f31fc32`'s note both updated to say the budget caps only the swap phase). Re-measuring with this fix gave the real 282.17s/3-deck/5.18B figure above — noticeably slower than the old (buggy) 103.92s, but that number represented incomplete work, not a faster algorithm.

## Synergy candidate-pool shells are measured over both intra-pair orderings, not the alphabetical order
- Date: 2026-07-17
- Context: `prune_candidate_pool`'s synergy-set marginal-score measurement (`backend/app/deck_search.py`) placed a `SYNERGY_SETS` pair into a reference shell in a fixed (alphabetical-slug) order. `burst_cycle` fires the leftmost eligible same-tier unit first — with the alphabetical order, Prika landed after Mint in the shell and never got to burst before her, so her Encore (which requires Mint to have already sung) never fired during the measurement. Prika and Mint's synergy score was silently near-zero. Caught in final review (Critical).
- Decision: measure a synergy pair's shell score under BOTH orderings of the pair (`members` and `members[::-1]`) and take the max, rather than a single fixed order. Applies to both `SYNERGY_SETS` entries: `{mint, prika}` and `{mast-romantic-maid, anchor-innocent-maid}`. Curation constants: `SYNERGY_SETS` (explicit pairs) plus `WEAPON_SYNERGY_ANCHORS = {"tove": "SG"}` (a themed pool — Tove pulls in SG-weapon B3 attackers as candidates whenever she's rostered, since a plain marginal-score cut would otherwise miss units whose value depends on her weapon-scoped buffs rather than direct stacking).
- Why: `burst_cycle`'s left-priority firing order makes a synergy pair's measured value order-dependent whenever one member's payoff requires the other to act first (Prika's Encore is exactly this shape) — a single fixed order silently measures only one of the two real in-game orderings, understating (here, near-zeroing) the pair's true synergy value.
- Consequences: The same commit also fixed marginal scores to be baseline-subtracted (each reference pass computes its own baseline once; a candidate already present in the reference correctly scores 0.0 without a redundant re-simulation) — a correctness cleanup found during the same review pass, not a new modeling choice. Any future `SYNERGY_SETS` addition must be checked for the same left-priority ordering trap before trusting a single-order measurement. See `docs/superpowers/plans/2026-07-17-five-deck-allocation.md`'s "Amendments (final review, 2026-07-17)" section.

## Deck-shape search is hard-constrained to (1,1,3)/(1,2,2)/(2,1,2), not "at least one of every tier"
- Date: 2026-07-17
- Context: The five-deck allocator's underlying single-deck search (`shape_combinations`, `backend/app/deck_search.py`) needed a tier-shape rule for which 5-unit Burst-1/2/3 combinations are worth generating. The general engine constraint up to this point was just "at least one of each tier" — which also admits shapes real play never uses (e.g. (3,1,1), (1,3,1)).
- Decision (Fienn): restrict shape enumeration to exactly three tuples of (B1, B2, B3) counts — `(1,1,3)`, `(1,2,2)`, `(2,1,2)` — reflecting Fienn's domain knowledge of which shapes real deck-building actually uses, rather than every combinatorially valid "at least one per tier" shape.
- Why: the untargeted "at least one per tier" rule was structurally correct but wasteful and meta-inaccurate — it would spend search budget generating and scoring shapes no real player deck takes, and could surface a "best" deck in a shape nobody would actually build. Hard-coding the three real shapes shrinks the search space to what matters and keeps recommendations aligned with how decks are actually played.
- Consequences: `ALLOWED_SHAPES = ((1, 1, 3), (1, 2, 2), (2, 1, 2))` in `deck_search.py` is now the sole shape filter for `shape_combinations`; any future shape found to be real play (a 4th tuple) needs an explicit addition here, not a reversion to the general rule. This constraint is also why the five-deck allocator's real-roster run could only build 3 decks (see the allocation-measurement entry above) — a roster with only 4 loadable B1 units runs out of B1 slots to fill these shapes well before 5 decks are built, and that scarcity is inherent to the roster, not a search-quality bug.

## Five-deck allocation algorithm: greedy peeling + same-tier swap hill-climb, not ILP or the search's own enumeration
- Date: 2026-07-17
- Context: Phase 5 needed to split a full roster into up to 5 non-overlapping decks maximizing combined damage against the same boss. Because every deck fights the SAME boss, total damage is separable — it's exactly the sum of each deck's own independently-computed score, which rules out needing a joint objective function and opens the door to a much simpler algorithm than a general multi-deck joint optimizer.
- Decision (Fienn): (1) build decks one at a time via greedy peeling — repeatedly take the best available deck from the remaining roster (via the existing budget-aware single-deck search) and remove its members before searching for the next deck; (2) follow with a same-tier swap hill-climb across the built decks, trying same-burst-tier unit swaps between decks to find local improvements, budgeted separately (see the swap-budget entry above). Alternatives considered and rejected: ILP/exact set-packing over all possible deck combinations (rejected — pre-computing every combination's score to feed an ILP solver was estimated at tens of hours on the real roster, infeasible); a two-stage "proxy score, then exact enumeration" scheme (rejected as the primary mechanism — the proxy's own enumeration step was itself the bottleneck being avoided, so it could only ever serve as a subordinate helper, not the main algorithm).
- Why: same-boss deck separability means a good deck for the "current best roster state" is very likely still a good deck once its members are removed — greedy peeling exploits this directly instead of paying for global joint optimization the objective's structure doesn't actually require. The swap hill-climb recovers most of what greedy peeling's local-only choices miss (a member that would be better used in a different deck) without the combinatorial cost of ILP.
- Consequences: `backend/app/deck_allocation.py`'s `allocate_decks` is peeling + swap, not exact — it is not guaranteed globally optimal, only a good-quality heuristic bounded by its time budget. This is the algorithm measured at 282.17s/3-decks/5.18B on the real roster (entry above). The swap phase needing its own budget (separate entry above) was a bug found after this algorithm shipped, not part of the original algorithm choice itself.

## Stage 0.5: epoch + stat-bundle memo cuts `total_for` call count, but 50ms target not reached — remainder handed to Fienn
- Date: 2026-07-17
- Context: After Stage 0's segment-table rewrite (below) got `evaluate_deck` to 133.66ms, profiling showed the remainder was flat per-call overhead: `total_for` was still being called ~255K times per sim (17 stats × per-damage-instance), each paying Python call/dict overhead even though the segment-table lookup itself is now cheap. Fienn's call was to attack call COUNT next, not per-call cost.
- Decision: Add `EffectRegistry.state_epoch(target, time)` — the union of every stat's boundary times for a target, collapsed into a single integer timeline — as a memo key, combined with `(slug, epoch, version)` to bundle all 17 phase-2-consumed stats (`_BUNDLE_STATS` in `raid_simulator.py`) into one dict resolved once per (target, epoch, version) instead of once per stat per call. Implemented as `raid_simulator.simulate_raid`'s local `_stat_bundle(slug, time)` closure, memoized in a plain dict keyed on `(slug, registry.state_epoch(target, time), registry.version)`.
- Why: Within one state epoch, every one of the 17 bundled stats is provably constant (see the epoch-superset-invariant insight below), so caching the whole bundle together — rather than each stat separately — is safe and cuts repeated `total_for` calls from 17/instance to amortized ~0/instance after the first hit in an epoch.
- Consequences: 133.66ms → 103.43ms (23% further cut on top of Stage 0's 94.5%). **The spec's 50ms target was NOT reached (2.1× over)** — the remaining cost is per-damage-event fixed overhead (dict construction + `calculate_damage` invoked ~21K times/sim), which no memo can remove since each call needs a genuinely distinct answer. Per the spec's own stop condition, no further mechanism was built without a doc-and-decide checkpoint — logged here and handed to Fienn to decide whether 103ms is acceptable or a different engine-level change (e.g. reducing damage-event count itself) is warranted. **Follow-up decision (Fienn, 2026-07-17): stop here.** 103.43ms is accepted as the final single-sim cost — the remaining gap is flat call overhead with no further algorithmic lever visible (ROI on more per-call optimization has collapsed), so the 2.1× shortfall against the 50ms target is absorbed by simulation-level parallelism instead (`ProcessPool`, see the throughput-lever decision above) rather than by a further per-call optimization pass. **`_stat_bundle` is phase-2-only** — see the insight below on the phase-1 version-churn trap this decision's implementation ran into and reverted from. Spec: `docs/superpowers/specs/2026-07-17-effect-registry-performance-design.md`; implementation plan: `docs/superpowers/plans/2026-07-17-effect-registry-stage05.md`.

## Stage 0: EffectRegistry rewritten to per-(stat, slug, element) segment tables + bisect, replacing the full linear Effect scan
- Date: 2026-07-17
- Context: `evaluate_deck` (the deck-search inner loop) took 2.4s/sim, 93% of it inside `EffectRegistry.total_for` — the original implementation linearly scanned every registered `Effect` on every call (5.25M active-effect checks per sim) to sum whichever ones matched a `(stat, target, time)` query. This made the simulator too slow to use for the planned larger deck search.
- Decision: Replace the linear scan with a per-`(stat, slug/scope-key, element)` segment table: each key maps to a sorted list of boundary times and running-sum segments, looked up via `bisect`. Invalidated by a registry-wide `version` counter bumped on every `add`/`add_refreshing`/`truncate_open_ended` call, so any mutation forces a full rebuild of affected segment tables rather than requiring incremental patching. **Hard constraint: bit-identical output** to the original scan — segment sums are accumulated in EFFECT INSERTION ORDER (not chronological order), because float addition is non-associative and re-ordering the sum by time could flip the last bit of a result versus the original code path. Verified via a parity net that runs the new segment-table implementation against a frozen, never-modernized copy of the original naive scan across the full existing test suite, plus dedicated segment-boundary/negative-window-truncation cases.
- Alternatives considered & rejected: (1) a stat-only index (drop the slug/element dimension) — too coarse, would still scan every effect matching just the stat, most of which don't match the actual target; (2) numpy-vectorized summation — pulls in a new dependency and requires a much larger rewrite for a problem this segment-table approach solves without one.
- Why: The `(stat, slug, element)` key is exactly the dimensionality `total_for`'s callers query on, so segment tables collapse what was an O(effects) scan into an O(log segments) bisect per call with no loss of query generality. Preserving insertion-order summation was non-negotiable per the parity requirement — this is a performance rewrite, not a numerics change, and any bit drift would be indistinguishable from a real bug during the parity net's own construction.
- Consequences: 2410ms → 133.66ms (94.5% reduction). The parity-net test pattern (frozen naive reference + cross-check) is a reusable template for future bit-identical performance rewrites (see the insight below). The existing test suite itself got 3× faster as a side effect (22s → 6.5s), since many tests exercise `total_for` heavily. Design spec: `docs/superpowers/specs/2026-07-17-effect-registry-performance-design.md`.

## dotgg data files are indexed by their JSON "url" field, never by filename
- Date: 2026-07-16
- Context: Building the roster assembly layer's dotgg-source skill-value parser and weapon-stats loader (`docs/superpowers/specs/2026-07-16-roster-assembly-api-design.md`). dotgg character JSON filenames use dotgg's OWN slug convention (e.g. `char_drake-nikke.json`), which does not match this project's roster slug (`drake`) — a naive `data/dotgg/char_<our_slug>.json` filename guess fails for any unit whose dotgg slug differs from ours.
- Decision: Locate a unit's dotgg data file by reading each file's own JSON `"url"` field (which encodes dotgg's slug unambiguously) and matching it against the unit, rather than constructing a filename from our slug. Implemented in `backend/app/skill_values.py` (`_dotgg_path_for`).
- Why: Filename-guessing silently fails (file not found → wrongly excluded) whenever the two slug conventions diverge, and that divergence is common enough (Drake is the first observed case) that it can't be dismissed as a one-off. Reading the file's own declared identity is robust to any slug-naming mismatch and doesn't require a hand-maintained our-slug→dotgg-slug lookup table.
- Consequences: Every dotgg-backed load (skill-value parsing source `"dotgg"`, and weapon_stats in `user_roster.py`) goes through `_dotgg_path_for` rather than a direct filename join. Adding a new dotgg-sourced unit needs no manual slug-mapping entry — it "just works" as long as the data file's `url` field is present, which is a data-collection precondition, not a code change.

## Skill-value manifests are colocated in each skill_rules module, verified by a fixture-comparison assembly harness
- Date: 2026-07-16
- Context: Roster assembly (`docs/superpowers/specs/2026-07-16-roster-assembly-api-design.md`) needs to turn a user's per-skill-level data into the `skill_values` dict each unit's builders expect (keyed by module-chosen sub-skill names, e.g. `values["transform"]`, holding `description_value_NN` slots). No code previously mapped a unit's builder-facing key names to skill-level slot indexes — that mapping only existed implicitly in each encoder's head when they hand-transcribed test fixtures.
- Decision: Each `skill_rules/<slug>.py` module declares its own `SKILL_VALUE_MANIFESTS` dict next to the builders whose key names it describes (mirroring the existing `_BUILDERS`-style per-module registration pattern), aggregated by `registry.get_skill_value_manifest(slug)`. Correctness is anchored by an assembly harness (`backend/tests/test_skill_value_assembly.py`) that, for every unit with a manifest, parses max-level `skill_values` from the real local data files and compares each slot against that SAME unit's own hand-transcribed test fixtures (the existing `TRANSFORM`/`ULTIMATE`/... module-level constants used to test the builders) — the fixtures are treated as ground truth since they were verified during encoding. A known hazard (encoders sometimes skip a non-value number in the raw text, e.g. "Burst stage 3," while counting another, e.g. "after 100 normal attack(s)") is handled by a per-unit `drop_tokens` override inside its `SKILL_VALUE_MANIFESTS` entry added only where the harness actually fails — never a speculative heuristic. Alternative considered and rejected: a single central slug→manifest table in `registry.py` (rejected — it would live apart from the builders whose key-name conventions it encodes, and would drift out of sync as builders change their key names without a forcing function to update it).
- Why: Colocation keeps the mapping beside the code whose key-name choices it depends on, the same way `_BUILDERS` registration already works — a builder rename is caught immediately (or at least locally) rather than silently breaking a distant central table. Comparing against each unit's own existing test fixtures (rather than writing new expected values) reuses already-verified ground truth instead of introducing a second, unverified source of truth for the same numbers.
- Consequences: A module without a `SKILL_VALUE_MANIFESTS` entry is simply not loadable from user data — excluded and reported (see the exclusion-policy decision below), not an error. Mismatches must be fixed via per-unit `drop_tokens` overrides, never by loosening the harness's comparison or editing the fixtures themselves — the fixtures are load-bearing ground truth for both the builder tests and this harness. New encodings must declare a manifest and pass the harness as a normal step of the encoding workflow going forward (per the `nikke-skill-encoding` skill). First batch: `ade_agent_bunny`, `anchor_innocent_maid`, `arcana`, `arcana_fortune_mate`, `blanc`, `brid_silent_track`, `drake`, `grave`, `little_mermaid`, `mast_romantic_maid`, `mint`, `modernia`, `nayuta`, `rapi_red_hood`, `rei_ayanami` — the remaining encoded roster is a pending backfill batch.

## Gap #3: member-subset targeting resolved as a live-filter "slugs:" scope, not a new Effect scope
- Date: 2026-07-16

## Ada Wong: Special Modification's charge-speed half folded into a net charge-damage bonus (magazine-boundary trap)

Implementation then hit the documented magazine-boundary trap (see `docs/insights.md`, "charge_speed_percent granularity"): charge speed is only evaluated once per magazine start, and a 1-round Effect granted mid-magazine covers no magazine boundary — so the ×4 slowdown NEVER actually lands, verified by `test_one_round_charge_speed_grant_is_inert_mid_magazine`. - Decision: Apply Fienn's documented fallback instead of the raw pair: a net 1-round `charge_damage_bonus` of `15/4 − 1 = +2.75` (the nominal +1500% bonus divided by the ×4 time cost it was supposed to cost, minus the round's own baseline of 1). - Why: A literal implementation of the two-buff pair, given the engine's existing per-magazine granularity, would be strictly better than the real skill (all of the damage bonus, none of the time cost) — an unintended overstatement caused by an engine limitation, not a deliberate simplification. Folding the time cost into the damage number keeps the net DPS effect honest without requiring the engine to support sub-magazine charge-speed windows (out of scope — see the general granularity insight).
- Consequences: See `backend/app/skill_rules/ada_wong.py`'s module docstring and `build_ada_wong_rules` for the derivation. This is the second known instance of the magazine-boundary charge-speed trap (the first being the general insight logged when Attack/Charge Speed were first built) — any future unit whose kit pairs a short-lived charge-speed grant with a charge-damage grant should be checked against this same trap before encoding literally.

- Date: 2026-07-16
- Context: Attack Speed and Charge Speed were previously documented as NOT modeled — filed in `docs/engine-gaps.md`'s "만들지 않는 것" (do-not-build) section and in the `nikke-skill-encoding` skill's "Stats the engine does NOT consume" list — on the rationale that they were inert (unwired, no damage-formula consumer).

Once two units' headline kits depended on it, the honest choice was to build the real mechanism rather than encode them thinly around a gap.

(3) `full_burst_bonus_eligible` — an opt-in boolean threaded through `record()`/`_damage_instance` and `Pulse` (both the `drain_instant_damage` and per-shot-nuke drain sites) — is the actual WIRING for the "as additional damage" text rule (see the entry below): at damage-computation time it's checked against the existing `full_burst_windows` list at that specific damage instance's own recorded time (`start <= time < end`), and only sets `full_burst_bonus=1.0` if both the opt-in flag and the window check pass.
- Why: A burst nuke firing on a delay (not at cast time) needed its own timing hook rather than forcing every `dynamic_hit_count_nukes` consumer through a zero-delay default; an own-status window needed to reuse the existing "count shots in a window" shape (`per_shot_every_during_full_burst`) rather than inventing a new fill mechanism, just anchored to a different event stream (`burst_times` instead of `full_burst_windows`). `full_burst_bonus_eligible` reuses the exact opt-in-per-instance pattern already established by `extra_charge_bonus`/`extra_flat_atk` on `record()`.
- Consequences: First consumer of all three: Asuka Shikinami Langley: Wille — Anti A.T. Field's stack-fill uses the status-window fill kind; Annihilation's 9s-delayed nuke uses `fire_delay` + `own_burst_delayed`; both of her "as additional damage" nukes (the unconditional 471.86% every-50-shots nuke and the delayed 6.62% Annihilation nuke) opt into `full_burst_bonus_eligible`. Latent edge case worth flagging for a future unit: `full_burst_start` fires at the SAME timestamp as the tier-3 burst that triggers it (not strictly after), and the window check is inclusive-start (`start <= time < end`) — so a hypothetical eligible nuke fired AT cast time with zero delay would still read as "inside" the Full Burst window under this check. Doesn't affect Asuka (her eligible nukes are either delayed 9s or fire on an unrelated per-shot timer), but the next unit with a same-instant, zero-delay "as additional damage" nuke should have this checked explicitly rather than assumed. Anti A.T. Field's own 15.62%-of-ATK per-shot direct-damage bullet (separate from the 471.86% nuke) remains deferred — it needs a Full-Burst/own-status-WINDOW-GATED PER-SHOT TRIGGER to directly fire a nuke, not just a resource fill, the same still-unbuilt shape as Soda's residual co-fired buff (`engine-gaps.md` gap #7) — Asuka is a second, still-unbuilt consumer of that gap.

## Squad-burst-cycle-conditional resource fill relies on Fienn-confirmed strict burst-tier ordering
- Date: 2026-07-12
- Context: Encoding Maiden: Ice Rose's MP resource ("Meditation": +1 stack if MP==0 whenever ANY squad member's Burst Stage 1 fires; +1 if MP>=1 on entering Full Burst) needed a fill mode unlike anything built so far - it's driven by GLOBAL burst-cycle events (not the resource owner's own shots, unlike every existing `fill` kind) AND conditioned on the resource's OWN running value at the moment of the event, making it a genuinely stateful walk rather than a flat deterministic schedule. Getting the fill right also depended on knowing precisely when Maiden's own burst (which drains MP to 0) fires relative to Full Burst formally starting, in the same instant.
- Decision: Add a `("squad_burst_cycle_conditional", [(event_predicate, gate_fn, delta), ...])` fill kind, resolved by a new `_resolve_squad_burst_cycle_resource` in `raid_simulator.py` that walks `simulate_burst_cycle`'s own event log in order, checking each `(event_predicate, gate_fn)` pair against the resource's running count as it reaches each event, and applying `delta` when both match. The owner's own-burst reset (from `ResourceSpec.resets`, `trigger: "own_burst"`) is checked INLINE against each event during the same walk - not merged in via a separate sort step - so that same-instant ordering between a reset and a fill rule is exactly what the underlying event log says it is, not an artifact of how two independently-sorted lists happen to interleave.
- Why: Fienn confirmed, when asked to resolve this ordering question directly, that burst1 -> burst2 -> burst3 -> full-burst-enter is a STRICT, NEVER-VIOLATED sequence in this engine - a unit's own burst-tier fire always precedes Full Burst entry within the same instant. This is what makes Maiden's Diamond Dust behave in a specific, verifiable way (see below) rather than being ambiguous, and it's the reason the inline-check approach (not a separate sort) was chosen: correctness had to be structural, matching the engine's own event-log order, not something that could silently drift if the two event streams were sorted independently with a tie-breaking convention that later changed.
- Consequences: This directly determined that Maiden's Diamond Dust (a `dynamic_hit_count_nukes` consumer, see below) always hits EXACTLY ONCE per cycle in this engine - her own burst provably drains MP to 0 before Full Burst's "if MP>=1" rule can ever observe a nonzero value, so that second fill rule is a real skill bullet that can never actually contribute in a simulated raid. It's modeled anyway (not silently dropped), with the reasoning spelled out in `maiden_ice_rose.py`'s module docstring, for documentation honesty. Also introduced in the same commit: `extra_flat_atk` on `record()`/`_damage_instance` (mirroring the existing `extra_charge_bonus` parameter's precedent exactly) - lets a specific nuke (Diamond Dust, "1372.8% of the sum of 10% of final Max HP and ATK") fold a percent-of-Max-HP bonus into ONLY that nuke's own flat_atk term, without leaking into normal attacks or any other damage instance from the same slug (a plain registry Effect would leak everywhere, since flat_atk is read unconditionally by every damage instance for that slug). And `dynamic_hit_count_nukes` itself: a burst nuke whose HIT COUNT (not just its percent) is a resource's value at burst time, reading the PRE-reset count via `resource_count_before_reset` (see the ADR below) for each of the owner's own bursts.

## Resource resets (pre/post value) and `resource_gated_buffs` resolve in the resolution pass, not `on_tier_fire`
- Date: 2026-07-12
- Context: Encoding Soda: Twinkling Bunny's Golden Chip needed two things no existing resource capability covered: (1) her burst RESETS the chip to a fixed value (17), consuming whatever had built up, rather than only ever incrementing; and (2) a burst-fired BUFF (ATK +65.25%/15s) gated on the chip having been at least 30 right before that same reset - the buff-side analog of the already-built `resource_scaled_nukes`, but for a buff rather than a nuke.
- Decision: (1) `SquadContext.reset_resource(slug, name, time, pre_value, post_value)` sets a resource to a fixed value at a point in time rather than incrementing it; `resource_count` uses the latest reset at or before the query time as its baseline (discarding fills recorded before that reset), and a new `resource_count_before_reset(slug, name, time)` exposes the value the resource held immediately BEFORE a reset recorded at an exact instant. `ResourceSpec` gained an optional `resets` field (`[{"trigger": "battle_start"|"own_burst", "value": X}, ...]`); the resolution pass merges the flat additive fill schedule with reset events (sorted by time, using `context.burst_times[slug]` for `"own_burst"` resets) and replays them chronologically so each reset's pre-value correctly reflects prior fills AND any earlier reset already applied. (2) `resource_gated_buffs`: a burst-fired buff gated on (or scaled by) a resource's count at the burst's own time, processed IN the resolution pass itself (not at `on_tier_fire`, when the burst actually fires) - iterating `context.burst_times[slug]` for each of the owner's own burst times and adding the Effect directly once the gate is checked against the now-known resource state.
- Why: A nuke can defer its percent computation to the existing phase-2 pass (`resource_scaled_nukes`, see the ADR below) because nukes are already recorded now / computed later throughout this engine. A buff has no equivalent deferred-computation stage - `on_tier_fire` fires while the resource's fills/resets for that cycle aren't known yet (they're populated by the resolution pass, which runs afterward), so a naive gate check at `on_tier_fire` time would always see a stale or zero count. Running the gate check inside the resolution pass itself, after the resource's full fill/reset schedule is known, is what makes it correct without inventing a new deferred-buff mechanism.
- Consequences: Verified to produce IDENTICAL output to the pre-existing behavior when no `resets` are present, since this touches the shared resolution-pass code every other resource-using Nikke relies on (Modernia, Guillotine, Cinderella all still pass unchanged) - a real regression risk worth calling out explicitly given how central that code path is. Also built in the same commit: `("per_shot_every_during_full_burst", N)` fill kind - a resource fill counting only shots whose time falls within a Full Burst window, computed from `simulate_burst_cycle`'s own event log (pairing `full_burst_start`/`full_burst_end` events) rather than re-deriving burst timing independently - needed for Golden Chip's "every 3 normal attacks during Full Burst" (shots outside Full Burst don't count at all, not even toward the "every 3rd" tally). First/only consumer of all of the above: Soda: Twinkling Bunny.

## Resource-scaled nukes resolve their percent in phase 2, not at record time
- Date: 2026-07-12
- Context: Encoding Julia, Cinderella, and Guillotine's previously-deferred Extermination DoT all needed a burst-fired nuke whose magnitude is gated or scaled by a named resource's count (Julia's Climax additional hit gated on Crescendo at max stacks; Cinderella's mirrored hit scaled by Beautiful's stack count; Guillotine's DoT scaled by Hero Level, recomputed every tick). The resource's fill schedule isn't known until the resolution pass runs, which happens AFTER the burst cycle that would normally record the nuke's damage event - so a naive `context.resource_count(...)` call from within a `SkillRule` action (fired during `on_tier_fire`) would always see zero fills.
- Decision: `record()` gained an optional `resource_gate` field - `(resource_name, cap, lifetime, scale_fn)` - carried on the recorded damage event but not resolved into a concrete percent until PHASE 2, via a new `_resolve_percent(ev)` that calls `context.resource_count(ev["slug"], name, ev["time"], cap, lifetime)` at the event's own time and multiplies by `scale_fn(count)`. A repeating DoT (`tick_count` > 1) records one event per tick, each carrying the same gate but evaluated at ITS OWN tick time, so a resource still accumulating during the DoT's window correctly raises later ticks over earlier ones. Wired end-to-end via `raid_simulator`'s new `resource_scaled_nukes` param, mirroring the existing `periodic_nukes`/`per_shot_rules` dict-of-specs pattern.
- Why: This is the same "record now, compute later" trick the engine already uses for every other damage instance (see the module docstring's record-then-compute section) and for deferred buffs (`RoundGrant`) - reusing it here means no restructuring of when `simulate_burst_cycle` runs relative to the resolution pass, and the resource's count is queried the same way everywhere (`resource_count`), whether from a buff's step-function emission or a nuke's percent resolution.
- Alternatives considered & rejected: moving resource fill population BEFORE the burst cycle (would require decoupling shot-time generation from the full-fight Effect registry, since shot generation currently reads live reload/max-ammo buffs that are only fully known after burst_cycle completes - a much larger restructuring for no added correctness); giving `SkillRule` actions direct access to `resource_count` (would silently return wrong/zero counts depending on trigger-firing order, an easy-to-miss correctness trap for future encodings - the deferred-percent approach makes the correct order structural rather than a convention to remember).
- Consequences: Also needed two smaller additions to make count-scaled nukes hit useful units: `burst_hit_counts` (a burst that "attacks sequentially N times" records N separate damage instances at the same instant, not one at N*percent - defense is a flat per-hit subtraction, so this matters whenever `enemy_def` > 0) and a `("periodic", interval)` resource fill kind (a resource that ticks on a fixed timer independent of the owner's shots, needed for Cinderella's Beautiful). First consumers: Julia/Julia-signature (Climax), Cinderella (Glass Slippers + Beautiful), Guillotine: Winter Slayer (Extermination's DoT, closing the gap flagged when she was first encoded).

## Named-resource / capped-stack-counter primitive (gap #2 Pattern A only)
- Date: 2026-07-12
- Context: Gap #2 (quantity-based resource tracking) blocked ~16 Burst-3 units, the biggest remaining encoding blocker after eb2. Inspecting the real skill text showed "resource tracking" is not one mechanism but two: **Pattern A** — accumulating/capped stack counters whose buffs scale with the count, filled by triggers we already have (per-shot counters, burst, battle-start) — and **Pattern B** — a time-draining gauge with a threshold transform (Ark Ranger battery), additionally blocked on part-destruction fill events the engine has no concept of.
- Decision: Build **Pattern A only**, as an extensible named-resource primitive: `ResourceSpec(name, fill, cap, buffs)` + `ResourceBuff` (in `effects.py`), `SquadContext.resource_fills`/`resource_count`, and a `raid_simulator` resolution pass; buffs built via `linear_resource_buff` / `leveled_resource_buff`. The resource's count is a **function of time** computed from a deterministic fill schedule (not a mutable running total), and each buff is emitted as a **step function of delta Effects** over the fill/expiry events (so `total_for`'s running sum equals `value_fn(count)` — permanent stacks ramp then plateau at the cap; timed stacks also decay). New Nikkes declare one `ResourceSpec` (name/fill/per-stack/cap/scope) with no new engine trigger — the extensibility Fienn asked for.
- Alternatives considered & rejected: a mutable per-unit integer counter mutated during the passes (breaks across the burst-cycle vs shot-loop phase ordering); attempting the full gauge incl. time-drain + transform now (Fienn chose Pattern A only); inventing a configurable part-break schedule as a sim input to reach Ark Ranger (rejected — fabricates a boss assumption, violates the no-invented-details rule); threading `core_hittable` through `assemble_simulation_inputs` for Guillotine's fill rate (rejected — the resolution pass already has `core_hittable`, so a core-conditional fill kind keeps the boss property out of the unit encoding).
- Consequences: First consumers Modernia (⚠ timed capped stacks) and Guillotine: Winter Slayer (⚠ permanent + Hero-Level-derived + core-conditional). Still deferred and now clearly scoped for follow-ups: **count-scaled nukes** (value read at burst time, before the fill schedule is resolved — Guillotine's Extermination DoT, Cinderella's stack-mirror, Julia); Pattern B gauges/transforms; multi-source / status-window-gated fills (Soda, Modernia's Giant Leap). Remaining Pattern A units (Soda, Quency, Cinderella, Maiden, Asuka…) are now encodable in a normal batch. See `engine-gaps.md` §2, `special-mechanics.md` "Named resource / capped stack counter".

## Bullet-count ("N round") buff duration + top-N highest-final-ATK precise targeting
- Date: 2026-07-12
- Context: Encoding Miranda (애장품) and Zwei (애장품). Both have "for 1 round" buffs, and Miranda additionally targets "N allies with the highest final ATK" — neither shape is representable by the existing seconds-based `Effect` duration or the existing static scopes (`self`/`squad`/`element:X`).
- Decision: (1) **Round buffs**: `round_buff_rule` records a `RoundGrant` (not a live `Effect`); `raid_simulator`'s shot loop converts each grant into a real timed `Effect` covering exactly the affected unit's next N normal-attack shots (window from the first covered shot to the next uncovered shot, or fight end), scoped `slugs:<unit>` — a squad-scoped grant is consumed independently per ally (one Effect per unit), matching per-ally bullet consumption. (2) **Highest-final-ATK targeting**: `SquadContext.top_atk_slugs(n, caster, registry, time)` ranks the deck by LIVE final ATK (base ATK + active buffs) at application time and returns the top-n slugs (excluding caster, filling from caster if too few allies); a new `slugs:a,b` Effect scope targets exactly those units. `highest_atk_buff_rule` (timed) and `round_buff_rule(..., ("top_atk", n))` (bullet-count) both build on this.
- Why: A round buff is genuinely a bullet-count duration, not a time or burst-cycle duration — my (the docs-keeper's, relaying the encoding session's) initial assumption that it was a continuous per-cycle refresh was wrong, caught by Fienn: "for N round(s)" is consumed by the affected ally's next N shots then gone, re-granted next cycle (so ~1 shot per affected ally per cycle for N=1, not continuous uptime). And a squad-wide approximation for highest-ATK targeting would over-apply a top-1/top-2 buff to every ally, including a second carry in a dual-carry deck — exactly the case this deck-builder must evaluate correctly, so Fienn required precise targeting over an approximation.
- Alternatives considered & rejected: continuous-refresh model for round buffs (wrong semantics, corrected above); a first-class "round" duration type resolved against the FB timeline (deferred as YAGNI — the shot-loop windowing trick reuses the existing seconds-based `Effect` + `total_for` machinery with no new duration primitive, and no collected unit yet needs the general one-shot-spans-N-rounds case); squad-scope approximation for highest-ATK targeting (rejected for the over-application reason above). Fienn chose to build the full shot-count mechanism now rather than approximate, since it generalizes to future N-round/stacking buffs (e.g. Zwei's deferred 3-stack pierce).
- Consequences: Both are reusable building blocks for the backlog (see `nikke-skill-encoding/references/special-mechanics.md`, "For N round(s) is a bullet-count duration" and "Highest-final-ATK top-N targeting"). The highest-ATK ranking reads the registry at TRIGGER time (phase 1 of record-then-compute), so per-shot buffs applied in the later shot pass aren't visible to the ranking — acceptable since those are self-scoped and don't change other units' relative ranking. Miranda promoted to ✅ (Health Up self-ATK per-shot, Powering Up top-2 exact targeting, Wake Up top-1 crit-rate 1-round buff all modeled; only inert Hit Rate steps remain deferred); Zwei's 1-round squad Pierce buff now modeled (FB-window normal-attack pierce stacking and weapon transform still deferred).

## Full-charge-count CDR modeled as a per-cycle CDR pulse

## Refreshing buffs for repeatedly re-applied per-shot buffs
- Date: 2026-07-11
- Context: `EffectRegistry.total_for` sums every currently-active effect. A per-shot buff with a multi-second duration that gets re-applied on every qualifying shot (Prika's Let's Get the Show Started!, Mint's Here I Go!) was being added anew each shot via `buff_rule`/`registry.add`, so overlapping windows summed instead of refreshing — inflating output roughly 2x for an SR's fire rate and ~13x for an AR's by fight's end. NIKKE refreshes these buffs (extends the duration at the same value); it does not stack them.
- Decision: Add `EffectRegistry.add_refreshing` — truncates any still-active effect with the same `(stat, source_slug, scope)` to end at the new `applied_at`, then adds the new instance, so overlapping re-applications from ONE source collapse to a single continuous value. Effects from a DIFFERENT source on the same stat (e.g. another unit's buff) are untouched and still sum. Add `refreshing_buff_rule` (`skill_rules/_helpers.py`) as the drop-in replacement for `buff_rule` on any repeatedly-retriggered buff.
- Why: Matches how NIKKE's duration-refresh buffs actually behave. Truncation is done in place, so it stays correct under record-then-compute's replay: an earlier query only sees effects with `applied_at` at or before its own time, so a later shot's truncation can't change an earlier answer.
- Consequences: This corrected Prika's already-committed damage numbers (previously overstated). Encoding a repeatedly-retriggered buff (per-shot or periodic) now requires an explicit stacks-vs-refreshes call: default to `buff_rule`/`add` (stacking) only when the wording implies an actual stacking counter; use `refreshing_buff_rule` whenever it's a duration extension. See the insights.md entry on this for the symptom to watch for.

## Time-indexed unit status for post-pass (per-shot) status queries
- Date: 2026-07-11
- Context: Record-then-compute's per-shot pass (gap #1's ADR) evaluates each shot's condition in a phase-2 pass against the FINAL context, so a bare boolean status flag (`has_status`) can't distinguish "true at shot time" from "true only later." Solo Mint's Dancing/Singing status alternates every burst cycle; a per-shot buff gated on "while Singing" via `has_status` would wrongly apply the end-of-fight status to every shot in the fight, including ones fired in an earlier, different-status cycle — and, paired with Prika, would over-apply to shots fired before Prika's Encore first pins Singing.
- Decision: `SquadContext` now records each unit's burst-tier fire times (`burst_times`, via `record_burst_time`) and timestamps status flags with when they were first set (`status_since` / `set_status(..., time=...)`, keeping the EARLIEST time so re-applications don't move it forward). Mint's rule computes her Singing state AT A GIVEN TIME (`mint_singing_at(time)`): Singing if Prika's Encore pinned it at or before that time, else by burst-count parity over only the bursts at or before that time.
- Why: Generalizes the existing `activation_count`-parity trick (see `docs/insights.md`, Burst rotation) to work correctly under record-then-compute, where "what was true when" matters, not just "what is true now." One time-indexed function now covers solo Mint and Prika-paired Mint, instead of two separate models with the solo case left deferred.
- Consequences: Any future per-shot/periodic condition on an alternating or pinned status must query it at the shot's own time, not via a bare `has_status` check, or it will silently use the end-of-fight status for every shot in the fight. Mint is now fully modeled (Here I Go! solo case no longer deferred); 290 tests pass.

## Cross-unit reactive trigger: `ally_burst_activate` (engine gap resolved)
- Date: 2026-07-11
- Context: Prika's Encore fires "when Sing Along [Mint's burst buff] takes effect" — i.e. it reacts to a DIFFERENT unit's burst, not her own. The engine's `own_burst_activate` dispatch only fired a unit's rules off its OWN burst tier (`raid_simulator.on_tier_fire`), so no rule could observe a specific ally bursting — a bigger architecture gap than the existing static `deck_contains` synergies (Blanc/Rouge, Mast/Anchor), which only check deck membership, not react to another unit's trigger firing.
- Decision: `on_tier_fire` records the bursting slug on the context (`SquadContext.last_burst_slug`) and fires a new `ally_burst_activate` trigger across every unit's rules (after the burster's own `own_burst_activate`, so the reacting rule sees the burst's own effects already applied). A reacting rule gates on `ally_bursted(slug)` (reads `last_burst_slug`), combinable with other conditions via the new `all_conditions(*conds)` helper. Like `periodic_rules`, these must be buff appliers only (no instant nukes).
- Why: Generalizes the existing single-burst dispatch to cross-unit reactions without touching the ~30 existing burst-rule modules (additive trigger, no signature change to any existing builder). Firing after the burster's own trigger keeps effect ordering predictable.
- Consequences: First consumer: Prika's Encore reacting to Mint's burst, which also pins a status on the OTHER unit (`context.set_status(context.last_burst_slug, ...)`) — a new pattern for one unit's rule to mutate another unit's state. A "maintained/extended duration" buff (Prika's Charge Damage, kept alive by repeated Encores) is modeled as permanent, gated on `deck_contains(partner)`, rather than re-added on each trigger — same-stat effects sum, so re-adding would double-count. See `nikke-skill-encoding/references/special-mechanics.md` ("Cross-unit reactive trigger") for the worked example and the per-shot state caveat it surfaced (a per-shot condition sees the FINAL context, so it can't track a solo per-cycle-alternating status — Mint's solo Singing alternation stays deferred as a result).

## Per-shot triggers + record-then-compute (gap #1)
- Date: 2026-07-11
- Context: ~30 collected units gate their headline damage/buffs on shot counts ("after/every N normal attacks", "N full charge attacks") - the top-ROI engine gap. Naively firing these during the normal-attack pass (which runs after the burst cycle) would mean a per-shot SQUAD buff (e.g. Rouge/Ade buffing a dealer) never reaches a burst nuke computed earlier - understating exactly the support-buffs-dealer synergy the recommender is meant to find. Fienn chose the accurate approach over a lower-risk scoped one.
- Decision: (1) Refactor `simulate_raid` to RECORD every damage instance (burst/instant/periodic/per-shot nukes + normal attacks) as an event during phase 1 (which only applies buffs), then compute them all in a phase-2 pass against the final registry. (2) Add `simulate_raid(..., per_shot_rules={slug: [(threshold, mode, [SkillRule])]})`, fired at the unit's shot counts ("after" once at N / "every" at each multiple of N); rules apply buffs (`buff_rule("per_shot", ...)`) or emit an `instant_damage_percent` pulse recorded as `per_shot_nuke`. Exposed via `registry._PER_SHOT_RULE_BUILDERS` / `get_per_shot_rules`, threaded by `roster`.
- Why: The refactor is provably behavior-preserving (effects are added with `applied_at >= their time`, and `truncate_open_ended` mutates in place, so deferring computation never changes an existing value - the 257 prior tests stayed green) while letting late buffs correctly reach earlier instances. The engine counts shots regardless of weapon (a charge weapon's every shot is a full charge), so "full charge N" and "normal N" unify to a shot count - the encoding picks N.
- Consequences: `per_shot_rules` rules must be stateless and must not affect shot generation (reload/ammo). "On firing the last bullet" is still a gap (needs magazine-boundary markers in `attack_rate`); per-shot nukes default to `attack` type. First consumer: Brid: Silent Track's Journey Ahead (675% every 5 normal attacks). The ~30 blocked units can now be re-encoded as a follow-up batch.

## Periodic skill trigger: cooldowned Skill 1/2 buffs fire on their own cooldown
- Date: 2026-07-11
- Context: Fienn confirmed a universal battle-system rule - a Skill 1/2 (not the Burst) that has a cooldown does NOT fire at battle start; it first fires at t=cooldown and repeats. Takina Inoue's Battlefield Control (cd 15s) applies squad ally True Damage +140% and enemy Damage Taken +10% every 15s starting at t=15 - her headline support - but the engine's only triggers were the 4 burst events, and `periodic_nukes` only handles damage, not buffs.
- Decision: Add `simulate_raid(..., periodic_rules={slug: [(cooldown, [SkillRule, ...])]})`. These fire each rule's action at t=cooldown, 2*cooldown, ... Because the buffs they apply are damage INPUTS (unlike `periodic_nukes`, an output post-pass), the pass runs BEFORE `simulate_burst_cycle` so any nuke computed during the cycle reflects them (effects are replay-safe, so pre-adding at future times is correct). Exposed via `registry._PERIODIC_RULE_BUILDERS` / `get_periodic_rules`, threaded by `roster`; rules built with `buff_rule("periodic", ...)` (a label - never dispatched by `fire_trigger`).
- Why: Generalizes the existing periodic mechanism to buffs; a universal rule so high reuse (Rosanna's Spina di Rosa cd30s buff part could use it later). First-fire-at-t=cooldown already matched `periodic_nukes`, so no inconsistency. Additive, defaults to `{}`/no-op.
- Consequences: Periodic rules run against the initial context, so they must be stateless buff appliers (no dependence on burst-cycle state) - documented. A periodic nuke with an internal duration shorter than its cooldown (duty cycle, e.g. Rosanna's Spina) is still an open gap. First consumer: Takina Inoue.

## Damage typing to make type-specific Damage-Up buffs non-inert
- Date: 2026-07-10
- Context: `sustained_damage_up` / `distributed_damage_up` / `true_damage_up` / `projectile_explosion_damage_up` exist in `damage_formula.py` but `raid_simulator` never read them, so buffs like Rosanna's "Sustained Damage +20%", Takina's "True Damage +140%", and Mint's "Projectile Explosion Damage +X%" were inert. Wiring them blanket (like `attack_damage_up`) would be wrong: they only raise damage OF that type, so a squad-wide sustained buff must not boost everyone's normal attacks. And gating them correctly is still inert unless the engine also produces instances of that type - so it's a coupled feature, not a one-line wire (correcting an earlier "~1 line each" estimate).
- Decision: Give every damage instance a `damage_type`; `raid_simulator._TYPE_BUCKETS` reads a type-gated Damage-Up bucket only for matching instances (always-on buckets stay global, so untyped "attack" instances are unchanged). Types are set via: `registry._BURST_DAMAGE_TYPES` for burst nukes (rapi-red-hood → projectile_explosion), a `"damage_type"` key on `periodic_nukes` entries, RL weapon → `projectile_explosion` for normal attacks, and a self-scoped `normal_attacks_deal_true` effect that converts a unit's normal attacks for a window (Takina).
- Why: Faithful to how the buffs work in-game (per-type multipliers) without over-crediting; additive and no-regression for existing decks (default type "attack" adds no bucket). Refactored the two duplicated `calculate_damage` call sites into one `_damage_instance` helper, so type-gating lives in exactly one place.
- Consequences: Emitting a type-gated buff is now live only when the deck also produces an instance of that type (the buff is a multiplier needing something to multiply). Mint's projectile-explosion buff now reaches RL allies; Rapi's burst nuke benefits from it. Semantics confirmed against the nikke.gg glossary (now captured in `nikke-skill-encoding/references/damage-formula-reference.md`): True Damage **ignores enemy DEF** (true-typed instances use `enemy_def=0`); Attack Damage is a general buff that **affects all damage**, so `attack_damage_up` stays global. Deferred: shield_damage_up and the major-modifier terms remain inert.

## Periodic-nuke engine capability for own-fixed-cooldown skills
- Date: 2026-07-10
- Context: Helm: Aquamarine's Aegis Cannon Suppression Fire is a separate active skill with its own 4-second cooldown, firing repeatedly throughout the fight independent of burst timing entirely (not gated on Full Burst, own burst, or normal-attack count) - a genuinely new mechanic shape, at 105.58% of final ATK per tick (~45 ticks over 180s) likely her primary DPS as an Attacker.
- Decision: Add `simulate_raid(..., periodic_nukes={slug: {"cooldown": sec, "percent": float}})` - each entry ticks independently up to `fight_duration`, computed via the same `_damage_from_percent` helper as burst/instant nukes, logged with `source="periodic"`. Exposed per-Nikke through a new `registry._PERIODIC_NUKE_BUILDERS` map (kept separate from the main `_BUILDERS` dict) and `registry.get_periodic_nuke`, wired automatically by `roster.assemble_simulation_inputs`.
- Why: Fienn approved building the capability over a thin/silent approximation, given the likely DPS weight. Kept as an additive, opt-in parameter (defaults to `{}`/no-op) so the ~25 existing encoded Nikkes are completely unaffected - no change to their builder return shape.
- Consequences: A third category of "how a Nikke deals damage" now exists alongside burst nukes and instant-damage pulses (see `references/special-mechanics.md`). Future Nikkes with a similar own-cooldown skill reuse this directly.

## Character data source priority = lootandwaifus.com first, dotgg fallback
- Date: 2026-07-10
- Context: dotgg (the original data source decision below) lags roughly the last ~2 months of NIKKE releases, so newer Nikkes (e.g. Prika) have no dotgg entry. lootandwaifus.com was found and cross-verified against dotgg (Little Mermaid, all 3 skills, every value at level 10 — exact match, no discrepancies), and its character-listing page carries richer metadata (mechanic tags in CSS classes) than dotgg's summary endpoint.
- Decision: Use lootandwaifus.com as the primary data source for all character collection going forward (not just as a fallback for missing characters); keep dotgg as a fallback/cross-check.
- Why: At least as current as dotgg, richer listing metadata, and validated as accurate. Reduces how often the fallback path is needed at all.
- Consequences: `nikke-data-collector` and the encoding skill's workflow now fetch from lootandwaifus first. lootandwaifus has no `description_value_NN` placeholder structure (unlike dotgg) — slots are numbered by left-to-right order of appearance in the rendered per-level text instead. Raw pages are saved to `data/lootandwaifus/` (gitignored, same as `data/dotgg/`). See `references/character-data-sources.md` (renamed from `dotgg-data.md`).

## Instant-damage pulses for non-own-burst nukes
- Date: 2026-07-10
- Context: Brid: Silent Track's Ignition Sequence deals 636% of final ATK on entering Full Burst, regardless of who bursts that cycle - a real damage source, but the existing engine only computed burst-nuke damage tied to the caster's OWN burst tier firing (`own_burst_activate` + `burst_damage_percents`). Encoding Brid without it would leave her almost valueless (buff-only), understating a deck that includes her.
- Decision: Add an `instant_damage_percent` Pulse (`_helpers.instant_nuke_pulse_rule`) that any trigger's action can emit; `raid_simulator.drain_instant_damage` drains it after every trigger fire (battle_start, own_burst_activate, full_burst_enter, full_burst_end) and computes damage the same way as a burst nuke, using the pulse's source_slug as caster.
- Why: Reuses the existing damage-calculation path (via a shared `_damage_from_percent` helper) rather than duplicating it; keeps the change additive (new pulse type + 4 drain calls) instead of altering the SkillRule action signature for every existing module.
- Consequences: Damage instances from this path are logged with `source="instant_nuke"` (distinct from `"burst"`/`"normal_attack"`). Future Nikkes with the same "deal damage on trigger X, not on own burst" pattern reuse this directly.

## Crit modeled as expected value
- Date: 2026-07-10
- Context: Many Burst-1 supporters (Volume, Miranda, Tove, …) exist mainly to buff Critical Rate / Critical Damage, but the simulator computed every hit as non-critical, so those buffs did nothing and the recommender would rate the units useless.
- Decision: Model crit as expected value — every hit's damage is scaled by `1 + crit_rate*(0.5 + crit_damage_sources)`, with base crit rate 15% and base crit damage +50%.
- Why: Captures the DPS contribution of crit buffs without per-hit RNG; matches nikke.gg/note.com's documented expected-value formula.
- Consequences: Crit-rate and crit-damage buffs now move output. `base_crit_rate` defaults to 0.15 but is overridable to 0.0 for deterministic tests.

## Search scope = single best deck first; encoded Nikkes only
- Date: 2026-07-10
- Context: The end goal is recommending 5 decks (25 Nikkes) that maximize summed damage, but that partition is a large combinatorial layer.
- Decision: Build the single-best-deck optimizer first (feasibility + pruning + exhaustive over intra-tier orderings); the 5-deck partition is a later layer. Candidate pool is restricted to Nikkes with encoded skill rules.
- Why: The single-deck evaluator is the building block for the partition. Engine usefulness scales with how many Nikkes are encoded, so encoding is the real lever.
- Consequences: Recommendations only consider encoded Nikkes; the roadmap includes encoding more and adding the 5-deck partition.
