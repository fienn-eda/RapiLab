## Gap #1 last-bullet re-encoding batch: Julia (base), Helm, Privaty consume the magazine-boundary marker
- Date: 2026-07-12
- Context: With the last-bullet capability built (see "Magazine-boundary 'last bullet' marker..." below), three previously-deferred units were re-encoded against it: Julia (base)'s Crescendo (the original motivating case for the whole investigation), Helm's Frontline Command (previously dead code — see below), and Privaty's LD Assault (a new mechanic shape combining last-bullet with a status-window bonus).
- Decision: (1) Julia's Crescendo modeled as `ResourceSpec(fill=("on_last_bullet",), cap=5, ...)` feeding a self Critical Damage buff (+24.79%/stack, 15s each); her Climax burst's additional hit is a `resource_scaled_nukes` entry GATED (not scaled) at max stacks via `scale_fn=lambda count: 1.0 if count>=5 else 0.0` (the same gate shape a generic engine test — `test_resource_scaled_nuke_threshold_gate_zero_below_cap` — was already written for, anticipating this exact case). Only the additional hit opts into `full_burst_bonus_eligible` (only its own text says "as additional damage"; the base 544.5% hit's text doesn't). (2) Helm's Frontline Command rewired from a dead `fire_trigger("on_last_bullet_hit", ...)` call (never actually dispatched by `simulate_raid`'s real event loop — see the insights.md entry on this) to `per_shot_rules`' `"last_bullet"` mode, using `refreshing_buff_rule` (Prika/Mint precedent — her charge-weapon (SR) magazine can empty faster than the buff's own 5s window, which would otherwise stack instead of refresh). (3) Privaty's LD Assault fires a squad Damage Taken debuff (+10.01%/10s) plus 256.17% additional damage on every last bullet (both `full_burst_bonus_eligible`), PLUS an ADDITIVE 1687% hit stacked on top when the target is currently in her own "Designated Target" status (set by her AK Missile burst, lasting 10s) — confirmed from raw skill text that both fire together, not either/or. Modeled as a live time-window check (`any(bt <= time < bt + designated_duration for bt in context.burst_times[caster_slug])`) evaluated fresh inside the per-shot rule's own action at the shot's own time, since no existing status primitive fits a 10s window against a 40s burst cooldown (too short a fraction of the cycle for `own_burst_fired_this_cycle()`'s per-cycle semantics).
- Why: Julia was the case that originally motivated building the marker; Helm and Privaty were the two other units already flagged in `docs/encoded-nikkes.md` citing this exact gap. Helm's dead-trigger bug was a genuine pre-existing correctness bug independent of this batch — caught only because rewiring naturally required inspecting how the rule actually fired in the real simulator, not just its unit test.
- Consequences: Closes out the three units flagged against gap #1's last-bullet residual in `docs/encoded-nikkes.md`. Privaty's same-instant Damage Taken debuff timing (does a last bullet's own damage see the debuff it just applied? do two debuffs within 10s stack or refresh?) is UNCONFIRMED in-game — both current behaviors are just the engine's existing default Effect semantics (mirroring Soda/Cinderella's confirmed precedent for the self-reference question, unlike Maiden's confirmed-opposite case), not verified facts; flagged in `privaty.py`'s module docstring as an open item, the same way Maiden's self-buff-timing question was flagged before Fienn confirmed it in-game. `test_deck_search.py`'s real-data Privaty fixture needed an `"ld_assault"` sub-dict added (realistic Lv7 values matching the fixture's existing `ak_missile` Lv7 data) once Privaty was registered in `_PER_SHOT_RULE_BUILDERS`, since that map's builders run unconditionally for every deck containing the slug — fixed by completing the fixture's data rather than making the encoding tolerate missing data.

## Magazine-boundary "last bullet" marker mirrors the existing shot-generation function shape (gap #1 closeout)
- Date: 2026-07-12
- Context: Gap #1's last residual variant — a burst/skill trigger that fires specifically on the shot that EMPTIES a magazine, right before reload ("마지막 탄", e.g. Julia (base)'s Crescendo, Helm's last-bullet trigger — both flagged "매거진경계 마커 부재" in `docs/encoded-nikkes.md`) — was unbuilt. Fienn pointed at `test_attack_rate.py::test_rate_of_fire_matches_fienns_60fps_table` and `app/attack_rate.py`'s existing magazine/shot-generation machinery as the base to build on, and flagged [Max Ammo Up] and attack/charge-speed buffs as concerns to account for.
- Decision: Add `magazine_last_bullet_times`/`charge_last_bullet_times`/`last_bullet_shot_times` to `attack_rate.py`, mirroring the EXISTING `generate_magazine_shot_times`/`generate_charge_shot_times`/`generate_shot_times`'s exact 3-tier structure (2 low-level raw-parameter functions + 1 weapon-dispatching wrapper) rather than changing those functions' return shape to carry the marker inline. Each new function re-derives `magazine_size` LIVE from the same `max_ammo_percent_at` callable the existing functions already thread through, so [Max Ammo Up] buffs shift the last-bullet marker automatically. Attack/charge speed were deliberately NOT modeled for this feature. Wired into `raid_simulator.py`'s `per_shot_rules` as a new `"last_bullet"` mode (reusing the existing `(threshold, mode, rules)` tuple shape with `threshold` unused), computed once per unit only when at least one `"last_bullet"` rule is present; the pre-existing inline `max_ammo_percent_at`/`reload_speed_percent_at` lambdas were extracted into named locals so `generate_shot_times` and `last_bullet_shot_times` share identical callables and produce bit-identical magazine boundaries (needed since the check is a float membership test).
- Why: An additive, same-structure-mirroring set of new functions achieves the feature with zero changes to any existing test or call site — the alternative (changing `generate_shot_times`'s return shape to e.g. `list[tuple[time, is_last]]`) would have broken 11 of `test_attack_rate.py`'s 13 existing tests for no real benefit. Attack/charge speed are structurally irrelevant here: neither is wired as a shot-interval modifier anywhere in this engine (shot cadence is fixed, computed once — see the "Stats the engine does NOT consume" list), and even if they were, they'd change shot CADENCE, not magazine CAPACITY, so they couldn't move which round is "last" regardless. Only `max_ammo_percent` determines magazine size.
- Consequences: Closes gap #1 fully (previously "'마지막 탄'만 잔여"). A magazine truncated by `fight_duration` ending mid-magazine (not because it was actually emptied) is correctly NOT marked as a last bullet — handled by construction, since `is_last` checks whether the recorded round's index reaches `magazine_size - 1`, not whether it's the last round appended to the output list (see `test_magazine_last_bullet_times_does_not_mark_a_fight_duration_truncated_shot`). The capability is built and tested but not yet used to re-encode any Nikke — Julia (base)'s Crescendo and Helm's last-bullet trigger (both currently deferred in `docs/encoded-nikkes.md` citing this exact gap) are the two immediately-unblocked candidates, not yet touched.

## full_burst_bonus_eligible generalizes beyond the "as additional damage" text phrase for repeating-tick DoTs
- Date: 2026-07-12
- Context: Fienn tested Mana's burst "Fatal Error!" (a flat, non-resource-scaled repeating DoT via `resource_scaled_nukes`, see the entry below) in-game and found its damage receives the base Full Burst Bonus (+50%), even though its skill text says "as sustained damage" — NOT the exact "as additional damage" phrase the existing text-phrase rule (see "full_burst_bonus wiring is opt-in per damage instance, gated on skill-text phrase" below) keys on. `resource_scaled_nukes` also had no `full_burst_bonus_eligible` wiring at all until now (only `record()`/`dynamic_hit_count_nukes` had it).
- Decision: (1) Add `full_burst_bonus_eligible` support to `resource_scaled_nukes`, mirroring the existing opt-in flag on `record()`/`dynamic_hit_count_nukes`. (2) Set it on Mana's `build_fatal_error_dot` spec. (3) Adopt a refined encoding rule going forward: the "as additional damage" text phrase is Fienn's proxy for a TIME-based fact — damage NOT computed at the cast instant, that happens to land inside a Full Burst window, gets the bonus. For a SINGLE-INSTANT nuke, cast-time vs. delayed is genuinely ambiguous from text alone, so the phrase check remains the right heuristic there. For a REPEATING-TICK DoT (any `resource_scaled_nukes` consumer), every tick after the first is inherently computed at a time strictly after cast "by construction" — so `full_burst_bonus_eligible=True` should be the DEFAULT assumption for repeating-tick damage, independent of whether the unit's own text happens to say "as additional damage," subject to confirming the DoT's duration doesn't obviously extend past the Full Burst window.
- Why: The phrase was always a proxy for timing, not the fundamental mechanism; Mana's case (different wording, same underlying "not cast-time" fact for later ticks) confirms the underlying rule is about WHEN damage is computed relative to cast, not which words the skill text uses. This scopes the existing phrase-based rule rather than reversing it — it's still correct for the case it was designed for (single-instant nukes).
- Consequences: Future single-instant nukes still need the phrase check (unchanged). Future repeating-tick DoTs (`resource_scaled_nukes` consumers) should default to `full_burst_bonus_eligible=True` during encoding rather than requiring the phrase. Retroactively applied the same day: Fienn confirmed (2026-07-12) `guillotine_winter_slayer.py`'s Extermination Hero-Level DoT (an earlier `resource_scaled_nukes` consumer, predates this capability) works on the same mechanism — `full_burst_bonus_eligible=True` added to her spec too.

## Delayed dynamic-hit-count nukes, own-status-window resource fills, and full_burst_bonus wiring (eb4)
- Date: 2026-07-12
- Context: Encoding Asuka Shikinami Langley: Wille's burst needed two mechanics no existing capability covered. First, her burst's second-phase nuke ("Annihilation") doesn't fire at cast time — it fires ~9s later, when her own "Annihilation State" self-status ends — and its hit count scales off "Anti A.T. Field," a stack debuff she applies to the ENEMY (not a caster-owned resource, unlike every prior `dynamic_hit_count_nukes` consumer, e.g. Maiden's MP). Second, Anti A.T. Field itself fills "+1 every 10 shots, but only while Annihilation State is active" — a resource fill window anchored to HER OWN burst-fire time (9s from her own burst), distinct from the already-built `per_shot_every_during_full_burst` (anchored to the squad's global Full Burst window, a different instant). Fienn approved building both as real capabilities via AskUserQuestion rather than approximating.
- Decision: (1) `dynamic_hit_count_nukes` gains an optional `fire_delay` (seconds); the nuke fires and reads the resource's PRE-reset count at `burst_time + delay` instead of exactly `burst_time`. `ResourceSpec.resets` gains a matching `"own_burst_delayed"` trigger (with its own `delay`) so the resource's own reset lands at the same delayed instant as the nuke that reads it, not at burst time. (2) New `ResourceSpec` fill kind `("per_shot_every_during_own_status_window", n, window_duration)` — counts shots toward the "every n" tally only if they fall within `window_duration` seconds of one of the owner's OWN burst-fire times (`context.burst_times`), mirroring `per_shot_every_during_full_burst`'s shape but with a per-owner, not squad-global, window. (3) `full_burst_bonus_eligible` — an opt-in boolean threaded through `record()`/`_damage_instance` and `Pulse` (both the `drain_instant_damage` and per-shot-nuke drain sites) — is the actual WIRING for the "as additional damage" text rule (see the entry below): at damage-computation time it's checked against the existing `full_burst_windows` list at that specific damage instance's own recorded time (`start <= time < end`), and only sets `full_burst_bonus=1.0` if both the opt-in flag and the window check pass.
- Why: A burst nuke firing on a delay (not at cast time) needed its own timing hook rather than forcing every `dynamic_hit_count_nukes` consumer through a zero-delay default; an own-status window needed to reuse the existing "count shots in a window" shape (`per_shot_every_during_full_burst`) rather than inventing a new fill mechanism, just anchored to a different event stream (`burst_times` instead of `full_burst_windows`). `full_burst_bonus_eligible` reuses the exact opt-in-per-instance pattern already established by `extra_charge_bonus`/`extra_flat_atk` on `record()`.
- Consequences: First consumer of all three: Asuka Shikinami Langley: Wille — Anti A.T. Field's stack-fill uses the status-window fill kind; Annihilation's 9s-delayed nuke uses `fire_delay` + `own_burst_delayed`; both of her "as additional damage" nukes (the unconditional 471.86% every-50-shots nuke and the delayed 6.62% Annihilation nuke) opt into `full_burst_bonus_eligible`. Latent edge case worth flagging for a future unit: `full_burst_start` fires at the SAME timestamp as the tier-3 burst that triggers it (not strictly after), and the window check is inclusive-start (`start <= time < end`) — so a hypothetical eligible nuke fired AT cast time with zero delay would still read as "inside" the Full Burst window under this check. Doesn't affect Asuka (her eligible nukes are either delayed 9s or fire on an unrelated per-shot timer), but the next unit with a same-instant, zero-delay "as additional damage" nuke should have this checked explicitly rather than assumed. Anti A.T. Field's own 15.62%-of-ATK per-shot direct-damage bullet (separate from the 471.86% nuke) remains deferred — it needs a Full-Burst/own-status-WINDOW-GATED PER-SHOT TRIGGER to directly fire a nuke, not just a resource fill, the same still-unbuilt shape as Soda's residual co-fired buff (`engine-gaps.md` gap #7) — Asuka is a second, still-unbuilt consumer of that gap.

## resource_scaled_nukes' "resource" field becomes optional (flat repeating DoT)
- Date: 2026-07-12
- Context: Encoding Mana's Fatal Error! (burst DoT: 396% of final ATK per second, 10 ticks one second apart) needed the same repeating-tick machinery (`tick_count`/`tick_interval`) already built for `resource_scaled_nukes` (Guillotine's Hero-Level DoT), but with NO resource scaling at all — a plain flat DoT.
- Decision: Make `"resource"` optional on a `resource_scaled_nukes` spec dict; when absent, `record()`'s `resource_gate` is `None` (no percent-scaling resolution in phase 2 — the flat `base_percent` is used as-is), reusing the same tick loop instead of requiring a fake always-present resource just to get repeating ticks.
- Why: Smallest change that avoids inventing a dummy resource (e.g. a fake capped-at-1 resource that always reads 1) purely to satisfy a previously-mandatory field — the tick-count/tick-interval repeating-DoT shape is the actually-reusable part, not the resource scaling.
- Consequences: First consumer: Mana's Fatal Error!. Any future flat repeating DoT (no resource involved) reuses this directly instead of round-tripping through a fake resource.

## full_burst_bonus wiring is opt-in per damage instance, gated on skill-text phrase
- Date: 2026-07-12
- Context: `full_burst_bonus` (+50% Major Modifier) has been unwired in `raid_simulator.py` since the damage formula was built — no call site reads it, so it contributes 0 for all 45 encoded Nikkes today. An earlier theory (Maiden: Ice Rose's Diamond Dust getting it via a ~1s cast-to-damage delay pushing its damage into the Full Burst window) was investigated, written up in `engine-gaps.md`, and then fully reverted via `git revert` after in-game testing showed Diamond Dust's damage is actually computed AT CAST TIME with no delay (see `docs/insights.md`, the retracted-delay-theory bullet under "Effects / stats"). That left "when does a burst nuke get `full_burst_bonus`" unresolved and blocked pending per-unit verification.
- Decision: Fienn gave a general, text-driven rule instead of a per-unit verification process: a burst skill's damage instance receives `full_burst_bonus` if and only if its official skill description contains the phrase "as additional damage"; absent that phrase, the damage is computed from cast-time effects only. Wire `full_burst_bonus` **opt-in per damage instance** — on the specific `record()`/`_damage_instance` call for a unit whose skill text contains that phrase — following the same precedent already set by `extra_charge_bonus`/`extra_flat_atk` on `record()`, not as a blanket engine-wide change to how `full_burst_bonus` is read.
- Why: The phrase is a reliable, checkable signal already present in the data (skill description text pulled at encoding time), so it replaces an intractable "verify delay vs. immediate per unit" process with a simple text check done once per unit during encoding — consistent with the existing "record now, compute later" opt-in pattern for damage-instance-specific bonuses, and avoids risking a regression across all 45 already-encoded, tested units.
- Consequences: All 45 currently-encoded units are unaffected until their burst skill text is re-checked for the phrase and `full_burst_bonus` is wired on the matching damage instance(s) as part of a normal re-encoding/verification pass — this is not a retroactive blanket fix. Diamond Dust itself does NOT receive it (cast-time damage, no delay, confirmed via the revert above) unless its text is re-checked and found to contain the phrase.

## Squad-burst-cycle-conditional resource fill relies on Fienn-confirmed strict burst-tier ordering
- Date: 2026-07-12
- Context: Encoding Maiden: Ice Rose's MP resource ("Meditation": +1 stack if MP==0 whenever ANY squad member's Burst Stage 1 fires; +1 if MP>=1 on entering Full Burst) needed a fill mode unlike anything built so far - it's driven by GLOBAL burst-cycle events (not the resource owner's own shots, unlike every existing `fill` kind) AND conditioned on the resource's OWN running value at the moment of the event, making it a genuinely stateful walk rather than a flat deterministic schedule. Getting the fill right also depended on knowing precisely when Maiden's own burst (which drains MP to 0) fires relative to Full Burst formally starting, in the same instant.
- Decision: Add a `("squad_burst_cycle_conditional", [(event_predicate, gate_fn, delta), ...])` fill kind, resolved by a new `_resolve_squad_burst_cycle_resource` in `raid_simulator.py` that walks `simulate_burst_cycle`'s own event log in order, checking each `(event_predicate, gate_fn)` pair against the resource's running count as it reaches each event, and applying `delta` when both match. The owner's own-burst reset (from `ResourceSpec.resets`, `trigger: "own_burst"`) is checked INLINE against each event during the same walk - not merged in via a separate sort step - so that same-instant ordering between a reset and a fill rule is exactly what the underlying event log says it is, not an artifact of how two independently-sorted lists happen to interleave.
- Why: Fienn confirmed, when asked to resolve this ordering question directly, that burst1 -> burst2 -> burst3 -> full-burst-enter is a STRICT, NEVER-VIOLATED sequence in this engine - a unit's own burst-tier fire always precedes Full Burst entry within the same instant. This is what makes Maiden's Diamond Dust behave in a specific, verifiable way (see below) rather than being ambiguous, and it's the reason the inline-check approach (not a separate sort) was chosen: correctness had to be structural, matching the engine's own event-log order, not something that could silently drift if the two event streams were sorted independently with a tie-breaking convention that later changed.
- Consequences: This directly determined that Maiden's Diamond Dust (a `dynamic_hit_count_nukes` consumer, see below) always hits EXACTLY ONCE per cycle in this engine - her own burst provably drains MP to 0 before Full Burst's "if MP>=1" rule can ever observe a nonzero value, so that second fill rule is a real skill bullet that can never actually contribute in a simulated raid. It's modeled anyway (not silently dropped), with the reasoning spelled out in `maiden_ice_rose.py`'s module docstring, for documentation honesty. Also introduced in the same commit: `extra_flat_atk` on `record()`/`_damage_instance` (mirroring the existing `extra_charge_bonus` parameter's precedent exactly) - lets a specific nuke (Diamond Dust, "1372.8% of the sum of 10% of final Max HP and ATK") fold a percent-of-Max-HP bonus into ONLY that nuke's own flat_atk term, without leaking into normal attacks or any other damage instance from the same slug (a plain registry Effect would leak everywhere, since flat_atk is read unconditionally by every damage instance for that slug). And `dynamic_hit_count_nukes` itself: a burst nuke whose HIT COUNT (not just its percent) is a resource's value at burst time, reading the PRE-reset count via `resource_count_before_reset` (see the ADR below) for each of the owner's own bursts.

## Resource resets (pre/post value) and `resource_gated_buffs` resolve in the resolution pass, not `on_tier_fire`
- Date: 2026-07-12
- Context: Encoding Soda: Twinkling Bunny's Golden Chip needed two things no existing resource capability covered: (1) her burst RESETS the chip to a fixed value (17), consuming whatever had built up, rather than only ever incrementing; and (2) a burst-fired BUFF (ATK +65.25%/15s) gated on the chip having been at least 30 right before that same reset - the buff-side analog of the already-built `resource_scaled_nukes`, but for a buff rather than a nuke.
- Decision: (1) `SquadContext.reset_resource(slug, name, time, pre_value, post_value)` sets a resource to a fixed value at a point in time rather than incrementing it; `resource_count` uses the latest reset at or before the query time as its baseline (discarding fills recorded before that reset), and a new `resource_count_before_reset(slug, name, time)` exposes the value the resource held immediately BEFORE a reset recorded at an exact instant. `ResourceSpec` gained an optional `resets` field (`[{"trigger": "battle_start"|"own_burst", "value": X}, ...]`); the resolution pass merges the flat additive fill schedule with reset events (sorted by time, using `context.burst_times[slug]` for `"own_burst"` resets) and replays them chronologically so each reset's pre-value correctly reflects prior fills AND any earlier reset already applied. (2) `resource_gated_buffs`: a burst-fired buff gated on (or scaled by) a resource's count at the burst's own time, processed IN the resolution pass itself (not at `on_tier_fire`, when the burst actually fires) - iterating `context.burst_times[slug]` for each of the owner's own burst times and adding the Effect directly once the gate is checked against the now-known resource state.
- Why: A nuke can defer its percent computation to the existing phase-2 pass (`resource_scaled_nukes`, see the ADR below) because nukes are already recorded now / computed later throughout this engine. A buff has no equivalent deferred-computation stage - `on_tier_fire` fires while the resource's fills/resets for that cycle aren't known yet (they're populated by the resolution pass, which runs afterward), so a naive gate check at `on_tier_fire` time would always see a stale or zero count. Running the gate check inside the resolution pass itself, after the resource's full fill/reset schedule is known, is what makes it correct without inventing a new deferred-buff mechanism.
- Consequences: Verified to produce IDENTICAL output to the pre-existing behavior when no `resets` are present, since this touches the shared resolution-pass code every other resource-using Nikke relies on (Modernia, Guillotine, Cinderella all still pass unchanged) - a real regression risk worth calling out explicitly given how central that code path is. Also built in the same commit: `("per_shot_every_during_full_burst", N)` fill kind - a resource fill counting only shots whose time falls within a Full Burst window, computed from `simulate_burst_cycle`'s own event log (pairing `full_burst_start`/`full_burst_end` events) rather than re-deriving burst timing independently - needed for Golden Chip's "every 3 normal attacks during Full Burst" (shots outside Full Burst don't count at all, not even toward the "every 3rd" tally). First/only consumer of all of the above: Soda: Twinkling Bunny.

## Resource-scaled nukes resolve their percent in phase 2, not at record time
- Date: 2026-07-12
- Context: Encoding Julia, Cinderella, and Guillotine's previously-deferred Extermination DoT all needed a burst-fired nuke whose magnitude is gated or scaled by a named resource's count (Julia's Climax additional hit gated on Crescendo at max stacks; Cinderella's mirrored hit scaled by Beautiful's stack count; Guillotine's DoT scaled by Hero Level, recomputed every tick). The resource's fill schedule isn't known until the resolution pass runs, which happens AFTER the burst cycle that would normally record the nuke's damage event - so a naive `context.resource_count(...)` call from within a `SkillRule` action (fired during `on_tier_fire`) would always see zero fills.
- Decision: `record()` gained an optional `resource_gate` field - `(resource_name, cap, lifetime, scale_fn)` - carried on the recorded damage event but not resolved into a concrete percent until PHASE 2, via a new `_resolve_percent(ev)` that calls `context.resource_count(ev["slug"], name, ev["time"], cap, lifetime)` at the event's own time and multiplies by `scale_fn(count)`. A repeating DoT (`tick_count` > 1) records one event per tick, each carrying the same gate but evaluated at ITS OWN tick time, so a resource still accumulating during the DoT's window correctly raises later ticks over earlier ones. Wired end-to-end via `raid_simulator`'s new `resource_scaled_nukes` param, mirroring the existing `periodic_nukes`/`per_shot_rules` dict-of-specs pattern.
- Why: This is the same "record now, compute later" trick the engine already uses for every other damage instance (see the module docstring's record-then-compute section) and for deferred buffs (`RoundGrant`) - reusing it here means no restructuring of when `simulate_burst_cycle` runs relative to the resolution pass, and the resource's count is queried the same way everywhere (`resource_count`), whether from a buff's step-function emission or a nuke's percent resolution.
- Alternatives considered & rejected: moving resource fill population BEFORE the burst cycle (would require decoupling shot-time generation from the full-fight Effect registry, since shot generation currently reads live reload/max-ammo buffs that are only fully known after burst_cycle completes - a much larger restructuring for no added correctness); giving `SkillRule` actions direct access to `resource_count` (would silently return wrong/zero counts depending on trigger-firing order, an easy-to-miss correctness trap for future encodings - the deferred-percent approach makes the correct order structural rather than a convention to remember).
- Consequences: Also needed two smaller additions to make count-scaled nukes hit useful units: `burst_hit_counts` (a burst that "attacks sequentially N times" records N separate damage instances at the same instant, not one at N*percent - defense is a flat per-hit subtraction, so this matters whenever `enemy_def` > 0) and a `("periodic", interval)` resource fill kind (a resource that ticks on a fixed timer independent of the owner's shots, needed for Cinderella's Beautiful). First consumers: Julia/Julia-signature (Climax), Cinderella (Glass Slippers + Beautiful), Guillotine: Winter Slayer (Extermination's DoT, closing the gap flagged when she was first encoded).

## Base vs signature-weapon builds are separate roster slugs
- Date: 2026-07-12
- Context: Julia has a signature weapon (dollskills) with a meaningfully different kit (multi-hit burst instead of single-hit, different Skill 1 buffs). Drake and Laplace will need the same call later (flagged in `roadmap.md` since eb2). Every existing signature-weapon character (Privaty, Helm: Aquamarine) is encoded as ONE slug that already assumes the signature version — there was no established pattern for a character that needs BOTH versions available side by side, since `slug` is the sole identity key threaded through `rules_by_slug`/`base_stats`/`weapon_stats`/the registry lookup everywhere in the engine.
- Decision: Model base and signature-weapon builds as **two separate roster slugs** (`julia` and `julia-signature`) — each a full, independent registry entry — rather than adding a `has_signature_weapon` flag to `NikkeSpec` that `build_nikke_rules` branches on.
- Why: Fienn's call, presented as a fork with trade-offs (separate slugs: reuses the existing single-identity architecture unchanged, at the cost of the deck-search/roster layer treating them as if they were different characters; a spec flag: more semantically accurate to "one character, optional weapon investment," but requires threading a new parameter through `NikkeSpec`, `build_nikke_rules`, and every registry getter). Separate slugs was chosen as the smaller, more consistent change — it needs zero engine changes and matches how every other multi-build character in this codebase already works.
- Consequences: `julia_signature.py` duplicates Julia's module shape (own `climax_burst_percent`, own periodic/battle_start rule builders) rather than sharing one parameterized module - acceptable duplication given the kits genuinely diverge (5-hit vs 1-hit burst, extra forced Skill-1 cast). Drake and Laplace will follow the same `<slug>` / `<slug>-signature` split when their batches come up. The user-facing deck search will show base and signature Julia as if picking between two different Nikkes - a reasonable simplification for the engine's single-identity model, worth revisiting only if it becomes a UX problem later.

## Named-resource / capped-stack-counter primitive (gap #2 Pattern A only)
- Date: 2026-07-12
- Context: Gap #2 (quantity-based resource tracking) blocked ~16 Burst-3 units, the biggest remaining encoding blocker after eb2. Inspecting the real skill text showed "resource tracking" is not one mechanism but two: **Pattern A** — accumulating/capped stack counters whose buffs scale with the count, filled by triggers we already have (per-shot counters, burst, battle-start) — and **Pattern B** — a time-draining gauge with a threshold transform (Ark Ranger battery), additionally blocked on part-destruction fill events the engine has no concept of.
- Decision: Build **Pattern A only**, as an extensible named-resource primitive: `ResourceSpec(name, fill, cap, buffs)` + `ResourceBuff` (in `effects.py`), `SquadContext.resource_fills`/`resource_count`, and a `raid_simulator` resolution pass; buffs built via `linear_resource_buff` / `leveled_resource_buff`. The resource's count is a **function of time** computed from a deterministic fill schedule (not a mutable running total), and each buff is emitted as a **step function of delta Effects** over the fill/expiry events (so `total_for`'s running sum equals `value_fn(count)` — permanent stacks ramp then plateau at the cap; timed stacks also decay). Fill sources reuse existing triggers; `("per_shot_every_core", core_n, noncore_n)` is resolved by the sim's own `core_hittable` rather than threading a boss property through assembly. **Defer** Pattern B (time-drain/transform) and all part-destruction-filled resources — do not invent a part-break schedule (Fienn, 2026-07-12).
- Why: Data-first ROI (Fienn's gap-inventory strategy): Pattern A unblocks the tractable majority for ~modest engine surface, while Pattern B is fewer units and blocked on an unrepresentable fill event. The function-of-time count (mirroring `total_for`/`top_atk_slugs`/`burst_times`) is what makes it phase-order-safe — a mutable counter would see all burst-cycle fills before any shot-loop fill. New Nikkes declare one `ResourceSpec` (name/fill/per-stack/cap/scope) with no new engine trigger — the extensibility Fienn asked for.
- Alternatives considered & rejected: a mutable per-unit integer counter mutated during the passes (breaks across the burst-cycle vs shot-loop phase ordering); attempting the full gauge incl. time-drain + transform now (Fienn chose Pattern A only); inventing a configurable part-break schedule as a sim input to reach Ark Ranger (rejected — fabricates a boss assumption, violates the no-invented-details rule); threading `core_hittable` through `assemble_simulation_inputs` for Guillotine's fill rate (rejected — the resolution pass already has `core_hittable`, so a core-conditional fill kind keeps the boss property out of the unit encoding).
- Consequences: First consumers Modernia (⚠ timed capped stacks) and Guillotine: Winter Slayer (⚠ permanent + Hero-Level-derived + core-conditional). Still deferred and now clearly scoped for follow-ups: **count-scaled nukes** (value read at burst time, before the fill schedule is resolved — Guillotine's Extermination DoT, Cinderella's stack-mirror, Julia); Pattern B gauges/transforms; multi-source / status-window-gated fills (Soda, Modernia's Giant Leap). Remaining Pattern A units (Soda, Quency, Cinderella, Maiden, Asuka…) are now encodable in a normal batch. See `engine-gaps.md` §2, `special-mechanics.md` "Named resource / capped stack counter".

## Bullet-count ("N round") buff duration + top-N highest-final-ATK precise targeting
- Date: 2026-07-12
- Context: Encoding Miranda (애장품) and Zwei (애장품). Both have "for 1 round" buffs, and Miranda additionally targets "N allies with the highest final ATK" — neither shape is representable by the existing seconds-based `Effect` duration or the existing static scopes (`self`/`squad`/`element:X`).
- Decision: (1) **Round buffs**: `round_buff_rule` records a `RoundGrant` (not a live `Effect`); `raid_simulator`'s shot loop converts each grant into a real timed `Effect` covering exactly the affected unit's next N normal-attack shots (window from the first covered shot to the next uncovered shot, or fight end), scoped `slugs:<unit>` — a squad-scoped grant is consumed independently per ally (one Effect per unit), matching per-ally bullet consumption. (2) **Highest-final-ATK targeting**: `SquadContext.top_atk_slugs(n, caster, registry, time)` ranks the deck by LIVE final ATK (base ATK + active buffs) at application time and returns the top-n slugs (excluding caster, filling from caster if too few allies); a new `slugs:a,b` Effect scope targets exactly those units. `highest_atk_buff_rule` (timed) and `round_buff_rule(..., ("top_atk", n))` (bullet-count) both build on this.
- Why: A round buff is genuinely a bullet-count duration, not a time or burst-cycle duration — my (the docs-keeper's, relaying the encoding session's) initial assumption that it was a continuous per-cycle refresh was wrong, caught by Fienn: "for N round(s)" is consumed by the affected ally's next N shots then gone, re-granted next cycle (so ~1 shot per affected ally per cycle for N=1, not continuous uptime). And a squad-wide approximation for highest-ATK targeting would over-apply a top-1/top-2 buff to every ally, including a second carry in a dual-carry deck — exactly the case this deck-builder must evaluate correctly, so Fienn required precise targeting over an approximation.
- Alternatives considered & rejected: continuous-refresh model for round buffs (wrong semantics, corrected above); a first-class "round" duration type resolved against the FB timeline (deferred as YAGNI — the shot-loop windowing trick reuses the existing seconds-based `Effect` + `total_for` machinery with no new duration primitive, and no collected unit yet needs the general one-shot-spans-N-rounds case); squad-scope approximation for highest-ATK targeting (rejected for the over-application reason above). Fienn chose to build the full shot-count mechanism now rather than approximate, since it generalizes to future N-round/stacking buffs (e.g. Zwei's deferred 3-stack pierce).
- Consequences: Both are reusable building blocks for the backlog (see `nikke-skill-encoding/references/special-mechanics.md`, "For N round(s) is a bullet-count duration" and "Highest-final-ATK top-N targeting"). The highest-ATK ranking reads the registry at TRIGGER time (phase 1 of record-then-compute), so per-shot buffs applied in the later shot pass aren't visible to the ranking — acceptable since those are self-scoped and don't change other units' relative ranking. Miranda promoted to ✅ (Health Up self-ATK per-shot, Powering Up top-2 exact targeting, Wake Up top-1 crit-rate 1-round buff all modeled; only inert Hit Rate steps remain deferred); Zwei's 1-round squad Pierce buff now modeled (FB-window normal-attack pierce stacking and weapon transform still deferred).

## Full-charge-count CDR modeled as a per-cycle CDR pulse
- Date: 2026-07-11
- Context: A recurring "when attacking with Full Charge for N time(s): Cooldown of Burst Skill down X sec" (D: Killer Wife's Assault Formation, Rouge's Card Throw) can't be modeled by counting shots per-shot, because the burst rotation is already simulated in phase 1 before the per-shot pass runs — a per-shot CDR pulse can never feed back into a rotation that's already fixed (harder than the "buff reaches a later nuke" case the per-shot-triggers ADR below solves).
- Decision: Approximate it as a per-CYCLE CDR pulse instead — a normal `cdr_pulse_rule("full_burst_end", X)` (squad), reusing the existing per-cycle CDR machinery every other CDR buff already uses, rather than adding shot-counting-into-rotation machinery.
- Why: Per Fienn: N full charges (a full charge is ~1 sec) is met essentially every cycle (typically 8+ seconds), so applying the reduction once per cycle is a faithful approximation without the added complexity.
- Consequences: Scope is limited to a RECURRING "every N" full-charge CDR — a one-time "after N" CDR would need different treatment. Slightly generous in an already-fast rotation (if stacked CDR shortens the cycle below the time to actually fire N full charges, the game would skip that cycle's reduction but the model still grants it) — a second-order effect, acceptable for a recommender. First consumers: D: Killer Wife's Assault Formation (8s → 7s) and Rouge's Card Throw (8s → 7s). See `nikke-skill-encoding/references/special-mechanics.md` ("Full-charge-count CDR → per-cycle CDR approximation") for the worked pattern and reuse for future units with the same shape.

## `flat_max_hp` encoded now despite being inert, for forward compatibility
- Date: 2026-07-11
- Context: Max HP buffs (e.g. Rouge's Game Master, Coin-gated) are pure survivability today — `raid_simulator` has no damage-formula term that consumes Max HP, so encoding them moves no simulated output, same as any other unconsumed effect bucket (see `docs/insights.md`, Effects/stats). The general policy elsewhere is to defer stats that don't move damage rather than encode dead effects.
- Decision: Carve out an explicit exception for `flat_max_hp`: encode Max-HP buffs (scaled off the caster's Max HP via `values["caster_max_hp"]`) as `flat_max_hp` effects even though nothing consumes them today, rather than deferring them like other survival-only stats.
- Why: Per Fienn: NIKKE has HP-scaling attackers, so he wants Max-HP buffs already in place for when that damage-formula consumer gets built, rather than re-deriving the encoding later.
- Consequences: `flat_max_hp` values sit in the registry inert until both a damage-formula consumer and a `total_for("flat_max_hp", ...)` read site exist — a real, tracked future gap, not a dead end (see the skill's `references/engine-capabilities.md`, "Exception: flat_max_hp"). This is a narrower exception than the general "defer unconsumed buckets" rule — don't extend it to other unconsumed stats (Hit Rate, Attack Speed, etc.) without similarly explicit direction from Fienn.

## Refreshing buffs for repeatedly re-applied per-shot buffs
- Date: 2026-07-11
- Context: `EffectRegistry.total_for` sums every currently-active effect. A per-shot buff with a multi-second duration that gets re-applied on every qualifying shot (Prika's Let's Get the Show Started!, Mint's Here I Go!) was being added anew each shot via `buff_rule`/`registry.add`, so overlapping windows summed instead of refreshing — inflating output roughly 2x for an SR's fire rate and ~13x for an AR's by fight's end. NIKKE refreshes these buffs (extends the duration at the same value); it does not stack them.
- Decision: Add `EffectRegistry.add_refreshing` — truncates any still-active effect with the same `(stat, source_slug, scope)` to end at the new `applied_at`, then adds the new instance, so overlapping re-applications from ONE source collapse to a single continuous value. Effects from a DIFFERENT source on the same stat (e.g. another unit's buff) are untouched and still sum. Add `refreshing_buff_rule` (`skill_rules/_helpers.py`) as the drop-in replacement for `buff_rule` on any repeatedly-retriggered buff.
- Why: Matches how NIKKE's duration-refresh buffs actually behave. Truncation is done in place, so it stays correct under record-then-compute's replay: an earlier query only sees effects with `applied_at` at or before its own time, so a later shot's truncation can't change an earlier answer.
- Consequences: This corrected Prika's already-committed damage numbers (previously overstated). Encoding a repeatedly-retriggered buff (per-shot or periodic) now requires an explicit stacks-vs-refreshes call: default to `buff_rule`/`add` (stacking) only when the wording implies an actual stacking counter; use `refreshing_buff_rule` whenever it's a duration extension. See the insights.md entry on this for the symptom to watch for.

## Time-indexed unit status for post-pass (per-shot) status queries
- Date: 2026-07-11
- Context: Record-then-compute's per-shot pass (gap #1's ADR) evaluates each shot's condition in a phase-2 pass against the FINAL context, so a bare boolean status flag (`has_status`) can't distinguish "true at shot time" from "true only later." Solo Mint's Dancing/Singing status alternates every burst cycle; a per-shot buff gated on "while Singing" via `has_status` would wrongly apply the end-of-fight status to every shot in the fight, including ones fired in an earlier, different-status cycle — and, paired with Prika, would over-apply to shots fired before Prika's Encore first pins Singing.
- Decision: `SquadContext` now records each unit's burst-tier fire times (`burst_times`, via `record_burst_time`) and timestamps status flags with when they were first set (`status_since` / `set_status(..., time=...)`, keeping the EARLIEST time so re-applications don't move it forward). Mint's rule computes her Singing state AT A GIVEN TIME (`mint_singing_at(time)`): Singing if Prika's Encore pinned it at or before that time, else by burst-count parity over only the bursts at or before that time.
- Why: Generalizes the existing `activation_count`-parity trick (see `docs/insights.md`, Burst rotation) to work correctly under record-then-compute, where "what was true when" matters, not just "what is true now." One time-indexed function now covers solo Mint and Prika-paired Mint, instead of two separate models with the solo case left deferred.
- Consequences: Any future per-shot/periodic condition on an alternating or pinned status must query it at the shot's own time, not via a bare `has_status` check, or it will silently use the end-of-fight status for every shot in the fight. Mint is now fully modeled (Here I Go! solo case no longer deferred); 290 tests pass.

## Cross-unit reactive trigger: `ally_burst_activate` (engine gap resolved)
- Date: 2026-07-11
- Context: Prika's Encore fires "when Sing Along [Mint's burst buff] takes effect" — i.e. it reacts to a DIFFERENT unit's burst, not her own. The engine's `own_burst_activate` dispatch only fired a unit's rules off its OWN burst tier (`raid_simulator.on_tier_fire`), so no rule could observe a specific ally bursting — a bigger architecture gap than the existing static `deck_contains` synergies (Blanc/Rouge, Mast/Anchor), which only check deck membership, not react to another unit's trigger firing.
- Decision: `on_tier_fire` records the bursting slug on the context (`SquadContext.last_burst_slug`) and fires a new `ally_burst_activate` trigger across every unit's rules (after the burster's own `own_burst_activate`, so the reacting rule sees the burst's own effects already applied). A reacting rule gates on `ally_bursted(slug)` (reads `last_burst_slug`), combinable with other conditions via the new `all_conditions(*conds)` helper. Like `periodic_rules`, these must be buff appliers only (no instant nukes).
- Why: Generalizes the existing single-burst dispatch to cross-unit reactions without touching the ~30 existing burst-rule modules (additive trigger, no signature change to any existing builder). Firing after the burster's own trigger keeps effect ordering predictable.
- Consequences: First consumer: Prika's Encore reacting to Mint's burst, which also pins a status on the OTHER unit (`context.set_status(context.last_burst_slug, ...)`) — a new pattern for one unit's rule to mutate another unit's state. A "maintained/extended duration" buff (Prika's Charge Damage, kept alive by repeated Encores) is modeled as permanent, gated on `deck_contains(partner)`, rather than re-added on each trigger — same-stat effects sum, so re-adding would double-count. See `nikke-skill-encoding/references/special-mechanics.md` ("Cross-unit reactive trigger") for the worked example and the per-shot state caveat it surfaced (a per-shot condition sees the FINAL context, so it can't track a solo per-cycle-alternating status — Mint's solo Singing alternation stays deferred as a result).

## Per-shot triggers + record-then-compute (gap #1)
- Date: 2026-07-11
- Context: ~30 collected units gate their headline damage/buffs on shot counts ("after/every N normal attacks", "N full charge attacks") - the top-ROI engine gap. Naively firing these during the normal-attack pass (which runs after the burst cycle) would mean a per-shot SQUAD buff (e.g. Rouge/Ade buffing a dealer) never reaches a burst nuke computed earlier - understating exactly the support-buffs-dealer synergy the recommender is meant to find. Fienn chose the accurate approach over a lower-risk scoped one.
- Decision: (1) Refactor `simulate_raid` to RECORD every damage instance (burst/instant/periodic/per-shot nukes + normal attacks) as an event during phase 1 (which only applies buffs), then compute them all in a phase-2 pass against the final registry. (2) Add `simulate_raid(..., per_shot_rules={slug: [(threshold, mode, [SkillRule])]})`, fired at the unit's shot counts ("after" once at N / "every" at each multiple of N); rules apply buffs (`buff_rule("per_shot", ...)`) or emit an `instant_damage_percent` pulse recorded as `per_shot_nuke`. Exposed via `registry._PER_SHOT_RULE_BUILDERS` / `get_per_shot_rules`, threaded by `roster`.
- Why: The refactor is provably behavior-preserving (effects are added with `applied_at >= their time`, and `truncate_open_ended` mutates in place, so deferring computation never changes an existing value - the 257 prior tests stayed green) while letting late buffs correctly reach earlier instances. The engine counts shots regardless of weapon (a charge weapon's every shot is a full charge), so "full charge N" and "normal N" unify to a shot count - the encoding picks N.
- Consequences: `per_shot_rules` rules must be stateless and must not affect shot generation (reload/ammo). "On firing the last bullet" is still a gap (needs magazine-boundary markers in `attack_rate`); per-shot nukes default to `attack` type. First consumer: Brid: Silent Track's Journey Ahead (675% every 5 normal attacks). The ~30 blocked units can now be re-encoded as a follow-up batch.

## Periodic skill trigger: cooldowned Skill 1/2 buffs fire on their own cooldown
- Date: 2026-07-11
- Context: Fienn confirmed a universal battle-system rule - a Skill 1/2 (not the Burst) that has a cooldown does NOT fire at battle start; it first fires at t=cooldown and repeats. Takina Inoue's Battlefield Control (cd 15s) applies squad ally True Damage +140% and enemy Damage Taken +10% every 15s starting at t=15 - her headline support - but the engine's only triggers were the 4 burst events, and `periodic_nukes` only handles damage, not buffs.
- Decision: Add `simulate_raid(..., periodic_rules={slug: [(cooldown, [SkillRule, ...])]})`. These fire each rule's action at t=cooldown, 2*cooldown, ... Because the buffs they apply are damage INPUTS (unlike `periodic_nukes`, an output post-pass), the pass runs BEFORE `simulate_burst_cycle` so any nuke computed during the cycle reflects them (effects are replay-safe, so pre-adding at future times is correct). Exposed via `registry._PERIODIC_RULE_BUILDERS` / `get_periodic_rules`, threaded by `roster`; rules built with `buff_rule("periodic", ...)` (a label - never dispatched by `fire_trigger`).
- Why: Generalizes the existing periodic mechanism to buffs; a universal rule so high reuse (Rosanna's Spina di Rosa cd30s buff part could use it later). First-fire-at-t=cooldown already matched `periodic_nukes`, so no inconsistency. Additive, defaults to `{}`/no-op.
- Consequences: Periodic rules run against the initial context, so they must be stateless buff appliers (no dependence on burst-cycle state) - documented. A periodic nuke with an internal duration shorter than its cooldown (duty cycle, e.g. Rosanna's Spina) is still an open gap. First consumer: Takina Inoue.

## Damage typing to make type-specific Damage-Up buffs non-inert
- Date: 2026-07-10
- Context: `sustained_damage_up` / `distributed_damage_up` / `true_damage_up` / `projectile_explosion_damage_up` exist in `damage_formula.py` but `raid_simulator` never read them, so buffs like Rosanna's "Sustained Damage +20%", Takina's "True Damage +140%", and Mint's "Projectile Explosion Damage +X%" were inert. Wiring them blanket (like `attack_damage_up`) would be wrong: they only raise damage OF that type, so a squad-wide sustained buff must not boost everyone's normal attacks. And gating them correctly is still inert unless the engine also produces instances of that type - so it's a coupled feature, not a one-line wire (correcting an earlier "~1 line each" estimate).
- Decision: Give every damage instance a `damage_type`; `raid_simulator._TYPE_BUCKETS` reads a type-gated Damage-Up bucket only for matching instances (always-on buckets stay global, so untyped "attack" instances are unchanged). Types are set via: `registry._BURST_DAMAGE_TYPES` for burst nukes (rapi-red-hood → projectile_explosion), a `"damage_type"` key on `periodic_nukes` entries, RL weapon → `projectile_explosion` for normal attacks, and a self-scoped `normal_attacks_deal_true` effect that converts a unit's normal attacks for a window (Takina).
- Why: Faithful to how the buffs work in-game (per-type multipliers) without over-crediting; additive and no-regression for existing decks (default type "attack" adds no bucket). Refactored the two duplicated `calculate_damage` call sites into one `_damage_instance` helper, so type-gating lives in exactly one place.
- Consequences: Emitting a type-gated buff is now live only when the deck also produces an instance of that type (the buff is a multiplier needing something to multiply). Mint's projectile-explosion buff now reaches RL allies; Rapi's burst nuke benefits from it. Semantics confirmed against the nikke.gg glossary (now captured in `nikke-skill-encoding/references/damage-formula-reference.md`): True Damage **ignores enemy DEF** (true-typed instances use `enemy_def=0`); Attack Damage is a general buff that **affects all damage**, so `attack_damage_up` stays global. Deferred: shield_damage_up and the major-modifier terms remain inert.

## Periodic-nuke engine capability for own-fixed-cooldown skills
- Date: 2026-07-10
- Context: Helm: Aquamarine's Aegis Cannon Suppression Fire is a separate active skill with its own 4-second cooldown, firing repeatedly throughout the fight independent of burst timing entirely (not gated on Full Burst, own burst, or normal-attack count) - a genuinely new mechanic shape, at 105.58% of final ATK per tick (~45 ticks over 180s) likely her primary DPS as an Attacker.

Exposed per-Nikke through a new `registry._PERIODIC_NUKE_BUILDERS` map (kept separate from the main `_BUILDERS` dict) and `registry.get_periodic_nuke`, wired automatically by `roster.assemble_simulation_inputs`.
- Why: Fienn approved building the capability over a thin/silent approximation, given the likely DPS weight. Kept as an additive, opt-in parameter (defaults to `{}`/no-op) so the ~25 existing encoded Nikkes are completely unaffected - no change to their builder return shape.
- Consequences: A third category of "how a Nikke deals damage" now exists alongside burst nukes and instant-damage pulses (see `references/special-mechanics.md`). Future Nikkes with a similar own-cooldown skill reuse this directly.

## Instant-damage pulses for non-own-burst nukes
- Date: 2026-07-10
- Context: Brid: Silent Track's Ignition Sequence deals 636% of final ATK on entering Full Burst, regardless of who bursts that cycle - a real damage source, but the existing engine only computed burst-nuke damage tied to the caster's OWN burst tier firing (`own_burst_activate` + `burst_damage_percents`). Encoding Brid without it would leave her almost valueless (buff-only), understating a deck that includes her.

- Consequences: Damage instances from this path are logged with `source="instant_nuke"` (distinct from `"burst"`/`"normal_attack"`). Future Nikkes with the same "deal damage on trigger X, not on own burst" pattern reuse this directly.

## Crit modeled as expected value
- Date: 2026-07-10
- Context: Many Burst-1 supporters (Volume, Miranda, Tove, …) exist mainly to buff Critical Rate / Critical Damage, but the simulator computed every hit as non-critical, so those buffs did nothing and the recommender would rate the units useless.
- Decision: Model crit as expected value — every hit's damage is scaled by `1 + crit_rate*(0.5 + crit_damage_sources)`, with base crit rate 15% and base crit damage +50%.
- Why: Captures the DPS contribution of crit buffs without per-hit RNG; matches nikke.gg/note.com's documented expected-value formula.
- Consequences: Crit-rate and crit-damage buffs now move output. `base_crit_rate` defaults to 0.15 but is overridable to 0.0 for deterministic tests.

## MVP user data = manual entry
- Date: 2026-07-10
- Context: ShiftyPad (the source of a user's real Nikke investment) requires login and isn't openly queryable.
- Decision: For the MVP, users enter their real stats/investment manually; automation (login-session scraping or API reversing) is deferred.
- Why: Simplest thing that works and isn't brittle to site changes. Overload option values are additive on top of the base character-info stat.
- Consequences: The engine consumes user-supplied real ATK/DEF/HP; the per-character base-stat growth table (dotgg `statTableId`) is unneeded and, conveniently, isn't exposed anyway.

## Data source = api.dotgg.gg
- Date: 2026-07-09
- Context: nikke.gg character pages are client-rendered; a static fetch returns only the navigation shell, not stats/skills.
- Decision: Pull character and skill data from `api.dotgg.gg` — the public, no-auth JSON API that nikke.gg's front end calls (discovered by capturing the page's network requests with Playwright).
- Why: Structured data with no scraping/HTML parsing and no auth. Alternatives rejected: scraping rendered HTML (brittle); the Chrome extension (unavailable in this environment).
- Consequences: `skills` vs `dollskills` (signature weapon) must be distinguished. The `statTableId` base-stat growth table isn't exposed by the API, but isn't needed (see MVP manual-entry decision).
