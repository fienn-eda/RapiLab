# 스탯 조립 계산기 설계 (Phase 7 — **B2: ATK 자동 계산**)

작성 2026-07-18. 상태: **구현 완료 — 159/159 오차 0** (2026-07-19). 결과는 문서 하단
"구현 결과"와 그 뒤 "코어 flat은 클래스가 아니라 유닛 단위" 참고.

## 위치와 명칭

로드맵이 **"Phase B"라는 이름을 두 작업에 겹쳐 쓰고 있어** 혼선이 있었다. 이 문서를
기준으로 다음과 같이 구분한다:

- **B1 — 정확 스탯 수집기** (완료). ShiftyPad을 스크랩해 실측 스탯을 얻는다.
  `2026-07-18-blablalink-stat-collector-{design,plan}.md`.
- **B2 — ATK 자동 계산** (이 문서). 육성 데이터로 스탯을 *계산*한다. 로드맵이
  "Phase B(ATK 자동 계산)는 분리"로 이미 떼어놓은 갈래이며, 거기 적힌 잔여 항목
  **"조립공식 1회 대조검증"**이 정확히 이 작업이다.

B1은 B2의 전제가 아니라 **검증 수단**이다 — B1이 만든 실측값이 B2의 정답지다.

## 목표

**순수 함수 하나**: 니케의 육성 상태 + 공개 참조 테이블 → **솔로레이드(레벨 400) ATK/HP**.

지금 이 값은 ShiftyPad 페이지를 유닛별로 긁어야만 얻어진다. 계산기가 생기면 육성
데이터만으로 산출되므로, (a) 수집기가 159번의 페이지 로드 없이 API 2회로 끝나고,
(b) **다른 유저의 스탯**을 계산할 수 있어 계정 동기화의 전제조건이 풀린다.

(b)가 본래 동기다. 계정 동기화는 `GetUserCharacterDetails`에서 스킬레벨·큐브·오버로드·
돌파·애장품·호감도를 모두 받아오지만 **ATK/HP/DEF는 어디에도 없다** — 270개 응답을
전수 검사해 확인했고, ShiftyPad이 클라이언트에서 계산한다. 계산기 없이는 동기화한
로스터를 추천기에 넣을 수 없다.

## 비목표

- API 클라이언트·네트워크 호출 — 계산기는 순수 함수다.
- 수집기 교체 — 이번엔 **병행 비교만** 한다. 수집기는 정답지를 생산하는 유일한 경로라,
  공식이 확증되기 전에 교체하면 검증 수단이 사라진다.
- **DEF** — 캐릭터별로 달라 클래스 균일이 성립하지 않고, 엔진에 소비처가 없다.
- 오버로드 % — 엔진이 이미 `overload_effects.py`로 별도 적용한다. 표시 ATK에도 미포함.

## 구조

```
backend/app/stat_assembly.py        계산기 (순수 함수)
data/nikke-stat-tables/             커밋되는 공개 참조 스냅샷
tools/collect-blablalink/           스냅샷·정답지 덤프 모드 추가
backend/tests/fixtures/stat_ground_truth.json   159유닛 정답지
backend/tests/test_stat_assembly.py 검증
```

계산기 입력은 API 응답 형태에 묶지 않고 자체 dataclass로 받는다. 그래야 동기화 경로가
생기든 수집기가 바뀌든 계산기가 그대로 재사용된다.

## 조립 공식

`data/blablalink-cdn/NOTES.md`의 초안은 **순가산**이었고, 실측 대조에서 불완전함이
확인됐다(해당 파일과 `docs/insights.md`에 정정 기록). 실제 형태:

```
stat = base[class][level] * (1 + r) + F
```

Rapi: Red Hood 2개 레벨로 역산한 값 — `r ≈ 18.72%`, `F ≈ 36,316`.

| 항 | 후보 구성 | 상태 |
|---|---|---|
| `base[class][level]` | 클래스 3종 배열(레벨 1–1200) | 확인됨. 클래스 균일 검증 완료 |
| `r` (base 비례) | `grade_ratio=200`(등급당 2%?) + 호감도 클래스 배율 | **미확정 — 이번 작업의 핵심** |
| `F` (가산) | 장비 4부위 + `core*200` + `grade*20` + 소장품 + 큐브 | 부분 확인. 장비 테이블 미확보 |

`r`과 `F`의 정확한 구성은 **가정하지 않고 데이터로 확정한다**. 159유닛 × 2레벨 = 318개
관측이 있으므로 후보 구성을 세우고 전수 대조로 반증하는 방식을 쓴다.

## 검증 전략

**단일 레벨 검증은 금지한다.** 초안 공식이 살아남은 이유가 바로 이것 — 한 레벨에만
맞추면 base 비례 항을 상수로 오인해도 통과한다. 모든 유닛에 대해 `raid400`과 `actual`
**양쪽**을 동시에 만족해야 한다.

정답지는 두 소스의 조인이다:

- `roster.json` — 실측 `raid400` / `actual` 스탯 (수집기가 이미 수집)
- `GetUserCharacterDetails` — 육성 입력 (core/grade/장비/큐브/소장품/호감도).
  `name_codes`가 배열이라 159유닛이 **호출 1회**

정답지는 `backend/tests/fixtures/`에 **커밋**한다(Fienn 결정). 계정 식별자
(`intl_open_id`·`role_name`·`uid`)는 제외하고 육성 입력과 실측 스탯만 담는다.

허용 오차는 **0**을 목표로 한다. 정수 연산이므로 반올림 위치만 맞으면 정확히 일치해야
하며, 근사 일치는 공식이 아직 틀렸다는 신호로 취급한다.

## 참조 데이터

`data/blablalink-cdn/`의 기존 3개 클래스 테이블은 gitignore된 `data/` 아래라 유실
위험이 있다. `nikke-directory.json`과 같이 **커밋되는 스냅샷**으로 재수집한다. 전부
계정 무관 공개 정적 데이터다.

필요 항목: 클래스 3종 `character_level_attack_list`/`_hp_list` · `stat_enhance_detail`
계수 · 호감도 배율(40행) · 장비 스탯(124행) · 큐브/소장품 배열.

CDN 해시는 회전하므로 URL을 하드코딩하지 않고 런타임 발견한다(디렉토리 스냅샷과 동일
방식). 스냅샷에는 수집 일자를 남긴다.

## 위험

- **`r`의 구성이 밸런스 패치로 바뀔 수 있다.** 스냅샷에 일자를 남기고, 정답지 회귀
  테스트가 깨지는 것으로 감지한다.
- **정답지가 한 계정에서만 온다.** Fienn의 육성 범위 밖(예: 다른 등급/코어 조합)에서
  일반화가 깨질 수 있다. 159유닛에 미투자 lv1 24기가 포함돼 범위가 넓은 편이지만,
  한계로 명시한다.
- **커밋된 정답지가 개인 육성 정보를 담는다.** 현재 원격이 없다는 전제 위의 결정이므로,
  저장소를 공개할 경우 재검토가 필요하다.

## 미해결

- `grade_ratio=200`의 정확한 의미(등급당 2% 가설).
- 호감도(`attractive_lv`) 배율이 ATK에 곱으로 들어가는지, 그리고 클래스별 테이블의
  어느 열인지.
- 장비 `option_id`의 flat 스탯 기여를 124행 테이블에서 어떻게 조회하는지
  (`grow_grade`·`tier`·`lv` 축).

## 구현 결과 (2026-07-18 세션 종료 시점)

`backend/app/stat_assembly.py` — **159유닛 중 133기(84%) 완전 일치**(오차 0).

### 확정된 공식

```
atk = base[class][level] × (1 + 0.02·grade) × (1 + 0.02·core)
    + core·CORE_FLAT[class] + grade·20        # 119 / 113 / 91
    + affinity[class][호감도]                  # flat (컬럼명이 _rate지만 비율 아님)
    + 기업연구랭크 × 25                        # 계정 단위
    + Σ 부위별 장비                            # base × (1 + 0.3·전용 + 0.1·레벨)
    + cube[레벨] + 소장품/애장품                # 애장품은 곡선 최댓값 고정
```

설계 문서가 "미해결"로 남겼던 항목은 전부 닫혔다:

- **`grade_ratio=200`의 의미** → 스텝당 2%. 등급과 코어는 **곱**한다.
- **호감도가 ATK에 곱으로 들어가는지** → 아니다. **가산**이며 클래스별 컬럼을 그대로 쓴다.
- **장비 `option_id`의 flat 기여 조회 방법** → `tid`로 장비 행을 찾고
  `base × (1 + 0.3·전용 + 0.1·레벨)`. 전용/레벨 보너스는 **곱이 아니라 합**이며
  가산분을 **half-up**으로 반올림한 뒤 base에 더한다.

### 검증 방식

`backend/tests/fixtures/stat_ground_truth.json`(159유닛 × 2레벨, 커밋됨)에 대해
전수 대조한다. 설계가 요구한 **2레벨 동시 검증**은 그대로 지켜졌고 실제로 제 몫을
했다 — 코어 항이 "레벨 400·663 양쪽에서 같은 flat을 남기는지"로 확정됐다.

로스터를 재수집(159/159 무실패)해 정답지 신선도도 배제했다. 결과가 동일했으므로
편차는 데이터 낡음이 아니라 모델 결함이었고, 그 사실이 코어 항 추적으로 이어졌다.

### 남은 것

- ~~**26유닛**이 최대 220 ATK 어긋난다~~ → **해결됨 (2026-07-19). 159/159 오차 0.**
  아래 "코어 flat은 클래스가 아니라 유닛 단위" 참고.
- **HP는 미구현.** 엔진이 ATK만 소비하므로 필요해질 때 같은 방식으로 확장한다.
  장비 레벨업 화면의 HP 라인은 half-up이 아닌 것으로 관측돼(24590.5 → 24590),
  스탯별 반올림 차이를 먼저 확인해야 한다.

### 방법론 메모

인게임 화면 캡처가 분석보다 빨랐던 사례가 **세 번** 있었다(추가 능력치 팝업 →
가산항 구성, 장비 레벨업 화면 → 레벨 규칙·반올림, 코어 화면 → 코어 flat).
공식이 막히면 해당 수치를 표시하는 화면을 먼저 찾는 편이 낫다. 캡처는
`capturedimages/`에 근거로 커밋돼 있다.

## 코어 flat은 클래스가 아니라 유닛 단위 (2026-07-19 — 159/159 달성)

남아 있던 26유닛 편차는 **작은 항이 하나 더 있는 것이 아니라, 코어당 flat이 클래스
상수가 아니었기 때문**이다. 편차를 `delta / core`로 나누자 유닛별 값이 클래스마다
3~4개의 이산 티어로 정확히 뭉쳤다 — 이것이 근본 원인이다.

| 클래스 | 표준 SSR | PILGRIM | OVERSPEC | 미설명 |
|---|---|---|---|---|
| Attacker | 118.95 | 142.90 | 132.95 | 94.22 (Vesti·Rosanna) |
| Defender | 107.87 | 127.22 | 116.79 | 91.15 (Nero) |
| Supporter | 113.29 | 미측정 | 미측정 | — |

세 그룹의 정체:

- **PILGRIM** — 8기(화력 5·방어 3) 전원이 해당 값이고 타 기업 유닛은 하나도
  들어오지 않는다. `corporation`만으로 판정되므로 규칙으로 구현했다.
- **OVERSPEC** — Rapi: Red Hood · Neon: Vision Eye · Anis: Star. CDN 캐릭터
  스탯파일을 Quency: Escape Queen과 전체 키 diff 하다 **`corporation_sub_type`이
  `OVERSPEC` vs `None`**으로 갈리는 것을 발견했다(같은 파일에서 `character_level_attack_list`
  1200개는 완전 일치 — 기초 곡선이 아니라 코어 항만 다르다는 직접 증거).
  이후 스냅샷에 필드를 추가해 **규칙으로 승격했다** — 아래 후속 절 참고.
- **미설명 3기** — Vesti(91)·Rosanna(280)·Nero(380). 클래스·기업·희귀도·sub_type
  어느 것으로도 표준 유닛과 갈리지 않는다. **측정값이지 유도값이 아니다.**

이전 세션이 "화력형인데 94.2"로 적어둔 4기 중 D:KW와 Poli는 별개 원인이었다 —
클래스 표준값 자체가 틀려 있었을 뿐이다(Defender 91 → 107.87, Supporter 113 → 113.29).
Defender 91은 하필 Nero(미설명 3기 중 하나)에 맞춰져 있었다.

`core_flat_atk(class, corporation=, corporation_sub_type=, resource_id=)`가
**유닛 > 기업 > OVERSPEC > 클래스** 순으로 해석한다. 측정된 적 없는 조합(코어 있는
PILGRIM/OVERSPEC 서포터)은 클래스 값으로 얼버무리지 않고 `KeyError`를 낸다 —
코어당 ~14~30 차이라 그럴듯하게 틀리는 편이 더 나쁘다.

### OVERSPEC은 규칙으로 승격됨 (2026-07-19, 같은 세션 후속)

Chrome 디버깅 포트를 띄워 CDN을 직접 조사한 결과:

- **`stat_enhance_id` 가설은 반증됐다.** 코어 보유 59유닛 전수 대조에서 같은
  id(Attacker 5105)에 94.23과 118.9가 공존한다. 코어 flat과 무관한 값이다.
- **`corporation_sub_type: OVERSPEC`이 상위 티어를 정확히 덮는다.** 59유닛 중 11기
  (순례자 8 + 카운터즈 3)가 OVERSPEC이고 그 외엔 하나도 없다. 순례자는 OVERSPEC 중에서도
  더 높으므로 별도 행으로 뒀다(순례자는 `corporation`만으로도 판정되므로 sub_type을
  모르는 호출자도 정답을 얻는다).
- **미설명 3기는 CDN 데이터로 설명 불가임이 확정됐다.** 캐릭터 스탯 파일의 모든 범주형
  스칼라 필드를 자동 탐색했으나 Vesti·Rosanna·Nero를 같은 클래스 동료와 가르는 필드가
  **하나도 없다**(기초 3곡선·희귀도·sub_type 동일, `stat_enhance_id`는 표준 유닛과 공유).
  다음 단서는 CDN 밖에 있다 — 방법론 메모대로 **인게임 코어 화면 캡처**가 유력하다.

`collect.js --directory --deep`이 194유닛의 `corporation_sub_type`을 스냅샷에 담는다
(디렉토리 payload엔 없어 유닛당 1페이지 로드 = 194회, 그래서 opt-in). 실측 194/194 무경고.
스냅샷의 OVERSPEC은 27기 — 측정된 11기 외에 **Mihara: Bonding Chain 등 미측정 유닛까지
포함**되므로, 하드코딩 목록이었다면 놓쳤을 유닛이 규칙으로 커버된다.
`--deep` 없이 스냅샷을 갱신하면 필드가 조용히 사라지므로 테스트가 이를 막는다.

### 잔여 (다음 세션)

1. **미설명 3기(Vesti·Rosanna·Nero)** — CDN은 막혔다. 인게임 코어 화면 캡처로 접근할 것.
2. **미측정 조합** — 코어 있는 PILGRIM/OVERSPEC 서포터가 Fienn 로스터에 없다.
   해당 조합은 `KeyError`로 거부한다(얼버무리지 않음).
3. **HP 미구현** · **수집기 교체 미착수.**
