# 스탯 조립 계산기 설계 (Phase 7 — **B2: ATK 자동 계산**)

작성 2026-07-18. 상태: 설계 승인 대기.

## 위치와 명칭

로드맵이 **"Phase B"라는 이름을 두 작업에 겹쳐 쓰고 있어** 혼선이 있었다. 이 문서를
기준으로 다음과 같이 구분한다:

- **B1 — 정확 스탯 수집기** (완료). ShiftyPad을 스크랩해 실측 스탯을 얻는다.
  `2026-07-18-blablalink-stat-collector-{design,plan}.md`.
- **B2 — ATK 자동 계산** (이 문서). 육성 데이터로 스탯을 *계산*한다. 로드맵이
  "Phase B(ATK 자동 계산)는 분리"로 이미 떼어놓은 갈래이며, 거기 적힌 잔여 항목
  **"조립공식 1회 대조검증"**이 정확히 이 작업이다.

B1은 B2의 전제가 아니라 **검증 수단**이다 — B1이 만든 실측값이 B2의 정답지다.

## 목표

**순수 함수 하나**: 니케의 육성 상태 + 공개 참조 테이블 → **솔로레이드(레벨 400) ATK/HP**.

지금 이 값은 ShiftyPad 페이지를 유닛별로 긁어야만 얻어진다. 계산기가 생기면 육성
데이터만으로 산출되므로, (a) 수집기가 159번의 페이지 로드 없이 API 2회로 끝나고,
(b) **다른 유저의 스탯**을 계산할 수 있어 계정 동기화의 전제조건이 풀린다.

(b)가 본래 동기다. 계정 동기화는 `GetUserCharacterDetails`에서 스킬레벨·큐브·오버로드·
돌파·애장품·호감도를 모두 받아오지만 **ATK/HP/DEF는 어디에도 없다** — 270개 응답을
전수 검사해 확인했고, ShiftyPad이 클라이언트에서 계산한다. 계산기 없이는 동기화한
로스터를 추천기에 넣을 수 없다.

## 비목표

- API 클라이언트·네트워크 호출 — 계산기는 순수 함수다.
- 수집기 교체 — 이번엔 **병행 비교만** 한다. 수집기는 정답지를 생산하는 유일한 경로라,
  공식이 확증되기 전에 교체하면 검증 수단이 사라진다.
- **DEF** — 캐릭터별로 달라 클래스 균일이 성립하지 않고, 엔진에 소비처가 없다.
- 오버로드 % — 엔진이 이미 `overload_effects.py`로 별도 적용한다. 표시 ATK에도 미포함.

## 구조

```
backend/app/stat_assembly.py        계산기 (순수 함수)
data/nikke-stat-tables/             커밋되는 공개 참조 스냅샷
tools/collect-blablalink/           스냅샷·정답지 덤프 모드 추가
backend/tests/fixtures/stat_ground_truth.json   159유닛 정답지
backend/tests/test_stat_assembly.py 검증
```

계산기 입력은 API 응답 형태에 묶지 않고 자체 dataclass로 받는다. 그래야 동기화 경로가
생기든 수집기가 바뀌든 계산기가 그대로 재사용된다.

## 조립 공식

`data/blablalink-cdn/NOTES.md`의 초안은 **순가산**이었고, 실측 대조에서 불완전함이
확인됐다(해당 파일과 `docs/insights.md`에 정정 기록). 실제 형태:

```
stat = base[class][level] * (1 + r) + F
```

Rapi: Red Hood 2개 레벨로 역산한 값 — `r ≈ 18.72%`, `F ≈ 36,316`.

| 항 | 후보 구성 | 상태 |
|---|---|---|
| `base[class][level]` | 클래스 3종 배열(레벨 1–1200) | 확인됨. 클래스 균일 검증 완료 |
| `r` (base 비례) | `grade_ratio=200`(등급당 2%?) + 호감도 클래스 배율 | **미확정 — 이번 작업의 핵심** |
| `F` (가산) | 장비 4부위 + `core*200` + `grade*20` + 소장품 + 큐브 | 부분 확인. 장비 테이블 미확보 |

`r`과 `F`의 정확한 구성은 **가정하지 않고 데이터로 확정한다**. 159유닛 × 2레벨 = 318개
관측이 있으므로 후보 구성을 세우고 전수 대조로 반증하는 방식을 쓴다.

## 검증 전략

**단일 레벨 검증은 금지한다.** 초안 공식이 살아남은 이유가 바로 이것 — 한 레벨에만
맞추면 base 비례 항을 상수로 오인해도 통과한다. 모든 유닛에 대해 `raid400`과 `actual`
**양쪽**을 동시에 만족해야 한다.

정답지는 두 소스의 조인이다:

- `roster.json` — 실측 `raid400` / `actual` 스탯 (수집기가 이미 수집)
- `GetUserCharacterDetails` — 육성 입력 (core/grade/장비/큐브/소장품/호감도).
  `name_codes`가 배열이라 159유닛이 **호출 1회**

정답지는 `backend/tests/fixtures/`에 **커밋**한다(Fienn 결정). 계정 식별자
(`intl_open_id`·`role_name`·`uid`)는 제외하고 육성 입력과 실측 스탯만 담는다.

허용 오차는 **0**을 목표로 한다. 정수 연산이므로 반올림 위치만 맞으면 정확히 일치해야
하며, 근사 일치는 공식이 아직 틀렸다는 신호로 취급한다.

## 참조 데이터

`data/blablalink-cdn/`의 기존 3개 클래스 테이블은 gitignore된 `data/` 아래라 유실
위험이 있다. `nikke-directory.json`과 같이 **커밋되는 스냅샷**으로 재수집한다. 전부
계정 무관 공개 정적 데이터다.

필요 항목: 클래스 3종 `character_level_attack_list`/`_hp_list` · `stat_enhance_detail`
계수 · 호감도 배율(40행) · 장비 스탯(124행) · 큐브/소장품 배열.

CDN 해시는 회전하므로 URL을 하드코딩하지 않고 런타임 발견한다(디렉토리 스냅샷과 동일
방식). 스냅샷에는 수집 일자를 남긴다.

## 위험

- **`r`의 구성이 밸런스 패치로 바뀔 수 있다.** 스냅샷에 일자를 남기고, 정답지 회귀
  테스트가 깨지는 것으로 감지한다.
- **정답지가 한 계정에서만 온다.** Fienn의 육성 범위 밖(예: 다른 등급/코어 조합)에서
  일반화가 깨질 수 있다. 159유닛에 미투자 lv1 24기가 포함돼 범위가 넓은 편이지만,
  한계로 명시한다.
- **커밋된 정답지가 개인 육성 정보를 담는다.** 현재 원격이 없다는 전제 위의 결정이므로,
  저장소를 공개할 경우 재검토가 필요하다.

## 미해결

- `grade_ratio=200`의 정확한 의미(등급당 2% 가설).
- 호감도(`attractive_lv`) 배율이 ATK에 곱으로 들어가는지, 그리고 클래스별 테이블의
  어느 열인지.
- 장비 `option_id`의 flat 스탯 기여를 124행 테이블에서 어떻게 조회하는지
  (`grow_grade`·`tier`·`lv` 축).
