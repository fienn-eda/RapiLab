# 명중률 → 탄착군 → 코어히트율 — 설계

날짜: 2026-08-07

출처: 아카라이브 니케 채널 「명중의 모든 것을 알려주겠다」(니미니스트, 2024-01-09
작성 / 2024-12-13 수정) — https://arca.live/b/nikketgv/96243965

엔진은 코어 히트를 **불리언**으로 다룬다. 보스에 코어가 있으면 모든 평타가 코어에
맞고, 없으면 아무도 안 맞는다. 실제 게임에서 코어에 맞는 비율은 **탄착군 크기와
코어 크기의 비율**이고, 탄착군은 **무기 클래스와 명중률 스탯**이 정한다. 그 두 항을
엔진에 들여온다.

부수 효과로 `hit_rate`가 소비자를 얻는다. 지금 이 스탯은 등록은 되지만 아무도 읽지
않아 15개 슬러그가 보류로 적어두고 있다.

## 배경 — 지금의 지형

- `raid_simulator.CORE_HIT_BONUS = 1.0`이 `damage_formula`의 major modifier에
  더해진다. 코어 히트 한 발은 논코어 한 발의 2.0배다.
- `BossProfile.core_hittable`(불리언)이 시뮬 전체를 토글하고,
  `core_eligible(source, damage_type)`이 그 안에서 어떤 인스턴스가 받는지 정한다 —
  평타만, 스킬딜은 never, Sustained/Distributed는 never. 예외 둘은
  `core_strike` 타입과 `core_eligible_override=True`(아니스: 스타의 소환물).
- `_entries()`가 이미 한 이벤트를 두 인스턴스로 쪼개는 선례를 갖고 있다 — 관통
  보유자의 평타가 코어를 뚫고 뒤의 본체를 때리는 경우.
- `hit_rate`는 `Effect`로 등록 가능하지만 `_BUNDLE_STATS`에 없어 아무도 안 읽는다.
- engine-gap #21이 이 영역을 이미 한 번 파고 「코어히트율은 그 판의 플레이 조건이지
  엔진 상수가 아니다」로 닫았다. **그 결론은 이 설계와 충돌하지 않는다** — §7 참고.

## 1. 모델

### 1.1 세 무기 공식은 하나다

글은 무기별로 따로 잰 회귀식 셋을 준다(x = 명중률 %, y = 탄착군 직경 px):

| 무기 | 글의 회귀식 | 기본 직경 | y = 0이 되는 x |
|---|---|---|---|
| SG | y = −2.18x + 240 | 240 | 110.09 |
| AR | y = −0.69x + 76 | 76 | 110.14 |
| SMG | y = −1.00x + 110 | 110 | 110.00 |

**셋 다 x = 110에서 직경 0으로 수렴한다.** 글이 「특이점(110%)」이라 부른 것이 이것이고,
회귀식 셋은 같은 한 식의 무기별 인스턴스다:

```
D(명중) = 기본직경 × max(0, 1 − 명중/110)
```

`max(0, ...)`가 필요한 이유는 명중 110% 초과가 실재하기 때문이다 — 도로시:
세렌디피티가 혼자 넘는다(§6).

### 1.2 코어히트율

탄착이 직경 D의 원에 균등 분포하고 조준점이 코어 중심에 있다고 보면, 코어(직경 C)에
드는 비율은 면적비다:

```
p = 1.0          (D ≤ C — 탄착군 전체가 코어 안)
    (C / D)²     (그 외)
```

**검증.** 글은 코어 크기를 말하지 않고 탄착군과 코어히트율의 쌍만 준다(블랙스미스
중거리, 팔 코어). 그래서 분포 모델을 **각 점이 함의하는 코어 크기로 역산해** 채점할 수
있다 — 모델이 맞다면 모든 점이 **같은 C**를 가리켜야 한다. 넷째 점은 p가 상한에
붙어 있어 하한만 준다.

| 탄착군 D | 글의 실측 p | 균등 원판이 함의하는 C = D√p | 가우시안(D=2σ)이 함의하는 C |
|---|---|---|---|
| 75px | 40% | 47.4px | 37.9px |
| 60px | 80% | 53.7px | 53.8px |
| 55px | 90% | 52.2px | 59.0px |
| 50px | ~100% | ≥ 50px | (닿지 못함) |
| | **산포** | **51.1px ± 6.1%** | 50.2px ± 21.0% |

**균등 원판이 3.4배 더 자기일관적이다.** 가우시안은 같은 세 점에서 37.9 ~ 59.0px를
가리켜 스스로 모순되고, 게다가 D = C에서 100%에 닿지 못하는데 실측은 닿는다.

부수 소득이 하나 더 있다: **균등 원판이 함의하는 코어 51.1px는 Fienn이 세운 50px
가정과 2% 차이다.** 두 값은 서로 독립이다(하나는 2024년 글의 실측 회귀, 하나는 이번
가정). 50px는 이제 임의의 출발점이 아니라 근거를 가진 값이다 — 단, 그 근거가 말하는
것은 **블랙스미스의 팔 코어**이지 모든 보스의 코어가 아니다.

## 2. 무기 탄착군 상수

신설 `backend/app/accuracy.py`:

| 무기 | 직경(px) | 게임 데이터 출처 |
|---|---|---|
| AR | 75 | `start = end = 75` |
| SG | 250 | `start = end = 250` |
| SMG | 110 | `start = end = 110` |
| MG | 10 | `end = 10` (§2.2) |
| SR | 10 | `start = end = 10` |
| RL | 10 | `start = end = 10` |

`data/shiftypad/raw/*.json`의 `shot_detail.start_accuracy_circle_scale` /
`end_accuracy_circle_scale`에서 온 값이고, 수집된 77유닛에서 **무기 클래스별로 완전히
균일하다**(클래스 내 분산 0).

글의 실측 240/76/110은 이 값의 근사다 — SMG는 정확히 일치, AR은 1px, SG는 4% 차이.
**게임 데이터 쪽을 채택한다.**

### 2.1 상수 테이블인 이유

무기 파이프라인(`user_roster._weapon_stats`)에 필드를 추가하면 로스터 재동기화가
필요해지는데, 값이 클래스별로 균일하므로 얻는 것이 없다. 대신 상수가 조용히 낡는 것을
막기 위해 **`scripts/audit_weapon_accuracy_scales.py`** 를 함께 만든다 — 수집된 전
유닛의 `shot_detail`을 읽어 이 표와 대조하고, 불일치가 있으면 exit 1.

### 2.2 MG는 수렴값을 쓴다

MG만 `start=250`, `end=10`, `accuracy_change_pershot=−7`이다. 탄창 첫 발이 250px에서
시작해 발당 7px씩 좁아져 29발째에 50px(코어)를 덮고 35발째에 10px로 수렴한다 — 연사
예열(`attack_rate.MG_SPINUP`)과 같은 형태의 **정확도 예열**이다.

**이번 범위에서는 수렴값 10px만 쓴다.** 예열 구간을 모델링하려면 탄창 내 발 인덱스가
데미지 이벤트까지 흘러야 하는데(`generate_magazine_shot_times`와 세그먼트
`_base_shot_records` 두 생성기 모두), 그 배선 비용에 비해 값이 작다.

그 대신 **이 단순화가 무엇을 결정하는지는 명시해 둔다**: MG의 기본 D가 10px이면
명중 디버프가 사실상 무해해진다. 마스트: 로맨틱 메이드의 Drunken 3스택(명중 −107.76%)이
D를 19.8px로 밀지만 여전히 코어 50px 안이라 p = 1.0이다. `start=250`을 썼다면 같은
디버프가 D를 495px로 밀어 p = 1.0%가 됐을 것이다 — **두 선택이 극단적으로 갈리는
자리이므로, 예열을 나중에 배선할 때 이 문장을 다시 읽을 것.**

놓치는 것: 탄창당 앞 29발의 코어 손실(탄창 300발 기준 약 8%의 코어 보너스, 딜 −4%
상당). 보류로 기록한다(§9).

## 3. `damage_formula` — 크리티컬과 대칭인 한 줄

`_major_modifiers`는 이미 크리티컬을 기대값으로 처리한다. 코어를 같은 모양으로 만든다:

```python
def _major_modifiers(
    crit_rate,
    other_critical_damage_sources,
    core_hit_rate,
    core_hit_bonus,
    other_core_damage_sources,
    full_burst_bonus,
    effective_range_bonus,
):
    # 기대값 크리: 확률 crit_rate로 (0.5 + 소스)를 더한다.
    expected_crit_term = crit_rate * (0.5 + other_critical_damage_sources)
    # 기대값 코어: 같은 구조. 조준점이 코어에 있어도 탄착군이 코어보다 크면 일부만
    # 코어에 들며, 그 비율이 core_hit_rate다. 코어 대미지 소스는 코어에 실제로 맞은
    # 발에만 붙으므로 확률 안쪽에 있다.
    expected_core_term = core_hit_rate * (core_hit_bonus + other_core_damage_sources)
    return (
        1
        + expected_crit_term
        + expected_core_term
        + full_burst_bonus * 0.5
        + effective_range_bonus * 0.3
    )
```

`calculate_damage`에 `core_hit_rate=1.0`을 추가한다. 기본값이 1.0이므로 **기존 호출은
의미가 바뀌지 않는다** — `core_hit_bonus`가 0이면 곱해도 0이고, 1.0이면 곱해도 1.0이다.

`_major_modifiers`는 `calculate_damage` 안에서 **위치 인자로** 불리므로 그 호출부도
같이 고쳐야 한다. 인자가 일곱 개가 되는 지점이므로 키워드 호출로 바꾼다 — 크리 쌍과
코어 삼중을 위치로 세는 것은 조용히 틀리기 좋은 모양이다.

`raid_simulator`의 호출부는 `hits_core` 불리언을 계속 쓰되(어떤 인스턴스가 코어 항을
받을 자격이 있는가) p를 함께 넘긴다:

```python
core_hit_bonus=CORE_HIT_BONUS if hits_core else 0.0,
other_core_damage_sources=bundle["other_core_damage_sources"] if hits_core else 0.0,
core_hit_rate=core_hit_rate_for(slug, time, is_normal_attack, damage_type),
```

### 3.1 인스턴스를 쪼개지 않는 이유

관통 선례를 따라 `instance(True)` × p + `instance(False)` × (1−p) 두 항으로 쪼갤 수도
있다. 기각한다: 데미지 로그 항목이 2배가 되고(하류의 `_summarize`가 전부 이 로그를
훑는다), 크리티컬은 기대값인데 코어만 분할이 되어 두 확률 항이 비대칭이 된다.

## 4. `BossProfile.core_diameter_px` — opt-in

```
core_diameter_px: float | None = None
```

- `None` → 지금 동작 그대로. `core_hittable`이 참이면 적격 인스턴스가 p = 1.0을 받고,
  거짓이면 0.0을 받는다. **기존 시뮬은 바이트 불변이다.**
- 값이 있으면 → 적격 평타가 §1.2의 p를 받는다.
- `core_hittable`이 거짓이면 이 값은 무시된다(코어가 없으면 크기를 물을 수 없다).

`api.BossProfileIn`에도 같은 필드를 추가한다. **프론트엔드는 이번 범위 밖이다** —
「코어 피격 가능」 체크박스와 그 동작은 그대로다.

기본값이 `None`인 이유는 §7.

## 5. `hit_rate`를 `_BUNDLE_STATS`에 추가

`raid_simulator._BUNDLE_STATS`에 `"hit_rate"`를 넣으면 `_stat_bundle(slug, time)`이
시각별 명중률을 돌려준다. 명중 버프는 대부분 지속시간이 있으므로(질 발렌타인 10초,
드레이크 10초) 시점별 조회가 그대로 필요하다.

**기본 명중률은 0%로 둔다.** 근거: 클래스 스탯 테이블(`data/nikke-stat-tables/
tables.json`의 `classes`)은 attack/hp/def만 담고, 오버로드 옵션은 7종인데 명중이 없다
(`overload.type_name` = 우월코드/최대장탄/공격력/차지대미지/차지속도/크리확률/크리댐).
즉 명중은 **스킬 버프에서만 온다.** — Fienn의 게임 내 확인이 필요한 유일한 가정이다
(§9).

### 5.1 적용 대상

p를 받는 것은 **평타뿐**이다. 코어 적격이지만 p = 1.0을 유지하는 둘:

- **`core_strike` 타입** — 스킬이 명시적으로 코어를 때린다고 원문에 적힌 딜이다.
  조준의 문제가 아니다.
- **`core_eligible_override=True`** — 아니스: 스타의 Shooting Stars. 원문이 "stars that
  aim and shoot on their own"이라 탄착군이 그녀 무기의 것이 아니다.

### 5.2 관통

관통 보유자의 평타는 코어를 뚫고 뒤의 본체까지 때린다. 코어를 **놓친** 발은 본체에
맞고 그대로 나가므로 두 번째 인스턴스가 없다. 따라서:

- 첫 인스턴스(코어 보너스 대상): `core_hit_rate = p`
- 두 번째 인스턴스(본체): `core_hit_rate = 0`, **데미지에 p를 곱한다**

p = 1.0이면 현재와 바이트 동일하다.

## 6. 영향 — 명중을 가진 15유닛

수집 데이터에서 `Hit Rate`를 언급하는 전 슬러그. p는 코어 50px 기준.

「명중」 열은 **한 슬러그 안의 단일 최대값**(10레벨)에서 최대 디버프를 뺀 대략치다.
실제 인코딩은 조건·지속시간·스택에 따라 다르고 **여러 항이 합산되면 이 값을 넘는다** —
도로시가 그 경우다(98.18% 한 항이 아니라 40.68 + 78.54 = 119.22%). 그리고 **버프
대상이 자신인지 아군인지를 이 열은 구분하지 않는다**: 디젤의 −100%는 그녀 자신이 아니라
**아군에게** 가는 디버프이므로, 그 행의 p는 「디젤 본인이 RL이라 무해」를 보여줄 뿐
효과의 실제 크기가 아니다(§6 두 번째 읽을 것). 마스트의 −35.92%는 자기 대상이 맞다.

읽을 것 셋:

  트리거(+78.54%)가 합쳐 110%를 넘으면 탄착군이 0이 되어 SG로 코어히트 100%를 낸다.
  지금은 두 항 모두 inert다.
- **RL·MG 4유닛은 여전히 inert이지만 이유가 바뀐다.** 「엔진이 안 읽는다」가 아니라
  「기본 탄착군 10px가 이미 코어 안이라 명중이 바꿀 것이 없다」가 된다. 디젤의 아군
  명중 −100%가 무해한 것도 아군이 RL/MG일 때만이므로, 그녀의 보류는 §2.2의
  MG 단순화와 함께 다시 봐야 한다(SG/SMG/AR 아군에게는 무해하지 않다).
- **SG는 명중을 챙겨도 코어를 못 때린다** — 4.0% → 8~10%. 글의 결론(「샷건 딜러는
  근본적인 설계 미스」)을 엔진이 재현한다.

## 7. 실기록 캘리브레이션과의 관계

**코어 50px를 실기록 보스에 켜면 캘리브레이션이 뒤집힌다.** 현재 무기군별 실기록 대비
배수는 MG 1.051x · SMG 1.145x · SR 1.118x · AR 1.116x · RL 1.035x(합계 1.047x,
19/25)인데, 50px를 적용하면 SMG는 major modifier가 2.0 → 1.207(−39.7%), AR은 2.0 →
1.444(−27.8%)가 되어 각각 0.69x · 0.81x로 **과대가 과소로 넘어간다.**

역산하면 현재 실기록과 정확히 맞는 코어 크기는 AR 기준 약 67px, SMG 기준 약 95px로
**서로 다르다.** 즉 단일 코어 크기로 두 무기군을 동시에 맞출 수 없고, 이는 실기록의
잔차에 탄착군 말고 다른 항이 더 있다는 뜻이다.

**그래서 기본값이 `None`이다.** engine-gap #21이 확립한 해석 — 엔진은 코어 100%라는
**상한**을 모델링하고 `sim/record`는 1.0보다 위가 정상 — 이 그대로 살아 있다. 이 설계는
그 해석을 뒤집지 않고 **직교하는 두 번째 항**을 추가한다:

```
실제 코어히트율 = p_조준(플레이 조건, 좌석별) × p_탄착(무기·명중, 결정론)
```

gap #21이 다룬 것은 첫 항이다(파츠를 직접 때린 좌석은 코어를 겨누지도 않았다). 이
설계는 둘째 항이다(코어를 겨눠도 탄착군이 코어보다 크면 빗나간다). 엔진은 첫 항을
계속 1.0(상한)으로 두고, 둘째 항만 opt-in으로 모델링한다.

실기록 보스에 이 모델을 켜는 것은 **보스 코어 크기 실측이 생긴 뒤의 별도 결정**이다.

## 8. 테스트

- **회귀 없음이 계약이다**: `core_diameter_px=None`에서 기존 시뮬 결과가 바이트
  동일. 픽스처 덱으로 고정한다.
- `accuracy.py` 단위: 무기별 D, 명중 0/50/110/120%에서의 D(110% 이상은 0), 음수 명중이
  D를 키우는 것, p의 D ≤ C 분기.
- **110% 특이점**을 명시적으로 고정한다 — 세 무기가 같은 x에서 0이 되는 것이 이 모델의
  근간이다.
- 무기별 기본 p(AR 44.4% · SG 4.0% · SMG 20.7% · MG/SR/RL 100%).
- `damage_formula`: `core_hit_rate` 기본 1.0이 기존 결과와 동일, 0.5가 코어 항만 절반으로
  줄이고 크리·FB·사거리 항은 안 건드리는 것.
- 적용 대상: `core_strike`와 `core_eligible_override=True`가 p를 무시하고 1.0을 쓰는 것.
- 관통: p=1.0에서 두 인스턴스가 현재와 동일, p<1에서 두 번째 인스턴스만 p배.
- **도로시: 세렌디피티 통합 테스트** — 두 명중 버프가 함께 걸리면 p=1.0에 도달.
- 감사 스크립트가 상수 테이블과 수집 데이터의 불일치를 실제로 잡는지(상수 하나를
  일부러 틀리게 하고 exit 1을 확인).

## 9. 남기는 보류

- **MG 정확도 예열** — 탄창당 앞 29발의 코어 손실(§2.2). 발 인덱스 배선 필요.
- **균등 원판 분포의 근거는 글의 실측 4점뿐**(오차 −10.6 ~ +4.4%p). 가우시안보다 낫다는
  것까지가 확인된 것이고, 실측으로 확정된 것은 아니다.
- **기본 명중률 0%** — 데이터에 명중 항목이 없다는 소극적 근거. Fienn의 게임 내 확인
  필요.
- **`core_damage_rate` 2.5배 4유닛** — 미란다 · 퀀시: 이스케이프 퀸 · 리틀 머메이드 ·
  치사토는 `shot_detail.core_damage_rate = 25000`인데 엔진은 `CORE_HIT_BONUS = 1.0`을
  전원에게 쓴다. 이 넷은 코어 보너스가 과소 계상 중이다. **이 설계와 독립인 별도
  결함**이므로 섞지 않는다.
- **디젤: 윈터 스위츠의 아군 명중 −100%** — SG/SMG/AR 아군에게는 무해하지 않다.
  §2.2의 MG 단순화와 함께 다시 볼 것.
- 글의 수치는 2024년 것이다. 현재 버전과 다를 수 있고, 특히 **글이 언급한 「명중
  오버로드」는 지금 게임 테이블에 없다**(7종 확인).
