# 탐색 재현성 — 스왑 예산을 벽시계에서 후보 수로

날짜: 2026-08-05

## 문제

같은 로스터·같은 보스로 추천을 두 번 눌러도 다른 덱이 나온다. 실측: 45초 예산
3회가 **28.05 / 23.86 / 28.17B**.

원인은 **하나뿐**이다 — `deck_allocation.py:293`의
`deadline = time.monotonic() + time_budget_sec`. 탐색의 나머지는 전부 결정적이다.

- `SimPool._map`은 `executor.map`이라 입력 순서를 보존한다
- 대리모델 표본은 고정 `FIT_SEED`(`surrogate.sample_feasible_combinations`)
- 그리디 peel과 마지막 순서 다듬기는 예산이 없다

**이 목록은 실측으로 확인했다(2026-08-05).** 파이썬은 프로세스마다 문자열 해시를
무작위화하므로, 집합 순회가 순서 결정에 닿는 곳이 하나라도 있으면 위 목록은
거짓이 된다. 그래서 `PYTHONHASHSEED=1`과 `=2`로 같은 입력을 각각 돌렸다 —
로스터 22 usable · 3덱 요청 · `workers=2` · 예산 600초(각각 52.0s · 50.6s에
**수렴**했으므로 데드라인이 물리지 않는 조건). 두 실행의 덱 구성과 leftover가
같고 총딜이 **마지막 자리까지** 같았다(`6089389733.91905`). 이 픽스처가 밟지
않은 경로는 남아 있다 — 속성저지 · 드래프트 · 캐스케이드가 예산을 넘는 경우.

그래서 **예산이 물리지 않으면(등반이 수렴하면) 이미 완전히 재현된다.** 갈라지는
것은 예산이 물릴 때뿐이다. 그런데 현재 상한 180초는 Fienn 로스터의 수렴점
176.6초에 붙어 있어 부하가 조금만 있어도 문다.

잘린 답은 재현이 안 될 뿐 아니라 **더 나쁘다**: 45초 27.90B vs 수렴 30.66B
(`docs/decisions.md` 2026-08-04 근거 표).

숨은 축이 하나 더 있다. `batch = max(4, worker_count * 4)`이므로, 예산이 물릴 때
**배치 폭이 잘리는 지점을 바꾼다** — 코어 수가 다른 머신이 다른 답을 낸다.

이 항목은 2026-08-04 `docs/decisions.md`에 대안 (b)로 적혀 있고 **"미채택이지
기각이 아니다"**로 남겨둔 것이다.

**목표(Fienn, 2026-08-05):** 앱에서 **같은 입력이 같은 답**. 동기는 측정 신뢰나
테스트가 아니라 **사용자 신뢰**다. 그리고 대기시간 상한을 잃더라도 **수렴까지
돌린다** — 예산은 품질 노브가 아니라 폭주 방지 장치가 된다.

### 왜 상한을 잃어도 안전한가

등반은 **반드시 끝난다.** 수용 조건이 `sum(totals) > baseline` 강부등호라 총딜이
단조 증가하고, 상태공간(유닛 → 덱 배정)이 유한하기 때문이다. 그래서 상한은
정확성 장치가 아니라 **인내심 장치**다. 사용자가 끊을 수단도 이미 있다
(`RecommendPanel.tsx:499`의 취소 버튼).

## 설계

### 1. 벽시계 데드라인 → 후보 예산

예산의 단위는 **검토한 후보 교환 수**다.

- `SWAP_TIME_BUDGET_SEC = 180.0` → `SWAP_CANDIDATE_BUDGET = <계측으로 정함>`
- `allocate_decks(..., time_budget_sec=...)` → `swap_budget=...`.
  **`0`은 스왑 단계를 통째로 건너뛴다는 기존 뜻을 유지한다** — 테스트 20여 곳이
  이 뜻에 의존한다.
- `_swap_pass(decks, leftovers, boss, budget, ...)` — 4번째 위치 인자가 실수
  `deadline`에서 정수 `budget`으로 바뀐다. 소모 합계는 `_swap_pass`가 자기
  안에서 들고 있으므로 가변 객체를 아래로 내릴 필요가 없다.
- 루프 조건: `while improved and time.monotonic() < deadline`
  → `while improved and spent < budget`
- 균등 배분(2026-08-04 PR #3)은 **그대로 유지**하고 산술만 정수로 바꾼다:
  `now + (deadline - now) / (len(items) - done)`
  → `share = (budget - spent) // (len(items) - done)`
- `_try_swaps(..., share, ...)`는 `(improved, used, exhausted)`를 돌려준다.
  `share`는 이 항목에 허락된 후보 수, `used`는 실제로 쓴 양이다 —
  `_swap_pass`의 누적 `spent`와 헷갈리지 않도록 이름을 나눈다.
  - 배치를 **자기 몫까지만** 자른다:
    `chunk = candidates[start:start + min(batch, share - used)]`
  - 과금은 `start`가 전진한 만큼이다 — 채택이 없으면 `len(chunk)`,
    채택하면 `accepted + 1`
  - `exhausted`는 후보 목록을 끝까지 봤는지(`start >= len(candidates)`)다.
    아래 §3이 이걸 쓴다.

**왜 시뮬 수가 아니라 후보 수인가.** `len(trials)`로 과금하면 배치 폭이 소모
속도를 바꾸므로 상한이 물리는 **지점이 머신마다 달라진다.** 그런데 상한이 물리는
순간이 정확히 재현성이 필요한 순간이라, 거기서 보장을 잃으면 의미가 없다. 후보
수로 과금하고 배치를 몫까지 자르면 그 지점이 머신 독립이 된다.

대가는 채택 뒤 버려지는 꼬리 채점이 과금되지 않는 것이다 — 예산과 실제 초의
비례가 조금 느슨해진다. 낭비는 채택당 배치 폭 미만이고 채택률이 **1% 미만**
(`_try_swaps` docstring의 실측)이라 작고, 상한이 폭주 방지용이라 정밀한 초
환산이 애초에 필요 없다.

**공짜로 따라오는 것.** 배치 폭은 **어느 후보가 채택되는지를 바꾸지 않는다** —
`_try_swaps`는 후보를 고정 순서로 훑어 처음 개선하는 것을 받아들이고, 배치는
몇 개를 미리 채점하느냐만 정한다. 따라서 **수렴하면 코어 수가 다른 머신도 같은
답**을 낸다. 예산이 물릴 때만 갈라지던 축이 같이 닫힌다.

### 2. 상한 값과 그 근거

**계측이 먼저다.** 이 값은 지금 정할 수 없고, 구현 계획의 1단계가 측정이다.

`scripts/measure_swap_budget.py`를 후보 단위로 개조한다:

- `--budgets`가 초 대신 후보 수를 받는다
- **수렴까지 쓴 후보 수** 열을 새로 뽑는다 (이게 상수의 근거가 된다)
- 기존 `converged` 판정(`took < budget * 0.99`)은 이제 `_swap_pass`가 돌려주는
  플래그(§3)를 그대로 읽는다 — 추정에서 사실로 바뀐다

측정 조건은 현 상수의 근거와 **같게 둔다.** 그래야 지금 표와 나란히 놓인다:
Fienn 로스터(78 usable) · 5덱 · `--element Fire`(수냉 약점) · def 31,784 ·
180초 · 코어 안 맞힘. **속성저지 ON/OFF 둘 다.**

**빈자리만 모드(`recommend_from_draft`가 `allocate_decks`를 3번 부르는 경로)는
§4 문구용으로만 잰다.** 예산은 `allocate_decks` **호출당** 부여되므로 그 경로도
상수는 같은 값을 쓴다.

상한 = 측정된 수렴량 × N. **N은 숫자를 보고 정한다 — 5배를 추천한다.** 근거:
후보 목록 길이는 벤치 크기를 타는데 지금 로스터는 78유닛(벤치 ~53)이고 전
캐릭터 보유자는 벤치가 ~134라 항목당 후보가 2.5배쯤 된다. 패스 수 증가까지
감안하면 3~5배 언저리다. **이건 추정이지 측정이 아니며**, 그래서 넉넉한 쪽을
고른다 — 취소 수단이 있고 등반이 유한하므로 관대한 상한의 비용이 작다.

상수 옆 근거 표는 현 관례를 유지하되, 후보 수는 초 환산이 머신마다 다르므로
**Fienn 머신 기준 초를 병기**한다. 캐비엇도 그대로 단다 — **로스터 하나**에서
고른 숫자다.

### 3. 상한 적중 신호

지금 `_swap_pass`는 아무것도 돌려주지 않는다. **수렴 여부**를 돌려주게 한다.

수렴 판정은 `not improved`만으로는 틀린다. 균등 배분 때문에 어떤 항목이 자기
몫에서 잘린 채 그 패스에서 개선을 못 찾았을 수 있고, 그건 수렴이 아니라 잘림이기
때문이다. 그래서:

```
converged = (마지막 패스에서 개선 없음) and (그 패스의 모든 항목이 exhausted)
```

상한이 폭주 방지용이 되면 `share`가 후보 수보다 훨씬 커서 `exhausted`는 항상
참이 된다 — 이 항은 상한이 실제로 물릴 때만 일한다.

배선:

- `allocate_decks` 반환 dict에 `"swap_converged": bool` 추가
- `recommend_from_draft`: 호출이 1회 또는 3회이므로 **실제로 돈 것들의 AND**.
  주의 — `within_draft`가 이기면 `recommended`를 새 dict로 다시 만드는 자리
  (`deck_allocation.py:594`)가 키를 둘만 싣는다. **거기서 플래그가 조용히
  사라지므로 같이 옮겨야 한다.**
- `api.py`: `RecommendRaidResponse`에 `swap_converged: bool = True`.
  기본값 True라 기존 클라이언트·테스트가 안 깨진다. `RecommendResponse`(단일
  덱)는 스왑 단계를 타지 않으므로 건드리지 않는다.
- 프론트: `false`일 때만 결과 옆에 한 줄 —
  *"탐색이 상한에 걸려 끝까지 가지 못했어요. 더 나은 배분이 남아 있을 수 있어요."*

문구가 "덜 최적"이 아니라 "남아 있을 수 있다"인 이유: 상한이 물린 런은 단순히
덜 돈 게 아니라, 균등 배분 때문에 **각 항목이 자기 후보 목록의 뒤쪽을 영영 못
보는** 모양으로 잘린다(패스마다 앞에서 다시 시작하므로). 이건 지금 벽시계
코드도 가진 성질이고 이번에 바꾸지 않는다.

### 4. 대기 문구

`RecommendPanel.tsx:612`의 "보통 2~5분"을 계측된 값으로 갈아끼운다. 바로 위
주석(`609-611`)이 `SWAP_TIME_BUDGET_SEC`을 **이름으로 지목**하고 있으므로 같이
갱신한다.

**한 줄을 덧붙인다** — *"머신 성능에 따라 더 걸릴 수 있어요."* 예산이 후보 수라
초 환산이 머신마다 다르고, 지금까지는 벽시계 상한이 지켜주던 약속이 사라지기
때문이다. 안 적으면 문구가 코어 적은 머신에서 그냥 거짓이 된다.

`/2~5분/`을 정규식으로 무는 테스트 3곳을 같이 고친다 — `App.test.tsx:211`,
`App.test.tsx:313`, `RecommendPanel.test.tsx:416`.

### 5. 파급 범위

`_swap_pass`의 4번째 위치 인자가 바뀌므로 직접 호출자를 전부 고친다.

- **`backend/tests/test_deck_allocation.py`** — `da._swap_pass(...)` 직접 호출
  10곳이 `time.monotonic() + 30.0` 꼴을 넘긴다. 정수 예산으로 바뀌면서 오히려
  단순해진다. `test_swap_pass_respects_an_expired_deadline`(180행)은 전제가
  "만료된 데드라인"에서 "예산 0"으로 바뀌므로 **이름도 같이 바꾼다.**
- **`scripts/measure_swap_phase.py`** — `_try_swaps`와 `_swap_pass`를 둘 다
  감싸고 `--budget`을 초로 받는다. 반환값이 튜플이 되므로 `wrap_try`를 고쳐야
  한다.
- **`scripts/measure_allocation_phase_split.py`**, **`scripts/audit_swap_ordering.py`**
  — `_swap_pass`를 감싸지만 시간만 재거나 그대로 위임하므로 인자 이름만 확인.
- **`scripts/measure_swap_budget.py`** — §2에서 어차피 다시 쓴다.

### 6. 테스트

**핵심은 하나다.** `test_allocate_decks_workers_parity`
(`test_deck_allocation.py:523`)를 **예산이 물린 채로** 강화한다. 지금 그 테스트는
주석에 *"`time_budget_sec=0`이 벽시계 상한 스왑 단계를 비교에서 빼둔다"*고
적어놨다 — 우리가 고치려는 결함을 테스트가 스스로 문서화해 둔 자리다. 이제
`workers=1`과 `workers=2`가 **상한에 걸리는 런에서도** 덱·총딜·leftover가 완전히
일치해야 한다. 픽스처는 등반이 후보를 실제로 만들 만큼 크고 예산은 물릴 만큼
작아야 한다.

그 위에:

- **같은 입력 2회 = 같은 답** (상한이 물리는 예산으로)
- **예산 회계** — 소모가 상한을 넘지 않고, 균등 배분이 항목 수로 정확히 나뉜다
- `swap_budget=0`이 스왑 단계를 건너뛰는 기존 뜻 유지
- `swap_converged` — 수렴한 런 True / 잘린 런 False, API 응답까지 실린다,
  프론트가 False일 때만 문구를 낸다

**새 테스트가 진짜로 잡는지 일부러 깨서 확인한다.** 배치 잘라내기 한 줄
(`min(batch, share - used)`)을 지웠을 때 parity 테스트가 빨개지지 않으면 그
테스트는 장식이다. (게이지 상수 때 1871개 중 0개가 지키고 있던 전례가 있다.)

## 하지 않는 것

- **GPU 가속** — 검토했으나 기각. 엔진은 이벤트 리스트 시뮬레이터(분기·dict·
  클로저 중심)라 GPU가 이기는 모양이 아니고, 등반의 순간 동시성이 ~44 시뮬이라
  GPU를 못 채운다. 결정적으로 **CPU/GPU 부동소수점 결과가 달라 재현성 축을
  새로 연다** — 오늘 고치는 결함을 우리가 못 고치는 층에 다시 심는 셈이다.
  대기시간이 동기라면 볼 곳은 따로 있다: `bench_evaluate_deck.py` 헤더가
  세그먼트 테이블 재작성 전 **~2410 ms/sim, 93%가 `EffectRegistry.total_for`
  선형 스캔**이었다고 기록한다 — 24배를 낸 건 하드웨어가 아니라 자료구조였다.
- **진행률 표시** — 수렴까지 몇 분이 될 수 있으니 값어치는 있지만 스트리밍이나
  폴링 엔드포인트가 필요하다. 별건.
- **벽시계 비상 상한 병행** — 잡히는 순간이 곧 재현성이 필요한 순간이라 보장을
  잃는다.
- **초안 기반 추천 기능 제외** — Fienn이 검토했으나 이번엔 그대로 둔다(2026-08-05).
  뺀다면 §3의 fold-in 항목과 §2의 빈자리만 측정 행이 사라진다.
