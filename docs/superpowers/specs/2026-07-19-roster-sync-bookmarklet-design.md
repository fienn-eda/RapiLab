# 로스터 동기화 — 유저 세션 북마크릿 방식 설계 (Phase 7 서브프로젝트 4)

작성 2026-07-19. 상태: **설계 승인(Fienn, 2026-07-19), 미구현.** 선행 슬라이스(서브프로젝트
1+2, 페치+조립)는 구현·병합 완료 — `docs/superpowers/specs/2026-07-19-roster-sync-fetch-assemble-design.md`.
멀티유저 전제조건(방어적 lookup)도 완료 — 브랜치 `wip/multiuser-preconditions`.

이 문서가 정하는 것은 **"호스티드 서비스가 blablalink API를 부를 때 누구의 세션을 쓰는가"**와
그에 따라오는 저장·식별 모델이다. 조립·스탯 계산 경로는 이미 있는 것을 그대로 쓴다.

## 결정 요약

| 사안 | 결정 | 소멸한 것 |
|---|---|---|
| 세션 공급 주체 | **유저 본인 세션** (북마크릿) | 운영자 계정·쿠키 저장·밴 리스크 |
| 로스터 저장 | **서버 저장 없음** (localStorage) | DB·계정 시스템·수신 토큰 |
| 유저 식별 | **익명 클라이언트 ID** (분석 전용) | 로그인 절차 |

부수 효과로 **서브프로젝트 3(소유권 증명)이 불필요해진다.** 자기 세션으로 자기 데이터를
자발적으로 제출하는 구조이므로 "이 로스터가 정말 네 것이냐"를 물을 대상이 없다.

## 실측으로 확정된 사실 (2026-07-19, Fienn 브라우저)

북마크릿 경로 전체가 추정이 아니라 실측으로 확인되었다. ShiftyPad 캐릭터 페이지
(`https://www.blablalink.com/shiftyspad/nikke?from=list&nikke=16`)에서 북마크릿을 실행한 결과:

- **CSP가 북마크릿 실행을 막지 않는다.** 세 번의 시도 모두 스크립트가 실행되어 서버 응답을 받았다.
- **`credentials:'include'` fetch가 CORS를 통과한다.** `http=200`, 본문 `{"code":0,"msg":"ok",...}`.
- **응답 데이터가 완전하다.** `outpost_info.recycle_room_researches`가
  `tid 1001 lv310 / 1101 lv176 / 1102 lv182 / 1103 lv167 / 1201 lv170 / 1202 lv170`으로,
  백엔드 테스트가 ground truth로 쓰는 값과 일치한다(Attacker HP 연구 = 310×450 + 176×750 = 271,500).
  즉 껍데기가 아니라 `stat_assembly`가 그대로 소비할 수 있는 데이터다.
- **`game_openid`는 HttpOnly다.** `document.cookie`로 읽히지 않는다(`cookie_ok=false`). 수집기가
  이 쿠키를 CDP로 읽는 것과 일치한다. **따라서 북마크릿은 open_id를 자력으로 알아낼 수 없고,
  유저가 공유 URL을 한 번 제공해야 한다.**

관측된 오류 코드(정확한 의미는 blablalink가 문서화하지 않았으므로, **관측 정황만** 기록한다):

| code | 관측된 상황 |
|---|---|
| `300001` | 세션 없는 익명 호출 (정찰 시, "game not login") |
| `1303005` | `intl_open_id`에 플레이스홀더 문자열을 그대로 보냄 |
| `1` | `intl_open_id` 형식이 잘못됨 |
| `0` | 정상 |

## 목표

1. 유저가 blablalink 로스터를 우리 사이트로 가져올 수 있다 — 우리가 어떤 자격증명도 보관하지 않고.
2. 재동기화가 클릭 두 번이다(장비 교체 후 갱신이 실사용 시나리오).
3. 우리는 타인의 로스터를 저장하지 않는다.
4. 제품 개선에 쓸 집계 데이터를 얻는다 — 특히 **미인코딩 유닛 실수요**와 **미지 오버로드 타입**.

## 비목표

- 기기 간 로스터 동기화. (localStorage 한정. 필요해지면 서버 저장 모델 B를 나중에 얹는다 —
  A→B는 파괴적 변경이 아니다.)
- 모바일 지원. 북마크릿 설치가 iOS/Android에서 현실적으로 불가능하므로 **데스크톱 전용**이다.
- 로그인·회원가입·비밀번호 복구.
- 소유권 증명(서브프로젝트 3). 위 결정으로 불필요해졌다.

## 구조

신규 5개. 조립·스탯 계산·슬러그 매핑은 기존 코드를 입력 소스만 바꿔 재사용한다.

### ① 북마크릿 생성기 (프론트, 신규)

유저가 ShiftyPad 공유 URL을 붙여넣으면 base64를 디코드해 `<region_id>-<intl_open_id>` 중
**대시 뒤 `intl_open_id`만** 취하고, 그 값이 박힌 개인화 북마크릿 링크를 만들어 보여준다.
앞자리(예 `29080`)는 ShiftyPad 리전 id이지 API가 받는 `nikke_area_id`가 아니다 —
`nikke_area_id`는 81 고정(`docs/insights.md`의 리전 id 함정).

북마크릿에는 자격증명이 들어가지 않는다. 유저 자신의 공개 식별자 하나뿐이다.

### ② 북마크릿 (인라인 JS, 신규)

1. `location.origin`이 blablalink가 아니면 안내 후 중단.
2. 세 콜을 순서대로: `GetUserCharacters` → `GetUserCharacterDetails`(owned의 `name_code` 전체를
   한 번에) → `GetUserProfileOutpostInfo`. 이는 `backend/app/blablalink_api.py::fetch_roster`와
   동일한 호출 순서·파라미터이며, 그 모듈의 `SessionCaller` 계약을 브라우저에서 구현한 것에 해당한다.
3. `window.open`으로 우리 `/import`를 열고 `postMessage`로 원시 payload 3종을 전달.

**로직을 최소로 유지하는 것이 이 컴포넌트의 설계 원칙이다.** 판단·조립·검증은 전부 서버로 미룬다.
이유는 아래 "운영 항목"의 재설치 부담 때문이다.

### ③ `/import` 수신 페이지 (프론트, 신규)

`event.origin`을 검증한 뒤(blablalink 출처만 허용) 원시 payload를 백엔드로 보내고, 돌아온
`roster.json` 형태를 기존 `parseRosterJson` → `mergeCollectorDrafts` → `localStorage`에 흘린다.
수집기 임포트 경로와 동일한 병합 규칙을 타므로, 스탯은 덮어쓰고 `id`/`core_level`은 보존된다.

### ④ `POST /api/assemble-roster` (백엔드, 신규)

- 입력: `{owned, character_details, recycle_room_researches}` — `fetch_roster`의 반환 형태 그대로.
- 처리: 기존 `roster_assembly.assemble_roster(tables, directory, raw)`를 호출.
- 참조 데이터: 커밋된 `data/nikke-stat-tables/tables.json` + `tools/collect-blablalink/nikke-directory.json`
  (194 엔트리, SSR 166 — 조립에 필요한 필드 전부 존재함을 확인).
- **완전 무상태.** 요청 본문은 응답 생성 후 폐기한다.

### ⑤ 익명 클라이언트 ID + 집계 (신규, 얇게)

우리 사이트 `localStorage`에 UUID 하나를 심고, **우리 백엔드로 가는 요청**(`/api/assemble-roster`와
기존 추천 API)에 헤더로 동봉한다. blablalink로 가는 호출에는 절대 실리지 않는다. 게임 계정과
무관하고 로스터와 결합 저장하지 않는다. 백엔드는 **집계 카운터만** 기록한다:

- 미인코딩 슬러그 등장 횟수 → 인코딩 우선순위를 실수요로 결정 (현재 `docs/engine-gaps.md`는
  Fienn 로스터 기준으로 ROI를 재고 있다)
- 미지 오버로드 타입/레벨 → **타 유저 데이터로 타입명표를 채울 유일한 경로**
- 디렉토리에 없는 `name_code` → 스냅샷 갱신 필요 신호
- 응답시간·실패율·요청수

## 데이터 흐름

```
유저의 blablalink 세션 (쿠키, 브라우저에만 존재)
  → 북마크릿 (blablalink 페이지 컨텍스트)
  → postMessage
  → 우리 /import 페이지
  → POST /api/assemble-roster (무상태 조립)
  → parseRosterJson → mergeCollectorDrafts
  → localStorage
```

우리 서버를 통과하는 것은 조립 요청 한 번뿐이고, 그 본문은 저장되지 않는다.

## postMessage를 선택한 이유

직접 POST는 blablalink 페이지의 CSP `connect-src`가 우리 도메인을 허용해야 성립하는데, 이는
**확인되지 않았다.** `postMessage`는 CSP 규제 대상이 아니므로 이 미지수를 테스트 없이 제거한다.
대가는 팝업 차단 가능성이지만, 북마크 클릭은 유저 제스처이므로 통상 허용된다.

폴백(설계에 포함하지 않되 막혔을 때의 경로): 클립보드 복사 → 우리 사이트에 붙여넣기.

## 프라이버시 규율

설계에 못 박는다. 이 선이 무너지면 "저장하지 않는다"는 약속 자체가 무의미해진다.

- **원시 로스터를 어떤 형태로도 기록하지 않는다.** 요청 처리 시점에 집계값만 뽑고 payload는 폐기.
- **`open_id`를 어떤 로그에도 남기지 않는다.** 게임 계정에 직결되는 식별자다.
- **익명 ID를 로스터와 결합 저장하지 않는다.**

근거: 182유닛의 정확한 투자 내역은 이름이 없어도 사실상 지문이며, 재식별 가능하다. "집계용으로
원본을 잠깐 쌓아둔다"는 흔한 미끄러짐을 금지 사항으로 명시한다.

공개 서비스로 배포한다면 개인정보 처리방침 문서가 필요하다(법률 검토는 이 문서의 범위 밖).

## 에러 처리

관측된 실패를 그대로 유저 메시지로 옮긴다.

| 상황 | 처리 |
|---|---|
| blablalink 아닌 페이지에서 실행 | "blablalink 페이지에서 눌러주세요" |
| `code 300001` | "blablalink 로그인이 필요해요" |
| `code 1303005` / `1` | "공유 URL을 다시 확인해주세요" |
| 팝업 차단 | 차단 안내 + 해제 방법 |
| 디렉토리에 없는 신규 유닛 | 조용히 스킵(기존 `assemble_roster` 동작) + 집계 |
| 미지 오버로드 타입 | 경고 로그 + 해당 라인만 스킵(구현 완료) + 집계 |

마지막 두 줄은 실패가 아니라 **데이터 수집 신호**로 취급한다.

## 테스트 전략

- **백엔드**: `/api/assemble-roster`의 계약 테스트. 조립 정확성은 기존 77/77 오버로드 패리티와
  159/159 스탯 패리티 픽스처가 이미 보장하므로 재검증하지 않고 재사용한다.
- **프론트**: postMessage 핸들러(**출처 검증 실패 케이스 포함**), 공유 URL 파싱(대시 앞자리를
  버리는지, 잘못된 base64를 거부하는지), 병합 후 localStorage 상태.
- **북마크릿 자체는 브라우저 밖에서 테스트할 수 없다.** 이것이 ②를 얇게 유지하는 설계 이유다.
  검증은 Fienn의 실제 계정으로 수동 스모크 1회.

## 운영 항목

- **디렉토리 스냅샷 갱신 루틴.** 신규 Nikke 출시 시 스냅샷에 없으면 그 유닛이 조용히 빠진다.
  현재 194 엔트리 기준. 집계(⑤)의 "디렉토리에 없는 name_code" 카운터가 갱신 시점을 알려준다.
- **북마크릿 로직 변경 = 전 유저 재설치.** 외부 스크립트 로딩은 blablalink CSP `script-src`에
  막힐 공산이 크므로 인라인이 강제된다. 엔드포인트나 파라미터가 바뀌면 재배포가 아니라
  재설치 공지가 필요하다. ②를 얇게 유지해 변경 빈도를 낮추는 것이 유일한 완화책이다.
- 배포 인프라는 현재 존재하지 않는다(리모트 없음). 모델 A는 정적 호스팅 + 기존 추천 API로 충분하다.

| 항목 | 상태 |
|---|---|
| 팝업 차단 동작 | 미확인. 유저 제스처이므로 통상 허용 예상, 스모크에서 확인 |

## 기각된 대안

**운영자 세션(서버사이드).** 유저는 공유 URL만 붙여넣으면 되어 UX가 최상이고 모바일도 되지만:
서비스 전용 blablalink 계정이 필요하고(게임 미연동 버너 계정으로 되는지 **미확인** — 익명 호출이
`game not login`으로 거절되는 정황상 실계정이 필요할 수 있다), 쿠키를 서버에 저장해야 하며
(프로젝트의 "자격증명 저장 안 함" 원칙 위반), 세션 만료 시 **전 유저가 동시에 멈추고** Fienn이
수동 복구할 때까지 죽어 있고, 한 계정이 수백 개의 서로 다른 `open_id`를 조회하는 트래픽은
정확히 스크래핑 탐지 대상이며, 그 계정이 정지되면 **서비스가 즉사**한다. 기각 사유: 미지수들이
전부 서비스 생존이 걸린 항목인데 우리가 통제할 수 없다. 반면 북마크릿 경로의 미지수는 구현
방식만 가르고 폴백이 있다.

**저장 모델 B(토큰=무암호 계정) / C(진짜 계정).** 사주는 가치는 기기 간 이동과 복구뿐인데,
북마크릿 방식에서 재동기화 비용이 클릭 두 번이라 값이 맞지 않는다. 또한 A는 "타인의 게임
데이터를 일절 보관하지 않는다"를 공짜로 얻는다. 요구가 실제로 생기면 그때 B를 얹는다.
