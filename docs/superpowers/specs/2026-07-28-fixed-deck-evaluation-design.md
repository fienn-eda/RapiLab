# 고정 편성 평가 · 유니온 레이드 — 설계

- Date: 2026-07-28
- Status: 초안 (Fienn 리뷰 대기)
- 관련: `docs/roadmap.md` Phase 5(5덱 분배) · Phase 6(입력 UI),
  `docs/superpowers/specs/2026-07-22-draft-based-allocation-design.md`(드래프트 모드)

## 배경

추천 탭의 세 모드는 전부 **엔진이 덱을 짜주는** 방향이다 — 단일 덱은 로스터에서
최선의 5인을 찾고, 레이드 분배는 25인을 배분하고, 드래프트는 유저의 부분 편성을
받아 빈 자리를 채운다.

없는 것은 반대 방향이다: **유저가 전부 직접 짜고 "이거 얼마 나와?"만 묻는 것.**
드래프트 모드에 25명을 다 채워 넣으면 응답의 `baseline_total_damage`가 정확히
그 값이긴 하다. 하지만 그걸 얻으려고 뒤에서 전체 로스터 탐색까지 같이 돌아서
수백 초가 걸린다(실측 완성-draft 797초, `docs/roadmap.md`). 답을 이미 갖고 있는데
찾아주는 값을 치르는 셈이다.

여기에 **유니온 레이드**가 겹친다. 유니온 레이드는 5속성 보스 중에서 유저가 골라
3회 전투하는 컨텐츠다(같은 보스 반복 가능). 즉 "보스 설정 + 5인 편성"을 3벌 돌리는
구조인데, 현재 보스 프로필은 **요청당 하나**라 표현할 수 없다.

두 요구가 같은 프리미티브로 만난다: **고정된 5인 덱 N개를, 각자의 보스로 채점하기.**
탐색이 없으므로 덱끼리 상호작용이 없고, 그래서 덱별 보스가 거의 공짜다.

## 결정

### 1. 접근 — 전용 엔드포인트 (덱별 보스)

세 안을 놓고 골랐다.

- **A. 새 엔드포인트 `POST /api/evaluate-decks`** ← 채택
- B. `/api/recommend-raid`에 `evaluate_only` 플래그 + `draft`에 덱별 보스
- C. 프론트가 `/api/recommend`를 덱 수만큼 호출

B는 이미 3단(`baseline_total_damage` ≤ `within_draft` ≤ `recommended`)인 응답에
의미가 다른 플래그를 얹는다 — 플래그에 따라 응답 필드 절반이 조건부로 비고, 그
조건을 프론트와 테스트가 양쪽에서 다시 알아야 한다. C는 `/api/recommend`가
"로스터에서 최적 덱을 **찾는**" 엔드포인트라 고정 5인 채점용이 아니고, 덱 간
중복 검증을 프론트가 떠안는다.

A는 새 계산을 만들지 않는다는 점이 핵심이다 — 아래 2를 보라.

### 2. 계산기는 이미 있다 — 새 엔진 표면을 만들지 않는다

`deck_allocation._best_ordering_summary(units, boss)`가 정확히 이 일을 한다:
고정 5인의 티어 내 순열을 전부 채점하고 최선을 골라 요약(총딜 · 버스트 · 평타 ·
스킬딜)을 돌려준다. `baseline_total_damage`가 이미 이걸 쓴다.

신규 `evaluate_decks`는 덱마다 자기 보스로 이 프리미티브를 부르고 합산할 뿐이다.
계산 경로는 `evaluate_decks` → `_best_ordering_summary` → `evaluate_deck` →
`simulate_raid`로 **기존 세 모드와 완전히 동일**하다.

이게 A를 고른 진짜 이유다. 데미지 공식을 고치든, 니케를 재인코딩하든, 버스트
사이클을 손보든 새 모드에 자동 반영된다. **딜 계산 경로가 둘로 갈라져 서로
어긋나는 종류의 위험이 없다.**

합산이 정확한 근거: 덱끼리 상호작용이 없다. 분배 최적화가 "같은 보스라 총합 =
덱별 합"이라는 성질에 기대는 것과 같은 성질이고, 보스가 덱마다 달라져도 각 덱이
자기 보스로 독립 채점되므로 그대로 성립한다.

### 3. 편성 순서는 엔진이 고르고, 결과가 알려준다

Fienn 지정. `DraftEditor`의 슬롯은 이미 **소속만 표현하고 버스트 순서는 표현하지
않는다**(컴포넌트 주석: "Slots are MEMBERSHIP ONLY — no burst order; the engine
assigns burst roles"). 그러므로 평가 모드에서도 유저가 순서를 넣을 자리가 없고,
엔진이 티어 내 최적 순서를 골라 그 5인 조합의 최대 기대값을 보고한다.

응답의 `deck` 배열이 **엔진이 고른 순서**이고, 프론트는 이걸 "이 순서로
배치하세요"로 읽는다. 인게임에서 순서는 쉽게 바꿀 수 있으니 손해가 없다.

`baseline_total_damage`가 이미 같은 기준을 쓰므로(모드 변형 좌석도 최선 해석을
채점) 두 모드의 수치가 서로 비교 가능하다.

### 4. 화면 둘, 엔진 하나

|  | 추천 탭 `평가` 모드 (4번째) | 새 `유니온 레이드` 탭 |
|---|---|---|
| 덱 수 | 1–5 (기존 `numDecks` 셀렉터 재사용) | 1–3, 기본 3 |
| 보스 | 공통 1개 (기존 `BossProfileField`) | **덱마다 전체 프로필**, 기본 180초 |
| 편성기 | `DraftEditor` (잠금 토글 숨김) | `DraftEditor` (잠금 토글 숨김) |
| 중복 편성 | 불가 | 불가 — 3덱 15명 전원 다름 |
| 제출 조건 | 선택한 덱을 **전부 5명** 채움 | 동일 |

유니온 레이드의 재사용 불가 규칙(Fienn 확인)이 솔로 5덱과 같으므로
`DraftEditor`의 기존 "이미 배치된 슬러그는 다시 못 놓는다" 불변식이 그대로 맞다.

잠금 토글은 평가 모드에서 의미가 없다(최적화가 없으니 고정할 것도 없다).
`DraftEditor`에 `showLocks?: boolean`(기본 `true`)을 더해 끈다.

전투 시간 기본값은 유니온도 **180초**(Fienn 확인).

### 5. 보스 스키마는 절대 갈라지지 않는다

보스 입력 지점이 둘(공통 / 덱별)로 늘어나는데, 여기서 스키마가 갈라지면 엔진이
`BossProfile`에 필드를 추가할 때마다 두 군데를 고쳐야 한다.

**같은 pydantic 모델(`BossProfileIn`)과 같은 React 컴포넌트(`BossProfileField`)를
양쪽이 그대로 재사용한다.** 새 요청 모델은 보스를 덱 안에 품을 뿐 필드를 다시
쓰지 않는다. pydantic 기본값 관례(`part_destructible: bool = False` 전례) 덕에
필드가 늘어도 옛 요청은 계속 통과한다.

### 6. 결과 캐시에 엔진 버전을 섞는다

이번 작업에 포함(Fienn 결정). 새 모드가 만든 문제가 아니라 **이미 있는 문제**다.

`RecommendPanel.tsx`의 `hashRecommendInputs(roster, boss, draft, numDecks)`는
입력만 해시한다. 바로 위 주석이 "엔진이 결정론적이라 같은 입력이면 같은 결과"라고
하는데 이는 **한 엔진 버전 안에서만** 참이다. 니케 하나를 재인코딩하면
localStorage에 남은 최대 20개(`RESULTS_CAP`) 결과가 낡은 수치를 조용히 계속
보여준다 — 에러도 표시도 없다.

해결: 백엔드가 응답에 엔진 버전 문자열을 싣고, 프론트가 그걸 해시에 섞는다.
버전이 바뀌는 순간 전 캐시가 미스가 되어 자연히 재계산된다.

버전 값은 **엔진 소스의 내용 해시**로 만든다 — 손으로 올리는 숫자는 올리는 걸
잊는 순간 조용히 틀리기 때문이다.

해시 대상은 **`backend/app/` 아래 모든 `.py`**다. 딜에 영향을 주는 모듈만
골라 열거하는 안도 검토했지만 기각했다: 새 모듈이 생겼을 때 목록에 넣는 걸
잊으면 바로 이 기능이 막으려던 "조용히 낡음"이 재발한다. 전부 해시하면 API
문구만 고쳐도 버전이 바뀌어 불필요한 재계산이 생기지만, 대가는 수 초짜리
재계산 한 번이고 실패 방향이 안전한 쪽이다.

정렬된 경로 순으로 소스 바이트를 이어 SHA-256을 뜨고 앞 12자를 쓴다.
프로세스 시작 시 1회 계산해 캐시한다.

노출: 세 엔드포인트(`/api/recommend`, `/api/recommend-raid`,
`/api/evaluate-decks`) 응답에 `engine_version: str`을 additive로 추가.

## API

```
POST /api/evaluate-decks
{
  "roster": [UserNikkeState, ...],
  "decks": [
    { "units": ["slug", ...5],
      "boss": { "element": "Iron", "core_hittable": false, "enemy_def": 0,
                "fight_duration": 180, "part_destructible": false } },
    ...
  ]
}
->
{
  "decks": [
    { "deck": ["slug", ...5],          // 엔진이 고른 순서
      "total_damage": 0.0, "burst_damage": 0.0,
      "normal_attack_damage": 0.0, "skill_damage": 0.0 }
  ],
  "combined_total_damage": 0.0,
  "excluded_slugs": ["..."],
  "engine_version": "a1b2c3d4e5f6"
}
```

덱 요약의 네 필드는 `DeckRecommendation`과 같은 모양이다(`_summarize`의 계약:
버스트 + 평타 + 스킬딜 = 총딜). `pinned_slugs`는 없다 — 잠금 개념이 없다.

`leftover_slugs`도 없다. 배분이 아니라 평가이므로 "남은 유닛"은 유저가 안 고른
전부일 뿐이고, 프론트가 이미 아는 정보다.

### 검증 (422)

- 덱이 0개
- 어떤 덱의 `units`가 5명이 아님 — 몇 번째 덱인지 명시
- 슬러그가 덱을 가로질러 중복 — 어떤 슬러그인지 명시
- 미보유/미지원 슬러그 — 클라가 보낸 슬러그 이름 그대로 보고
  (`/api/recommend-raid`의 `draft references unusable slug: X` 문구 체계를 따름)
- **티어 조합 불가** — `_intra_tier_orderings`가 빈 제너레이터를 내는 경우
  (예: 버퍼 좌석 규칙 위반). 지금 `_best_ordering_summary`는 이 경우
  빈 시퀀스에 `max()`를 불러 `ValueError`로 터진다. 새 경로는 먼저 검사해
  "N번째 덱은 버스트 티어 조합이 불가능합니다"로 422를 낸다.

### 모드 변형 좌석 (MODE_VARIANTS)

신데렐라처럼 엔진이 여러 모드로 모델링하는 캐릭터는 유저가 모드를 고르지 않는다.
`/api/recommend-raid`가 하는 것과 똑같이 `alternatives`를 조립하고
`_seed_choices`로 모든 해석을 채점해 **최선을 채택**한다 —
`baseline_total_damage`가 이미 쓰는 기준이라, 유저가 고르지도 않은 모드로 수치가
부풀지 않는다.

## 성능

시뮬 횟수 = Σ(덱별 티어 내 순열 수). 5덱이면 대략 60회 안팎, 순열당 ~103ms이므로
**수 초** 규모다. 탐색·배분·스왑이 전부 없어서 드래프트 모드(797초 실측)와는
자릿수가 다르다.

**직렬로 시작한다.** `SimPool`은 워커 초기화 때 보스를 고정하므로 덱마다 보스가
다르면 배치를 가로지를 수 없고, 보스별로 풀을 여러 개 띄우는 건 이 규모에서
득보다 실이다. 착지 후 실측하고, 느리면 같은 보스끼리 묶어 풀을 태우는 게 후속
레버다.

## 테스트

**백엔드**

- `evaluate_decks`: 합계 = 덱별 합 · 반환 `deck`이 실제 최적 순서 · 덱별 보스가
  결과를 실제로 바꾼다(속성 우위를 1번 덱에만 걸고 같은 편성의 딜이 갈리는지)
- 검증 5종: 빈 덱 목록 · 덱 크기 · 덱 간 중복 · 미지원 슬러그 · 티어 조합 불가
- MODE_VARIANTS 좌석이 최선 해석으로 채점되는지
- 같은 편성·같은 보스라면 `/api/evaluate-decks`의 덱 총딜이
  `/api/recommend-raid`의 `baseline_total_damage`와 **일치**하는지 — 두 경로가
  같은 프리미티브를 쓴다는 주장을 고정하는 테스트
- `engine_version`: 세 엔드포인트가 같은 값을 실어주는지 · 엔진 소스가 바뀌면
  값이 바뀌는지 · 같은 소스에서는 호출마다 같은 값인지
- TestClient E2E

**프론트**

- `useEvaluateDecks` 훅 (성공 / 422 / 취소)
- 유니온 탭: 덱별 보스 폼이 독립적으로 움직이는지 · 3덱 15칸 중복 방지 ·
  전부 안 채우면 제출 잠김
- 추천 탭 `평가` 모드: 모드 스위치가 다른 모드 결과를 새어 보이지 않는지
  (기존 `raidResultMode`/`displayMode` 가드와 같은 계약)
- `showLocks={false}`일 때 잠금 버튼이 렌더되지 않는지
- 입력 해시가 `engineVersion`을 반영하는지 (버전이 다르면 캐시 미스)

## 범위 밖

- **유니온 레이드 추천(엔진이 3덱을 짜줌).** 배분 알고리즘이 덱별 보스를 알아야
  하고, 스왑 언덕오르기의 "같은 보스라 총합 = 덱별 합" 가정을 다시 검토해야 한다.
  훨씬 큰 작업이고, 평가 모드가 먼저 쓰여봐야 필요 여부가 드러난다.
- **보스 프리셋.** 5속성 보스 각각의 코어 타격/파츠 파괴 특성을 저장해두고
  이름으로 고르는 것. 그 값들을 아직 모른다(Fienn이 알려줘야 함).
- **평가 결과에서 최적화로 이어주기.** "이 편성을 개선해볼까요?" 유도는 넣지
  않는다 — 드래프트 모드가 이미 그 일이다.
- 캐시 무효화를 엔진 버전 외의 축(예: 스탯 테이블 갱신)으로 확장하는 것.
