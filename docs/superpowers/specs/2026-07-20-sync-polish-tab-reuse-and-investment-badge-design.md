# 동기화 후속 다듬기 — 북마크릿 탭 재사용 + 돌파/코어 뱃지

- 날짜: 2026-07-20
- 상태: 설계 확정 (구현 대기)
- 관련: `docs/roadmap.md` To-Do "로스터 동기화 후속"

로스터 동기화 병합 후 남은 UX 항목 두 개를 한 스펙으로 묶는다. 둘 다 프론트엔드와
북마크릿에서 끝나고 서로 독립적이지만, 같은 화면·같은 테스트 표면을 건드리므로
따로 사이클을 도는 비용이 내용보다 크다. 신규 니케 출시 대응은 성격이 달라
(기능이 아니라 반복 운영 절차) 별도 스펙으로 분리한다.

---

## ① 북마크릿 탭 재사용

### 문제

재동기화할 때마다 새 탭이 쌓인다. `frontend/src/lib/bookmarklet.ts:43`이
`window.open('${appOrigin}')`을 창 이름 없이 호출하기 때문이다.

### 설계

창 이름을 준다.

```js
const w=window.open('${appOrigin}','nikke-deck-builder');
```

같은 이름의 창이 이미 있으면 브라우저가 그 창을 재사용하고 URL로 이동시킨다.

### 왜 안전한가

재사용은 **그 탭을 새로고침시킨다.** 그래도 잃는 것이 없다:

- `frontend/src/hooks/useRoster.ts:47-49`가 `useEffect(..., [drafts])`로 draft가
  바뀔 때마다 localStorage에 기록한다. 편집 중이던 내용도 이미 저장돼 있다.
- `nikke-sync-ready` / `nikke-sync-payload` 핸드셰이크는 앱이 mount 시 ready를
  보내므로, 새 탭이든 재사용된 탭이든 동작이 같다. 북마크릿 쪽 변경은 없다.

### 받아들이는 한계

**북마크릿이 직접 연 탭만 이름으로 찾아진다.** 사용자가 주소창으로 따로 연 앱 탭은
브라우징 컨텍스트 그룹이 달라 이름 조회 대상이 아니고, 그 경우엔 새 탭이 열린다.
우회하지 않는다 — "탭을 아예 안 열고 기존 탭만 갱신"은 구조적으로 불가능하다
(북마크릿은 blablalink 오리진에서 돌고, BroadcastChannel·localStorage는 동일 오리진
한정). 이 한계는 로드맵 To-Do에 이미 조사돼 있다.

### 지금 하는 이유

북마크릿을 바꾸면 **전 사용자가 재설치**해야 한다. 현재 사용자가 1명이므로 지금이
가장 싸다. 미루면 비싸지는 종류의 작업이다.

## ② 돌파(grade) / 코어(core) 뱃지

### 문제

임포트한 유닛의 `core_level`이 항상 0으로 보인다. 코어 7짜리 유닛이 0으로 표시되면
"내 로스터가 잘못 들어왔나"라는 오해를 부른다. `grade`는 아예 표시되지 않는다.

### 원인 — 표시 문제가 아니라 데이터가 안 온다

`backend/app/roster_assembly.py`의 `assemble_unit`은 `grade`/`core`를 **읽지만**
(`extract_inputs`의 42-43행, ATK/HP 계산 입력) **페이로드로 내보내지 않는다.**
반환 딕셔너리는 `name_en` / `resource_id` / `raid400` / `skill_levels` / `overload`
뿐이다. 그래서 `frontend/src/lib/rosterImport.ts`가 `core_level: '0'`을 하드코딩할
수밖에 없었다. 프론트에는 표시할 값 자체가 없다.

### 값의 실제 구조 (실측, 127유닛)

- `grade` 0~3 (돌파 단계)
- `core` 0~7
- **`core > 0`은 오직 `grade == 3`에서만 나타난다** — 실측 예외 0건이고,
  **게임 시스템 규칙이다: 3돌파를 마친 뒤에야 코어 강화가 시작된다**(Fienn 확인,
  2026-07-20). 즉 둘은 독립 축이 아니라 하나의 순차적 투자 단계다.

뱃지는 그래도 **`core > 0`이면 `grade`와 무관하게 `+N`을 그린다.** 규칙에 기대어
`grade == 3`을 전제하지 않는 편이 코드가 더 짧고(분기 없음), 데이터가 규칙을 어기는
경우에도 값을 숨기지 않고 보여준다. 규칙은 뱃지가 강제할 대상이 아니라 배경 사실이다.

### 설계

**백엔드.** `assemble_unit`의 반환에 `grade`와 `core`를 추가한다. 이미 `inp`에
들어 있으므로 새로 계산할 것은 없다.

**뱃지 (읽기 전용).** 별 3칸 + 코어 카운트:

```
★★★ +7     grade=3, core=7
★★★        grade=3, core=0
★★☆        grade=2, core=0
☆☆☆        grade=0, core=0
(없음)      grade/core 자체가 없는 유닛
```

- 별은 항상 3칸, 채워진 칸 수 = `grade`.
- `+N`은 `core > 0`일 때만.
- 입력이 아니라 표시다. 편집 불가.

**값이 "없는 것"과 "0인 것"을 구분한다.** 수동 입력으로 만든 유닛은 grade/core를
알 수 없다. 이를 `☆☆☆`로 그리면 "돌파 0단계"라는 **거짓 주장**이 된다. 그래서
draft의 `grade`/`core`는 선택적 필드로 두고, 없으면 뱃지를 렌더하지 않는다.
이것은 추가 비용이 아니라 **오히려 더 적은 코드**다 — 없는 값을 0으로 강제하는 쪽이
결정을 하나 더 요구한다. 수동 입력 경로 자체는 장래 제거 대상이므로 그 경로를 위한
별도 투자는 하지 않는다(Fienn, 2026-07-20).

**`core_level` 입력칸을 제거한다.** `models.py`에 선언만 있고 **백엔드가 읽는 곳이
0건**이다 — 값은 이미 raid400 ATK/HP에 접혀 있다. 즉 지금은 아무 일도 하지 않는
입력이며, 하모니 큐브의 `pve_cube`에 내린 것과 같은 판단이다(아무것도 하지 않는
입력칸은 사용자를 속인다). 읽기 전용 뱃지 옆에 같은 개념의 무력한 입력칸이 나란히
있으면 더 이상하다. `UserNikkeState.core_level`도 함께 내린다.

## 테스트

- **북마크릿:** 생성된 소스가 `window.open`에 창 이름 `nikke-deck-builder`를
  넘기는지 단언. 기존 북마크릿 테스트가 소스 문자열을 검사하는 방식(그리고 지난번
  hollow 정규식 사고)을 따르되, **캡처 범위를 좁게 앵커**할 것.
- **백엔드:** `assemble_unit`이 `grade`/`core`를 실제 detail 값 그대로 내보내는지.
  기존 `test_roster_assembly.py`의 키 집합 단언(`set(u) == {...}`)이 깨지므로 함께
  갱신 — 약화가 아니라 새 키를 포함하도록.
- **임포트:** `rosterImport`가 페이로드의 grade/core를 draft로 옮기는지, 그리고
  **키가 없는 페이로드에서는 draft에도 없는 상태로 남는지**(0으로 채우지 않음).
- **뱃지 렌더:** 위 표의 5가지 경우 각각. 특히 "값 없음 → 렌더 안 함"과
  "grade=0 → `☆☆☆` 렌더"를 구분해서 — 이 둘을 뭉개는 것이 이 설계의 유일한 함정이다.
- **회귀:** `core_level` 제거 후 기존 저장 로스터(그 필드를 담은 localStorage 값)가
  계속 로드되는지.

## 범위 밖

- 신규 니케 출시 대응 루틴 — 별도 스펙.
- 수동 입력 경로 개선 또는 제거 — 장래의 별도 제품 결정.
- 사용자가 주소창으로 연 탭까지 찾아내기 — 구조적으로 불가능(위 참조).
