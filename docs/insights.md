## 「데이터에 없다」는 갭 문서의 단정을 **원본 페이로드로** 검증하라

- 확립: 2026-07-31 (engine-gap #19 클립형 재장전).
- 갭 #19는 *"게임 데이터 파일에는 `maxAmmo=6`, `reloadTime=0.5`만 있어 분할 횟수가
  어디에도 없다"* 고 적혀 있었고, 그래서 **유닛별 실측 캠페인이 선행돼야 하는 작업**으로
  분류돼 미착수로 남아 있었다. 실제로는 ShiftyPad 원본 `detail.shot_detail`에
  **`reload_bullet`**(10000 = 탄창 100%를 한 번에)이 있었다. 착수 첫 5분에 원본
  JSON의 필드를 훑는 것으로 갭 전체가 사라졌다.
- **왜 안 보였나:** `normalize_shiftypad`가 dotgg 모양에 맞춰 무기 **6필드만**
  뽑는다. 갭을 적은 사람은 정규화된 파일을 봤고, 거기 없으면 원본에도 없다고
  적었다. **정규화된 데이터에 없다는 것은 원본에 없다는 뜻이 아니다.**
- 같은 스캔이 덤으로 준 것: 막힌 유닛이 2명이 아니라 **9슬러그**였고, 무기군도
  런처·샷건이 아니라 **AR(Grave)까지** 포함이었다. 문서의 "2 확인 + 일부 미확인"은
  추정이었고 원본 전수 스캔은 30초짜리였다.
- **실무 규칙:** 갭 문서의 "데이터에 없다 / 실측이 필요하다"는 **재확인 대상**이지
  전제가 아니다. 착수 전에 `data/shiftypad/raw/*.json`의 해당 섹션 키를 전부 찍어
  볼 것. 아직 미해석으로 남은 필드도 있다 — `reload_start_ammo`는 전 유닛
  `max_ammo − 1`이라 판별력이 없다.
- 이것은 「gap을 닫으면 그 사유를 인용한 독스트링을 grep하라」(아래)의 **거울상**이다:
  낡은 사유가 코드에 남는 것과 같은 방식으로, **틀린 전제가 갭 문서에 남는다.**

## 시뮬 로그의 데미지는 **크리 기대값**이다 — 논크리 실측과 직접 비교하지 말 것

- 확립: 2026-07-28 (민트 평타 검증 중 하마터면 오진할 뻔했다).
- `damage_log`의 `damage`는 크리 확률로 가중된 **기대값**이라, Fienn이 주는 "논크리 표기값"과
  형식이 다르다. 민트의 두 창 비를 로그로 재면 **2.81946**이 나와 실측 2.35598 대비
  19.7% 과대해 보이지만, **크리율이 두 창에서 다른 것**(0.2642 vs 0.4636)이 섞인 결과다.
- **올바른 방법: 엔진이 쓴 `calculate_damage` 입력을 그대로 꺼내 `crit_rate=0`으로 다시 계산**한다.
  그러면 2.35747로 실측과 **0.064%** 안에서 맞는다.
- **표적 DEF도 맞춰야 한다.** flat ATK 버프는 DEF 차감 뒤가 아니라 앞에 더해지므로,
  버프량이 다른 두 창의 비는 **DEF에 민감**하다 — 같은 입력을 레이드 DEF 31,784로 계산하면
  2.50046(6.1% 과대)이 되어 없는 버그를 만들어낸다. **사격장 표적은 DEF ≈ 0으로 볼 것.**

## 「데이터가 틀렸다」던 두 유닛은 사실 **딜레이가 빠져 있었다** — 흑련·레이븐

- 확립: 2026-07-29 (Fienn 실측으로 두 유닛의 간격을 분해).
- 둘 다 **간격 전체를 `charge_time`에 덮어쓰는** 방식으로 모델링돼 있었고, 수집 데이터의
  차지 시간이 "많이 틀렸다"고 적혀 있었다. 발사↔차지 간격을 따로 재니 **데이터가 옳았다**:

  | | 실측 간격 | 실측 딜레이 | 차 | 데이터 파일 |
  |---|---|---|---|---|
  | 흑련 | 0.7325 | **0.43** | 0.3025 | **0.30** ✓ |
  | 레이븐 | 2.0275 | **1.014** | 1.0135 | **1.0** ✓ |

  틀린 것은 차지 시간이 아니라 **검을 휘두르는 애니메이션**이었다. 둘 다 "로켓 런처"인데
  실제로는 칼을 쓴다.
- **★ 교훈: 「데이터가 틀렸다」는 결론 전에 빠진 항이 있는지 보라.** 간격 하나만 재면
  `charge`와 `delay`를 구분할 수 없어 덮어쓰기가 유일한 수단처럼 보인다. **두 시점을
  재면 분해된다.**
- **분해는 미관 문제가 아니다.** 차지 속도 버프는 **차지에만** 걸리고 딜레이엔 안 걸린다.
  흑련은 리베랄리오와 자주 짝지어지는데, 덮어쓰기 모델에서는 버프가 **0.73 전체**에
  걸려 있었다. `+50% 차지속도`에서 옛 모델 0.3823초 vs 실제 0.5800초 — **1.52배 과대**.
  리베랄리오의 **정액 −0.19초**는 두 모델이 거의 같아서(0.5423 vs 0.5400) 실기록
  캘리브레이션은 **0.981x로 불변**이다 — 퍼센트 버프에서만 갈린다.
- **선결로 엔진 바닥을 고쳤다** — `shot_interval_with_speed`가 `CHARGE_INTERVAL_FLOOR`를
  **딜레이 미측정 유닛에만** 적용한다. 바닥 자체가 신데렐라의 딜레이(영구 +100% 차지속도
  상태에서 남은 0.345초)를 전원에게 일반화한 값이라, 실측 딜레이가 있는 유닛에 둘 다
  걸면 **같은 멈춤을 두 번 센다.** 특히 흑련은 차지 0.30이 바닥 0.3448보다 짧아
  `min(charge, floor)`에 걸려 **차지속도를 아예 못 받고 있었다.**
- **바닥이 유닛별로 다르다는 증거:** 레드후드의 변신 창은 10초에 **33발**(0.303초 간격),
  신데렐라는 같은 차지-0 상태에서 **0.345초**. 그래서 바닥을 전원 하드 하한으로 두면
  레드후드가 29발로 깎인다 — 폴백이어야 하는 이유다.
  (레드후드의 33발은 `rate_of_fire` 측정 앵커라 케이던스 버프도 모션 딜레이도 안 받는다.)

## 차지 모션 딜레이 재는 법 — **대미지 표기 간격이 아니라 차지게이지 시작점**을 볼 것

- 확립: 2026-07-28 (Fienn이 민트·프리카를 이 방법으로 실측).
- **방법:** 「차지가 끝까지 차고 탄환이 날아가는 시점」과 「다음 평타의 차지게이지가
  차오르기 시작하는 시점」을 FB 잔여시간으로 읽는다(60FPS → ±0.01초).
- **★ 대미지 표기 간격을 쓰면 안 되는 이유:** RL의 유탄은 **날아가는 데 시간이 걸리고
  그 시간이 보스와의 거리에 따라 변한다.** 표기 시각 간격에는 이 비행시간이 섞여 들어가
  거리마다 다른 값이 나온다. 차지게이지는 발사와 동시에 판정되므로 거리와 무관하다.
- **측정이 스스로를 검증한다:** 발간 간격이 `차지시간 + 딜레이`로 떨어져야 한다.
  민트 간격 **1.40초** = 1.0 + 0.39 ✓ · 프리카 **1.36 / 1.35초** = 1.0 + 0.34 ✓.
  이 자기검증이 붙으면 값 하나가 아니라 **모델 자체**가 확인된다.
- **★ 프레임 미만을 가려야 하면 FB 시계를 버리고 영상 프레임 번호를 클럭으로 쓸 것**
  (2026-07-30, 브래디). FB 잔여시간 표시는 0.01초 단위인데 **구간마다 0.04초씩
  건너뛴다** — 22프레임과 24프레임을 구분하지 못한다. 브래디의 딜레이가 FB 시계로
  네 번 모두 "0.40"으로 읽혔지만 프레임 번호로는 **22프레임(0.36667초)** 이었다.
- **★ 절대값은 판독 편향을 타고 간격은 안 탄다 — 모델 판정은 간격으로 할 것.**
  발사는 대미지 표기라 실제보다 늦게(`m ≥ 0`), 차지시작은 게이지 첫 양수 픽셀이라
  역시 늦게(`k ≥ 0`) 읽힌다. 그래서 **차지와 딜레이의 절대값은 `m − k` 만큼 편향되지만
  둘의 합인 간격은 양 끝이 같은 판독이라 편향이 정확히 상쇄된다.** 브래디에서 차지
  평균이 57프레임에서 −0.235, 딜레이가 22프레임에서 +0.163 벗어났는데 **합은 간격과
  0.042프레임**으로 맞았다 — 편향의 서명이다. 절대 평균으로 두 모델을 재면 어느 쪽도
  안 맞는 것처럼 보인다.
- **★ 프레임 격자를 판정할 유닛은 차지 1.0초짜리를 고를 것.** 차속 한 줄이 사는
  프레임 수의 소수부가 클수록 격자 가설과 비격자 가설이 벌어진다. 6.09% 한 줄에서
  흑련(0.30초)은 1.00 대 1.20프레임밖에 안 갈리는데 브래디(1.00초)는 3.00 대
  3.60프레임으로 **3배** 갈린다. 그리고 차지시간을 직접 읽을 수 있으면 계정 간 비교가
  필요 없어진다 — 흑련 측정이 미해결 계정 축에 막힌 이유가 그것이었다.
- **값은 유닛마다 다르다** — 스노우화이트 0.4 · 민트 **0.39** · 프리카 **0.34**.
  그래서 레지스트리가 "상수 하나 + 명단"에서 **슬러그→초 매핑**으로 바뀌었다.
  아직 스톱워치를 못 댄 유닛(에이드·헬름·브래디·벨벳)만 공용 기본값을 쓴다.
- **효과:** 민트 1.502x → **1.107x** · 프리카 1.353x → **1.087x**,
  덱4 1.033 → **1.004x**, ±15% 이내 18/25 → **20/25**, 과대 합계 1.126B → **1.005B**.
- **남은 반례: 볼륨 1.244x는 SMG라 차지가 없다** — 이 설명 밖의 별개 원인이다.

## 민트의 과대는 데미지 모델이 아니라 **발수**였다 — 전 층 검증 후 실측으로 종결

- 확립: 2026-07-28 (Fienn 사격장 3값 + 1차/2차 버스트 비교).
- **코어 = +1.000000 정확**: 코어히트 6,427,544 / 논코어 6... 아니 3,856,527 = 1.6666664,
  논코어 버킷 1.5(풀버스트만)에서 코어 보너스가 정확히 **+1.0**. 그녀는 **RL이라 사거리 항이
  없어** 대수가 깨끗하게 떨어진다.
- **크리 대미지 = 0.6149**(코어 크리 9,293,976... 9,293,972 / 코어 논크리 6,427,544 = 1.4459601,
  버킷 2.5) — **엔진이 내놓는 값과 소수점까지 동일**.
- **자기 버스트 킷도 정확**: 그녀가 버스트하지 않은 1차 창 대비 버스트한 2차 창의 비가
  실측 2.35598, 엔진 2.35747(**0.064%**). flat ATK · attack_damage_up · 투사체폭발 버킷까지
  전부 맞다는 뜻이다.
- **따라서 그녀의 1.502x는 전부 발수에 있다** — 딜이 100% 평타이고 발당 인자가 전부 검증됐다.
  엔진은 180초에 **158발**(간격 1.139초)을 주는데, 기록이 함의하는 간격은 **1.711초**
  (약 105발) — 차이 **+0.57초**로, 이미 5유닛에서 확인된 **차지 모션 딜레이**와 같은 모양이다.
- **덱4 전체를 같은 방식으로 환산하면 이야기가 일관된다**:
  프리카(SR) 함의 딜레이 **+0.39초**로 스노우화이트 실측 0.4초와 거의 같고,
  신데렐라(RL)는 **−0.01초 = 없음**으로 "일괄 적용은 신데렐라를 무너뜨린다"는 기존 실측과 일치.
  볼륨은 **SMG라 차지가 없어** 이 설명이 안 되고 별개 원인이다.
- **⚠ 함의값은 피팅이지 측정이 아니다.** 다만 차지 모션 딜레이는 Fienn이 시계로 잰 적 있는
  **물리량**이므로, 180초 타수를 세어 확인하는 것은 정당한 데이터 수집이다.

## 유닛의 속성과 인스턴스의 종류를 혼동하지 말 것 — `has_pierce`가 스킬 딜에 샜다

- 확립: 2026-07-28 (스노우화이트:헤비암즈 사격장 실측, 1.110x → **0.999x**).
- **버그의 형태:** `pierce_damage_up`이 `has_pierce > 0`만 보고 **그 유닛의 모든 데미지
  인스턴스**에 붙고 있었다. 그런데 Pierce는 "관통하는 **평타**"(damage-formula 레퍼런스)라
  **유닛의 속성이자 동시에 인스턴스의 종류**다. 관통을 가진 유닛이 쏘는 **스킬 넉은
  관통 데미지가 아니다.**
- **실측이 소수점까지 지목했다.** 첫 버스트 FB 창 안, 오토파이어 15발 중 1발
  **6,286,230** vs 같은 발의 41.9% 스윕 **1,342,112** → 비 4.68383.
  맨계수 비 105.59/41.9 = 2.52005이므로 초과분 1.85863 = `(1+A+순차)/(1+A)`,
  순차 1.584를 넣으면 **A = 0.8448**. 그런데 엔진의 `attack_damage_up`은 **정확히
  0.8448**이었고 버킷 총합만 1.9757 — 차이 **0.1309가 그녀의 `pierce_damage_up`과
  정확히 일치**했다.
- **크리/논크리 쌍이 major 버킷을 동시에 확정했다:** 9,066,420/6,286,230 = 1.442267,
  크리 델타 = 0.5 + 오버로드 8.6% + **볼륨 1티어 크리대미지 7.74%** = 0.6634 →
  버킷 **1.500000**. 풀버스트만, 코어 없음, 사거리 없음 — 엔진과 일치.
  덤으로 볼륨의 7.74%와 "다른 크리대미지 소스 없음"이 재확인됐다.
- **★ 진단이 쉬웠던 이유: 두 인스턴스를 같은 발에서 읽었다.** ATK·DEF·버프 상태가
  전부 공유되므로 남는 것은 **버킷 차이뿐**이다. 한 인스턴스의 절대값을 맞히려 하지 말고
  **같은 순간의 두 인스턴스 비**를 볼 것.
- **재발 방지의 일반형:** `has_*` 류의 **유닛 속성 플래그**로 damage-up 버킷을 여는
  코드는 전부 의심할 것 — 그 버프가 정말 "이 유닛의 모든 딜"인지, 아니면 "이 유닛의
  **어떤 종류의 딜**"인지 확인해야 한다. 후자면 `_TYPE_BUCKETS`처럼 인스턴스 쪽에서
  게이팅해야 한다.
- **낡은 테스트가 버그를 고정하고 있었다.** `test_pierce_needs_the_property.py`가 게이트를
  **버스트 데미지**로 측정하고 있어서, 요구사항 1(속성 필요)을 확인하는 김에
  요구사항 2(평타여야 함)의 **반대를 조용히 단언**하고 있었다. 테스트의 주제가 옳아도
  **측정 수단이 규칙을 함께 못박는다** — 무엇으로 재는지까지 골라야 한다.

## 엔진 출력끼리의 비는 **일관성**만 검증한다 — 진실은 게임과의 비로만 나온다

- 확립: 2026-07-28 (아니스:스타 −0.358B의 정체, Fienn 사격장 영상으로 종결).
- **어떻게 숨었나.** 감사가 그녀의 세 소스를 한 창 안에서 서로 나눠보고 "설명 안 되는
  것 없음"이라고 결론냈다. 그때 적은 문장이 곧 버그였다 — *"별 틱 vs 평타 = 코어 1.5388
  × 투사체폭발 버킷 1.4994"*. 차이를 **관찰**하고 그것을 **정당한 것으로 기록**했다.
  소스 대 소스 비는 **시뮬의 숫자가 시뮬의 가정과 맞는지**만 볼 수 있고, "그 가정이
  게임과 맞나"는 원리적으로 못 본다.
- **솔로 사격장도 못 봤다.** 솔로는 풀버스트에 들어가지 않아 Stardust의 FB 게이팅
  버프(+92.03%)가 없다 → 두 인스턴스 사이에 **비교할 투사체폭발 인자가 아예 없었다.**
  그래서 "발당은 0.002%로 완벽"과 "버킷이 틀렸다"가 동시에 참일 수 있었다.
- **★ 판정한 측정: 덱 안 · 풀버스트 창 안에서 두 인스턴스.**
  논크리 코어히트 별 틱 **1,786,809** vs 논크리 코어히트 평타 **7,492,265** → 비 4.193098.
  맨계수 비는 (61.3% × 273.675%) / 40.01% = **4.193021** — **0.0018% 일치**.
  비가 맨계수와 같다는 것은 **모든 수정자가 약분됐다**는 뜻이고, 곧 틱이 평타와
  **완전히 같은 상태**에 있다는 뜻이다(코어 + PE 버킷 둘 다).
- **덤: 이 비가 소장품 배율도 독립 확증한다.** 273.675 = RL 기본 250 × 1.0947이므로,
  비가 맞는다는 것은 「차지대미지 9.47% 배율」이 실제로 그렇게 붙는다는 증거다.
- **일반화할 규칙 두 개:**
  1. **"스케줄 틱은 코어를 못 받는다"류의 포괄 규칙은 방출 경로를 기준으로 삼는다.**
     `scheduled`는 엔진이 **어떻게 내보내는지**일 뿐 게임이 그걸 무엇으로 보는지가
     아니다. **소환체의 사격은 평타다 — 소유자의 평타가 아닐 뿐.**
     그래서 `core_eligible`은 damage_type이 아니라 **인스턴스 단위 opt-in**이다.
  2. **"무의미한 스탯"으로 치운 항목이 분류의 증거일 수 있다.** 버스트의
     「폭발 범위 +100%」를 inert로 넘겼는데, **폭발하지 않는 것에 폭발 범위를 붙이지
     않는다.** 미모델 목록은 주기적으로 "이게 왜 여기 있나"로 다시 읽을 것.
- **효과:** 0.739x → **0.946x** (코어만 0.823x · 타이핑만 0.818x · 둘 다 0.946x),
  덱1 0.977x → **1.000x**, ±15% 이내 17/25 → **18/25**, 미달 −0.789B → **−0.505B**.
- **★ 같은 영상의 Starfall은 반대로 엔진이 이미 맞았다 — 크리/논크리 쌍이 판정한다.**
  버스트 전 568,126/917,751 → 버킷 **1.000000**, FB 안 2,282,272/3,218,612 → **1.500000**.
  크리는 `0.5 + 크리대미지업`을 코어·FB와 **같은 가산 버킷**에 더하므로, 같은 인스턴스의
  두 값을 나누면 **나머지가 전부 약분되고 버킷만 남는다.** 1.0 = 코어X·FBX·사거리X,
  1.5 = FB만. 즉 Starfall은 코어를 못 받고 FB는 받는다 — 현행 그대로.
  **소환체라서 코어를 받는 것이지, 그 유닛의 스킬이라서가 아니다.** 하나를 고쳤다고
  옆의 것까지 같이 고치지 말 것(회귀 테스트로 고정함).
- **⚠ damage-up은 전부 한 가산 버킷이다** (`damage_formula`의 `damage_up = 1 + (attack
  + sustained + … + projectile_explosion + …)`). PE를 **별도 곱셈 인자로 놓고**
  교차 비를 세우면 설명 안 되는 ×1.41이 나온다 — 실제로 이번에 한 번 그렇게 오진했다.
  올바른 형태는 `(1 + A + PE)/(1 + A)`이고, 그러면 엔진 재현비 **2.29617** vs 실측
  **2.35068**(창 안 다른 시점의 버프 상태 차이)로 구조는 일치한다.
- **덤: RL은 적정사거리 보너스를 아예 못 받는다** (Fienn, 2026-07-28) — 그래서 버킷이
  1.30이 아니라 정확히 1.000000이다. **"사거리 밖에 서 있었다"가 아니라 구조적 제외**다.
  이건 제약이 아니라 **측정 도구**다: RL 유닛의 논크리 평타는 사거리 항이 없어
  major 버킷이 `1 + 코어 + 풀버스트`로 깔끔하게 떨어지므로, **RL을 기준자로 쓰면
  미배선 항 하나를 빼고 대수를 세울 수 있다.**
  적정사거리는 **평타 전용**(코어와 같은 범위 규칙)이고 근거리 SG·SMG / 중거리 AR·MG /
  원거리 SR. 정본은 `nikke-skill-encoding`의 `references/damage-formula-reference.md`,
  배선 조건은 `docs/engine-gaps.md` #16.

## 자원이 "빨리 찬다"가 아니라 **두 발동 사이에 얼마에 도달하나**를 물어라

- 확립: 2026-07-28 (네온: 비전 아이의 화력게이지, Fienn 인게임 관측으로 정정).
- **오진의 형태:** 인코딩이 리필 항목(평타당 +2 · Firepower Charge 종료시 +45 ·
  틱당 +1)을 보고 "40초 쿨다운 **안에 충분히** 찬다 → 매 사이클 Super Firepower"라고
  적었다. 항목을 **합산해보지 않았다** — 실제로는 두 버스트 사이에 100에 못 미쳐
  **1·4·7번째 버스트에만** 켜진다. 게이지100 보너스 3종을 3배로 지급했고
  그녀는 **1.306x**였다(정정 후 **1.013x**).
- **판정법: 임계값과 한 주기 리필을 나눠보라.** "빨리 찬다"는 서술이지 수치가 아니다.
  리필 합이 임계의 몇 배인지 계산하고, 1보다 작으면 **주기가 늘어난다**.
- **★ 시작 상태가 위상을 정한다.** 전투 시작 게이지 100이라 **1번째**가 자격 버스트이고,
  그래서 주기는 `count % 3 == 1`(`activation_count`는 액션 안에서 1-based)이지
  `% 3 == 0`이 아니다. 소모형 자원은 **첫 발동이 공짜인지**를 반드시 확인할 것.
- **동치 논증을 적어둘 것.** "Super Firepower 상태 중 풀버스트 진입" 보너스를 그냥
  **자기 자격 버스트**에 붙였는데, 이게 맞는 이유는 두 가지다 — 그녀는 B3라 자기 버스트와
  자기가 연 풀버스트가 같은 순간이고(`FULL_BURST_OPEN_DELAY`), 자기 버스트 간격이
  10초 상태창보다 넓어 **남이 연 풀버스트가 창 안에 들어올 수 없다**. 근거 없이 옮기면
  다른 덱에서 조용히 틀린다.
- **기본분과 자격분을 분리하라.** 「Effect: X. Additional effect of <상태>: Y」는 **두 줄**이다
  — X는 무조건, Y만 게이팅. 한 덩어리로 묶으면 게이팅이 X까지 잘라먹는다.

## 실기록을 **최선 순서**로 채점하면 시뮬이 스스로에게 유리하게 편향된다

- 확립: 2026-07-28 (덱3/4/5 좌석 순서를 Fienn에게 받아 재채점).
- **문제의 형태:** 좌석 순서가 기록에 없어 캘리브레이션이 `feasible_orderings`를 전부
  돌려 **총딜 최대인 순서**로 채점했다. 이건 중립적인 기본값이 아니다 — argmax는
  정의상 시뮬의 상한을 고르므로, 기록은 고정인데 시뮬만 최선을 받는다.
- **진폭이 유닛 단위로 크다.** 덱4 민트 **1.015–1.502x** · 프리카 0.764–1.353 ·
  덱5 아크레인저 **0.562–1.183** · 덱3 레이 **0.309–0.936**. 25유닛 중 **15기**의
  배수가 순서에 따라 이만큼 움직였고, **과대 유닛 거의 전부가 자기 범위의 최상단**에
  앉아 있었다. 즉 "이 유닛이 과대하다"는 진단 자체가 채점 방식의 산물일 수 있었다.
- **교훈: 미기록 자유도를 목적함수로 채우지 말 것.** 순서·모드·분기처럼 기록에 없는
  축은 "최선을 고른다"가 아니라 **Fienn에게 물어 데이터로 고정**해야 한다. 물어보는
  비용은 한 문장이고, 안 물으면 그 축이 잔여 오차를 통째로 흡수해 엉뚱한 유닛을
  용의자로 만든다. (같은 사고의 앞선 사례: 덱2 신데렐라의 **무기 모드**가 미고정이라
  덱2 배수가 모델 변경 없이 움직였다.)
- **효과:** ±15% 이내 14/25 → **16/25**, 과대 합계 +1.895B → **+1.672B**,
  아크레인저 1.183→1.113 · 스노우화이트 1.151→1.110. 순서를 못 받은 덱1·2는 argmax를
  유지하되 출력에 "seat order unrecorded"라고 찍는다 — 남은 편향을 숨기지 않기 위해서다.
- **좌석 순서는 티어 내 우선순위다** — `burst_cycle`이 준비된 멤버 중 `eligible[0]`을
  고르므로, 덱 리스트의 순서가 곧 "같은 티어에서 누가 먼저 버스트하나"다.
- **★ 부수 확인: 기록된 순서에서는 엔진이 이미 옳게 굴고 있었다.** 헬름·미하라가
  **버스트 미사용(토템)**이고 프리카가 **1회만** 쓴다는 Fienn의 진술을, 좌석 순서만
  넣은 엔진이 그대로 재현했다(셋째 B3를 쓸 일이 없어서). 그래도 `max_bursts`로
  명시했다 — **우연히 맞는 것은 검증이 아니다.** 쿨감이 조금만 달라져도 스케줄러가
  토템에게 버스트를 시키고, 그러면 실제로 없었던 풀버스트가 조용히 생긴다.

## 유닛별 배수는 **기록 딜이 작을수록 과대**해진다 — 개별 유닛 버그로 쫓지 말 것

- 확립: 2026-07-27 (에이드 1.629x 조사, 25유닛 전수).
- **패턴:** `sim/record` 배수와 `log(기록 딜)`의 상관이 **r = −0.559**(n=25)로, 찾은 것 중
  가장 강한 예측자다. 기록 하위 6기(<0.35B) 평균 **1.268**, 상위 6기(>2B) 평균 **0.890**.
  즉 시뮬은 **덱 안의 딜 격차를 압축한다** — 작은 기여자를 과대, 큰 딜러를 과소.
- **따라서 "가장 과대한 유닛"은 대개 "기록 딜이 가장 작은 유닛"이다.** 에이드가 1.629x로
  최악인 것은 그녀의 기록이 **0.102B로 25기 중 최소**(2위 볼륨 0.174B의 절반 이하)라서다.
  **절대 오차로는 +0.064B(자기 덱의 1.5%)로 덱 내 4위**에 불과하고, 같은 덱의 미하라가
  −0.303B로 5배 크다. 배수 순위로 조사 대상을 고르면 작은 유닛만 쫓게 된다 —
  **절대 오차로 정렬하라.**
- 기각된 설명들: 평타 비중(r=+0.22에 불과 — 100% 평타 7기의 배수가 0.934~1.629로 흩어진다) ·
  무기군(SR 평균 1.256이지만 같은 SR인 liberalio가 0.837).

## "대미지 ▲ N%"는 계수를 곱하지 않는다 — **버킷에 더해진다**

- 확립: 2026-07-28 (스노우화이트: 헤비암즈 사격장, 라피+크라운 편성).
- 「순차 공격 대미지 ▲ 158.4%」를 엔진은 순차타 계수에 **×2.584**로 곱하고 있었다.
  실측이 요구한 것은 **×1.69249**이고, 그것은 `1 + 1.584/(1 + 버킷)`이다 —
  엔진이 그 순간 계산한 버킷 1.2874를 넣으면 소수 5자리까지 맞는다.
- **일반 규칙:** 「~ 대미지 ▲ N%」 계열은 `attack_damage_up`·`pierce_damage_up`과
  **같은 가산 버킷**에 들어간다. 계수에 곱하면 버프가 많이 쌓인 상태일수록
  과대해진다(여기서는 1.527배). 인코딩할 때 `(1 + N)`을 percent에 곱하고 있다면
  거의 확실히 틀린 것이다.
- **타입 게이팅으로 표현한다.** 그 버프가 스킬의 *일부* 타격에만 붙으면(여기서는
  순차타에만, 전체타 스윕에는 안 붙음) 펄스를 **쪼개고** `damage_type`을 주어
  `_TYPE_BUCKETS`가 그 인스턴스에만 스탯을 넘기게 한다. 신규 타입 추가는
  `_TYPE_BUCKETS` + `_BUNDLE_STATS` + `calculate_damage` 인자 3곳.
- **「for 1 round」이 자기 샷을 덮어야 하면 `round_buff_rule`을 쓸 수 없다** —
  그건 *다음* 샷들을 덮는다. 지속시간을 **기본 차지 시간**으로 두면 정확하다:
  세그먼트 종료 후 기본 사격이 정확히 한 차지 뒤에 오고 효과 구간이 반열림이라
  경계에서 배제된다(검증: FA 샷 4.26515 → 바로 다음 기본 샷 2.52005).
- **사격장 측정 설계 요령:** 같은 구간 안에서 **두 계수의 비**를 읽으면 버프·ATK가
  전부 상쇄돼 계수만 남는다. 스윕(41.9%)처럼 **버프를 안 받는 작은 타격**이 있으면
  그것이 최고의 기준자다. 이번에 6개 비율 중 5개가 이 방식으로 즉시 확증됐다.

## 평타도 Full Burst 보너스를 받는다 — "옵트인" 플래그가 평타 경로만 비워두고 있었다

- 확립: 2026-07-28 (Fienn 사격장 측정, 아니스 B1 + 에이드 B2 + 리베랄리오 B3, 표적 DEF 100).
- **측정:** 같은 코어·논크리 평타가 창 밖 **1,586,816** · 창 안 **7,492,265**.
  두 가설이 정확히 `(1+1.0+0.5)/(1+1.0) = 1.25`배 갈리고 실측은 **적용 쪽에 0.00003%**로
  안착한다. 중간값이 나올 수 없는 판정이라 한 쌍으로 끝난다.
- **원인의 형태가 교훈이다.** `full_burst_bonus_eligible`은 2026-07-12에 "추가 대미지
  문구를 가진 스킬 넉만 옵트인"으로 도입됐다. 2026-07-26/27에 규칙이 **"연산 시점으로
  판단하라"**로 재구성됐지만, 그때 손본 것은 **스킬 인스턴스뿐**이고 평타 `record()`
  호출은 애초에 플래그를 안 넘기고 있어서 **재검토 대상 목록에 오르지도 않았다.**
  → **규칙을 바꾸면 그 규칙의 "기본값 경로"도 다시 훑을 것.** 옵트인 플래그는
  누락이 침묵한다.
- **덤으로 얻은 교훈 — 골든 테스트가 보너스를 조용히 지운다.** 19건이 깨졌는데 전부
  "모든 샷이 X"류였다. 숫자만 1.5배로 올리면 다음에 이 보너스가 사라져도 안 잡힌다.
  `fb_factor(result, time)` 헬퍼로 **각 기대값이 자기 창 상태를 곱하게** 바꿨고, 스택
  카운트를 읽는 헬퍼들은 정규화 기준에서 FB를 **나눠 뺐다**.
- **효과:** 합계 0.936x → **1.023x**, 미달 −3.884B → −1.954B. 그리고 **오차의 주된 방향이
  미달에서 과대로 뒤집혔다** — 이제 최대 오차는 스노우화이트 +0.694B · 아스카 +0.540B다.
  이 프로젝트에서 반복된 패턴 그대로: **맞는 방향의 수정이 그 아래 깔린 반대 오차를 드러낸다.**

## 차지 무기의 발당 간격 ≠ 차지 시간 — **유닛마다 다른 모션 딜레이**가 있다

- 확립: 2026-07-28 (Fienn 인게임 측정 + 180초 타수 카운트).
- **엔진은 차지 시간만 발당 간격으로 썼다.** 실제로는 발사 후 다음 차지를 시작하기까지
  **발사모션↔차지모션 딜레이**가 있고, 스노우화이트는 **약 0.4초**다.
- **타수 카운트가 이걸 못 박는다.** 그녀의 180초 실측 **86타(Fully Active 14 + 기본 72)**를
  시간으로 환산하면 `14×(3.2+0.4) + 72×(1.2+0.4) + 7×2.0(재장전) = 179.6초 / 180초`.
  딜레이 없이는 135.9초밖에 안 차고 **44.1초가 붕 뜬다.** 엔진은 그만큼 발수를 더 줬다
  (기본 96발 vs 실측 72발, **37% 과대**).
- **★ 무기군 상수가 아니라 유닛별이다.** 리베랄리오도 SR인데 차지샷을 **딜레이 없이**
  연달아 쏜다(Fienn). 일괄 적용은 실측이 기각한다 — 모든 차지 무기에 +0.4초를 주면
  스칼렛이 0.981x → **0.559x**, 신데렐라가 0.971x → 0.654x로 무너진다. 둘 다 현행이
  거의 정확하다. **딜레이 보유 유닛은 Fienn이 인게임으로 지목한 5명**(스노우화이트:헤비암즈 ·
  에이드:에이전트버니 · 헬름 · 브래디 · 벨벳) — `registry._CHARGE_MOTION_DELAY`.
- **엔진의 `CHARGE_INTERVAL_FLOOR`가 사실 같은 것이었다.** 10/29 = 0.345초는 신데렐라가
  차지속도 +100%로 **차지를 0으로 만든 상태**에서 10초에 29발을 쏜 측정이다 — 차지가
  사라졌을 때 남는 것, 곧 그녀의 모션 딜레이다. `interval = charge + delay`로 보면
  그 "바닥"은 특수 케이스가 아니라 자연스러운 귀결이다.
- **효과:** ±15% 이내 13/25 → **14/25**, 과대 합계 +2.377B → **+1.895B**.
  에이드 1.970→**1.451** · 헬름(애장품) 1.699→**1.243** · 스노우화이트 1.320→**1.151** ·
  벨벳 1.213→1.074. RL과 리베랄리오는 **전부 불변**.
- **⚠ 이 항목의 "나머지는 0.4초를 빌려 쓴다"는 서술은 2026-07-28~29에 낡았다.**
  이제 **7기가 실측**됐고 값이 제각각이다 — 스노우화이트 0.4 · 앵커 0.4 · 민트 0.39 ·
  에이드 0.35 · 프리카 0.34 · 흑련 0.43 · 레이븐 1.014. 공용 기본값을 아직 빌려 쓰는
  것은 헬름×2 · 브래디×2 · 벨벳 다섯뿐이다. 현황은 `scripts/audit_charge_motion_delay.py`.

## 차지 케이던스에서 유도한 값은 딜레이·재장전 두 겹으로 민감하다

- 확립: 2026-07-30 (Centi 애장품의 Skill 2 유효 쿨다운 인코딩).
- 차지 모션 딜레이는 그 유닛의 평타 딜만 바꾸는 게 아니다. **케이던스에서 유도한
  다른 값**이 있으면(여기서는 Skill 1의 풀차지 쿨감을 환산한 Skill 2의 유효
  쿨다운) 딜레이 오차가 그 값으로도 전파된다. Centi는 22프레임(Fienn 실측,
  위 "차지 무기의 발당 간격 ≠ 차지 시간" 참조)을 넣느냐 마느냐로 유효 쿨다운이
  **5.11초 ↔ 5.74초**로 갈린다. 12%짜리 차이지만 그녀의 딜 기여 전부가 이 쿨다운의
  가동률에 달려 있다 — 딜레이를 안 물어봤다면 그만큼 조용히 과대평가됐을 것이다.
- 같은 이유로 재장전 모델 오차도 전파된다 — 클립형 재장전(`docs/engine-gaps.md`
  #19)이 Centi에서 발견된 것도 이 경로였다: 그녀의 발당 간격(→유효 쿨다운)은
  6발 탄창의 재장전을 1회로 뭉뚱그린 탓에 1.45초(모델) vs 1.617초(실제)로
  낙관적이다.
- 실무 규칙: 차지 무기 유닛에서 "발당 간격"을 읽어 무언가를 유도했다면, 그
  유도값은 차지 모션 딜레이 답과 재장전 모델의 **양쪽 정확도에 걸려 있다**고
  명시할 것. See `skill_rules/centi.py::field_discussion_effective_cooldown`.

## 탄환 환급(택티컬 베어)은 스탯으로 근사할 수 없다 — 발사 타임라인 안에서 카운터를 돌려야 한다

- 확립: 2026-07-31 (Fienn 인게임 룰링 + 실기록 3-변형 채점, `docs/engine-gaps.md`
  항목 12-b).
- 택티컬 베어 큐브의 「10발 사격 시 탄환 3발 충전」을 「탄창 +N%」 같은 flat
  스탯으로 근사해 봤더니 흑련(deck1) 배율이 **비단조**했다: +11% → 0.9804x,
  +22% → **0.9736x**, +43% → 0.9930x. 탄창을 키우면 재장전 위상이 10초 풀버스트
  창에 대해 밀리므로, 어떤 크기에선 재장전이 오히려 창 안으로 들어와 딜을 깎는다 —
  그래서 답이 커질수록 단조롭게 좋아지지 않는다. **근사치는 외삽이 안 된다.**
- 대신 실제 발사 타임라인 안에서 카운터를 직접 걷는다 — 누적 발수 카운터가
  `every_shots`의 배수에 닿을 때마다 `rounds`를 넣되 `capacity`에서 캡한다
  (`attack_rate.AmmoRefund` + `magazine_shot_count`). 카운터는 **재장전을 넘어
  누적**된다(전투 시작부터 총 발수를 센다). `refund=None`이면 기존 산술과
  비트 단위로 동일하다는 회귀 앵커를 지켰다.
- **값어치는 "없는데 준 것"이 아니라 "있는데 안 준 것"에 있었다.** 렐릭 베어를
  잘못 주고 있던 재장전속도 29.69%를 떼기만 하면 흑련은 0.9809x → 0.9805x로
  **0.0004x밖에 안 움직인다** — 있지도 않은 재장전속도 오류는 사실상 무해했다.
  환급을 넣고 나서야 0.981x → 0.999x로 크게 움직였다.
- **엔진이 맞아질수록 남은 과대가 드러나는 패턴도 여기서 재확인됐다.** 흑련만
  고쳤는데 25유닛 합계는 1.011x → **1.015x**로 오히려 멀어졌다 — 그녀의
  절대오차 −0.124B가 다른 유닛의 과대를 가려주고 있었다. "합계가 개선됐다"는
  개별 항목이 다 맞다는 뜻이 아니다 — "잔여 편차에 공통 원인은 없다" 항목과
  같은 계열의 함정.
- **`RECORD_CUBES`는 캐릭터가 아니라 정확한 무기변형 slug로 키를 걸어야 한다.**
  `cinderella`(기본, RL 24발)와 `cinderella-crystal-wave-mg`(MG 300발)는 이름이 같은
  캐릭터지만 실기록에서 **다른 덱의 다른 슬러그**다(deck4 대 deck2) — 택티컬 베어를
  끼는 쪽은 기본이고(2026-07-31, Fienn 확인), 같은 항목을 `cinderella-crystal-wave-mg`에
  잘못 붙이면 0.977x → **1.029x**로 과대해진다. 게다가 탄약 소모 카운터가 발사
  타임라인을 공유하는 덱메이트로 번져, 리틀머메이드도 동반으로 1.038x → 1.047x까지
  같이 뛴다 — 잘못된 큐브 배선의 오차가 그 유닛 하나로 국한되지 않는다는 뜻. 큐브를
  실기록에 매길 때는 슬러그 단위로 정확히 매칭할 것.
- See `docs/superpowers/specs/2026-07-31-tactical-bear-ammo-refund-design.md`,
  `backend/app/attack_rate.py::AmmoRefund`/`magazine_shot_count`,
  `scripts/raid_record.py::RECORD_CUBES`.

## Full Burst 보너스는 **대미지 연산 시점** 하나로 판정된다 — 「추가 대미지」 문구 규칙은 삭제됨

- 확립: 2026-07-28 (Fienn). 폐기된 규칙: 2026-07-12의 문구 판정.
- **폐기된 규칙:** "스킬 원문이 `as additional damage`면 FB 보너스 대상, `as damage`면 비대상."
- **왜 오랫동안 맞아 보였나 — 상관관계였다.** B3의 즉발 스킬 중 `as damage`로 적힌 것들은
  **캐스트 시점에 연산**되는데, 캐스트는 풀버스트 진입보다 한 박자 앞선다. 즉 그것들은
  **들어갈 창 자체가 없었다.** 문구가 원인인 적은 없고, 타이밍과 같이 움직였을 뿐이다.
  (헬름: 아쿠아마린이 교과서적 반례였다 — 원문은 `as additional damage`인데 B2라 창이
  열리기 전에 터져서 보너스를 못 받는다. 문구 규칙으로는 설명이 안 된다.)
- **확정 규칙:** 그 인스턴스의 **대미지가 연산되는 시각**이 풀버스트 창 안이면 받고,
  밖이면 못 받는다. 끝이다. B3 사용과 FB 진입 시점이 분리된 이 엔진에서는 이걸로 전부 결정된다.
- **결정적 측정 (Fienn, 스노우화이트 오토파이어).** FB 보너스는 크리와 **같은 가산 버킷**의
  +0.5라, **같은 인스턴스의 크리/논크리 비**를 잡으면 다른 게 전부 상쇄되고 보너스만
  분모에 남는다. 원문이 `as damage`인 오토파이어가:
  | | 측정 | 보너스 없음 | 보너스 있음 |
  |---|---|---|---|
  | 창 밖 | 1.586000 | **1.586000** (0.00001%) | 1.390667 |
  | 창 안 | 1.390667 | 1.586000 | **1.390667** (0.00000%) |
  가설이 12~14% 벌어지는데 각각 한쪽에 0.00001% 이내로 안착한다. `as damage`도 받는다.
- **코드에서 지운 것:** `full_burst_bonus_eligible` 플래그 전부(엔진 파라미터·`Pulse` 필드·
  헬퍼 인자·스펙 키·약 40개 호출부·테스트 단언). 규칙을 지우려면 **그 규칙만을 위해 존재하던
  배선도 지워야 한다** — 낡은 규칙이 독스트링에 남아 평타(07-28)와 per-shot 넉(같은 날)을
  연달아 놓친 게 정확히 이 때문이다.
- **살린 것과 그 이름:** 플래그는 사실 **두 가지 일**을 하고 있었다. 버스트 넉과 자원스케일
  DoT에서는 기록 시각을 `FULL_BURST_OPEN_DELAY`만큼 **뒤로 밀고** 있었는데, 그건 진짜
  모델링 결정이다("이 대미지는 캐스트에 터지나, 한 박자 뒤에 터지나"). 그래서 그 역할만
  `resolves_after_cast`로 **이름을 바로잡아** 남겼다. 나머지는 전부 죽은 게이트였다.
- **효과:** 리틀머메이드 0.850→**1.048** · 미하라 0.753→**0.909** · 라피 0.924→**0.990** ·
  신데렐라:크리스탈웨이브 0.897→**0.962** · 스노우화이트 1.152→**1.386** · 아스카 1.055→1.074.
  **±15% 이내 11/25 → 13/25**, 미달 −1.552B → **−0.873B**.
- **드러난 것:** 스노우화이트가 1.386x로 절대오차 1위(+0.649B)가 됐다. 맞는 수정이 그 밑에

## "엔진이 못 한다"는 보류 사유에는 유통기한이 있다 — gap이 닫히면 그 사유를 되짚어라

- 확립: 2026-07-28 (아스카 시키나미 랑그레이:WILLE, +0.540B → +0.155B).

  앞의 둘만 걸고 세 번째를 빠뜨렸고, 독스트링에 사유까지 적혀 있었다:
  "평타에만 스코프를 거는 수단이 엔진에 없다 — 새 엔진 능력이 필요하다."
- **그 사유는 그 시점엔 사실이었고, 지금은 아니다.** `normal_attack_damage_multiplier`는
  이후 **gap #9**에서 만들어졌고 질 발렌타인이 쓰고 있다. 필요한 것은 새 능력이 아니라
  **같은 스탯의 음수 값** 한 줄이었다. 아무도 되짚지 않아 그대로 남았다.

  엔진은 계속 자란다. → **gap을 닫을 때, 그 gap을 사유로 든 독스트링을 grep할 것.**

  "긍정 효과보다 영향이 작다"고 눈대중한 원래 독스트링의 판단이 정확히 여기서 틀렸다.

## "공격 횟수에 따라 효과가 달라진다"는 임계값 3개가 아니라 **회전** 하나다

- 확립: 2026-07-28 (아르카나: 포춘 메이트, Fienn 인게임 관측 + 사격장 측정).
- **원문:** "Effect varies according to the number of attacks. **Only one effect is
  triggered at a time.** Two times: 재장전 / Four times: 행복한기억 / Six times: 소중한추억."
  독립된 세 임계값처럼 읽히지만, 실제로는 **2타마다 셋 중 하나씩 순환**한다 —
  2·4·6 → 8·10·12 → 14·16·18. 카운터는 상태가 사라질 때 리셋된다.
- **결정적 관측은 부정형이었다.** 12타에서 행복한기억과 재장전이 **안 뜬다.** 임계값
  모델이면 12는 4의 배수도 2의 배수도 되므로 셋 다 떠야 한다. 한 번의 "안 뜸"이
  두 모델을 갈랐다.
- **그래서 "N회당 1스택" 같은 상수로 접으면 안 된다.** 회전이 어디까지 도느냐는
  **발수**가 정하고, 발수는 덱이 정한다 — 그녀는 단독이면 창당 약 14발(각 2스택)이지만
  토브의 공격속도를 받으면 **22발**로 셋 다 3스택 만렙이다. **덱에 따라 2배 갈린다.**
  (EVE의 크리 44회 트리거를 고정 발수로 접지 않은 것과 같은 이유 — Fienn, 2026-07-20.)
- **엔진에 남긴 것:** `per_shot_cycle_in_own_status_window` (first, period, window) —
  기존 `every_during_own_status_window`는 **창을 이어 붙여** 세기 때문에 창이 주기의
  배수가 아니면 위상이 다음 창으로 밀려 영영 안 맞는다. 회전에는 **창마다 리셋**이 필수다.

## 스킬 설명에 적힌 효과가 **실제로는 아무것도 안 하는** 경우가 있다

- 확립: 2026-07-28 (아르카나의 청춘의 기록 / Snapshots of Youth).
- **원문:** "행복한 기억 발동 시 청춘의 기록: 평타 대미지 배율 ▲10%, 최대 3중첩."
  인게임에서 **버프 아이콘도 정상적으로 뜬다.**
- **그런데 발당 대미지가 오히려 내려간다** — 행복한기억 스택이 오를 때마다 펠릿 1개당
  ×0.992143 / ×0.993399 / ×0.994377. **양수 버킷 항은 어떤 희석을 받아도 비를 1 아래로
  못 내린다.** 기존 버킷 `B`를 미지수로 두고 풀면
  `(10+k)/10 × (1+B+0.1k)/(1+B) = 1+0.091354k` → **B = −13.7**, 해 없음.
- **교훈 두 가지.** ① 버프 아이콘은 **효과의 증거가 아니다**. ② 그래서 인코딩은 스킬
  텍스트가 아니라 **측정된 총 배수**를 넣어야 한다 — 행복한기억(펠릿 +1)과 청춘의기록은
  인게임에서 항상 1:1로 같이 오르고 둘 다 자기 평타 전용이라 **분리 자체가 불가능**하다.
  측정된 스택당 +9.1354%가 이미 둘을 다 담고 있다. 쪼개면 측정이 부정하는 분해를
  발명하는 것이다.
- **부수로 얻은 것: 기본 펠릿 수는 데이터 소스에 없는데 측정으로 풀린다.** 총 대미지의
  스택당 증가분이 **일정해지는** P를 찾으면 된다 — P=10에서 편차 0.013%,
  P=9나 11에서 20배 나빠진다. Fienn이 인게임으로 10을 확인해 일치.

## 가로채기가 빈손이면 "세션이 없다"가 아니라 "**앱이 그 파일을 요청하지 않는다**"를 먼저 의심하라

- 확립: 2026-07-27 (소장품 전 등급 수집).
- **증상:** `collect.js --collectibles`가 CDN 응답을 가로채는데 레코드 0건.
  앞선 세션의 진단은 "로그인된 Chrome이 없어서"(`ECONNREFUSED`)였다.
- **실제:** 자기 브라우저를 띄우는 `--headless`로 돌려 보니 **브라우저는 뜨고
  디렉터리도 해석되는데** 여전히 0건이었다. 소장품 테이블은 로그인한 Collection
  화면이 렌더될 때만 요청된다 — 가로채기는 **앱이 요청해 주기를 기다리는** 방식이라
  앱이 안 부르는 파일에는 원리적으로 도달 못 한다. 세션 문제가 아니었다.
- **판별법:** 가로채기가 비면 *다른 응답은 잡히는가*를 본다. 디렉터리·스탯 파일이
  잡히는데 목표만 안 잡히면 접근 권한이 아니라 **트리거**가 없는 것이다.
- **해법이 열어 준 것:** ShiftyPad의 정적 테이블 경로는 **회전 매니페스트가 아니라
  경로의 순수 함수**다 — 디렉터리 세그먼트는 djb2(깊이별 소수), 파일명은 경로 전체의
  md5. 번들에서 옮겨 적으면(`tools/collect-blablalink/resource-url.js`) 어떤 게임
  테이블이든 **브라우저·세션 없이 평범한 HTTP GET**이 된다. 논리 경로는 번들에서
  문자열로 찾을 수 있다(`getGameJsonResource(\`/equip/...\`)`).
- **옮겨 적을 때 틀리기 쉬운 두 곳:** (a) djb2의 `& 0xFFFFFFFF`는 JS에서 **부호 있는**
  32비트 변환이라 음수가 나오고 뒤의 `((h % p) + p) % p`가 그걸 되돌린다 — 둘 다
  그대로 옮길 것. (b) 각 세그먼트는 자기 세그먼트가 아니라 **경로 전체**를 해시한다.
- **검증은 관측된 URL로 하라.** 코드에서 재유도한 값끼리 비교하면 아무것도 증명 못
  한다. 실제로 흐른 URL 4개를 `resource-url.test.js`에 고정했다.

  하나만 읽고 있어서 R 보유자를 그만큼 과대평가하고 있었다.
- **왜 159/159 피팅이 이걸 못 잡았나:** 그 로스터의 R 보유자가 **전부 레벨 0**이라
  기여가 0으로 처리됐다 — 잘못된 커브를 읽을 기회 자체가 없었다. **피팅이 닫혔다는
  것은 그 데이터가 건드린 경로만 맞다는 뜻이다.**
- 일반화: `*_sample` 이름이 붙은 테이블 항목은 "대표값"이라는 주장이지 증명이 아니다.
  전 등급 데이터가 들어오면 **그 주장을 먼저 재검사할 것**.

## 같은 슬롯이라도 **스킬 축과 스탯 축은 따로 켜진다** — 레벨 0이 그 경계다

- 확립: 2026-07-27 (Fienn 인게임 전수 확인 + 159유닛 실측).
- **소장품 레벨 0은 "미착용"이 아니라 "착용됐지만 스탯이 아직 0"이다.**
  스킬은 **레벨 0부터** 나오고(사다리 1단), 스탯(ATK/HP)은 **레벨 1부터** 붙는다.
- **판별 규칙:** 착용 여부를 말하는 것은 **레벨이 아니라 `favorite_item_tid`**다.
  빈 슬롯은 tid가 0이고, 레벨 0 착용은 tid가 살아 있다. 레벨로 착용 여부를 판정하면
  두 상태가 조용히 합쳐진다.
- **실측이 축을 갈랐다:** 레벨 0에 스탯 커브의 index 0을 주면 159 측정 유닛 중
  **정확히 31기**(= 레벨 0 착용자 전원)가 그 값만큼 어긋난다(SR 3,029 · R 638).
  배열에 index 0이 **있다는 것**이 그것이 레벨 0의 값이라는 뜻은 아니다 — 같은 레코드
  안에서 스킬 사다리(`level1[0]`은 진짜 레벨 0)와 스탯 커브가 서로 다르게 인덱싱된다.
- **일반화:** 한 아이템의 두 효과 경로가 서로 다른 조건으로 켜질 때, "일관성"을 위해
  한쪽을 다른 쪽에 맞추면 **측정으로 확인된 쪽을 망가뜨린다.** 두 경로를 한 테스트에
  묶어 두는 편이 낫다(`test_level_zero_gives_the_skill_but_no_stat_...`).
- **애장품 레벨은 또 다른 축이다.** 인게임 SSR 10단계인 유닛도 API `favorite_item_lv`는
  2(= 레코드 `max_level`)로 온다. 엔진이 안 흔들리는 이유는 애장품 레코드의 사다리가
  `level1 = [4, 4, 4]`라 **어느 값이든 최상단**이기 때문이다 — 값이 우연히 맞는 게
  아니라 **어느 축을 쓰든 답이 같게 생겼다.**

## Full Burst 보너스의 기준은 **연산 시점**이다 — "추가 대미지" 문구는 그 대리 지표일 뿐

- 확립: 2026-07-26~27 (Fienn). 2026-07-12의 문구 규칙을 **대체하지 않고 감싼다.**
- **원칙:** 대미지 인스턴스가 **연산되는 시각이 Full Burst 창 안이면** 보너스를 받는다.
  문구는 보지 않는다.
- **그럼 "as additional damage" 규칙은 왜 있었나:** B3 유닛의 버스트 스킬에서 그 문구는
  "**캐스트 순간이 아니라 얼마간 딜레이 후에 대미지가 들어간다**"는 뜻이고, 그 딜레이가
  인스턴스를 FB 창 안으로 밀어넣는다. 즉 문구는 시점을 텍스트로 추정하는 **대리 지표**였다.
- **적용 규칙 (판단 순서):**
  1. **연산 시각을 알 수 있으면 문구를 보지 않는다.** 샷·틱·소환물처럼 캐스트 이후의
     구체적 시각에 계산되는 것은 `full_burst_bonus_eligible=True`로 두고, 엔진의
     창 검사(`start <= time < end`, 인스턴스 자기 시각)에 맡긴다. 플래그는 **검사를
     켤 뿐**이라 창 밖 인스턴스는 자동으로 못 받는다 — 근사가 아니라 정확하다.
  2. **시각이 텍스트만으로 모호한 단일 순간 넉에만** 문구 검사를 남긴다.
  3. 여전히 유효한 타이밍 사실: B1/B2가 **자기 버스트 시각에** 터뜨리는 인스턴스는
     `full_burst_start` **이전**이라 자격을 줘도 죽은 코드다(헬름: 아쿠아마린 사례).
     **B3도 마찬가지다** — 사이클이 [3단계 진입 → B3 사용 → **풀버스트 시작**]이므로
     B3의 캐스트-시각 인스턴스도 창이 열리기 **전**이다(Fienn 사격장 측정, 2026-07-27 —
     아래 "★ 진짜 원인" 참조). 창 안에 드는 것은 **캐스트 이후에 연산되는** 인스턴스뿐이다.
- **보너스의 크기는 +0.5다** (Fienn 확인, 2026-07-27). `full_burst_bonus`는 **크기가
  아니라 플래그**다 — `raid_simulator`가 창 안이면 `1.0`을, 밖이면 `0.0`을 넘기고
  `damage_formula._major_modifiers`가 **`full_burst_bonus * 0.5`** 로 major modifier
  버킷에 더한다. **호출부의 `1.0`만 보고 "+100%"로 읽지 말 것** — 실제로 이 착각이
  한 번 나왔다. 크리티컬(`0.5 + 크리 대미지원`)·코어와 **같은 버킷**이라 서로 가산이지
  곱셈이 아니다.
- **이 원칙으로 고친 다섯 곳** — 모두 문구 규칙이 놓치던 자리다:
  - **나유타** Hypocrisy 풀차지 넉(530.46%): 트리거가 풀차지(1.8초)이고 그건 그녀의
    버스트 이후에만 일어난다 → 전부 창 안. 0.79x → 0.85x.
  - **홍련** 단계 넉(283.03/565/848.03%): 각 단계가 **자기 샷의 시각**에 연산된다.
    0.62x → 0.76x.
  - **아니스: 스타** Shooting Stars(40틱): 버스트→FB 발동 **0.2초**, 틱 간격 **0.25초**
    → 첫 틱부터 창 안. 0.748B → 0.816B.
  - **반복 틱 DoT 일반**(기존 Mana 사례): 첫 틱 이후는 구성상 캐스트 이후 → 기본 True.
  - **신데렐라** Flawless Glass 퍼샷 넉(136.6%, 2026-07-27 추가): 풀차지 명중마다
    발동하므로 샷의 시각을 안다. 486발 중 **160발(33%)이 창 안**이고 그 창이 이 소스
    딜의 61%를 갖는다. 넉 +27.9%.
- **함정 1:** 문구 규칙을 그대로 믿고 "as damage니까 자격 없음"으로 적어둔 독스트링이
  여럿 있었다(홍련·아니스). **"보수적 해석"이라 적혀 있으면 대개 미검증 가정이다.**
- **함정 2 — 감사는 유닛이 아니라 불릿 단위로 돌려야 한다.** 2026-07-26의 FB 감사는
  **버스트 넉 경로만** 훑으면서 신데렐라를 "그녀의 additional damage 불릿은 Beautiful
  미러(자원 게이팅 넉)"라며 **유닛 단위로** 기각했다. 그런데 Flawless Glass에 **두
  번째 그런 불릿**(평범한 퍼샷 넉)이 있었고 그것이 1년치 딜의 22~29%였다. 그 감사문
  자신이 남긴 결론이 "유닛 수로 세면 틀리고 불릿 단위로 읽어야 맞는다"였는데, 정작
  그 감사가 유닛 단위로 끝났다. **경로별로 훑을 때는 다른 경로에 같은 문구의 불릿이
  남아 있는지 반드시 되짚을 것.**

## 사격장 한 발이 시뮬 한 시즌보다 낫다 — 볼륨의 에스컬레이션 버프가 처음부터 최대였다

- 조사: 2026-07-27. 신데렐라 과대(덱4 1.48x)의 원인 추적. **실기록(180초 총합)으로는
  못 갈랐고, Fienn의 사격장 단발 측정이 한 번에 갈랐다.**
- 측정 설정(Fienn): 볼륨 · 크라운 · 신데렐라, Lv 665, 표적 작열/우월코드 미적용/DEF 100,
  **전투 개시 1초의 첫 버스트만**. 표기값 — 불릿1 **12,674,307**(논크리) / **20,958,234**(크리),
  불릿2 **513,863** / **737,770**.
- **크리 배율 두 개가 열쇠였다.** 크리는 major modifier에 `0.5 + 크리대미지원`을 **가산**하므로
  `(M+c)/M = r`. 두 불릿의 비를 나누면 **M₂/M₁ = 0.65361/0.43574 = 1.50000** — 소수 5자리까지
  정확히 1.5다. 즉 **M₁ = 1, M₂ = 1.5**이고 이것이 한 번에 세 가지를 확정했다:
  **FB 보너스 = +0.5** · **버스트 불릿1("as damage")은 FB 보너스를 못 받는다**(엔진 정상) ·
  **불릿2("as additional damage")는 받는다**(엔진 **누락**).
- **그리고 크리대미지원을 역산하니 0.65361 − 0.5 = 0.1536이었다.** 신데렐라 오버로드가
  0.0762이므로 스쿼드 기여분은 **0.0774**. 엔진은 **0.2845**를 주고 있었다.
- **원인:** `volume.py`가 Drop the Beat의 크리 대미지를 **세 에스컬레이션 단계의 합**
  (7.74 + 9.42 + 11.29 = **28.45%**)으로 계산해 **전투 시작부터** 건다. 독스트링이 스스로
  "Simplification ... steady-state value is the sum of all three"라고 적어 뒀다.
  게임은 **첫 발동에 1단계 7.74%만** 준다 — `description_value_04`와 실측이 **소수점까지
  일치**한다. 크리 대미지원을 0.1536으로 바꾸면 크리 배율이 **1.6536 = 1.6536**으로
  정확히 맞는다.
- **왜 이게 큰가:** 스쿼드 범위 버프라 **볼륨이 낀 덱 전원**이 초반 사이클에서 부풀어
  오른다. 그리고 이것은 마스트 취기와 **같은 유형**이다 —
  [[prefer-cycle-accurate-escalation]]의 "에스컬레이션 버프는 사이클별로 모델링하라"가
  이미 있는 규칙인데 볼륨에 적용되지 않았다.
- **일반 교훈: 총합 실기록으로는 상쇄되는 오류를 못 가른다.** 180초 5덱 합계는 22개
  유닛 × 여러 버프의 곱이라 어떤 조합으로도 맞출 수 있다. **단일 히트의 표기값 + 크리/
  논크리 쌍**은 major modifier 버킷을 **대수적으로 분리**해 준다 — 앞으로 의심스러운
  버프는 사격장 단발로 재는 게 압도적으로 싸다.
- **★ 진짜 원인 (Fienn, 2026-07-27) — B3의 버스트 대미지는 풀버스트가 열리기 *전에*
  연산된다.** 버스트 사이클은 [1단계 진입 → B1 사용 → 2단계 진입 → B2 사용 →
  **3단계 진입 → B3 사용** → **풀버스트 시작**] 순이다. B3의 버스트 스킬 대미지는
  *자기 캐스팅 시점*에 확정되고, 그 시점은 풀버스트 창이 열리기 **직전**이다. 따라서
  B3의 버스트 넉은 **FB 보너스도, `full_burst_enter`로 붙는 어떤 버프도 받지 못한다.**
  반면 "as additional damage"처럼 **나중에** 연산되는 라이더는 **둘 다** 받는다.
  이것은 이 파일 맨 위의 "**FB 보너스의 기준은 연산 시점**" 원칙과 정확히 같은 말이며,

## **"버스트 N단계 진입 시" ≠ "풀버스트 시작 시"** — 한 사이클 안에서 서로 다른 순간이다

- 확립: 2026-07-27 (Fienn 지적). 위 "★ 진짜 원인" 수정을 넣자 **그것이 가리고 있던 두
  번째 오독이 드러났다** — 이 프로젝트에서 반복된 그 패턴이다.
- **두 표현은 B3 캐스트를 사이에 두고 갈라진다:**

  ```
  1단계 진입 → B1 → 2단계 진입 → B2 → [3단계 진입] → B3 사용 → [풀버스트 시작]
                                            ↑                          ↑
                                    캐스트 前 = B3 버스트에 닿음   캐스트 後 = 안 닿음
  ```
- **판별은 오직 원문이다.** 크라운 One for All = *"Activates **at the start of Full
  Burst**"* → `full_burst_enter`(안 닿는다, 정상). 민트 Fantastic Performance =
  *"Activates when **entering Burst Stage 3**"* → `ally_burst_activate` +
  `burst_stage_entered(3)`(닿는다). **엔진은 이 둘을 오래 `full_burst_enter` 하나로
  뭉뚱그려 놨고**, 두 순간이 같은 타임스탬프였을 때는 그 오류가 보이지 않았다.
- **왜 지금 드러났나:** 창을 한 순간 뒤로 밀기 전에는 `full_burst_enter`가 B3 캐스트와
  동시각이라 stage-N 불릿도 **우연히 맞았다**. 창을 옮기자 그 우연이 사라지면서
  잘못된 배선이 노출됐다. **수정이 다른 결함을 드러내는 것은 진전이다.**
- **전수 대조 결과** (원문 표기 ↔ 배선): "at the start of Full Burst"를 쓰는 인코딩
  유닛은 **크라운 하나뿐**이고 올바르게 배선돼 있다. "entering Burst Stage N" 쪽은
  **5기가 틀려 있었고 전부 수정했다**(2026-07-27) — `mint` · `mihara-bonding-chain` ·
  `rei-ayanami` · `snow-white-heavy-arms` · `mast-romantic-maid`(2건).
  **2026-07-29에 여기에 2기가 더 붙었다**(`ein` · `laplace-ultimate-hero`) — 아래 참조.
- **불릿 단위로 봐야 한다는 규칙에 내 스크립트가 걸렸다.** `maiden-ice-rose`는
  파일 단위 grep이 잡은 **오탐**이었다 — 걸린 것은 룰이 아니라 `_full_burst_enter`라는
  **헬퍼 함수 이름**이었다. **정적 grep은 후보 목록일 뿐이다.**
  (2026-07-29 정정: 당시 "그녀 원문도 'entering Full Burst'라 현행이 맞다"고 적었으나
  Meditation은 **두 불릿**이고 1번은 실제로 "entering Burst **Stage 1**"이다. 무죄
  판정 자체는 유효한데 **이유가 다르다** — 그 MP 적립은 SkillRule이 아니라
  `_resolve_squad_burst_cycle_resource`가 처리하고, 거기서 이미 **스쿼드 단위**로
  "누구든 1단계가 발동하면"으로 걸려 있다. 오탐의 근거는 원문이 아니라 **처리 경로**다.)
- **★ 그 전수 대조는 전수가 아니었다 (2026-07-29).** 한 가지 표현만 grep했기 때문에
  **두 유닛이 구조적으로 안 보였다**: `ein`의 원문은 "entering Burst **Skill** Stage 3"
  이라는 **표현 변종**이고, `laplace-ultimate-hero`는 ShiftyPad 수치만 수집돼 있어
  **대조할 원문 자체가 없다**(독스트링에만 "[Burst Stage 3 entry]"라고 적혀 있었다).
  둘 다 진짜 결함이었다. 교훈 둘: **① 표현은 변종을 가정하고 정규식으로 훑을 것**,
  **② "원문이 없어 확인 못 함"을 "이상 없음"과 절대 섞지 말 것.**
  `scripts/audit_burst_stage_triggers.py`가 이 둘을 각각 별도 버킷으로 보고한다.
- **한 룰에 두 불릿이 묶여 있으면 트리거를 갈아끼울 수 없다.**
  `snow_white_heavy_arms`는 Fully Active(자기 버스트 스킬)와 Shades of White(3단계
  진입)를 **하나의 `own_burst_activate` 룰**에 담고 있었다. 두 순간이 같았을 때는
  무해했지만, 갈라지자 분리 없이는 어느 쪽도 옳게 만들 수 없었다. **트리거가 다른
  불릿은 처음부터 룰을 나눠 둘 것.**
- **순환하는 카운터를 "최초 1회" 게이트로 쓰지 말 것.** 마스트의 Drunken 스택은
  앵커가 없으면 `((cycle−1) % 3) + 1`로 **순환**한다. 상시 버프를 "스택이 1일 때
  한 번만"으로 걸면 4번째 사이클에 다시 1이 되어 **영구 버프가 중복 적립**된다.
  원시 카운터(`_burst_stage_one_entries`)를 따로 두고 그쪽을 읽어야 한다.
- **닿는 이유(엔진):** `on_tier_fire`가 `own_burst_activate` → `ally_burst_activate`를
  먼저 쏘고 **그 다음에** 버스트 넉을 기록한다. 셋 다 같은 타임스탬프이고 레지스트리는
  `applied_at <= time`으로 걷으므로, stage-N 버프는 그 캐스트의 버스트 대미지에 들어간다.

## "버스트 N단계 진입 시"를 `own_burst_activate`로 인코딩하면 좌석을 나눌 때 조용히 샌다

- 확립: 2026-07-27 (신데렐라 검증 중 발견). 마스트 취기(1단계)에서 나온 판정과 **같은
  규칙**인데, 그때는 스택 카운터였고 이번엔 트리거 자체다.
- **원칙:** "Activates when entering Burst Stage N"은 **단계**에 대한 서술이지 시전자에
  대한 서술이 아니다. 그 사이클에 **누가** 그 티어 슬롯을 가져가든 일어난다. 따라서
  `ally_burst_activate` + `burst_stage_entered(N)`으로 걸어야 한다. 엔진의
  `squad_engine.burst_stage_entered` 독스트링이 이미 이 문장을 그대로 담고 있다 —
  "Using `own_burst_activate` instead would silently drop those cycles."
- **왜 오래 안 들켰나 — 틀린 근거가 코드에 명시돼 있었다.** `snow_white_heavy_arms.py`가
  선례 검토까지 적어두고 이렇게 결론냈다: *"her Burst Skill is fixed at position 3
  (a game attribute, not a deck-configurable seat), that's every cycle she reaches
  Full Burst."* **이 문장이 틀렸다.** 버스트 위치가 고정인 것과 그 사이클에 그녀가
  실제로 쏘는 것은 다른 얘기다 — **B3를 2기 앉히면 둘이 번갈아 쏜다.** 실측: 신데렐라 +
  스노우화이트:헤비암즈 편성에서 11사이클이 **6/5로 갈린다**.
- **증상의 서명:** B3 단독 편성에서는 **정확히 무변화(1.0000x)**, 좌석을 나누면 커진다
  (신데렐라 1.0727x). 그래서 단일-B3 셸로만 A/B하면 **영원히 안 보인다** —
  `sweep_slug_damage.py`의 tier3 셸이 바로 그 모양이다.
- **잔존(2026-07-27 기준, 신데렐라만 수정됨):** 원문에 이 표현을 쓰면서 아직
  `own_burst_activate`인 유닛 **6기** — `ein`(Feather Standby) · `maiden-ice-rose` ·
  `mast-romantic-maid`(**3단계** 불릿, 1단계 스택 카운터는 별건으로 이미 수정됨) ·
  `mint` · `rei-ayanami` · `snow-white-heavy-arms`(Shades of White). 정상 처리된
  선례는 `flora-signature`(`burst_stage_entered` 사용)와 `rei-ayanami`의 Attack
  Support(스쿼드 범위라 `full_burst_enter`로 처리 — **범위가 self가 아니면 답이
  다르다**). 유닛마다 **불릿 단위로** 확인이 필요하다: 같은 파일의
  `own_burst_activate`가 전부 이 표현인 것은 아니다.
- **찾는 법:** 수집 데이터에서 `Activates when entering Burst (Skill )?Stage (\d)`를
  훑고, 걸린 슬러그의 모듈에 `burst_stage_entered`가 없는데 `own_burst_activate`가
  있으면 후보다(현재 9기 적중, 인코딩된 것 7기).

## "탄약 N발 소모"는 탄창이 아니라 **장부**다 — 실탄은 1발만 나간다

- 발견: 2026-07-19 (신데렐라 스나이프 모드) / 배선: 2026-07-26 (리틀 머메이드 캘리브레이션)
- 벨벳 "파우치에서 300발 소모", 신데렐라 스나이프 "40발 소모" — **실제로 발사되는
  총알은 1발**이다. N은 **소모량 연동 시너지를 먹이기 위한 회계 수치**다. 이걸
  탄창 소모로 읽으면 발사 속도가 틀리고, 반대로 **무시하면 소모량 카운터가 굶는다.**
- 이 장부를 먹는 소비자는 실재한다: 리틀 머메이드 버블 배러지(아군 총 500발마다
  85%×10히트) · 버블 오더(400발마다 버스트 게이지 37%) · 신데렐라 크리스탈 웨이브
  (200발마다 게이지 12%). 즉 **한 유닛의 회계 표기가 다른 유닛의 딜을 결정한다.**
- 규모: 벨벳은 188초에 **129발**밖에 안 쏘지만 장부에는 **약 31,500라운드**를 올린다.
  총알로 세면 카운터에 0.9% 기여, 라운드로 세면 **약 70%** 기여다. 배러지 28회 → 89회.
- 배선 방법: 슬러그 → `(풀버스트 중 라운드, 풀버스트 밖 라운드)` 2튜플
  (`registry._AMMO_ROUNDS_PER_SHOT`). 시뮬레이터가 `context.shot_ammo_rounds`를
  `context.shot_times`와 **평행한 리스트**로 채운다. 창별로 갈리는 이유는 벨벳의
  **파우치 스킬이 두 개**여서다 — 풀버스트 안은 Bullets of Love(300), 밖은
  Sticky Fingers(100). 스칼라 하나로는 표현이 안 된다.
- 함정: 한 샷이 **여러 임계값을 동시에 넘을 수 있다**(1,200라운드 = 500짜리 배러지 2회).
  `while expended >= next_barrage` 루프여야 하고, `for i in range(threshold-1, n, threshold)`
  같은 인덱스 스텝은 총알 카운터에서만 맞는다.
- 전수 조사: 수집된 로스터에서 "expends ... round(s)" 표기를 가진 유닛은
  **벨벳과 신데렐라: 크리스탈 웨이브 둘뿐**이다. 새 유닛을 인코딩할 때 이 문구가
  보이면 레지스트리 테이블에 추가할 것.

  그래서 실기록 대조 스크립트는 죽지 않고 **틀린 로스터로 조용히 돌아간다.**
- 해법: 싱크 스크립트에 `SYNCED_FILES`를 추가했다. 워크트리에서 측정을 시작하기 전에
  `python3 scripts/sync_worktree_data.py`를 먼저 돌릴 것 — `--check`는 exit 1로 알려준다.
- 일반 교훈: **폴백은 편의를 위해 만들지만, 측정 스크립트에서는 침묵하는 오류가 된다.**

## "Damage to Parts"와 "Damage to Interruption Parts"는 **다른 대상**이다 — 이름이 거의 같아서 반드시 오독된다

- 발견: 2026-07-26 (Fienn이 helm 스킬2 "포문 개방"의 한글 원문을 읽다가 지적)
- **"저지 부위 공격 대미지"(Damage to Interruption Parts)** 는 **기믹 수행 시 타격해야 하는
  구역**의 딜을 올린다. **"파츠 대미지"(Damage to Parts)** 는 **파괴 가능 파츠**의 딜을
  올린다. 이름이 거의 같지만 **가리키는 타겟이 아예 다르다.** 한글 표기는 확실히
  구분되는데("저지 부위" vs "파츠") 영문은 `Interruption`이라는 단어 하나 차이라,
  영문 데이터만 보고 인코딩하면 거의 확실히 뭉개진다 — 실제로 뭉개져 있었다.
- 로스터를 원문으로 갈라보면 정확히 반반이다:
  - **Interruption Parts (저지 부위)**: `helm`(Fire Away, 스쿼드 상시) ·
    `noir`(Finale, 스쿼드 10s+30s) · `anis-sparkling-summer`(자기, 10s) ·
    `rapi-red-hood`(자기, 10s)
  - **Parts (파괴 가능 파츠)**: `rosanna-chic-ocean` · `cinderella-crystal-wave`(Destroy
    모드) · `snow-white-heavy-arms` · `raven`(Vital Attack, defer 중)
- 이 오독이 왜 조용했나: 여덟 유닛이 **전부 같은 스탯 `damage_to_parts_up`에 써넣고**
  있었고, 엔진은 그걸 일반 Damage-Up 버킷에 넣어 모든 타격에 곱했다. 두 개념을
  구분하든 안 하든 수치가 같으니 아무도 볼 이유가 없었다. **몸통 딜에서 이 항을
  뺀 뒤에야**(같은 날의 별도 판정) 두 스탯이 서로 다른 미래를 갖게 됐다.
- 해법: 스탯을 분리한다(`damage_to_interruption_parts_up` 신설). **둘 다 몸통 딜에는
  안 붙으므로 지금 수치는 1도 안 변한다** — 이 작업의 가치는 전적으로 "다음 사람이
  파츠를 실제 타겟으로 모델링할 때 잘못된 네 유닛을 합치지 않게 하는 것"이다.
  회귀 테스트 `test_parts_vs_interruption_parts.py`가 유닛별로 어느 쪽인지 고정한다.
- 일반화: **한글 표기가 영문보다 구분이 명확한 경우가 있다.** 인코딩 근거를 영문
  데이터에서만 뽑으면 이런 구분이 통째로 사라진다 — 값이 아니라 **대상**이 의심스러울
  때는 한국 서버 원문을 확인할 것([[korean-service-naming]]와 같은 이유).

## 시뮬레이터를 실측에 대조할 때 판정 기준은 배율이 아니라 배율의 **편차**다 — 그리고 "함의된 파라미터" 역산이 캘리브레이션과 모델 오차를 갈라준다
- Fienn의 두 시즌 전 솔로레이드 실기록 5덱을 그대로 시뮬에 넣었더니 합계 **1.46배 과대**였다. 여기서 "1.46로 나누면 되겠다"로 가면 안 된다 — **덱별 배율이 0.93x~2.00x로 흩어져 있었고**, 순위는 편차만 보기 때문이다. 당시 추천이 주장하던 우위는 +9.9%로 **오차 폭보다 작았다**. 총량 편향은 랭킹에서 상쇄되고 편차는 랭킹을 파괴한다는 것은 `scripts/measure_unmodeled_damage_share.py`가 이미 세워둔 잣대와 같은 원리다.
- **캘리브레이션 오차와 모델 오차를 가르는 방법: 의심되는 파라미터가 데미지에 선형으로 들어간다면 역산하라.** 코어 히트 보너스는 major modifier에 가산되므로 총딜이 코어 히트 비율 f에 선형이다(`total(f) = off + f*(on-off)`). 그래서 각 덱의 실기록이 함의하는 f를 풀 수 있었고 결과는 **52% / 10% / 28% / 2% / 117%**였다. **하나가 100%를 넘는 순간 "전역 노브" 가설은 죽는다** — 어떤 값을 넣어도 다섯 덱이 동시에 맞지 않으므로, 남은 것은 모델 자체가 덱마다 다르게 틀렸다는 결론이다. 노브를 UI에 다는 것은 모델 오차를 유저 입력으로 위장하는 짓이다.
- **부호가 반대인 이상치 하나가 가장 정보량이 크다.** 다섯 덱 중 넷이 과대(1.26~2.00x)인데 하나만 **과소**(0.93x)였다. 그 하나를 파고든 것이 Moran Fervor 쿨감 누락(풀버스트 6회 대 실제 12.5초 사이클)을 잡아냈고, 고친 뒤 그 덱은 1.15x로 **나머지와 같은 방향**으로 정렬됐다. 전부 같은 방향으로 틀린 오차는 투자 드리프트 같은 공통 원인으로도 설명되지만, 방향이 다른 것은 반드시 구조적 결함이다.
- **실측 대조는 유저의 로스터가 그때 이후로 자랐다는 사실을 반드시 같이 적어라.** 여기서 남은 1.08배 중 얼마가 모델 오차이고 얼마가 투자 성장인지는 분리되지 않았다. 분리하지 않은 채로 1.08을 "거의 맞음"이라고 부르면 다음 사람이 그 숫자를 기준선으로 쓴다.
- 재현: 진단 하네스는 실기록 5덱을 `feasible_orderings`로 최적 배치해 채점하고, 같은 덱을 `core_hittable` on/off로 두 번 돌려 f를 역산한다. `docs/decisions.md`의 "코어 데미지는 평타 전용이다" 항목 참조.

## refreshing 버프는 "스킬 불릿" 단위로 묶여야 한다 — 유닛 단위로 묶으면 남의 버프를 지운다

- 발견: 2026-07-21 (Fienn이 Liberalio의 Raging Current 작동 여부를 점검 요청)
- `EffectRegistry.add_refreshing`이 `(stat, source_slug, scope)`가 같은 **모든**
  활성 효과를 truncate했다. 의도는 docstring에 적힌 대로 "한 소스의 재적용을 합치는
  것"이었지만, 키가 **유닛**이라 **같은 유닛의 다른 스킬**까지 잡아먹었다.
- 증상이 지독한 이유: **조용하고, 큰 쪽이 죽는다.** Liberalio는 자기
  `attack_damage_up`을 두 불릿에서 주는데(영구 231% + 매 풀차지 refreshing 20.83%),
  첫 샷에서 231%가 등록되자마자 같은 샷의 20.83%가 그걸 duration 0으로 잘랐다.
  테스트는 전부 통과했다 — 각 불릿을 따로 보면 맞게 동작하기 때문이다. 유닛 단위
  테스트로도 안 잡히고, **두 불릿이 한 시뮬에서 만나야만** 드러난다.
- 해법: `Effect.refresh_group`(옵셔널) — `refreshing_buff_rule` 인스턴스마다 하나.
  `RoundGrant.cap_group`(2026-07-20, Zwei 스택 캡)과 **정확히 같은 형태의 문제이고
  같은 해법**이다. 그룹이 없으면 기존처럼 묶이므로 충돌이 없던 소비자는 불변.
- 파급: 77 슬러그 중 **75개의 딜이 변했다**(전부 상승 — 옛 동작은 살아있어야 할
  버프를 지우는 방향으로만 틀릴 수 있다). Liberalio +132.6%, ark-ranger-black +44%,
  snow-white-heavy-arms +33.6%. 넓은 +4~17% 꼬리는 대부분 **Crown** 때문이다:
  같은 날 추가한 Royal Attire(refreshing 스쿼드 AD)가 그녀 자신의 Last Kingdom
  버스트 버프(36.24%)를 매번 지우고 있었다.
- 교훈: **새 refreshing 버프를 추가할 때, 그 유닛이 같은 (stat, scope)를 다른
  불릿에서도 주는지 반드시 확인할 것.** 안 그러면 새 인코딩이 기존 인코딩을
  조용히 무효화한다.
- **후속 감사 (2026-07-21, 역방향 점검): 옵셔널 그룹으로는 부족했다.** 위 수정은
  `refreshing_buff_rule` 경로만 덮었고, 손으로 쓴 `add_refreshing` 호출부는 전부
  그룹을 안 붙여 **하나의 "무그룹" 양동이**를 계속 공유했다. 게다가 그 양동이에는
  평범한 `registry.add`로 넣은 효과까지 들어간다 — refreshing 불릿이 절대 건드리면
  안 되는 것들이다. **Grave가 Liberalio와 똑같은 버그를 그대로 안고 있었다**:
  Overheat I의 영구 자버프 ATK +15.48%(`add`)를, 창(window) 한정 Overheat II의
  refreshing ATK +20.66%가 첫 발동에서 잘라 없앴다. 기존 테스트가 못 잡은 이유는
  **Overheat I과 II를 서로 다른 registry에서 검증**했기 때문 — 한 registry에 같이
  넣어야만 드러난다.
- 최종 해법: **`add_refreshing`은 이제 `refresh_group`이 없으면 `ValueError`를 던진다.**
  한 사례를 고치는 대신 이 버그 부류 자체를 도달 불가능하게 만든 것 — 불릿 이름을
  붙이는 게 호출자의 명시적 결정이 되고, `add`로 넣은 효과는 group `None`을 유지하므로
  어떤 refresher도 그걸 무너뜨릴 수 없다. 유닛의 연속 버프를 자기 트리거로 **일부러**
  끝내는 경우는 별도의 `truncate_open_ended`를 쓴다.
- 그룹 부여 단위가 중요하다: 헬퍼는 **룰 인스턴스마다**, `escalating_buff_rule`은
  **티어마다**(티어는 누적이므로 같은 stat을 주는 두 티어는 합쳐져야지 서로를 대체하면
  안 된다), `raid_simulator`의 resource-fill 버프는 **spec마다**.
- 영향: 72개 슬러그 스윕에서 **Grave 단독 +1.07%**, 나머지 71개 불변. 수정이 표적만
  건드렸다는 증거다. 이 A/B는 `scripts/sweep_slug_damage.py`로 재현한다(고정 셸에
  대상 유닛 한 명씩 넣어 측정 → `--compare before.json after.json`).

## E2E 딜 측정 셸은 대상 유닛과 같은 버스트 티어를 포함하면 안 된다

- 발견: 2026-07-21 (Zwei 무기변형 인코딩의 영향이 **정확히 0%**로 측정됨)
- 사이클마다 **티어당 한 명만** 버스트한다. 측정용 고정 셸에 대상과 같은 티어의 유닛이
  있으면 그 유닛이 버스트 슬롯을 가져가고, 대상의 **버스트 발동 효과는 통째로 측정되지
  않는다**. Zwei(B1)를 liter+volume(둘 다 B1)이 든 셸로 재니 그녀의 burst 이벤트가

- 조용한 실패다: "변화 없음"은 "영향 없음"과 구분이 안 간다. 세그먼트가 시뮬레이터까지
  배선됐는지 확인하고 나서야 셸이 원인임이 드러났다.
- 부분적 왜곡도 생긴다. Nayuta(B2)를 crown(B2)이 든 셸로 쟀을 때는 0%가 아니라 **과소평가**

  뺏긴 경우다.
- 해법: `scripts/sweep_slug_damage.py`는 이제 **대상의 티어에 따라 셸을 고르고, 그 셸은
  나머지 두 티어에서만 뽑는다**(`SHELLS`). 부수 효과로 측정 대상이 72 → **77 슬러그**로 늘었다
  (셸 멤버도 자기가 안 든 셸에서 측정되므로).
- 교훈: 버스트 로테이션이 있는 시뮬레이터에서 **A/B 측정 하네스는 그 자체로 검증이 필요한

## 버스트가 DPS 손해인 유닛이 있다 — 무기변형 세그먼트를 넣는 게 오히려 부정확할 수 있다

- 발견: 2026-07-21 (Modernia의 New World Destroy Mode 세그먼트 인코딩 시도 중, Fienn 판정)
- Modernia의 버스트(New World)는 **보스전에서 순손해**다: Destroy Mode 평타 2.24%가 base MG
  7.71%보다 훨씬 낮고, 멀티타겟 auto-aim은 "stage target을 파츠 무관 단일 취급"이라 무가치.
  그래서 실전 운용은 **버스트 미사용** — (1,1,3) 맨 오른쪽에 앉혀 평타로만 딜(Fienn).
- 함정: 무기변형 프리미티브가 있다고 Destroy Mode를 세그먼트로 넣으면, 엔진이 버스트를 강제해
  실전에 없는 Destroy Mode를 발동시킨다 → Modernia ~12% 저평가(스윕 확인). **세그먼트가
  "정확한 무기 모델"이지만 "정확한 유닛 운용"은 아니다.**
- 통찰: 버스트 미사용 유닛은 버스트로 발동하는 모든 것(변형·무한탄약·버프)이 실전에서 발동 안
  하므로, **아무것도 안 넣은 base 무기 상태가 오히려 정확한 근사**다. Modernia의 버스트는 이미
  `([], None)`(nuke·버프 전무)이라 현재 상태가 버스트 미사용 딜러에 가깝다.
- 정확한 표현은 `burst_delay`에 `skip_cycles: float("inf")`를 줘 영구 미사용으로 만드는 것.
  실험상 (1,1,3)에서 대상 버스트 0회 + 나머지 B3 2명 로테이션 유지가 확인됐다(B3 ≥2명 보장).
  단 `sweep_slug_damage.py`의 tier3 셸은 대상이 유일 B3라, skip 시 B3 버스트가 없어 Full Burst가
  붕괴 → 측정 불가. 스윕 셸 재설계가 얽힌 아키텍처 작업이라 후속으로 분리.
- 교훈: **엔진 프리미티브가 표현 가능하다는 것과, 그 표현이 유닛의 실제 최적 운용과 맞다는 것은
  별개다.** 무기변형을 넣기 전에 "이 유닛이 실제로 그 변형을 쓰는가"를 먼저 물어라.

## 같은 버스트 bullet이 변형과 데미지타입 변환을 함께 걸면, 변환은 세그먼트에 `damage_type`으로 고정하라 — 별도 효과에 의존하지 말 것
- 발견: 2026-07-22 (Takina Inoue의 Suppression Initiated 인코딩)
- 문제: Takina의 버스트는 한 bullet에서 (a) 무기를 200.64%/발 급사무기로 변형(10초)하고 (b) 그 10초 동안 평타를 진댐으로 변환한다. 이 변형샷이 곧 그녀의 버스트 중 평타이므로, 세그먼트 발사를 기존 self `normal_attacks_deal_true` 효과의 폴백(`normal_attack_type`)에 맡기면 논리적으로 맞아 보인다.
- 함정: 효과 활성 구간은 **우측 배타적** `[applied_at, applied_at+duration)`(effects.py `_is_active`)이다. Fienn 실측 25발을 `until_shots: 25`로 넣으면 마지막 발이 정확히 t=burst+10(=창 끝)에 놓여 변환 창 **밖**으로 떨어진다 → 25발 중 1발이 진댐이 아닌 일반딜로 잘못 타이핑.
- 해결: 세그먼트 프로파일에 `damage_type="true"`를 **직접 고정**한다. 변형과 변환이 같은 bullet·같은 10초라 이 샷들이 진댐인 것은 인과적으로 확실하므로, 경계에 취약한 별도 효과에 기대는 것보다 직접 서술이 정확하다. 변형이 버스트 중 평타를 전부 대체하므로(창 안에 base 샷 없음) 이제 잉여가 된 self `normal_attacks_deal_true` 효과는 제거했다 — "모델된 것처럼 보이나 소비자가 없는 효과"를 남기지 않는다.
- 일반화: **측정 발수가 있으면 `until_shots`(정확), rate×duration 유도는 `end`**. `end` 방식은 `start + k*interval < seg_end` 조건이라 마지막 발이 경계에 딱 걸리면 드랍된다 — Takina를 `end`로 넣었으면 25발이 아니라 24발이 됐다(laplace base가 `end`를 쓴 건 실측 발수가 없어 유도값이었기 때문).

## `supported_units()` must resolve a slug's metadata the same way `load_nikke_spec` does

## 드래프트 완성 비용은 좌석 수에 반비례한다 — 그리고 축소 품질을 검증하는 잣대는 "제약이 적을수록 좋아야 한다"이다
- 발견: 2026-07-25 (`best_completions` 예산화, `backend/app/deck_search.py`)
- **직관과 반대다.** 드래프트가 덜 찰수록 완성 방법이 많아지므로 탐색이 **비싸진다**. 실제 77유닛 로스터(B1 13/B2 17/B3 47) 실측: 좌석 5개 = 4순서, 4개 = 372, 3개 = 10,835, 2개 = 126,513, **1개 = 1,830,670**(8워커 ~6.5시간). 완성 드래프트를 기준으로 성능을 재면 가장 싼 케이스만 보게 되고, 유저가 가장 먼저 닿는 "칩 하나" 경로가 무응답이라는 것을 못 본다. **드래프트 경로 성능은 가장 얇은 드래프트로 재라**(`scripts/measure_thin_draft.py`).
- **축소(프루닝/캐스케이드) 품질을 검증하는 잣대: 드래프트는 제약이므로 좌석이 적을수록 결과가 좋거나 같아야 한다.** 좌석 N개의 답은 좌석 N-1개 문제의 유효한 해이기도 하므로, 좌석 1개가 좌석 2개보다 낮게 나오면 그건 제약의 대가가 아니라 **탐색 결함**이다. `prune_candidate_pool`만 붙였을 때 정확히 이 위반이 나왔다(좌석1 36.73B < 좌석2 42.99B, 14.6% 낮음). 총딜 절대값만 보면 "드래프트를 지켰으니 그럴 수 있다"로 넘어가기 쉽다 — 좌석 수를 늘려가며 단조성을 보는 것이 결함을 드러낸다.
- 왜 얇은 드래프트가 축소에 더 취약한가: 좌석이 적을수록 완성 유닛 5개 중 더 많은 수(좌석 1개면 4개)를 축소 풀에서 뽑는다. `prune_candidate_pool`은 **드래프트가 없는 레퍼런스 덱**에서 한계 기여만 재므로 그 recall 오차에 그만큼 더 노출된다. 캐스케이드(더 넓은 풀 + 덱 전체 랭킹)는 이 노출을 상쇄한다 — 자유 덱에서는 선택이던 것이 완성 경로에서는 필수가 되는 이유.
- 함정: 축소 풀이 **완성을 하나도 못 만들 수 있다**(어떤 티어에 남은 후보가 전부 드래프트된 유닛의 MODE_VARIANTS 형제인 경우 등). 이때 빈 결과를 그대로 반환하면 `allocate_decks`가 `InfeasibleDraft`를 던져 **플레이어가 실제로 낼 수 있는 편성을 "불가능"이라 말한다**. 전수 경로로 되돌아가는 것이 맞다 — 느린 것이 틀린 것보다 낫다.

## Raid decks are unordered — match result decks to a submitted draft by slug overlap, never by array index
- 발견: 2026-07-22 (draft-based deck allocation, `DraftResults` per-deck diff, fixed in `68e5e8f`)
- `recommend_from_draft` (and `allocate_decks` underneath it) picks `_better(scratch, warm)` for the `recommended` tier, and `scratch` may fully repartition the roster into decks that don't correspond 1:1 with the player's submitted deck groupings — deck labels/positions are arbitrary (same boss, same scoring either way), so "deck 1" in the result has no necessary relationship to "deck 1" in the draft.
- 함정: a naive "per-deck diff vs. what the user submitted" that zips result decks against submitted decks by array index will compare unrelated decks whenever the optimizer reshuffles membership across deck boundaries, producing a diff that's nonsensical (e.g. showing a deck's damage change as if it kept the same 5 units when it didn't).
- 해법: match each result deck to the submitted deck it overlaps most with by slug set intersection, not by index, before computing a per-deck diff.

## Damage formula
- **The attack/skill coefficient scales the whole Base Damage, not the ATK stat.** A normal attack's "% of ATK" or a skill's "X% of final ATK" multiplies Base Damage *after* defense is subtracted — pass raw summary ATK plus a separate `attack_coefficient` to `calculate_damage`. Folding the coefficient into ATK mis-scales the defense subtraction and any flat ATK (~14% overstatement against a defended boss, and unevenly across Nikkes since coefficients range from ~5% normal attacks to ~8000% bursts, which would skew deck rankings). See `damage_formula.calculate_damage`.

## Performance (EffectRegistry)
- **`_stat_bundle`-style memos keyed on a global `version` counter are only safe in phase 2 — in phase 1, per-shot mutations churn `version` every call, so every bundle lookup misses and rebuilds, costing more than it saves.** Tried wiring `normal_attack_type` (a phase-1 stat, read while shots are being generated and rules are firing) into the phase-2 `_stat_bundle` memo — Stage 0.5's gain collapsed from 23% to 6% (133.66ms → 125.07ms) because every phase-1 call bumped `registry.version` and invalidated the very bundle it was trying to reuse. Reverted to a direct single-stat `total_for` lookup for `normal_attack_type`, which restored the full 23% gain (→ 103.43ms). Rule: **`_stat_bundle` is phase-2 only** — see the warning comment above `_stat_bundle` in `raid_simulator.py`. Any future stat added to `_BUNDLE_STATS` must be confirmed phase-2-only (read only during damage computation, not during shot/rule generation) before being added.
- **Bit-identical performance refactor pattern: freeze a naive reference implementation, preserve float-addition order, and cross-check with a parity net.** Requiring "bit-identical," not "approximately equal," output from a performance rewrite (Stage 0's segment-table `EffectRegistry.total_for`) needs three things: (a) a frozen copy of the original naive implementation committed with a "do not modernize" comment, so it can't drift out of sync with the fast path it's meant to validate; (b) preserving the ORIGINAL summation order (effect insertion order, not chronological order — float addition is non-associative, so re-ordering can flip the last bit); (c) a parity-net test that runs both implementations against the full test suite plus dedicated mutate/query interleaving cases, not just a handful of hand-picked spot checks. Side benefit: the test suite itself got 3× faster (22s → 6.5s) as a byproduct, since many tests exercise `total_for` heavily. See `docs/decisions.md` ("Stage 0: EffectRegistry rewritten to per-(stat, slug, element) segment tables...").
- **Two mathematically-equivalent float expressions can differ by 1 ULP — a "bit-identical" parity fixture set needs an odd/ugly value, not just round numbers, to catch it.** Unifying every unit's weapon-shot generation onto the new segmented generator (`docs/decisions.md`, "Weapon-mode segments v1...") required rewriting `_base_shot_records`' magazine-shot-time arithmetic from `(i + 1) * effective_charge` to `effective_charge + i * effective_charge`. The two are algebraically identical but not bit-identical under IEEE-754 (float multiplication doesn't distribute over addition in floating point) — the regression was invisible against the existing `SR_BASE`/`AR_BASE` fixtures (`charge_time=1.0`/`0.0`, both exact binary values with nothing to round), and only surfaced once a fixture with no exact binary representation (`SR_ODD`, `charge_time=1.19`) was added specifically to stress it. Rule of thumb: a bit-identical parity net needs at least one "ugly" float per input dimension being refactored, or it can pass while the code underneath is subtly wrong. See `backend/tests/test_attack_rate.py`'s `SR_ODD`, and the "Bit-identical performance refactor pattern" bullet above for the sibling Stage 0 case this generalizes.
- **The epoch superset invariant is what makes bundling multiple stats into one memo safe: the union of every matched Effect's boundaries (`state_epoch`) is itself the superset of each individual stat's own boundaries, so within one epoch ALL bundled stats are simultaneously constant.** `EffectRegistry.state_epoch(target, time)` collapses every stat's own boundary-time set (for effects matching that target) into one combined timeline. Because it's a union (not an intersection or a single stat's own boundaries), any two instants inside the same epoch segment are guaranteed to see identical values for every stat in the bundle — not just the one the epoch happens to be named after. This is the correctness argument for `_stat_bundle` memoizing 17 stats behind one epoch+version key instead of one key per stat. See `docs/decisions.md` ("Stage 0.5: epoch + stat-bundle memo...").

## Crit
- **Crit is expected value, not per-hit RNG.** The major modifier gains `crit_rate*(0.5 + crit_damage_sources)`. Base crit rate is 15%, base crit damage +50%; both buff types are additive. Crit-damage buffs are inert with no crit chance. See `damage_formula._major_modifiers` and `raid_simulator.BASE_CRIT_RATE` (overridable via `base_crit_rate`, set 0.0 for deterministic tests).

- **`pierce_damage_up` is a general damage-up term.** It's applied to every hit, not gated to actual pierce hits — a known simplification.
- **Caster-scaled buffs use the base character-info ATK.** "ATK X% of caster's ATK" multiplies the caster's base ATK (gear + breakthrough + cube only; excludes overload and other skill effects), modeled as `flat_atk` via `values["caster_atk"]`, which `roster.assemble_simulation_inputs` injects.
- **Steady-state approximation for ramping buffs.** Escalating "previous effects trigger repeatedly" or "stacks up to N" effects are encoded at their max/settled value — a 3-minute raid reaches it almost immediately. Documented per module. **Valid specifically when the fill cadence far exceeds the stack's own decay/reset window** — check the numbers, don't assume: Quency's Explore Route stage chain (3 stages, each gated on the previous being AT its cap) fills every 2 normal attacks, and her SMG fires 20/s, so each stage's ~0.1s fill cadence is far faster than any stage's own 0.5-2s decay window — once a stage first caps, it stays capped continuously for the rest of the fight, making the real ~2.5s ramp-to-full negligible against a 180s raid. - **A buff re-applied on every trigger (per-shot/periodic) silently STACKS unless you opt into refreshing.** `EffectRegistry.total_for` sums all active effects, and `buff_rule`/`registry.add` adds a fresh instance each time, so a multi-second-duration buff re-applied on every qualifying shot (e.g. "ATK +X% for 3s on every Full Charge") overlaps and sums — inflated a real unit's numbers ~2x (SR fire rate) to ~13x (AR fire rate) over a fight before this was caught. If the in-game wording is a duration refresh (not an actual stacking counter), use `refreshing_buff_rule` (`EffectRegistry.add_refreshing`) instead — it truncates that source's still-active same-`(stat, scope, refresh_group)` instance rather than stacking a new one. The `refresh_group` (one per rule instance, required) is what keeps it from also truncating the SAME unit's other buffs on that stat — see the refreshing-buff section at the top of this file. See `skill_rules/prika.py`, `skill_rules/mint.py`.
- **"For N round(s)" is a bullet-count duration, not seconds or a burst cycle — confirm with Fienn whenever a duration unit is ambiguous.** Easy to misread as continuous uptime or a per-cycle refresh; it actually means the buff is consumed by the affected ally's next N normal-attack shots, then gone (re-granted next cycle). Modeled via `round_buff_rule`'s `RoundGrant`, not a live `Effect` — see `docs/decisions.md` ("Bullet-count round buffs...") and `nikke-skill-encoding/references/special-mechanics.md` ("For N round(s) is a bullet-count duration") for the mechanism.
- **A skill's stated ammo/round cost can be pure ACCOUNTING for a consumption-counting synergy elsewhere, not actual magazine drain — check what the unit really fires, not what the text charges other counters for.** Cinderella: Crystal Wave's Snipe full charge reads "expends 40 rounds," but the unit fires ONE round per full charge (Fienn's ruling, 2026-07-19) — the same accounting-only pattern as Velvet's ammo pouch. `cinderella_crystal_wave.py`'s Snipe weapon profile fires a real single-round SR shot; the 40-round figure is unconsumed here (it only feeds the deferred burst-gauge-fill mechanic). - **The timed-Effect-with-window-to-next-shot trick lets a shot-count buff reuse the existing seconds-based `Effect` + `total_for`, with no new duration primitive.** `applied_at` = the first covered shot's time; `duration` = (next-uncovered-shot time − applied_at), or fight end if there is no later shot. Reusable pattern for any future "expires after N shots" mechanic. See `raid_simulator`'s shot loop, `round_buff_rule`.
- **RoundGrant→Effect conversion runs as a SECOND pass after ALL units' shot loops (gap #9 refactor) — not interleaved per-unit.** Originally each unit's round grants were converted right after that unit's own shot loop; the gap #9 (first-bullet marker) work moved this to a separate loop over `shot_times_by_slug` that runs once every unit's shots are generated (`raid_simulator.py`, the `for slug, shot_times in shot_times_by_slug.items(): for grant in registry.round_grants():` block). This means a grant recorded by a PER-SHOT rule (not just a burst-cycle trigger) — e.g. Jill Valentine's Magnum first-bullet grant — now converts correctly too, since per-shot rules only run during the (now-earlier) shot loop and couldn't previously be converted inline within that same pass. Burst-cycle-trigger grants (Zwei, Miranda) are unaffected/byte-identical, since those grants already exist before any shot loop runs regardless of which pass converts them.
- **A quantity-based resource must be a FUNCTION OF TIME, not a mutable running total — otherwise it breaks across the two-phase pipeline.** Fills can arrive from the burst-cycle phase (burst / battle-start) AND the shot-loop phase, and the burst cycle runs first, so a counter that accumulates as events are processed would see all burst fills before any shot fill — wrong time order. Instead record fills as `(time, amount)` events and compute `resource_count(time, cap, lifetime)` on demand (like `total_for`/`top_atk_slugs`/`burst_times`). Phase-order-safe because a query at time t only sums fills with `fill_time ≤ t`. See `SquadContext.resource_count`.
- **A count-scaled buff is emitted as a step function of DELTA Effects, so `total_for`'s running sum reproduces `value_fn(count)` at every time — including for TIMED stacks that decay.** Walk the fill/expiry events; at each, add an `Effect(value − prev_value, duration=None)`. Permanent stacks give all-positive deltas that plateau at the cap; timed stacks emit negative deltas as they expire (window = `(t − lifetime, t]`). No truncation bookkeeping, no new registry concept — reuses `add`/`total_for`. A shot sees its OWN fill (inclusive `≤ t`), matching the existing per-shot-rule convention. See `raid_simulator`'s resource resolution pass, `effects.ResourceSpec`/`ResourceBuff`.
- **Resolve boss-dependent fill rates in the sim, not the unit encoding.** Guillotine's EXP fills every 3 Core hits on a core-hittable boss but every 6 normals otherwise. Rather than thread `core_hittable` through `assemble_simulation_inputs`, the `("per_shot_every_core", core_n, noncore_n)` fill kind is resolved by `raid_simulator`'s own `core_hittable` — the boss property stays out of the unit module. Same spirit as gating `other_core_damage_sources` on `core_hittable`.
- **A resource-scaled nuke's percent must resolve in phase 2, not when the nuke is recorded.** A burst-fired nuke gated/scaled by a named resource's count (Julia's Climax additional hit, Cinderella's mirrored hit, Guillotine's Extermination DoT) is recorded during `on_tier_fire` — but the resource's fills aren't populated until the resolution pass runs, which happens AFTER the whole burst cycle. Calling `context.resource_count(...)` at record time would always see zero. Fix: `record()` carries an optional `resource_gate` (name/cap/lifetime/scale_fn) that's resolved into a concrete percent in phase 2 via `context.resource_count(ev["slug"], name, ev["time"], cap, lifetime)` — the same "record now, compute later" trick already used for every other damage instance. A repeating DoT tick just records one event per tick, each independently resolved at its OWN time, so a resource still accumulating mid-DoT correctly raises later ticks. See `docs/decisions.md` ("Resource-scaled nukes resolve their percent in phase 2...") and `raid_simulator`'s `resource_scaled_nukes`.
- **A burst that "attacks sequentially N times" is N separate damage instances, not one instance at N×percent.** Defense is a FLAT per-hit subtraction (`_base_damage`), so splitting into N hits changes the total whenever `enemy_def > 0` — pre-multiplying the percent would overcount (defense only subtracted once instead of N times). `burst_hit_counts` records N identical events at the same instant. See Cinderella's Glass Slippers (10x), Julia-signature's Climax (5x).
- **A burst-fired BUFF gated on a resource has no "phase 2" to defer to, unlike a nuke — so it must be resolved IN the resolution pass itself, not at `on_tier_fire`.** A resource-scaled/gated NUKE can record now and compute its percent later (`resource_scaled_nukes`, above) because every damage instance in this engine is already record-now/compute-later. A buff has no equivalent second pass: `buff_rule`/`registry.add` mutate the registry immediately when the trigger's action runs, and `on_tier_fire` (where a burst's rules fire) runs BEFORE the resolution pass that populates the resource's fills/resets for that cycle — so a gate check done at `on_tier_fire` time would always see a stale or empty resource. Fix: process `resource_gated_buffs` inside the resolution pass itself, once the resource's full fill/reset schedule for the whole fight is known, iterating `context.burst_times[slug]` for each of the owner's own burst times and adding the Effect directly. First/only consumer: Soda's ATK+65.25%/15s (gated on Golden Chip's pre-reset count >= 30). See `docs/decisions.md` ("Resource resets... and `resource_gated_buffs` resolve in the resolution pass...").
- **Same-instant event ordering must be preserved by checking inline against the event log as you walk it, not by merging two independently-sorted lists.** A resource fill mode conditioned on BOTH a global event stream (any squad member's burst-tier fires, Full Burst starts) AND the resource's own running value (Maiden's MP: "+1 if MP==0 on any squad Burst 1", "+1 if MP>=1 on Full Burst enter") needs to know, at each instant, whether the resource's own reset (from its owner's own burst) has already happened relative to that instant's other events. Sorting the reset events and the burst-cycle events separately and merging by timestamp risks an arbitrary tie-break at equal timestamps. Instead, `_resolve_squad_burst_cycle_resource` walks `simulate_burst_cycle`'s own event log in order and checks the owner's own-burst reset inline against each event as the walk reaches it — so same-instant ordering is exactly what the underlying event log already encodes, not a second-order artifact of the merge. This mattered concretely: Fienn confirmed burst1->burst2->burst3->full-burst-enter is a strict, never-violated sequence, so a unit's own burst-tier fire always precedes Full Burst entry in the same instant — which is what makes Maiden's MP-drain-then-refill sequence resolve deterministically (and, as a consequence, makes her second MP-fill rule a provable no-op **when she's the sole Burst-3 unit** — sharing the tier with another Burst-3 attacker breaks the invariant, see the `own_burst_fired_this_cycle()` bullet below and `docs/decisions.md`).
- **A ZERO-LENGTH weapon-mode segment is an INSTANT magazine refill — the same trick as the zero-shot segment below, with the window collapsed to a point.** `_segment_shot_records` returns `cursor = seg["start"]` when `start == end`, and the overlap guard is `seg["start"] < cursor` (strict), so a zero-length segment neither fires a shot nor consumes time nor trips the guard — even two at the same instant are legal. The next stretch then restarts the base weapon with a fresh magazine at that exact time. Scarlet: Black Shadow's Asura ("Reload 100% of the magazine(s)" on Full Burst entry) is encoded this way. Note the charge-weapon consequence and why it keeps the encoding a FLOOR: `_base_shot_records` fires a charge weapon's first shot one charge-time after the window start, so the reset discards any charge in progress — every modeled shot time is at or after its real one. Measured on Scarlet: +17.8% own damage and +10.3% sequence procs, while her total shot COUNT fell by 2, because the refill moves shots inside her burst window where her sequence requirement is cut.
- **A "stacks up to N" buff measured in ROUNDS needs an explicit cap — `RoundGrant` has no stack semantics, and the overflow only shows up on charge-weapon recipients.** A round grant becomes one Effect per recipient covering that recipient's next N shots, so concurrent grants simply sum. For a fast magazine ally that is self-limiting (they fire faster than the granter, never holding more than one), but a charge weapon (RL/SR) idles through a reload and its first shot afterwards collects every grant that accumulated meanwhile — Zwei's "stacks up to 3" Pierce Equation was landing 5 on that shot. The fix is an opt-in `cap` + `cap_group` on `RoundGrant`, enforced per recipient in the conversion pass, keeping the most recent `cap` (matching a full stack pushing the oldest out, and never extending the buff past where the uncapped version had it). Two things this teaches beyond the bug: a stack cap expressed in rounds is invisible until a slow-cadence recipient exists, and "grants sum" is only accidentally correct when every recipient outpaces the granter.
- **A weapon-mode segment that fires NOTHING is the engine's "discard the magazine and reload" — you do not need a firing-timeline primitive to model a forced reload.** `_base_shot_records` regenerates the base weapon per stretch, restarting with a FRESH magazine at each stretch's `window_start` (the post-transform resume semantic). That means a segment boundary already truncates whatever is left in the current magazine, and a segment covering exactly the reload window with no shots of its own reads as "ammo dumped here, reloading, fresh magazine after". Milk: Blooming Bunny's "Removes 100% of ammo + Forced Reload" is encoded this way, and engine-gaps #11 ("forced reload state machine", sized 중~대) collapsed to that plus two small pieces. Use `rate_of_fire` rather than `charge_time` for the empty profile: explicit-rate profiles deliberately take NO cadence buffs, so an ally's Charge Speed buff cannot shrink the interval enough to leak a phantom shot into the window. Verified end to end — shots stop before the window, none land inside, and the base resumes one charge-time after it ends.
- **Reload SPEED and reload TIME are reciprocal mirrors, and the engine only modeled one direction for a long time.** `reload_time / (1 + speed)` is right for a buff (+50% → 1/1.5x) but doubles the reload at -50%, where the game actually adds half (Milk's "reload speed fixed at a 50% reduction" is 3s against her 2s base, not 4s — Fienn, 2026-07-20). `attack_rate.reload_time_with_speed` now branches: `base / (1 + s)` for `s >= 0`, `base * (1 - s)` for `s < 0`. This lay dormant because every consumer until Milk buffed reload speed UPWARD — worth remembering as a shape: a formula can be wrong in a direction nothing has exercised yet. The negative branch rests on one in-game observation, so it is anchored, not proven across magnitudes.
- **A buff whose duration is "until this unit's next own burst" cannot be applied from an `own_burst_activate` rule — that rule runs while the burst-cycle walk is still deciding future bursts.** `context.burst_times` is only complete after `simulate_burst_cycle` returns, so at `on_tier_fire` time the next burst literally does not exist yet. `burst_anchored_buffs` (with the `UNTIL_NEXT_OWN_BURST` duration sentinel) resolves these after the walk but BEFORE the shot loop, which matters: buffs landed there are visible both to shot generation (max ammo / reload / cadence callables) and to phase 2's damage bundles, unlike the resource-driven buff passes further down that run after the timeline is already fixed. First consumer: Milk's Embarrassment state, which only her next burst clears.
- **"After/every N CRITICAL hits" has no per-hit event to count — but it is representable as an EXPECTED-crit accumulator, which is what `per_shot_rules`' `every_n_critical_hits` mode does (2026-07-20; supersedes the earlier "permanently deferred" ruling).** The engine treats crit as expected value (every hit's damage scaled by `crit_rate * (0.5 + crit_damage)`), never rolling per-hit RNG — so there genuinely is no "was this specific shot a crit" event, unlike a plain normal-attack or full-charge counter. Encoding Julia's signature Crescendo/Marcato this was read as a permanent structural limit; encoding EVE showed the counter can instead be converted the same way the damage path already converts crit: each shot contributes the unit's crit rate at that instant to a running total, and the trigger fires whenever the total crosses N (remainder carried forward). **The load-bearing detail is that the rate is read PER SHOT, not folded into a fixed shot threshold at build time** — Fienn's condition for accepting the conversion at all (2026-07-20) was that deck crit buffs must move the cadence, and a build-time `N / own_crit_rate` would silently ignore every ally crit buffer. Two caveats: shot loops run per unit, so a crit buff applied by a LATER-processed ally's own per-shot rules isn't visible (burst / full-burst-triggered ones are, which covers the usual crit buffers); and the crossing test needs a `1e-9` tolerance, since summing a rate like 0.3 ten times lands at 2.9999999999999996 and would push a proc a whole shot late. Julia's signature Crescendo/Marcato was encoded the same day on the same accumulator - but note it needed a SECOND consumer shape: Crescendo is a CAPPED stack, which `per_shot_rules` cannot express, so the resource fill `("per_critical_hit_every", N)` was added alongside the per-shot mode. Both call `_expected_crit_positions`, deliberately, so the two paths cannot drift. See `skill_rules/eve.py`, `raid_simulator.py`'s `every_n_critical_hits` branch.

See `skill_rules/maiden_ice_rose.py`.

This is intentional, not an oversight — widening the during filter to match would double-count a boundary shot in both tallies. The result is a narrow, currently-inert gap: a shot at exactly a window's end boundary is claimed by neither filter. Only matters if a future per-shot consumer needs a boundary-instant shot counted one way or the other — check which filter (or neither) currently claims it before assuming. See `raid_simulator.py::_resource_fill_times`, `docs/decisions.md` ("The outside-Full-Burst per-shot filter is closed on the right...").
- **`every_during_segment`/`every_outside_segment` must match a shot by record IDENTITY (shot index), not by shot TIME — a magazine weapon's segment-resume boundary can put two different records at the exact same timestamp.** These modes exist to make double-counting between a transform's empowered attack and its normal attack structurally impossible (first consumer: Snow White: Heavy Arms's Auto Fire, boosted inside her Fully Active segment, plain outside it). The first implementation matched by comparing each `ShotRecord`'s `time` against pre-computed during/outside time sets, and it silently double-fired: when a magazine-type base weapon (AR/MG/SMG/SG) resumes after an `until_shots` segment ends, `attack_rate.py`'s documented resume semantic starts the fresh magazine's first shot AT the segment's own end instant — so the segment's last `ShotRecord` (`in_segment=True`) and the resumed magazine's first `ShotRecord` (`in_segment=False`) can share one timestamp, which a time-keyed lookup can't tell apart, firing BOTH modes at that instant. Fixed by pre-computing the fire sets as shot-INDEX sets instead (`raid_simulator.py`'s `window_fire_indices`, commit `dfd48cb`), which are inherently per-record. **Charge weapons cannot hit this bug**, which is why the original exclusivity test (built against an SR) passed despite it: a charge weapon's resumed first shot always lands one full charge-time AFTER the segment ends, never coincident with it. Any future segment-boundary test for a magazine-type weapon needs an explicit boundary-collision case — reusing a charge-weapon fixture will not exercise it. See `test_raid_simulator.py`'s `test_per_shot_every_during_segment_and_every_outside_segment_stay_exclusive_at_a_shared_time`.
- **[2026-07-27: 이 예외가 일반 원칙으로 승격됐다 — 반복 틱뿐 아니라 연산 시각을 알 수 있는 모든 인스턴스에 적용된다.]**
- **For repeating-tick DoTs, `full_burst_bonus_eligible` should default to True — the text-phrase check is specifically a single-instant-nuke heuristic.** The "as additional damage" phrase (above) is a proxy for a TIME-based fact: damage NOT computed at the cast instant, landing inside a Full Burst window, gets the bonus. Mana's Fatal Error! (a flat `resource_scaled_nukes` DoT, see below) confirmed this in-game — it gets the Full Burst Bonus even though its text says "as sustained damage," not "as additional damage." For a single-instant nuke, cast-time-vs-delayed is genuinely ambiguous from text alone, so the phrase check is still the right call there. For a repeating-tick DoT, every tick after the first is inherently computed strictly after cast "by construction," independent of wording — so assume `full_burst_bonus_eligible=True` by default for any `resource_scaled_nukes` consumer (subject to checking the DoT's duration doesn't obviously outlast the Full Burst window), rather than requiring the phrase. `resource_scaled_nukes` gained the same opt-in flag `record()`/`dynamic_hit_count_nukes` already had, to make this possible. Not yet retroactively applied to Guillotine's Extermination Hero-Level DoT (earlier consumer, predates this capability) — open follow-up. See `skill_rules/mana.py`, `docs/decisions.md` ("full_burst_bonus_eligible generalizes beyond the 'as additional damage' text phrase for repeating-tick DoTs").
- **A resource-scaled repeating nuke's `"resource"` key is optional — omit it for a flat, non-scaled repeating DoT.** `resource_scaled_nukes`' tick_count/tick_interval loop is genuinely two features bundled together (repeating ticks + resource-based percent scaling); when a unit only needs the repeating-tick shape (Mana's Fatal Error!, a flat 396%/sec DoT), leave `"resource"` out rather than inventing a dummy always-full resource just to satisfy a previously-mandatory field. See `raid_simulator.py`'s `resource_scaled_nukes` loop.
- **A burst nuke that fires on a DELAY (not at cast time) needs `fire_delay` + a matching `"own_burst_delayed"` reset — don't assume every burst effect lands instantly.** `dynamic_hit_count_nukes`' optional `fire_delay` fires the nuke (and reads/reset its resource) at `burst_time + delay`; `ResourceSpec.resets` supports `"own_burst_delayed"` with its own `delay` so a resource's own reset lands at that same delayed instant, not at burst time. First/only consumer: Asuka's Annihilation nuke (fires 9s after her burst, when her "Annihilation State" self-status ends). Don't reuse the zero-delay default and hope it's close enough — a mistimed nuke changes which Full Burst window (if any) it falls in for `full_burst_bonus_eligible` purposes.
- **A resource fill window can be anchored to the OWNER's own burst-fire time, not just the squad's global Full Burst window.** `("per_shot_every_during_own_status_window", n, window_duration)` counts shots toward an "every n" tally only within `window_duration` seconds of one of `context.burst_times[slug]` — distinct from the earlier `per_shot_every_during_full_burst` (anchored to `full_burst_windows`, a squad-global instant). Needed whenever a unit's own short self-status window (e.g. Asuka's 9s Annihilation State) starts at HER burst, not at Full Burst start, which is a different instant. See `raid_simulator.py`'s resource fill resolution.
- **A `scheduled_nukes` "attach now, explode later" pair must let attachments ACCUMULATE across multiple attach events landing before the same explosion — one attach event does not mean one explosion event.** Rapi: Red Hood's Attachable Projectiles (Fienn's confirmed semantics, 2026-07-19): every time her normal-attack counter reaches the requirement, a projectile attaches (counter resets) and stays pending; every pending attachment explodes TOGETHER — one explosion hit per attachment, defense subtracted per hit like any other multi-hit burst — the next time the squad enters Full Burst. `build_attachable_projectiles_scheduled_nukes` (`skill_rules/rapi_red_hood.py`) computes this as two schedules sharing one derivation: the attach schedule walks `context.shot_times[slug]`; the explosion schedule maps each attach time to the first `start` in `context.full_burst_windows` strictly after it, so N attachments accumulated before the next FB entry correctly emit N separate damage instances at that one instant. Her Stage 3 burst lowers the attach requirement by 60 for 10s via a live window check (`context.burst_times[slug]`) inside the same attach schedule, not a separate mechanism.
- **`charge_speed_percent`/`attack_speed_percent` are only evaluated once per MAGAZINE BOUNDARY — a short-lived Effect window can silently be inert or over-apply.** Both callables (`attack_rate.py`'s `_at(t)` pattern, threaded through `generate_shot_times`/`generate_charge_shot_times`) are read once at each magazine's start, not per-shot. A speed-change Effect whose window is shorter than a magazine either (a) never lands at all, if granted mid-magazine (no boundary falls inside it — confirmed by `test_one_round_charge_speed_grant_is_inert_mid_magazine`), or (b) slows/speeds the ENTIRE next magazine, if it happens to cover a boundary — neither matches literal "for N seconds"/"for 1 round" semantics. Don't model a short-lived charge/attack-speed grant literally; fold its intended time cost/benefit into a damage-bonus approximation instead (Ada Wong's Special Modification: the ×4 charge-time slowdown that can't land is folded into a reduced net `charge_damage_bonus`, `15/4 − 1 = +2.75` — see `docs/decisions.md`, "Ada Wong: Special Modification's charge-speed half..."). Check this trap before encoding ANY unit that pairs a short-duration charge/attack-speed grant with another buff meant to offset its cost.

- **A magazine-boundary "last bullet" marker is the shot at index `magazine_size - 1`, re-derived from the SAME live `max_ammo_percent_at` callable already used to size each magazine — this is what makes [Max Ammo Up] "just work" with zero extra plumbing.** `attack_rate.magazine_last_bullet_times`/`charge_last_bullet_times`/`last_bullet_shot_times` mirror `generate_magazine_shot_times`/`generate_charge_shot_times`/`generate_shot_times`'s exact 3-tier structure (2 raw-parameter functions + 1 weapon-dispatching wrapper) instead of changing those functions' return shape to carry the marker inline — an additive sibling set avoids breaking any of `test_attack_rate.py`'s existing assertions on a flat list of shot times. General pattern worth reusing: when a new per-shot marker needs to piggyback on existing shot-generation math, mirror the function's tier structure as new functions rather than reshaping its return type. Correctness edge case: a magazine truncated by `fight_duration` ending (not actually emptied) must NOT be marked last — handled by construction, since "is_last" checks the recorded round's INDEX against `magazine_size - 1`, not whether it's the last round appended to the output list. See `docs/decisions.md` ("Magazine-boundary 'last bullet' marker mirrors the existing shot-generation function shape").
- **Attack/charge speed change shot CADENCE, not magazine CAPACITY, so they're structurally irrelevant to any magazine-boundary feature — and neither is wired as a shot-interval modifier anywhere in this engine anyway.** Shot cadence is fixed, computed once from `RATE_OF_FIRE_60FPS`/`charge_time` and never re-read from the registry (both stats are on the "Stats the engine does NOT consume" list). Even if they were modeled, they'd shift WHEN shots land, not HOW MANY rounds fit in a magazine — only `max_ammo_percent` determines magazine size. Confirmed while building the last-bullet marker above: no special-casing needed for attack/charge speed, and none should be added speculatively.
- **A passing unit test that manually calls `fire_trigger("some_name", ...)` doesn't prove `raid_simulator` ever fires that trigger for real.** Helm's Frontline Command last-bullet Crit Rate buff had a passing test built by invoking `fire_trigger("on_last_bullet_hit", ...)` directly — but `on_last_bullet_hit` isn't one of the engine's real trigger names (only `battle_start`/`own_burst_activate`/`ally_burst_activate`/`full_burst_enter`/`full_burst_end` are dispatched by `simulate_raid`'s actual event loop), so the rule silently never fired in any real simulated raid despite its own unit test being green. A test that manually fires a trigger only proves the rule's ACTION logic is correct in isolation, not that anything in the real engine ever calls it with that name. Worth grepping other modules for `fire_trigger("<name>"` calls whose `<name>` isn't in the real trigger list. Fixed by rewiring to `per_shot_rules`' `"last_bullet"` mode instead (a different mechanism entirely — checked directly against per-shot loop state, not dispatched via `fire_trigger` at all). See `skill_rules/helm.py`.
- **A live time-window check against `context.burst_times[caster]` is the fallback when a self-granted status's duration doesn't line up with `own_burst_fired_this_cycle()`'s per-cycle semantics.** `own_burst_fired_this_cycle()` (see Burst rotation, below) works as a status-equivalence trick specifically because the status lasts the WHOLE cycle until the next reset (Asuka/Mana). Privaty's "Designated Target" (set by her burst, lasting a fixed 10s against her own 40s burst cooldown) is a genuine fraction of the cycle, not the whole thing — so it's instead checked as `any(bt <= time < bt + duration for bt in context.burst_times[caster_slug])`, evaluated fresh at the querying shot's own time, inside the per-shot rule's action. Reusable whenever a self-granted status has a real timed window shorter than the caster's own burst cycle. See `skill_rules/privaty.py`.
- **Unconfirmed default: a same-instant self-applied debuff is assumed to affect its own triggering hit's damage, and repeated triggers within the debuff's window are assumed to STACK (not refresh).** Privaty's LD Assault adds its squad Damage Taken debuff via plain `registry.add` (not `add_refreshing`) at the same instant as the hit that triggers it — under the engine's default same-instant-inclusive Effect semantics this means (a) that hit's own damage already reflects the debuff it just applied (same-instant self-reference, like Soda/Cinderella's confirmed precedent, unlike Maiden's confirmed-opposite case), and (b) two last bullets within 10s of each other produce two separate summed debuff instances rather than one refreshed value. Neither is verified in-game — it's just what the engine defaults to absent contrary evidence, the same open-item status Maiden's self-buff-timing question had before Fienn confirmed it in-game. Flag for future in-game verification. See `skill_rules/privaty.py`'s module docstring.
- **A `SkillRule`'s action has no access to the boss's element unless it's threaded onto `SquadContext` — `boss_is_element(element)` is the condition helper for "if the enemy is X Code" bullets.** `raid_simulator` injects `SquadContext.boss_element` from `BossProfile.element` (deck_search already passes this end-to-end); `boss_is_element(element)` (`squad_engine.py`) mirrors the existing `ally_bursted`/`deck_contains` condition-helper pattern rather than gating inside each action (which would duplicate the check across modules). `buff_rule`/`refreshing_buff_rule`/`instant_nuke_pulse_rule` all gained an optional `condition` param so a gated bullet reuses the same builder as an ungated one. First consumers: Brid: Silent Track (Wind debuffs), Helm: Aquamarine, Marciana: Marine Study. See `docs/decisions.md` ("Gap #5: boss_element context...").
- **`boss_is_element` composes with any per-shot mode — a per-shot nuke/buff can be boss-element-gated (and even window-gated) at once.** A per-shot rule's `SkillRule.condition` is honored in every `per_shot_rules` mode (`after`/`every`/`last_bullet`/the window-gated modes), so nothing extra is needed to combine a boss-element gate with a shot-count or window trigger. Marciana's High-Risk 20-normal nuke is a plain `every 20` gated on `boss_is_element("Electric")` (the "High-Risk Target state" is treated as maintained whenever the boss is Electric, so it's NOT windowed — Fienn 2026-07-16).
- **`enemy_def_percent` was fully specified in `damage_formula` but silently inert until gap #5 — `raid_simulator` never read it from the registry.** Wired as `enemy_def_percent=registry.total_for("enemy_def_percent", target, time)` in `_damage_instance`, emitted as a squad-scope enemy debuff exactly like `damage_taken_up`. No DEF=0 floor clamp exists yet — none of the currently-encoded units' debuffs are large enough to need one (boss DEF 31784 stays positive against the largest current DEF-down, Marciana's 10.56%) — add a clamp if a future unit's debuff risks it. First consumer: Marciana: Marine Study's "High-Risk Target" DEF ▼ debuff, but the wire moves damage for every attacker against every deck now that it's live, not just her. See `docs/decisions.md` ("Gap #5...").
- **Solo-raid global assumptions**, adopted encoding Marciana and applicable to any future encoding: Rapture count is always 1 (the boss) — "N or fewer Raptures" conditions are always met, "N or more Raptures" (N>1) bullets never fire; boss DEF = 31784 is the `enemy_def` value to use for solo-raid sims (`BossProfile.enemy_def` defaults to 0.0, so callers must set it explicitly); "Flagged Target" / "highest Max HP enemy" = the boss (the single/highest-HP enemy in a raid). See `docs/decisions.md` ("Gap #5...").

- **The `per_shot_rules` pass runs AFTER `simulate_burst_cycle` has already fired every burst-cycle trigger — so a burst-cycle rule (`battle_start`/`own_burst_activate`/`full_burst_enter`/`full_burst_end`) cannot read a counter or status that a per-shot rule builds.** `raid_simulator.simulate_raid` calls `simulate_burst_cycle` first (firing all four burst-cycle trigger types against the current context), then runs the `per_shot_rules` pass afterward. A burst-cycle rule that tries `context.activation_count(...)`/`context.has_status(...)` for something only a per-shot rule increments will see the pre-per-shot value (typically zero), not the real end-of-cycle count. Concretely: if a buff's VALUE depends on a running normal-attack count AND another burst-cycle rule must read that count (Arcana: Fortune Mate's Keepsake Album, fired on `full_burst_end`, reads the Precious Moments stack that would naturally be built from "6th normal attack" shot-counting), the count must instead be built in the burst-cycle pass — e.g. increment once per Full Burst on `full_burst_enter` via `record_activation`/`activation_count`, not by counting shots directly. This substitution is only valid when the normal-attack threshold is guaranteed reached exactly once per relevant window (an exact per-cycle equivalence, not an approximation onto the wrong trigger) — Fortune Mate's SG fires far more than 6 shots in a 10s Full Burst window, so "6th normal during Making Memories" and "once per Full Burst" coincide exactly. Contrast: the resource-scaled/gated NUKE path (`resource_scaled_nukes`, `resource_gated_buffs`, above) IS deferred into a later resolution pass, so a nuke scaled by a per-shot-built resource count works fine — but a buff added directly to the registry via `registry.add` inside a burst-cycle rule's action does NOT get that deferred resolution; it reads the context synchronously, at the time the burst-cycle pass runs. See `raid_simulator.py` (the `simulate_burst_cycle` call followed by the `per_shot_rules` pass) and `skill_rules/arcana_fortune_mate.py::gain_precious_moments`/`apply_keepsake_album` for the worked example.

- **"Every 1 sec for N sec" is N ticks, not N+1** — the established convention (mana's `drop_tokens`/`resource_scaled_nukes` batching) applies unchanged to a repeating DoT elsewhere in the kit: Diesel: Winter Sweets' "63.33% of final ATK every 1 sec for 9 sec" DoT and her burst's 9-tick 1s DoT (`skill_rules/diesel_winter_sweets.py`) are both `tick_count=9`, not 10.
- **A charge weapon (RL/SR) fires a full charge on EVERY shot, so a "on full charge" trigger needs no separate full-charge counter — it's just `per_shot_every 1`.** Diesel's "Full Charge stacks (3s, cap 2)" buff is `("per_shot_every", 1)` feeding a `ResourceSpec(cap=2, lifetime=3.0)`, since every RL shot already IS a full charge. And a stack with both a CAP and a LIFETIME needs `ResourceSpec` specifically — `buff_rule` (infinite stacking) has no cap, `refreshing_buff_rule` (1-stack refresh) has no cap above 1, so any capped-stack mechanic (here: her 1s charge time holds both stacks inside one magazine, and the 2s reload lets one expire) should reach for `ResourceSpec` rather than either buff-rule helper.

## 버스트 사이클에는 "N단계 진입"이라는 별도 이벤트가 없다 — `[버스트 N단계 진입 시]`는 **그 티어의** `ally_burst_activate`다

> **⚠ 이 절의 인코딩 규칙은 2026-07-27에 뒤집혔고 제목도 2026-07-29에 고쳤다.**
> 옛 규칙("그 유닛의 `own_burst_activate`로 인코딩하라")은 **결함의 원인**이었다 —
> 그대로 따른 `ein`과 `laplace-ultimate-hero`를 2026-07-29에 고쳤고, 후자는 이 절이
> 모범 사례로 인용하던 바로 그 유닛이다. 아래 본문은 정정본이다.

Fienn의 정본 로테이션은 `게이지 충전 → 1단계 진입 → B1 사용 → 2단계 진입 →
B2 사용 → 3단계 진입 → B3 사용 → 풀버스트 10초`지만, 엔진(`burst_cycle.py`)은
"진입"과 "사용"을 하나로 접는다 — `on_tier_fire(tier, slug, time)`이 곧 "BN
사용"이자 그 티어의 진입이다. **풀버스트는 그 뒤 `FULL_BURST_OPEN_DELAY`만큼
늦게 열린다**(`full_burst_start = tier3_fire_time + 1e-6`) — 한때 두 시각이 같아서
`full_burst_enter`가 stage-N 불릿의 대역으로 우연히 맞았고, 그 우연이 사라지면서
이 절의 옛 규칙이 무너졌다.

버프가 넉에 닿는지는 두 가지가 결정한다:
1. `effects.py`의 active-window는 **시작 포함**(`applied_at <= now < applied_at
   + duration`).
2. `raid_simulator`는 record-then-compute라, 넉 데미지는 2단계에서 **넉 시각
   기준 라이브 버프**를 읽는다 — 워크 도중의 등록 *순서*는 무관하고 오직
   버프 시작 시각 vs 넉 시각만 중요하다.

따라서 (`tests/test_burst_cycle_buff_timing.py`가 고정한 결과):
- **B3 유닛의 자기 버스트 넉**: `full_burst_enter` 버프도 `own_burst_activate`
  버프도 **둘 다 닿는다**(동시각 + 시작 포함). 수치적으로 동등.
- **B1/B2 유닛의 자기 버스트 넉**: `auto` 모드는 티어 간 gap이 0이라 동시각 →
  `full_burst_enter` 버프가 닿지만, **`manual` 모드는 티어 간 0.1초 간격이라
  B1 넉이 `full_burst_enter`보다 0.2초 먼저 발생 → 못 닿는다.**

**인코딩 규칙 (현행):** 스킬텍스트가 `[버스트 N단계 진입 시]`라고 말하면
**`ally_burst_activate` + `burst_stage_entered(N)`으로 인코딩하라.**
그 문구는 **단계**에 대한 서술이지 시전자에 대한 서술이 아니다 — 그 사이클에 누가
그 티어 슬롯을 가져가든 일어난다. 트리거가 넉 기록보다 먼저 발동하므로, 그 유닛이
직접 쏜 사이클엔 **여전히 자기 버스트딜에 곱해진다**(잃는 것이 없다).
`full_burst_enter`는 진짜로 "풀버스트 창 진입"이 조건인 효과에만 쓴다 — 그것은
캐스트보다 **뒤**의 순간이라 B3의 자기 버스트딜에 못 닿는다.

**옛 규칙이 든 이유 (b)는 정확히 거꾸로였다.** "같은 티어의 다른 유닛이 대신
버스트한 사이클에 지급되는 것"을 **과대지급이라 불렀지만, 그것이 정답이다.**
`own_burst_activate`로 걸면 그 사이클을 통째로 잃는다 — B3를 2기 앉히면 대략 절반이고,
실측으로 에인 덱 **−3.81%** · 라플라스(UH) 덱 **−1.12%**였다.
이유 (a)(B1/B2는 manual 모드에서 `full_burst_enter`가 자기 버스트딜을 놓친다)는
여전히 유효하지만, 그 대안은 `own_burst_activate`가 아니라 위의 stage 배선이다.

**2026-07-24 확장 (Flora 애장품):** 아래 "스코프가 실제 판별 기준" 규칙은
**Stage 3 = Full Burst 진입**이라는 전제 위에 있다(`full_burst_enter`가 정확히
tier-3 발동 시각과 같으므로 "스쿼드 스코프 → `full_burst_enter`"가 성립).
Stage 1/2에는 대응하는 스쿼드 스코프 이벤트가 없어 이 규칙이 적용되지 않는다 —
Flora(B2)의 Petunia 불릿("Burst Stage 2 진입 시", 스쿼드 스코프)이 그 사례다.
`own_burst_activate`는 다른 B2가 슬롯을 가져간 사이클을 놓치고, `full_burst_enter`는
애초에 잘못된 이벤트(Stage 2 ≠ Full Burst)라 둘 다 못 쓴다. 해법은 신규 조건
`burst_stage_entered(tier)` + `ally_burst_activate`(모든 유닛 룰에 발동해 캐스터
자신의 사이클도 커버) — 자세한 내용은 `docs/decisions.md`("Burst Stage N 진입"은
own_burst_activate가 아니라...) 참고.

**스코프가 실제 판별 기준이다** (`snow_white_heavy_arms.py` docstring이 이미
명문화한 선례): 같은 "Burst Stage N 진입" 문구라도 —
- **자기 스코프** → `own_burst_activate` ("그 유닛이 곧 그 티어 슬롯이므로 그
  순간이 자기 버스트 발동"). 선례: `cinderella`(Flawless Glass),

## Burst rotation
- **A state-machine unit's state must be asked "decided by WHAT" before picking a modeling trick — a static mode slug lies the moment the deciding axis is one the engine actually simulates.** If the axis is something the engine does NOT simulate (Bready's Taste: which buff TYPE she receives), a static `MODE_VARIANTS` slug is enough — nothing in the sim depends on it. If the axis IS something the engine simulates (Diesel: Winter Sweets' Intro/Highlight lock depends on whether she bursts into the FIRST Full Burst — a real burst-schedule fact), a static slug is a lie: labelling her "Highlight" while still letting her burst on cycle 1 credits her the Highlight buff (235.03% vs Intro's 60.19%, ~4x) without ever paying the cost of skipping that burst. Fixed by making the Highlight slug actually skip that cycle via `burst_delay: {"skip_cycles": 1}` (see `docs/decisions.md`, "Diesel: Winter Sweets를 Intro/Highlight 2슬러그로 인코딩"), so the state-defining action is really taken, not just claimed. Ask this question first for any future locked-state unit.
- **A per-member burst delay (`burst_cycle.py::_ready_at`) lets a deck-search-driven sim represent a unit the player deliberately holds back, in three shapes that fold into one ready-time calculation:** `{"skip_cycles": N}` excludes the unit from the opening N cycles (returns `float("inf")` until then — Diesel, above); `{"not_before": T}` holds it until wall-clock T (Elegg: Boom and Shock, below); `{"min_interval": S}` stretches its effective cooldown to S whenever a refilling resource is slower than the cooldown itself (also Elegg). All three route through the same `_ready_at`, so tier selection and eligibility keep identical arithmetic regardless of which delay a member carries. A delayed unit left alone in its tier simply never bursts that cycle rather than firing early to "make something happen" — deliberate, since `ALLOWED_SHAPES` (`(1,1,3)`/`(1,2,2)`/`(2,1,2)`) never actually produces a lone-delayed-member tier in Burst 3 (always ≥2 members), so this can't silently zero out a real deck.
- **A resource that refills on WALL CLOCK must be measured from the unit's actual fire time, not the CDR-rewound cooldown timestamp.** `burst_delay`'s `min_interval` (Elegg: Boom and Shock's 13 Ghosts — caps at 13 stacks for a 13-hit branch vs 6-hit below cap; her real cadence is `spend_at_cap * capture_interval` = 54s, which outlasts her 40s cooldown) is measured against a SEPARATE timestamp, `last_fired_at`, that mirrors `last_used_at` but is never rewound by an ally's CDR pulse. Using the CDR-rewound `last_used_at` instead shortened her 54s refill window to 39s across 3 bursts in an early build — allied cooldown reduction speeds up HER cooldown but does nothing to how fast her ghosts actually refill, so the timer that represents the resource must be immune to the timer that represents the cooldown. Both `not_before` (her first cap: `cap * capture_interval` = 78s) and `min_interval` are derived from her own skill values in `skill_rules/elegg_boom_and_shock.py::build_elegg_burst_delay`, not hardcoded measurements — see `docs/decisions.md`.
- **`own_burst_fired_this_cycle()` doubles as an equivalence trick for "on FB enter while in [a self-status my own burst just granted]" — no new status-tracking needed.** Both Asuka's Emergency Repair (Skill 2, "on FB enter while in Annihilation State") and Mana's Metal sigma (Skill 2, "on FB enter while in Metal sigma status, consumed then restored by her own burst") describe a continuous named self-status gating a Full-Burst-entry buff. Because this engine's strict burst1→burst2→burst3→full-burst-enter ordering means a unit's own tier-3 burst always fires immediately before full_burst_enter in the SAME cycle, "her own burst fired this cycle" (the already-existing `own_burst_fired_this_cycle()` condition, previously used by Grave/Arcana for a full_burst_END gate) is exactly equivalent to "her self-granted status is still active" at the instant full_burst_enter checks it — for any deck this engine can simulate (one attacker per burst tier). Reuse this condition directly on a `full_burst_enter` trigger for any future unit with this shape, rather than building real `set_status`/`clear_status` bookkeeping. See `skill_rules/asuka_shikinami_langley_wille.py`, `skill_rules/mana.py`.
- **"Who bursts vs who buffs" = deck left-to-right order.** `burst_cycle` fires the leftmost eligible Nikke per burst tier, so the intra-tier ordering *is* the role assignment. The deck search explores those orderings. See `burst_cycle.py`.
- **Cycle timing waits for the slowest tier's cooldown.** The next Full Burst starts when whichever burst tier's cooldown clears latest (the gauge always charges faster than cooldowns for a raid-viable deck). A cycle is only "missed" when a burst tier is structurally absent from the deck, not when cooldowns lag.
- **`activation_count` starts at 0 — guard alternating-parity statuses against the pre-first-activation state.** A skill that alternates between two statuses each burst (e.g. Mint: Dancing on her 1st burst, Singing on her 2nd, ...) is naturally modeled as `count % 2 == 0` for the "even" status, but count 0 (before she has ever burst) also satisfies that — wrongly treating the unit as already in the even status from t=0. Guard with `count > 0`. See `skill_rules/mint.py::_mint_is_singing`.
- **Precise "highest final ATK" targeting must rank at APPLICATION time, using live buffs — not a static/squad approximation.** `SquadContext.top_atk_slugs` ranks the deck by each unit's ATK as buffed so far, evaluated when the targeting rule fires. This matters because of the same tier-ordering fact above: a Burst-1 unit's own burst (`own_burst_activate`, tier 1) fires before her Full-Burst-enter skill (tier 3), so by the time her FB-enter targeting rule runs, her own burst's ATK buff is already applied and correctly reflected in the ranking — dynamic (not pre-computed) resolution handles this automatically. See `skill_rules/miranda.py`, `nikke-skill-encoding/references/special-mechanics.md` ("Highest-final-ATK top-N targeting").
- **A per-shot/periodic condition sees the FINAL context, not a live one — timestamp alternating statuses instead of checking `has_status`.** Record-then-compute's post-pass evaluates every shot's condition against the whole-fight-final `SquadContext`, so `activation_count`/`has_status` there answer "at the end of the fight," not "at this shot's time." For a status that alternates or gets pinned mid-fight (Mint's Singing), record when it's true instead: `SquadContext.burst_times` (per-unit burst-tier fire times) + `status_since`/`set_status(..., time=...)` (earliest-set timestamp), then compute the status AT a given time (`skill_rules/mint.py::mint_singing_at`) rather than querying it live. This is what let solo Mint's per-cycle Dancing/Singing alternation finally be modeled (previously deferred as untrackable under per-shot).

## Deck search
- **Intra-tier order is a role assignment, not a tie-break — a deck search must score every ordering of a combination, not refine a canonical-order shortlist.** `simulate_burst_cycle` fires the FIRST ready member of each burst tier, so who sits leftmost within a tier decides who actually bursts and who becomes a buffer/normal-attacker that never does (a (1,1,3)'s rightmost Burst 3 commonly never bursts, Prika must precede Mint for her Encore hand-off, Velvet/Helm: Aquamarine are usually seated silent — see "Who bursts vs who buffs" below). Ranking a shape combination on one arbitrary ("canonical") order and only permuting a top-K shortlist by that score therefore mis-ranks the field twice over: once for the combinations scored on their wrong order, and again for any combination whose true value never made the shortlist at all. Measured on real data: up to 78% low, with the true best (1,1,3) landing outside a top-40 shortlist entirely (rank #21 under canonical scoring). `search_best_decks` now scores every intra-tier ordering of every combination (`_all_intra_tier_orderings`); `sim_budget` counts orderings, not combinations, since that's what the sims actually cost. See `docs/decisions.md` ("Deck search now scores every intra-tier ordering per combination...") and `backend/scripts/measure_intra_tier_ordering_impact.py` (reusable — rerun after touching `burst_cycle` or deck-search scoring).
- **`prune_candidate_pool`'s internal reference decks are decks too — they must satisfy the same legality invariants as decks the search actually returns, or the candidate pool they select from is silently wrong.** Landing mode-variant dual slugs (`docs/decisions.md`, "Mode-variant dual-slug expansion...") exposed this the hard way, over four separate follow-up fixes (commits `2eb7490`..`487aa25`): a reference shell could seat two variants of one base (missed because reference-deck construction calls `evaluate_deck` directly, bypassing the real candidate path's `_no_variant_clash` check); a cross-tier variant sibling (a `MODE_VARIANTS` pair spanning `VARIANT_BURST_TIERS`, e.g. Rapi: Red Hood's B1↔B3 pair) could displace the reference's only occupant of a DIFFERENT tier during swap-in, since the swap-in logic only checked same-base clashes, not cross-tier occupancy; and refusing an illegal swap outright silently starved the candidate at a permanent 0.0 score instead of falling back to measuring it against a legal alternative reference. The durable lesson: any new roster-shape rule (a clash constraint, a sole-occupant constraint, a cross-tier tie) must be threaded through the pruning heuristic's OWN internal deck construction, not just the search's real enumeration paths — the two are easy to keep in sync at the time a rule is written and easy to let drift the moment a second rule is added. See `docs/decisions.md` ("Rapi: Red Hood's Combat Assist branch is now a real Burst-1 candidate...") and `backend/app/deck_search.py`'s `_reference_deck`/`_variant_safe_top`/`_swap_slot`.

- **적합 그룹 안에서 어떤 변수가 상수면 그 변수의 효과는 적합값에 흡수되고, 전수 패리티가 통과하는데도 모델이 틀린다 — "설명 안 됨" 예외는 그 흡수가 깨진 자리다.** 스탯 모델은 호감도를 배수 밖에 더했고 159기를 오차 1.0 안에 재현했다. 그게 통했던 이유는 코어 있는 유닛이 적합 그룹마다 **호감도가 단일**했기 때문이다(class 30, PILGRIM/OVERSPEC 40). 호감도가 다양한 그룹은 둘뿐이었고, 그 안의 호감도 10 유닛이 정확히 `CORE_FLAT_*_BY_RESOURCE_ID`의 "NOT explained" 3기(Vesti·Rosanna·Nero)였다. 진짜 규칙은 **호감도가 `(1 + 0.02×코어)`로 스케일된다**는 것이고, 넣어보니 그 3기가 오차 0.01~0.27로 설명되고 **OVERSPEC 계층도 사라졌다**(그것도 호감도 40 대 30의 착각). 진단 순서가 재현 가능하다: ① 같은 조건이어야 하는 관측값이 어긋나면 ② **적합 그룹별로 다른 변수들의 분포를 세어라** — 단일한 변수가 있으면 그게 흡수된 후보다 ③ 두 점으로 적합해 세 번째 점을 **예측**해 검정하라(여기서는 오차 1.11 대 기존 22.3). 그리고 **표를 최대한 줄이려는 유혹을 참으라**: ATK를 2행(PILGRIM 여부)으로 줄여도 159기를 통과하지만 최대 오차가 0.99로 임계값에 붙어 새 유닛 하나에 깨진다.
- **"추측하지 않고 예외를 던진다"는 옳은 판단이지만, 그 예외의 폭발 반경을 정해두지 않으면 데이터 공백 하나가 계정 전체를 못 쓰게 만든다.** `core_flat_atk`/`core_flat_hp`는 측정 안 된 조합(코어 올린 PILGRIM/OVERSPEC **Supporter**)에 대해 class 값으로 폴백하는 대신 `KeyError`를 던진다 — 폴백은 코어당 14~30 틀리므로 **옳은 설계다**. 그런데 그 예외가 엔드포인트까지 올라가 **부계정 첫 싱크가 500**으로 죽었다. 유닛 1기의 공백이 나머지 ~150기를 못 쓰게 만든 것이다. 고친 방향: 전용 예외(`UnmeasuredStat`)를 두고 로스터 조립이 **그 유닛만 빼고 이유와 함께 보고**한다 — `assemble_roster`가 이미 디렉토리 누락·상세 누락·비SSR을 건너뛰는 것과 같은 취급이다. 조용히 빼면 안 된다(그 유닛은 인코딩돼 있어서 그냥 사라진 것처럼 보인다). **진단 함정 둘**: ① `if core:` 가드가 있어서 코어 0이면 호출조차 안 된다 — 그래서 본계정은 같은 유닛(Grave·Nayuta·Little Mermaid)을 갖고도 내내 정상이었고, "부계정이라 투자가 적어서"라는 가설은 **재현으로 반증됐다**(투자 0·연구 0·어피니티 0으로도 200). ② ATK를 고치면 **HP에서 다시 터진다** — `CORE_FLAT_HP_OVERSPEC`에도 Supporter가 없고 PILGRIM은 OVERSPEC로 취급된다. 같은 공백은 표가 나뉘어 있으면 표마다 확인하라. 영향 유닛은 정확히 PILGRIM∩OVERSPEC Supporter 6기(Chime·Dorothy·Grave·Little Mermaid·Nayuta·Rapunzel).
- **실패를 삼키는 별도 호출에서 읽어온 선택적 값은, 저장된 좋은 값을 덮어쓰면 안 된다 — 빈 값은 "없음"이 아니라 "이번엔 못 읽었음"이다.** 계정 닉네임은 로스터와 다른 blablalink 호출(`GetUserProfileBasicInfo`)에서 오고, 북마클릿이 그 호출을 `.catch(()=>null)`로 감싸 실패해도 싱크는 성공한다. 그런데 `upsertProfile`이 `nickname: args.nickname`으로 무조건 덮어써서, 그 호출이 한 번 실패한 재싱크가 **잘 저장돼 있던 닉네임을 지우고** Account 드롭다운을 원래 open_id로 되돌렸다. 증상이 "코드 회귀"처럼 보이지만 코드(`ProfileSwitcher`의 `nickname || openId`)는 멀쩡하고 **데이터가 비어 있는 것**이다. 그리고 앱이 매 렌더에 북마클릿 href를 새로 만들어도 **유저 북마크바에 저장된 복사본은 그 시점에 얼어 있다** — 닉네임 지원이 들어오기 전에 저장한 북마클릿을 계속 쓰면 매 싱크가 빈 닉네임을 보낸다. 일반화: 값의 **출처가 본체와 다른 호출**이고 그 실패가 조용하면, 저장 계층에서 `new || stored`로 방어하고 못 읽었다는 사실을 사용자에게 보이게 하라.
- **어떤 유닛을 화면에서 "빼서" 문제를 피할 때는, 그 화면이 다른 기능도 겸하고 있는지 보라 — 드래프트 팔레트는 제외 토글까지 겸한다.** 드래프트로 앉힐 수 없는 유닛(소유 슬러그가 구체적 spec이 아닌 경우)을 드래프트 팔레트에서 걸러내 422를 피했는데, 드래프트 모드에서는 풀 팔레트가 **아예 렌더되지 않아**(`mode !== 'draft'`) 그 유닛이 **보이지도·제외되지도** 않게 됐다. "raid 모드와 동일하니 회귀 없음"이라는 판단이 모드별로 렌더 트리가 다르다는 사실에서 깨졌다. 일반화: **필터로 문제를 회피하기 전에, 그 리스트를 소비하는 컴포넌트가 몇 가지 역할을 하는지 세라.** 또 하나 — 이런 유닛을 "유저가 직접 고르게" 하는 우회는 **선택의 주체가 도메인마다 다를 때 거짓이 된다**: Cinderella의 MG/Snipe는 플레이어가 고르지만 Bready의 모드는 덱의 버퍼가 결정한다. 결국 엔진이 후보별로 덱을 완성해보고 고르는 쪽(`_seed_choices`)이 정답이었다. 그리고 **잠금·대조는 반드시 같이 base 키로 옮겨야 한다**: 잠금을 슬러그로 비교하면 `bready` 잠금이 실제 앉은 `bready-lingering`에 안 걸려 조용히 풀리고, 결과 대조를 슬러그로 하면 "하나 빼고 하나 넣음"으로 읽히며 슬러그 겹침 기반 덱 짝짓기는 그 덱을 못 짝지을 수 있다. `docs/decisions.md`("드래프트도 소유 슬러그로 받는다...") 참조.
- **한 개체가 "소유 단위"와 "엔진 후보 단위"로 서로 다른 이름을 가지면, 그 둘을 교집합하는 화면이 조용히 유닛을 잃는다 — 카탈로그가 두 어휘를 다 말해야 한다.** 동기화된 로스터는 플레이어가 **소유한** 것(`bready`)을 이름하고, 결과 덱은 엔진 **후보**(`bready-lingering`)를 이름한다. `/api/supported-units`가 후보만 반환했으므로 "owned ∩ supported"로 팔레트·로스터 그리드·풀 카운트를 만드는 프론트가 3명을 탈락시켰고, 그 3명을 백엔드는 내내 출전시키고 있었다 — 화면이 "아직 지원 안 됨"이라 적은 유닛이 추천 덱에 앉아 있는 상태. **증상이 카운트로 먼저 드러난다**: `70/70`(실제 77유닛/73캐릭터)과 `89`(백엔드 excluded는 86)가 3만큼 어긋났고, 그 3이 정확히 문제의 캐릭터 수였다. 산술로 검산하라 — 배치+벤치+제외가 로스터 크기와 안 맞으면 어휘가 어긋난 것이다(25+52+86=163=159+확장 4). 해법은 후보 엔트리를 **대체**하지 말고(결과 화면이 후보로 조회한다) 소유 슬러그 엔트리를 **추가**하는 것이며, 같은 규칙이 초상화 매니페스트에도 적용된다(한쪽 어휘만 키로 두면 다른 쪽이 빈 박스를 그린다). 그리고 **어휘를 늘리면 그 어휘를 좁게 받는 경로를 반드시 같이 점검하라**: 팔레트에 base가 등장하면 드래프트로 끌어놓을 수 있게 되는데 `api.py`는 드래프트 좌석을 구체적 spec으로만 해석해 422를 준다 — 새 엔트리가 새 버그를 만들 뻔했다(`canSeatInDeck`으로 드래프트 팔레트만 걸러냄). `docs/decisions.md`("`supported-units`가 두 어휘를 다 말하게...") 참조.
- **"한 덱 안에서 안 겹친다"는 규칙은 레이드 할당에서 부족하다 — 동시 출전하는 5덱 전체가 하나의 배타 범위다.** `MODE_VARIANTS`는 한 소유 캐릭터를 여러 후보 슬러그로 부풀리고, 그 규칙을 `_no_variant_clash`가 **덱 단위로** 지켰다. 레이드 할당은 덱을 슬러그로만 서로소로 유지했으므로 통과했고, 실제 로스터에서 `rapi-red-hood`(Deck 2)와 `rapi-red-hood-b1`(Deck 4), `cinderella-crystal-wave-mg`(Deck 2)와 `-snipe`(Deck 4)가 동시에 앉은 결과가 나왔다 — 게임에서 만들 수 없는 편성이고 합계 데미지도 과대평가였다. 일반화하면: **어떤 개체가 "여러 후보로 부풀려진 하나"라면, 배타 범위는 그 후보들이 함께 소비되는 가장 넓은 단위여야 한다.** 여기서는 덱이 아니라 할당 전체다. 두 번째 함정은 **불변식을 언제 세우느냐**였다 — peel에서 캐릭터 단위로 걸러도 두 후보가 **모두 벤치에 남는** 경우(실측: `bready-lingering`·`bready-recommended` 동시 벤치)가 있어서, 힐클라임이 하나씩 서로 다른 덱으로 끌어올려 같은 버그를 재생산한다. `_try_swaps`의 "후보 목록은 절대 낡지 않는다"는 불변식에서 **유일하게 낡는 필터**가 이것이므로, 채택 시점에 아직 안 본 꼬리만 걷어낸다(전체 재계산은 스캔 순서를 바꿔 "첫 개선 채택" 규칙을 깬다). 배타 키는 단일 함수 하나로만 두라 — 같은 분기를 두 곳에 복제하면 `supported_units`/`user_roster` 때처럼 한쪽만 갱신된다("`supported_units()` must resolve a slug's metadata..." 참조). `docs/decisions.md`("레이드 할당의 배타 단위를 슬러그에서 소유 캐릭터로...") 참조.
  **2026-07-28 후속: 이 함수 자체가 `MODE_VARIANTS`(팬아웃 표)에서 파생되던 것이 결함이었다.**
  `MODE_VARIANTS`는 원래 "엔진이 무엇을 고를 수 있는가"를 답하는 별개 표인데, 정체성 배타
  검사가 거기서 파생돼 애장품(`-signature`) 13쌍이 정체성으로 안 잡혔다(`variant_base`가
  `miranda`와 `miranda-signature`를 다른 캐릭터로 봄). `registry.character_map()`(매니페스트
  `data_slug` 그룹핑에서 파생, 정체성 전용)을 신설해 `variant_base`/`_no_variant_clash`를
  `character_of`/`_no_character_clash`로 개명하고 거기서 읽도록 고쳤다 — **팬아웃 표는
  안 넓혔다**, 그랬다면 애장품 없는 유저에게 엔진이 `-signature` 인코딩을 골라줄 뻔했다.
  자세한 결정과 세 안 비교는 `docs/decisions.md`("정체성 그룹과 후보 팬아웃을 분리...") 참조.
- **The peel+swap hill-climb only ever accepts a strictly-improving swap, so a weak/uninvested unit can never win a seat away from the field — a pool-reduction lever (letting the user exclude units from the search) buys speed and preference, not result quality.** Peeling and the same-tier swap phase (see "Five-deck allocation algorithm" below) both only take moves that raise the summed score, so a unit that would lower it never gets picked regardless of whether it's in the searched pool or not — excluding it from the pool changes how long the search takes and whether irrelevant units even get shown, not which units the recommender would have chosen. Keep this in mind before reaching for a pool-shrinking feature as a *quality* fix — it's a speed/preference lever, and the algorithm's own monotone-improvement property already keeps weak units out of results without one. See `docs/decisions.md` ("유저 주도 '사용할 니케' 풀 선택...").

- **A deck's damage lives in timeline-dependent nukes, so a fit-free static scorer cannot rank decks — measured, not assumed.** `backend/app/closed_form.py` (**deleted 2026-07-31, `866bb2c`** — the finding below stands, but the file itself is gone; read it via `git show f2dc3a3:backend/app/closed_form.py`) fired a deck's skill rules once against a real `EffectRegistry` (the encodings are thin closures over `Effect(stat, value, scope, duration)`, so this harvests the whole buff table with no timeline and no shot loop) and estimated damage off that snapshot, mirroring `raid_simulator._damage_instance` term for term. It was ~140x faster than a simulation (0.79 ms vs 110 ms per deck) and skipped zero skill bullets — and it still only reached **Spearman 0.54** against real damage, with the true-best deck landing at rank 157 of 300 and its own top pick delivering **64% of the best damage** (a random pick averages 33%). The reason is structural and quantified (`scripts/measure_unmodeled_damage_share.py`, 60 decks, 40-unit roster): only **60% of damage comes from normal attacks + burst nukes**, the two sources a static snapshot can see. The rest is per-shot nukes (17.6%), resource-scaled nukes (7.1%), periodic (5.9%), scheduled (5.0%), instant (3.2%) and dynamic-hit-count (1.0%) — and the unseen share swings from **6% to 62% per deck**, so it is deck-dependent noise, not a constant bias that would cancel out of a ranking. Two rounds of fixing the obvious errors (only the tier's leftmost unit bursts; the cycle length derived from the bursters' cooldowns minus the deck's own CDR instead of a fixed 20s) moved Spearman by −0.02, i.e. nothing: the ceiling is the unmodeled 40%, not the modeling of the visible 60%. Before reaching for "just use a cheap formula like the other tools do" (Genshin Optimizer et al. — see `docs/decisions.md`), note that those tools' damage IS their formula, whereas here the formula is 60% of the answer. See `docs/decisions.md` ("캐스케이드 대리모델: 표본 회귀 vs 닫힌 수식...", and "기각된 닫힌 수식 스코어러(`closed_form.py`)를 삭제한다..." for the deletion). **Why it was finally deleted rather than left as a documented dead end:** nothing imported it in production, but a stray comment in `user_roster.py` listed it as a live consumer, which made a later doc entry (engine-gaps.md gap #20) wrongly claim a fix to it would move deck-search rankings — deleting is what makes a rejected approach unable to be mistaken for a live path again.

- **A pair bonus with a FIXED partner is representable by a per-unit additive model — so it proves nothing about synergy blindness. Use a cancelling pair instead.** Written while building the cascade's quality regression test, where the first fixture planted "`{A,B}` together = +100" believing a unit-only ridge could not express it. It can: `A` co-occurs with the bonus in every sampled deck that contains it, so the fit simply absorbs the bonus into `A`'s coefficient. Measured, the effect is not merely weak but *inverted* — raising the bonus 40 → 100 moved `A` from third to first in its tier's coefficient ranking and made the cascade return the optimum at **every** shortlist width, i.e. the test became unable to fail. The fix is a synergy whose sign depends on the partner: `{A,B}` = **+100** and `{A,C}` = **−100**, so `A`'s coefficient averages toward neutral and the additive model genuinely cannot tell the good partner from the bad one. Only then did the fixture expose real behaviour. The general rule for testing any additive surrogate: a term is representable if it correlates with a single feature — to defeat it you need one that cancels across that feature's occurrences. See `backend/tests/test_deck_allocation.py`.
- **The cascade's `prune_candidate_pool` seat is load-bearing, not belt-and-braces — measured at 100% vs 90.6% of optimal.** `widened_pool` seats prune's picks before filling the rest by surrogate coefficient, and that ordering is what rescues a unit whose value lives entirely in a synergy the surrogate cannot see: such a unit ranks LAST by coefficient (correctly — its solo value is low), so the coefficient-ranked pass drops it at the tier cap before `top_k` is ever consulted. `prune_candidate_pool` measures marginal contribution by actually simulating a reference deck, so it *does* see the synergy and pulls the unit in. With the safety net the cascade returned the true optimum; with prune stubbed out it returned **90.6%**. The two filters are worth keeping precisely because their blind spots differ — a cheap ranker's failure mode is not a reference-deck heuristic's. See `docs/decisions.md` ("캐스케이드 Phase 2 착지...") and the paired tests in `backend/tests/test_deck_allocation.py`.

- **A uniform-investment roster is not a neutral perf fixture — it changed the measured value of a change by 2.6x, in the direction nobody predicted.** Every deck-builder perf number up to 2026-07-25 came from "the first N supported slugs, all at ATK 60,000 / skills 10/10/10 / no overload". The real synced roster differs on every axis a swap verdict touches: ATK 82,895-144,793 (1.75x spread), 23 distinct skill-level combinations, 0-6 overload rows per unit. The prediction going in was that uniform stats make same-tier units nearly interchangeable, maximizing near-tie verdicts, so the synthetic fixture would OVERSTATE the hill-climb's difficulty. Half right and wrong where it counted: the real roster does converge sooner (22.2s / 2,363 sims vs 31.3s / 3,734), but the damage the old serial cut-off was throwing away is **10.5% of the allocation total on the real roster against 4.0% on the synthetic** — the fixture was understating the fix's worth, not overstating its cost. Real rosters have clearly-better units, so greedy peeling's mistakes are *larger* and concentrated where swap arrives late. Do not reason about which direction a synthetic fixture biases a perf number; measure on the real roster (`scripts/roster_fixture.py` loads it, and reports which one a run used).
- **A serial hill-climb parallelizes without changing its answer if you batch SPECULATIVELY and re-batch on acceptance — the trick is proving the candidate LIST is invariant even though the scores are not.** The swap phase looked unparallelizable ("each accepted swap changes the state the next candidate is judged against", `docs/decisions.md` 2026-07-17) and was deferred twice for that reason. But the dependency is only on the *scores*: the candidate list — (seat, partner) pairs surviving the same-tier and not-locked filters — cannot change, because a same-tier swap leaves both seats' tiers untouched and a locked unit is never a swap source on either side. So the whole list can be scored ahead of the walk, and the walk keeps the serial rule (accept the FIRST improvement, in the original order); only when it accepts does the rest of that batch become stale, and then it re-batches from the next candidate. The result is bit-identical to the serial version — pin that with a test that runs the same fixture at several batch widths and asserts one outcome, plus one where the second candidate improves on the ORIGINAL deck but not the accepted one (a naive implementation trusting stale scores seats the worse unit). Waste is bounded by the acceptance rate, which was under 1% of candidates on a 78-unit roster. General shape: before declaring a sequential loop unparallelizable, separate what the iteration *reads* from what it *decides* — often only the former is order-dependent.
- **A threshold that guards creating an expensive resource must not also gate reusing it.** `SimPool.SPAWN_THRESHOLD = 32` ran small batches inline, which is right when the cost in question is starting a `ProcessPoolExecutor` (spawning processes, pickling the roster into each). Applied to *every* batch, though, it silently refused an executor that was already warm — and the swap hill-climb's deck-to-deck candidates arrive ~22 at a time, so they all fell through to the serial path. First measurement of the batched phase came back at 1.9x instead of the workers' worth; the 282 inline sims were ~29s of a 45s budget while the pooled leftover batches did twice the work in ~4s. Fix was one condition (`len(decks) < threshold and self._executor is None`). Watch for this shape wherever a lazily-created resource has a "is it worth it?" guard — the guard's cost model is about creation and stops being true the moment the resource exists.
- **A real scoring bias can still be worth leaving in: the swap hill-climb judges candidates on ONE canonical ordering — a method this codebase measures as up to 78% low — and fixing it buys ≤0.47%.** `_swap_pass` scores a deck in the order the search returned it, then replaces one seat and re-scores in that same order. The decks arriving from `search_best_decks` are already at their BEST ordering while the unit swapped in may want a different seat in its tier, so the error does not cancel between incumbent and challenger — it is biased *against* the challenger, and the hill-climb rejects swaps that would have won. All true, and measured worthless to fix: judging every candidate on its best ordering, run to convergence on the real 77-unit roster, gained **+0.02% (Water/180s), +0.47% (Fire/180s), +0.14% (Electric/90s)** while making the whole allocation 3.3-5.4x slower (`scripts/audit_swap_ordering.py`). **The reason is that the objective is flat near its optimum** — the Water run's two methods produced *completely different* five-deck compositions whose totals differed by 0.02%. A mis-ranked swap does flip the verdict; it just lands on another local optimum of the same value. The durable lesson: a demonstrable bias in a heuristic's judgment is not the same as a loss in its output, and on a flat objective the two can differ by two orders of magnitude — measure the output, not the bias. (Revisit if shells grow, raising orderings per deck, or if synergies become far more order-sensitive.) See `docs/roadmap.md`.

## Frontend (React)
- **정사각 얼굴 크롭에 새 에셋은 필요 없다 — `object-position: center 18.75%`가 그 답이고, 숫자는 유도된다.** 초상화 원본은 256×512 전신이고 CDN에 다른 크기는 없다(`si_`/`ci_`/`fi_`/`icon_` 접두사, `.png`, `/assets/nikke/` 전부 404 — 2026-07-25 실측). 정사각 박스에서 `object-fit: cover`는 이미지를 W×2W로 그리므로 세로로 W(=**이미지 256행**)가 잘린다. `object-position`의 퍼센트는 **잘리는 양에 대한 비율**이지 이미지 높이에 대한 비율이 아니다 — 위에서 48행을 건너뛰려면 48/256 = **18.75%**다(512로 나눠 9.375%가 아니다). y=0/24/48/72를 실제로 잘라 비교했을 때 48이 표본 전원의 머리와 턱을 온전히 남겼다: y=0은 머리 위 여백이 남고 턱이 잘리며, y=72부터 머리가 잘리기 시작한다. 덱 슬롯·로스터 타일·결과 셀이 이 한 규칙을 공유한다(`App.css`의 "THE FACE CROP").
- **"빼서 다시 넣기"로 이동을 구현하면 목적지가 꽉 찼을 때 대상이 삭제된다 — 정원 검사를 제거보다 먼저 하라.** 덱 간 유닛 이동을 `placeUnit(removeUnitBySlug(draft, slug), target, slug)`로 쓰면, `placeUnit`이 정원 초과로 no-op을 반환하는 순간 남는 것은 **제거만 적용된 draft**다. 즉 거부돼야 할 조작이 유닛을 조용히 없앤다. `moveUnit`은 목적지 용량을 확인한 **뒤에** 제거한다(`components/DraftEditor.tsx`). 부수 효과로 드롭 경로가 하나로 합쳐진다 — 팔레트에서 온 슬러그는 어디에도 앉아 있지 않아 제거 절반이 no-op이 되고, 기존 배치 동작과 그대로 일치한다.
- **Vitest는 `css: false`로 돌아 레이아웃 버그를 구조적으로 못 잡는다 — 레이아웃 변경은 Playwright 스크린샷으로 확인할 것.** 실제로 놓친 사례: `.panel { display: flex }`가 `hidden` 속성의 UA 규칙(`display: none`)을 **우선순위로 이겨서** 비활성 탭이 계속 보였는데, 접근성 트리는 정확했으므로 전 테스트가 통과했다. 클래스 레벨 `display`는 언제나 `hidden`을 덮으므로 `[hidden]` 규칙을 명시해야 한다. 같은 이유로 "칩이 정렬돼 보이나"류는 `getBoundingClientRect`를 브라우저에서 읽어 확인하는 편이 빠르고 확실하다.
- **한 문자열을 색만 다르게 두 `<span>`으로 쪼개면 `getByText`가 부모와 자식에 동시에 걸린다.** 돌파 별을 채운 별(금색)/빈 별(흐림)으로 나누려다 발견: `grade=0`이면 바깥 span과 안쪽 "빈 별" span의 `textContent`가 **둘 다** `☆☆☆`라 `getByText('☆☆☆')`가 "multiple elements" 오류를 낸다(`grade=3`도 대칭으로 동일). 별 전체를 한 색으로 두는 쪽이 옳았다 — 빈 슬롯은 어차피 외곽선이라 이미 구분되고, 게임도 그렇게 그린다. 일반화하면: **한 값을 표현하는 텍스트는 쪼개지 말 것.** 정말 필요하면 부모에 `aria-hidden`이나 다른 쿼리 축을 쓰라.

- **Per-profile UI isolation needs a `key={activeProfileId}` remount, not just swapping the data underneath a persistent component.** A shared async hook (e.g. `useRecommendRaid`) living inside a panel component that ALSO persists its result on completion can leak across profiles: a slow request submitted under profile A can resolve after the user has already switched to profile B, and its persist callback — closed over whatever "current profile" means at call time — writes A's result into B's slot (or displays it). - **An application logger's INFO records are silently dropped under uvicorn, and pytest's `caplog` hides this from a normal test suite.** uvicorn only configures its own `uvicorn.*` loggers; the root logger keeps its default WARNING level with no handler for application loggers, so a module-level `logging.getLogger(__name__).info(...)` emits nothing in a real server run even though the request itself succeeds (uvicorn's own access log still shows `200 OK`). A test using `caplog.at_level(logging.INFO)` forces the level for the duration of the test and therefore passes regardless — the telemetry looks tested while being dead in production. Found 2026-07-19 via `logging.getLogger('app.api').getEffectiveLevel()` returning 30 (WARNING) against a real run of the roster-sync endpoint. Fix: configure the application logger's own handler + level directly (`if not logger.handlers: logger.addHandler(logging.StreamHandler()); logger.setLevel(logging.INFO)`), not root — this leaves uvicorn's own access/error loggers untouched and doesn't double-log. A regression test that would actually catch this must exercise the real default-logging path (e.g. run the endpoint in a bare subprocess, no pytest/caplog involved) rather than a `caplog.at_level`-forced one. See `backend/app/api.py`, `backend/tests/test_assemble_roster_api.py`, commit `5069dc2`.

Don't assume a UI's convention is uniform across every stat-contributing source it displays; check each one. This mattered far more for automated ingestion than manual entry: a human copying numbers by hand tends to notice something looks off, but a scraper swallows ShiftyPad's displayed numbers wholesale and would silently double-count (or drop) a source's contribution if the fold-in assumption is wrong.
- **NIKKE base stats (ATK/HP) are uniform across all characters of the same class (Attacker/Supporter/Defender) — only DEF varies per-character, and the engine doesn't consume DEF anyway.** blablalink's CDN serves each character's stat table as a `character_level_attack_list`/`_hp_list` array (level 1-1200); byte-for-byte diffing two Attackers (Rapi, Quency) showed the attack and HP arrays are identical, and likewise for Supporter (Mast) and Defender (Moran). Breakthrough/core coefficients (`grade_attack=20`, `core_attack=200`, `grade_hp=3000`, `core_hp=200`, etc.) are also identical across all four characters checked. Collectible-item stats are uniform per rarity tier (R/SR), and a favorite item (SSR) is fixed at "SR collectible at level 15" rather than its own stat curve. Cube flat stats are uniform regardless of cube type. **Practical consequence: a per-character stat manifest is unnecessary** — 3 class stat tables plus the shared breakthrough/core coefficients cover the whole roster (Phase B's collector design leans on this). See `data/blablalink-cdn/NOTES.md` (gitignored local data, not committed) and `docs/decisions.md` ("Phase B redefinition...").
- **The displayed-ATK assembly formula is NOT purely additive — a percentage term scales with base ATK, and it is only visible if you compare two levels of the same unit.** `data/blablalink-cdn/NOTES.md` drafted the formula as `base + grade*20 + core*200 + favorite + cube` (all additive); measured against the collected roster that under-explains ATK, and by a level-dependent amount. Rapi: Red Hood — base[Attacker][400]=90,318 vs measured 143,543 (residual 53,225); base[663]=322,224 vs measured 418,862 (residual 96,638). Solving `residual = F + r*base` across the two levels gives **r ≈ 18.72%, F ≈ 36,316**. Prime suspects for `r`: `grade_ratio=200` (the coefficient NOTES left as "용도 미확인" — plausibly 2%/grade, so 6% at grade 3) plus the affinity table's class `attack_rate` at `attractive_lv` 40 (~12.7%). The flat part F is consistent with 4 pieces of T10 gear (~22.6k) on top of core+grade+collectible+cube (13.7k). **Consequence: a single-level check cannot validate this formula** — a fit that looks perfect at one level silently mis-scales at another, so validate against both the `raid400` and `actual` stats the collector records per unit. Verify against all 159 collected units before trusting it; this two-level derivation comes from one unit.

A later session re-derived it from scratch by live probing. Keep the raw dumps under `data/`, but write the *conclusions* into `docs/insights.md` where they survive and are greppable.
- **The solo-raid ATK formula, derived and measured against 159 units — 159/159 exact (closed 2026-07-19; an earlier 133/159 milestone is superseded, see the per-core-flat bullet below).** `backend/app/stat_assembly.py`:
  ```
  atk = base[class][level] * (1 + 0.02*grade) * (1 + 0.02*core)
        + core*core_flat_atk(class, corporation, resource_id) + grade*20   # per-UNIT, not a class constant
        + affinity[class][affinity_lv]                 # flat, despite the `_rate` column name
        + corporation_research_rank * 25               # account-wide, per corporation
        + per-slot gear                                # base * (1 + 0.3*own_corp + 0.1*level)
        + cube[cube_lv] + collectible                  # collectible: curve[lv], or curve[-1] for a favorite item
  ```
  Every piece was measured, not assumed. Two structural findings are easy to get backwards: the **breakthrough terms multiply** (grade 3 with core 1 measures 1.0812, not the additive 1.08) while the **gear bonuses add** (own-corporation gear at LV.05 is base*1.8, not base*1.3*1.5). Rounding is half-**up** on the bonus, applied before adding to base.
- **When a residual against ground truth won't close, divide it by the investment count before hypothesising a new additive term — discrete clustering of delta/count is the tell that the existing term's coefficient is wrong per-unit, not that a term is missing.** Closing Phase B2's last 26/159 ATK mismatches: the leftover deltas looked like noise as raw ATK, but `delta / core_count` collapsed them onto exactly 3-4 discrete values per class (Attacker: 118.95 standard / 142.90 PILGRIM / 132.95 OVERSPEC / 94.22 unexplained; Defender: 107.87 / 127.22 / 116.79 / 91.15; see `core_flat_atk` in `backend/app/stat_assembly.py`) — i.e. the per-core flat ATK constant was itself a hidden per-unit property, not a universal class constant plus a missing correction term. **A class default fitted to too few units can itself be the bug, not just imprecise:** the old `CORE_FLAT_ATK["Defender"] = 91` had been fitted to Nero, and Nero turned out to be one of the three "unexplained, measures less" outliers — so the wrong default was silently masking the correct one (107.87) for every OTHER Defender in the roster. Re-derive a class default from a large, deviation-free subset, and re-check it once outliers are identified, rather than trusting an early single-unit fit. See the design doc's "코어 flat은 클래스가 아니라 유닛 단위" section, `docs/superpowers/specs/2026-07-18-stat-assembly-calculator-design.md`.
- **To find WHY two units of the same class behave differently, diff their full blablalink CDN character-stat JSONs key-by-key — don't assume the difference is in the base curve.** Rapi: Red Hood (core flat 132.95) vs Quency: Escape Queen (core flat 118.95, the class default) — same class, same rarity — were diffed field-by-field, surfacing `corporation_sub_type: OVERSPEC` (vs `None` for the ordinary unit) as the actual discriminator. The SAME diff simultaneously proved the base level-attack curve was NOT the cause: `character_level_attack_list` (1200 entries) was byte-identical between the two files, so whatever explains the ATK gap has to be in a coefficient applied on top of the curve, not the curve itself — turning a wide search into a targeted one. Files live in `data/blablalink-cdn/` (gitignored, not committed — see the worktree-sync insight above). Reusable pattern for any future "two same-class units disagree" puzzle: diff the full JSON before hypothesising, and treat an unexpectedly-identical sub-array as evidence ruling that piece out, not just a non-finding.
- **ShiftyPad's "Core Enhancement" stepper is a combined grade+core counter (0..10) whose consecutive deltas at level 400 give per-core flat ATK/HP directly and GEAR-INDEPENDENTLY, single-unit — an alternative to cross-unit fitting that verifies it without entangling the equipment model.** Discovered 2026-07-19, prompted by Fienn noting ShiftyPad has grade/core adjustment buttons alongside the level slider. On a single unit's page (`/shiftyspad/nikke?nikke=<resource_id>`), `div.upgrade-btns` with only −1/+1 whose parent text contains "Core Enhancement" steps 0→3 through limit-break grades (grade 0→3 at core 0) and 3→10 through core enhancements (core 0→7 at grade 3). Sweeping it at level 400 and reading the level-400 ATK/HP at each step: consecutive differences in the core regime cancel every core-independent term (equipment/affinity/cube/corporation), so `core_flat = (ATK[step10]-ATK[step3])/7 - base400*0.02*1.06` — no cross-unit fit needed. The grade regime independently recovers `grade_attack≈20`/`grade_hp≈3000`, confirming those table constants too. **Reading gotcha:** level-400 value = displayed value + delta, and delta can be POSITIVE (unit's real level is below 400) as well as negative (the common case) — a regex that only accepts `-?\d+` silently fails on positive-delta units (e.g. Vesti); use `[+-]?\d+` (same delta-sign fact as the jsdom stat-panel bullet above, now confirmed to bite the core sweep too).
  Swept 10 units and every one matched its cross-fit tier gear-independently: class (Brid Atk 118.97, Miranda Sup 113.52, Bay Def 108.08), PILGRIM (Scarlet Atk 142.97, Noah Def 127.36), OVERSPEC (Rapi:RH Atk 132.97, Anis Def 117.36), and the three "measured-not-explained" low outliers (Vesti 94.26, Rosanna 94.26, Nero 91.51). This resolved the OVERSPEC-Defender n=1 weakness — Anis alone gives 7 consistent core steps (~1394 ATK each) — and independently corroborated the unexplained-low trio as a real sub-class tier (Vesti and Rosanna both measure exactly 94.26; still unexplained WHY, but the value itself is solid, not a gear artifact). Also surfaced a genuine model-collapse: HP merges PILGRIM and OVERSPEC into ONE value (PILGRIM-Atk HP 6663.1 == OVERSPEC-Atk HP 6663.1), which is why `CORE_FLAT_HP` has one OVERSPEC tier while `CORE_FLAT_ATK` keeps them split.
  **Why the swept slope values were NOT swapped into `stat_assembly.py` despite confirming the tier ordering:** the slope runs ~0.2-0.57 ATK above the cross-fit for Supporters/Defenders (Attackers match near-exactly), because the cross-fit's `core_flat` and its equipment model are a SELF-CONSISTENT decomposition tuned together to reproduce the measured total — the equipment model has silently absorbed a small per-core bias. Swapping in the gear-independent slope value without also re-deriving the equipment model gear-independently would break the 159/159 parity (a core-7 Supporter would land ~1.6 ATK off, over the <1.0 tolerance band). Both decompositions produce the SAME final level-400 ATK, which is all the simulator consumes — so a full re-derivation buys at most ~4 ATK on a max-core unit (<0.003%) and was deliberately deferred. This sweep's value is **verification of the tier structure**, not a refinement to ship. Code ref: `backend/app/stat_assembly.py` (`CORE_FLAT_ATK`/`CORE_FLAT_HP`); the sweep itself was a live CDP probe, not committed to the repo.
- **Three values in blablalink's own stat tables do not mean what their names say — trust measurement over the schema.** (a) The affinity table's `attacker_attack_rate` is **flat ATK**, not a percentage: rank 40 reads 2340 in game and 2340 in the cell. (b) `recycle_research.attack = 25` is **per rank**, not a total: at rank 170 it contributes 4,250. (c) `stat_enhance.core_attack = 200` is **wrong for ATK entirely** — it is identical across all three class tables and reproduces no measured unit; the real per-core flat is a per-UNIT value (118.95 / 113.29 / 107.87 for a standard SSR Attacker / Supporter / Defender, higher for OVERSPEC units and Pilgrims — the earlier 119/113/91 reading was a class constant fitted to too few units, see the per-unit entry below), read off ShiftyPad's core screen where an Attacker gains 2,034 ATK per core at level 400 and 6,950 at 663, both leaving the same flat once the 2% step is subtracted. - **Two ID systems must be joined via a third, rotating-URL source: the game API keys by `name_code`, ShiftyPad's URL keys by `resource_id`.** Join path: the nikke **directory** (a CDN JSON array carrying both `resource_id` and `name_code`, plus `original_rare` and `name_localkey.name` = English name; its URL hash rotates, so discover it at runtime by intercepting whichever JSON response on a ShiftyPad page load is an array whose items have both fields) × `GetUserCharacters` (the owned-roster API, keyed by `name_code`), filtered to `original_rare === 'SSR'` (raid content is SSR-only). **`GetNikkesOrder` is a favourites list only — it is NOT the owned roster and must not be used for enumeration**, a trap because its name suggests otherwise. See `tools/collect-blablalink/RECIPE.md` section (c)/(d), `collect.js`.
- **A name-alias table SHARED by two import paths with different naming conventions is a latent mis-mapping bug — and a silent one, because a wrong slug is still a *valid* slug.** The ExiaInvasion export uses short in-game names, the collector's `roster.json` uses full directory names, and both went through one `resolveSlug` alias table, so the two paths wanted contradictory mappings for the same string. Nothing errored: base `"Soline"` simply resolved to `soline-frost-ticket`, and since drafts merge by `character_slug`, the variant's accurate collected stats got clobbered by the base's. Fixed by giving the collector path its own `resource_id`-keyed table (`frontend/src/lib/resourceIdSlugMap.ts`) and leaving the alias table untouched for ExiaInvasion. Name-based schemes also can't separate the three distinct units that all display as `"Rei"`. See `docs/decisions.md` ("Collector roster units map to slugs by `resource_id`...").
- **When two encodings of the same character share ONE game ID, that ID cannot be the discriminator — identity keys answer "which character", investment/progression state needs its own layer.** A "dual-slot" unit (both `<slug>` and `<slug>-signature` encoded — Drake, Julia) has one `resource_id` for both; whether the signature applies depends on the user owning the in-game Favorite Item, which is per-user and changes over time. So `resourceIdSlugMap` maps id → BASE slug only, and ownership lives in a separate `SIGNATURE_OWNED` set. Merging the two into one table looks tidier and is wrong for everyone but the author, at one moment in time.
- **A guard test can only catch what its source of truth knows — name the blind spot as part of the guard's contract.** `backend/tests/test_resource_id_slug_map.py` cross-checks the hand-authored frontend map against the live `ENCODED_SLUGS`, so it catches typos, stale slugs, missing entries, and newly encoded dual-slots (encoding a new Nikke red-fails the backend suite until the map or `KNOWN_UNMAPPED` is updated — intentional). It cannot catch a wrong-but-VALID `resource_id`, because no committed data maps ids to names; closing that needs a committed public directory snapshot — **which now exists**, see the next bullet.
- **The public half of a session-gated source can often be committed even when the personal half cannot — splitting them turns "needs a live run to verify" into a normal test.** The nikke directory (194 units: `resource_id`/`name_code`/English name/rarity) arrives on the same authenticated ShiftyPad load as the roster, but carries no account data, so `collect.js --directory` dumps it to a committed `nikke-directory.json` while `roster.json` stays gitignored. The mode returns *before* the `game_openid` lookup, so it needs no account at all. `backend/tests/test_resource_id_directory.py` then checks each mapped slug against the directory's English name (normalised), closing the wrong-but-valid-id hole above — verified by injecting the exact bug class (Soline's base 71 in place of variant 74): the new guard names it, the old guard stays green. Two design notes that make the check honest: (a) the rule was derived from data, not assumed — 51 of 57 entries matched normalised-equality exactly, and the 6 that didn't were all collab units whose ShiftyPad name is a short form (`Ada` vs `ada-wong`), so they became an explicit `SLUG_NAME_EXCEPTIONS` table; (b) each exemption is **pinned to the exact directory name** it may differ from, so an exemption cannot widen into hiding a real mis-mapping. A side effect worth knowing: ids no longer require someone to *own* the unit, which is what let `jill-valentine` be mapped from evidence (841) rather than guessed, emptying `KNOWN_UNMAPPED`.
- **`data/dotgg/` and `data/lootandwaifus/` are gitignored local data assets — a git worktree does not get them for free.** Data-dependent tests fail broadly in a fresh worktree until both directories are copied over from the main checkout; conversely, deliverables produced while working in a worktree (new/updated data files) are handed off by copying them back to the main checkout, not by committing them (they're gitignored everywhere).
- **ShiftyPad's public share-URL uid's leading number is a ShiftyPad REGION id, not the API's `nikke_area_id` — a plausible-looking decode is a false lead.** `blablalink.com/shiftyspad?uid=<base64>` decodes to `<shiftypad_region_id>-<intl_open_id>` (e.g. `29080-1234567890123456789`). Calling `GetUserCharacters`/`GetUserCharacterDetails`/`GetUserProfileOutpostInfo` with `nikke_area_id=29080` (the uid's own leading number) returns `code 1303001` ("param invalid") — 29080 is unrelated to the game API's area. Cost one round-trip to discover; don't trust a decoded uid's leading number without checking the API's actual response code first. **The uid does not carry the account's region at all** — see the region-id entry below for where the real `nikke_area_id` comes from.
- **`nikke_area_id` is the game SERVER REGION, and 81 is Japan — not "international".** The authoritative list is `GET https://api.blablalink.com/api/lip/direct/commodity/Game/GetRegionList?game_id=29080`, which returns `area_list`: **81 Japan · 82 NA · 83 Korea · 84 Global · 85 SEA**. This project hardcoded 81 everywhere and called it "the international server" for weeks; that survived only because both accounts it was ever tested against were Japan-region. The first Korea-region account broke it: `GetUserCharacters` with area 81 for a KR `open_id` fails `code 1303002` ("proxy.GetUserShiftyspadPrivacy error") even when the target's ShiftyPad visibility IS public — the privacy record is looked up in the wrong region, so a region mismatch is indistinguishable from a privacy problem by its error message alone. **Lesson: a constant that happens to work for every sample you have is not a constant.** The value was only discoverable from blablalink's own region-list endpoint, not from the share URL, not from the account, and not by inference.
- **A failing first call can be reported as a failure of the SECOND one.** The bookmarklet's `GetUserCharacters` result is read as `(await call(...)).characters||[]`, so when that call is the one that breaks, the `||[]` flattens it into an empty roster and the NEXT call (`GetUserCharacterDetails` with `name_codes: []`) is what raises the visible error — `param invalid`, pointing at the wrong endpoint and the wrong parameter. Diagnosing it required a probe that reported every call's own `code` instead of stopping at the first throw. **When an error names a step, check that the step before it actually succeeded** — a defaulting `||` between two calls will hide the real one.
- **A caller-side authenticated blablalink session can read ANY user's roster/investment data once that user sets ShiftyPad visibility to public — the target's own credentials are never needed, but the call still isn't anonymous.** From one account's logged-in session, `GetUserCharacters`/`GetUserCharacterDetails`/`GetUserProfileOutpostInfo` for a DIFFERENT (public) account all return `code 0` with the full per-unit investment payload (`arm_equip_*`/`attractive_lv`/`harmony_cube_*` — exactly what `backend/app/stat_assembly.py`'s calculator consumes) and account-wide corporation-research rows — these are the same three endpoints `tools/collect-blablalink/collect.js`'s `fetchOwned`/`collectDetails` already call, just pointed at a different `open_id`. A session-less (anonymous) call to the same endpoints is refused with `code 300001` ("game not login") — so this is consent-gated by the target's visibility toggle, not by session ownership, but it is NOT a truly anonymous public API; some valid session is required, just never the target's. See `docs/decisions.md` ("Phase 7 Stage 1 reconnaissance: cross-account roster sync IS feasible...").
- **An ownership proof binds an `open_id` to a user by having them edit a cross-account-readable game-profile field — but NIKKE's game profile has no free-text bio, so the free channel is the showcase team, not a pasted code.** For a "first sync proves ownership, later re-syncs don't" flow (the abuse it stops: submitting someone else's public share URL as your own — false attribution / mass harvest of public rosters). The real endpoint is `GetUserProfileBasicInfo` (NOT `...BaseInfo`; guessed names return `code 220000` "not permission"), which returns cross-account `nickname` / `lv` / `profile_team` (5 showcase slots as `{name_code, slot}`) / `icon_id` — dumped in full against a public account, there is NO intro/comment/signature free-text field. So the two editable+readable proof channels are `nickname` (free text, high entropy, but a NIKKE nickname change costs currency) and `profile_team` (free to edit). The showcase team is the better channel precisely because we already read the user's owned roster: the challenge can be "put these N units you own into slots 1..N in this order," which is free, always performable, high-enough entropy, and proves in-game access — no reliance on a bio field edenpj's precedent implied but this API doesn't expose (edenpj likely read the community profile or the nickname). Endpoints observed on a shared-ShiftyPad load also include a whole community/guild layer under `/api/ugc/...` and `/api/lip/...` (distinct from `/api/game/proxy/Game/...`), some of which return the SESSION user's data rather than the viewed profile's — don't assume every endpoint on that page is keyed to the profile being viewed.
