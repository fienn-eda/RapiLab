# Insights

Engine gotchas and reusable patterns — the things that surprised us or would
trip up the next person. Grouped by topic. For the encoding procedure and the
full stat/trigger/scope catalog, see the `nikke-skill-encoding` skill.

## Damage formula
- **The attack/skill coefficient scales the whole Base Damage, not the ATK stat.** A normal attack's "% of ATK" or a skill's "X% of final ATK" multiplies Base Damage *after* defense is subtracted — pass raw summary ATK plus a separate `attack_coefficient` to `calculate_damage`. Folding the coefficient into ATK mis-scales the defense subtraction and any flat ATK (~14% overstatement against a defended boss, and unevenly across Nikkes since coefficients range from ~5% normal attacks to ~8000% bursts, which would skew deck rankings). See `damage_formula.calculate_damage`.

## Performance (EffectRegistry)
- **`_stat_bundle`-style memos keyed on a global `version` counter are only safe in phase 2 — in phase 1, per-shot mutations churn `version` every call, so every bundle lookup misses and rebuilds, costing more than it saves.** Tried wiring `normal_attack_type` (a phase-1 stat, read while shots are being generated and rules are firing) into the phase-2 `_stat_bundle` memo — Stage 0.5's gain collapsed from 23% to 6% (133.66ms → 125.07ms) because every phase-1 call bumped `registry.version` and invalidated the very bundle it was trying to reuse. Reverted to a direct single-stat `total_for` lookup for `normal_attack_type`, which restored the full 23% gain (→ 103.43ms). Rule: **`_stat_bundle` is phase-2 only** — see the warning comment above `_stat_bundle` in `raid_simulator.py`. Any future stat added to `_BUNDLE_STATS` must be confirmed phase-2-only (read only during damage computation, not during shot/rule generation) before being added.
- **Bit-identical performance refactor pattern: freeze a naive reference implementation, preserve float-addition order, and cross-check with a parity net.** Requiring "bit-identical," not "approximately equal," output from a performance rewrite (Stage 0's segment-table `EffectRegistry.total_for`) needs three things: (a) a frozen copy of the original naive implementation committed with a "do not modernize" comment, so it can't drift out of sync with the fast path it's meant to validate; (b) preserving the ORIGINAL summation order (effect insertion order, not chronological order — float addition is non-associative, so re-ordering can flip the last bit); (c) a parity-net test that runs both implementations against the full test suite plus dedicated mutate/query interleaving cases, not just a handful of hand-picked spot checks. Side benefit: the test suite itself got 3× faster (22s → 6.5s) as a byproduct, since many tests exercise `total_for` heavily. See `docs/decisions.md` ("Stage 0: EffectRegistry rewritten to per-(stat, slug, element) segment tables...").
- **The epoch superset invariant is what makes bundling multiple stats into one memo safe: the union of every matched Effect's boundaries (`state_epoch`) is itself the superset of each individual stat's own boundaries, so within one epoch ALL bundled stats are simultaneously constant.** `EffectRegistry.state_epoch(target, time)` collapses every stat's own boundary-time set (for effects matching that target) into one combined timeline. Because it's a union (not an intersection or a single stat's own boundaries), any two instants inside the same epoch segment are guaranteed to see identical values for every stat in the bundle — not just the one the epoch happens to be named after. This is the correctness argument for `_stat_bundle` memoizing 17 stats behind one epoch+version key instead of one key per stat. See `docs/decisions.md` ("Stage 0.5: epoch + stat-bundle memo...").

## Crit
- **Crit is expected value, not per-hit RNG.** The major modifier gains `crit_rate*(0.5 + crit_damage_sources)`. Base crit rate is 15%, base crit damage +50%; both buff types are additive. Crit-damage buffs are inert with no crit chance. See `damage_formula._major_modifiers` and `raid_simulator.BASE_CRIT_RATE` (overridable via `base_crit_rate`, set 0.0 for deterministic tests).

## Effects / stats
- **`damage_taken_up` and `other_core_damage_sources` are now wired.** `raid_simulator` reads both from the registry at each damage instance. Model an enemy "Damage Taken ▲" debuff as a **squad-scoped** effect so every attacker gains it (the debuff is on the boss, so all allies share the same value). **Core-damage sources are gated on `core_hittable`** — like the flat core-hit bonus, "Damage dealt when attacking core ▲" contributes nothing when the boss has no hittable core.
- **"Activates when the enemy appears" = `battle_start`, permanent.** A skill worded that way (e.g. Little Mermaid's Bubble Wave, "Bubble: Damage Taken +5.05% continuously") is always-on for the whole raid — the boss is present from t=0 — so encode it as a permanent squad-scoped enemy-debuff effect fired on `battle_start`, not as a target-state effect gated on some other condition. See `skill_rules/little_mermaid.py`.
- **Other Damage-Up buckets remain unconsumed pass-throughs.** `damage_formula` also accepts `sustained_damage_up`, `true_damage_up`, `shield_damage_up`, `projectile_explosion_damage_up`, `distributed_damage_up`, plus `full_burst_bonus`/`effective_range_bonus`/`final_atk_modifier` — but `raid_simulator` does not read them yet. Encoding an effect with one passes tests yet moves no simulated damage. Wire the specific bucket a unit needs (one line at each `calculate_damage` call site) rather than faking it. (Cross-check the "engine CONSUMES" list in the skill's `references/engine-capabilities.md` and `grep registry.total_for raid_simulator.py`.)
- **"As additional damage" in a burst skill's damage description is the text signal for `full_burst_bonus`.** Fienn resolved the ambiguity (after the retracted Maiden cast-delay theory below) with a general rule: if a burst skill's own damage description contains the phrase "as additional damage," that specific damage instance receives `full_burst_bonus`; otherwise the damage is computed from cast-time effects only and never gets it. This turns "wire `full_burst_bonus`" from a per-unit-verification problem into a well-defined, opt-in-per-damage-instance decision — pass it on that specific `record()`/`_damage_instance` call, mirroring the existing `extra_charge_bonus`/`extra_flat_atk` precedent, not a blanket change touching all 45 existing units. See `docs/decisions.md` ("full_burst_bonus wiring is opt-in per damage instance, gated on skill-text phrase").
- **`distributed_damage_up` is a DPS synergy buff, not a defensive stat.** "Distributed Damage ▲ X%" raises the output of Distributed-Damage dealers (e.g. Scarlet: Black Shadow). It's one of the unconsumed buckets above and additionally needs per-unit gating (only distributed-damage units benefit). Encode it (squad scope) but know it's inert until wired. Easy-to-misread mechanics like this are catalogued in the skill's `references/special-mechanics.md`.
- **`pierce_damage_up` is a general damage-up term.** It's applied to every hit, not gated to actual pierce hits — a known simplification.
- **Caster-scaled buffs use the base character-info ATK.** "ATK X% of caster's ATK" multiplies the caster's base ATK (gear + breakthrough + cube only; excludes overload and other skill effects), modeled as `flat_atk` via `values["caster_atk"]`, which `roster.assemble_simulation_inputs` injects.
- **Steady-state approximation for ramping buffs.** Escalating "previous effects trigger repeatedly" or "stacks up to N" effects are encoded at their max/settled value — a 3-minute raid reaches it almost immediately. Documented per module. **Valid specifically when the fill cadence far exceeds the stack's own decay/reset window** — check the numbers, don't assume: Quency's Explore Route stage chain (3 stages, each gated on the previous being AT its cap) fills every 2 normal attacks, and her SMG fires 20/s, so each stage's ~0.1s fill cadence is far faster than any stage's own 0.5-2s decay window — once a stage first caps, it stays capped continuously for the rest of the fight, making the real ~2.5s ramp-to-full negligible against a 180s raid. See `skill_rules/quency_escape_queen.py`.
- **A buff re-applied on every trigger (per-shot/periodic) silently STACKS unless you opt into refreshing.** `EffectRegistry.total_for` sums all active effects, and `buff_rule`/`registry.add` adds a fresh instance each time, so a multi-second-duration buff re-applied on every qualifying shot (e.g. "ATK +X% for 3s on every Full Charge") overlaps and sums — inflated a real unit's numbers ~2x (SR fire rate) to ~13x (AR fire rate) over a fight before this was caught. If the in-game wording is a duration refresh (not an actual stacking counter), use `refreshing_buff_rule` (`EffectRegistry.add_refreshing`) instead — it truncates that source's still-active same-`(stat, scope)` instance rather than stacking a new one. See `skill_rules/prika.py`, `skill_rules/mint.py`.
- **"For N round(s)" is a bullet-count duration, not seconds or a burst cycle — confirm with Fienn whenever a duration unit is ambiguous.** Easy to misread as continuous uptime or a per-cycle refresh; it actually means the buff is consumed by the affected ally's next N normal-attack shots, then gone (re-granted next cycle). Modeled via `round_buff_rule`'s `RoundGrant`, not a live `Effect` — see `docs/decisions.md` ("Bullet-count round buffs...") and `nikke-skill-encoding/references/special-mechanics.md` ("For N round(s) is a bullet-count duration") for the mechanism.
- **The timed-Effect-with-window-to-next-shot trick lets a shot-count buff reuse the existing seconds-based `Effect` + `total_for`, with no new duration primitive.** `applied_at` = the first covered shot's time; `duration` = (next-uncovered-shot time − applied_at), or fight end if there is no later shot. Reusable pattern for any future "expires after N shots" mechanic. See `raid_simulator`'s shot loop, `round_buff_rule`.
- **RoundGrant→Effect conversion runs as a SECOND pass after ALL units' shot loops (gap #9 refactor) — not interleaved per-unit.** Originally each unit's round grants were converted right after that unit's own shot loop; the gap #9 (first-bullet marker) work moved this to a separate loop over `shot_times_by_slug` that runs once every unit's shots are generated (`raid_simulator.py`, the `for slug, shot_times in shot_times_by_slug.items(): for grant in registry.round_grants():` block). This means a grant recorded by a PER-SHOT rule (not just a burst-cycle trigger) — e.g. Jill Valentine's Magnum first-bullet grant — now converts correctly too, since per-shot rules only run during the (now-earlier) shot loop and couldn't previously be converted inline within that same pass. Burst-cycle-trigger grants (Zwei, Miranda) are unaffected/byte-identical, since those grants already exist before any shot loop runs regardless of which pass converts them.
- **A quantity-based resource must be a FUNCTION OF TIME, not a mutable running total — otherwise it breaks across the two-phase pipeline.** Fills can arrive from the burst-cycle phase (burst / battle-start) AND the shot-loop phase, and the burst cycle runs first, so a counter that accumulates as events are processed would see all burst fills before any shot fill — wrong time order. Instead record fills as `(time, amount)` events and compute `resource_count(time, cap, lifetime)` on demand (like `total_for`/`top_atk_slugs`/`burst_times`). Phase-order-safe because a query at time t only sums fills with `fill_time ≤ t`. See `SquadContext.resource_count`.
- **A count-scaled buff is emitted as a step function of DELTA Effects, so `total_for`'s running sum reproduces `value_fn(count)` at every time — including for TIMED stacks that decay.** Walk the fill/expiry events; at each, add an `Effect(value − prev_value, duration=None)`. Permanent stacks give all-positive deltas that plateau at the cap; timed stacks emit negative deltas as they expire (window = `(t − lifetime, t]`). No truncation bookkeeping, no new registry concept — reuses `add`/`total_for`. A shot sees its OWN fill (inclusive `≤ t`), matching the existing per-shot-rule convention. See `raid_simulator`'s resource resolution pass, `effects.ResourceSpec`/`ResourceBuff`.
- **Resolve boss-dependent fill rates in the sim, not the unit encoding.** Guillotine's EXP fills every 3 Core hits on a core-hittable boss but every 6 normals otherwise. Rather than thread `core_hittable` through `assemble_simulation_inputs`, the `("per_shot_every_core", core_n, noncore_n)` fill kind is resolved by `raid_simulator`'s own `core_hittable` — the boss property stays out of the unit module. Same spirit as gating `other_core_damage_sources` on `core_hittable`.
- **A resource-scaled nuke's percent must resolve in phase 2, not when the nuke is recorded.** A burst-fired nuke gated/scaled by a named resource's count (Julia's Climax additional hit, Cinderella's mirrored hit, Guillotine's Extermination DoT) is recorded during `on_tier_fire` — but the resource's fills aren't populated until the resolution pass runs, which happens AFTER the whole burst cycle. Calling `context.resource_count(...)` at record time would always see zero. Fix: `record()` carries an optional `resource_gate` (name/cap/lifetime/scale_fn) that's resolved into a concrete percent in phase 2 via `context.resource_count(ev["slug"], name, ev["time"], cap, lifetime)` — the same "record now, compute later" trick already used for every other damage instance. A repeating DoT tick just records one event per tick, each independently resolved at its OWN time, so a resource still accumulating mid-DoT correctly raises later ticks. See `docs/decisions.md` ("Resource-scaled nukes resolve their percent in phase 2...") and `raid_simulator`'s `resource_scaled_nukes`.
- **A burst that "attacks sequentially N times" is N separate damage instances, not one instance at N×percent.** Defense is a FLAT per-hit subtraction (`_base_damage`), so splitting into N hits changes the total whenever `enemy_def > 0` — pre-multiplying the percent would overcount (defense only subtracted once instead of N times). `burst_hit_counts` records N identical events at the same instant. See Cinderella's Glass Slippers (10x), Julia-signature's Climax (5x).
- **A burst-fired BUFF gated on a resource has no "phase 2" to defer to, unlike a nuke — so it must be resolved IN the resolution pass itself, not at `on_tier_fire`.** A resource-scaled/gated NUKE can record now and compute its percent later (`resource_scaled_nukes`, above) because every damage instance in this engine is already record-now/compute-later. A buff has no equivalent second pass: `buff_rule`/`registry.add` mutate the registry immediately when the trigger's action runs, and `on_tier_fire` (where a burst's rules fire) runs BEFORE the resolution pass that populates the resource's fills/resets for that cycle — so a gate check done at `on_tier_fire` time would always see a stale or empty resource. Fix: process `resource_gated_buffs` inside the resolution pass itself, once the resource's full fill/reset schedule for the whole fight is known, iterating `context.burst_times[slug]` for each of the owner's own burst times and adding the Effect directly. First/only consumer: Soda's ATK+65.25%/15s (gated on Golden Chip's pre-reset count >= 30). See `docs/decisions.md` ("Resource resets... and `resource_gated_buffs` resolve in the resolution pass...").
- **Same-instant event ordering must be preserved by checking inline against the event log as you walk it, not by merging two independently-sorted lists.** A resource fill mode conditioned on BOTH a global event stream (any squad member's burst-tier fires, Full Burst starts) AND the resource's own running value (Maiden's MP: "+1 if MP==0 on any squad Burst 1", "+1 if MP>=1 on Full Burst enter") needs to know, at each instant, whether the resource's own reset (from its owner's own burst) has already happened relative to that instant's other events. Sorting the reset events and the burst-cycle events separately and merging by timestamp risks an arbitrary tie-break at equal timestamps. Instead, `_resolve_squad_burst_cycle_resource` walks `simulate_burst_cycle`'s own event log in order and checks the owner's own-burst reset inline against each event as the walk reaches it — so same-instant ordering is exactly what the underlying event log already encodes, not a second-order artifact of the merge. This mattered concretely: Fienn confirmed burst1->burst2->burst3->full-burst-enter is a strict, never-violated sequence, so a unit's own burst-tier fire always precedes Full Burst entry in the same instant — which is what makes Maiden's MP-drain-then-refill sequence resolve deterministically (and, as a consequence, makes her second MP-fill rule a provable no-op **when she's the sole Burst-3 unit** — sharing the tier with another Burst-3 attacker breaks the invariant, see the `own_burst_fired_this_cycle()` bullet below and `docs/decisions.md`).
- **"After/every N CRITICAL hits" is not representable — this is a structural limit of the engine's crit model, not an unbuilt trigger.** The engine treats crit as expected value (every hit's damage scaled by `crit_rate * (0.5 + crit_damage)`), never rolling per-hit RNG — so there is no "was this specific shot a crit" event to count, unlike a plain normal-attack or full-charge counter (which per_shot_rules already handles). Discovered encoding Julia's signature Crescendo/Marcato (both crit-hit-count triggers) — permanently deferred, not a to-do for a future extension. Watch for this phrasing (`eve` likely has the same issue, per `roadmap.md`).
- **A buff a burst grants to ITSELF does not retroactively boost that same burst's own damage — confirm in-game, don't assume same-instant means "applies."** Maiden's Diamond Dust and her own "MP is used" self-buff (Elemental Advantage Attack Damage, ATK from Max HP) both fire from the same `own_burst_activate` trigger at the same recorded time, and the engine's default Effect semantics (`applied_at <= now`, inclusive) would let the buff apply to that same instant's damage — but Fienn confirmed in-game (2026-07-12) that Diamond Dust's damage is locked in at cast time, before the self-buff takes effect; only LATER damage (per-shot nukes, normal attacks) sees it. This contradicted an earlier (retracted) theory that a ~1-second cast-to-damage delay was involved — the real mechanism is simpler: cast-time damage, buff active only after. Fixed by applying the self-buff at `time + 1e-6` instead of `time` — small enough that every other consumer is unaffected, but strictly excludes a same-instant query. Don't assume the reverse (that a self-buff DOES apply to its own trigger's damage) either — this is unit-specific and needs confirmation; contrast with Soda's Onward Soda! and Cinderella's Flawless Glass, where the gated/caster-scaled buff DOES apply to that same burst's own nuke (confirmed via those unit's own end-to-end tests). See `skill_rules/maiden_ice_rose.py`.
- **`full_burst_bonus_eligible` is the wiring; "as additional damage" is the policy — the check runs against the damage instance's OWN recorded time, and `full_burst_start` shares an instant with the tier-3 burst that triggers it.** `_damage_instance`/`record()`/`Pulse` all carry an opt-in `full_burst_bonus_eligible` flag; when set, it's checked against `full_burst_windows` (`start <= time < end`) at that specific instance's own time — not the caster's burst time in general. Because `full_burst_start` fires at the SAME timestamp as the tier-3 burst that triggers it, a hypothetical eligible nuke fired at cast time with zero delay would already read as "inside" the window under the inclusive-start check. See `raid_simulator.py::_damage_instance`, `docs/decisions.md` ("Delayed dynamic-hit-count nukes, own-status-window resource fills, and full_burst_bonus wiring (eb4)").
- **Full Burst Bonus vs burst tier timing: whether a Burst-2/-1 unit's own-burst "as additional damage" nuke actually gets the bonus depends on which tier they are, now confirmed with real consumers on both sides.** `full_burst_windows`' start = the tier-3 (slowest) burst's own fire time. A **Burst 3** unit's own-burst/full-burst-enter damage instance lands AT that start (inclusive-start check) → inside the window → gets the bonus (Marciana: Marine Study's "additional damage" Flagged Target nuke fires at `full_burst_start` and correctly receives it). A **Burst 1/2** unit fires at `tier_time - k*gap`, strictly BEFORE the window opens → an "eligible" instance at its own-burst time never actually gets the bonus — marking it eligible would be inert dead code. Helm: Aquamarine (Burst 2)'s Electric-only "additional damage" bullet in Aegis Cannon Overload is the confirmed case: modeled fired at her own burst time WITHOUT the bonus (understates that bullet ~50%) rather than either marking it eligible (dead code) or shifting its fire time to `full_burst_start` (a bigger unit-specific hack). So: an "as additional damage" burst bullet only actually receives the FB bonus in this engine if the caster is Burst 3, OR the instance is delayed/on a per-shot timer into the window (Asuka's pattern — 9s `fire_delay`, or an unrelated per-shot timer). See `docs/decisions.md` ("Gap #5: boss_element context, enemy_def_percent wiring, and Full Burst Bonus timing for a Burst-2 'additional damage' bullet").
- **For repeating-tick DoTs, `full_burst_bonus_eligible` should default to True — the text-phrase check is specifically a single-instant-nuke heuristic.** The "as additional damage" phrase (above) is a proxy for a TIME-based fact: damage NOT computed at the cast instant, landing inside a Full Burst window, gets the bonus. Mana's Fatal Error! (a flat `resource_scaled_nukes` DoT, see below) confirmed this in-game — it gets the Full Burst Bonus even though its text says "as sustained damage," not "as additional damage." For a single-instant nuke, cast-time-vs-delayed is genuinely ambiguous from text alone, so the phrase check is still the right call there. For a repeating-tick DoT, every tick after the first is inherently computed strictly after cast "by construction," independent of wording — so assume `full_burst_bonus_eligible=True` by default for any `resource_scaled_nukes` consumer (subject to checking the DoT's duration doesn't obviously outlast the Full Burst window), rather than requiring the phrase. `resource_scaled_nukes` gained the same opt-in flag `record()`/`dynamic_hit_count_nukes` already had, to make this possible. Not yet retroactively applied to Guillotine's Extermination Hero-Level DoT (earlier consumer, predates this capability) — open follow-up. See `skill_rules/mana.py`, `docs/decisions.md` ("full_burst_bonus_eligible generalizes beyond the 'as additional damage' text phrase for repeating-tick DoTs").
- **A resource-scaled repeating nuke's `"resource"` key is optional — omit it for a flat, non-scaled repeating DoT.** `resource_scaled_nukes`' tick_count/tick_interval loop is genuinely two features bundled together (repeating ticks + resource-based percent scaling); when a unit only needs the repeating-tick shape (Mana's Fatal Error!, a flat 396%/sec DoT), leave `"resource"` out rather than inventing a dummy always-full resource just to satisfy a previously-mandatory field. See `raid_simulator.py`'s `resource_scaled_nukes` loop.
- **A burst nuke that fires on a DELAY (not at cast time) needs `fire_delay` + a matching `"own_burst_delayed"` reset — don't assume every burst effect lands instantly.** `dynamic_hit_count_nukes`' optional `fire_delay` fires the nuke (and reads/reset its resource) at `burst_time + delay`; `ResourceSpec.resets` supports `"own_burst_delayed"` with its own `delay` so a resource's own reset lands at that same delayed instant, not at burst time. First/only consumer: Asuka's Annihilation nuke (fires 9s after her burst, when her "Annihilation State" self-status ends). Don't reuse the zero-delay default and hope it's close enough — a mistimed nuke changes which Full Burst window (if any) it falls in for `full_burst_bonus_eligible` purposes.
- **A resource fill window can be anchored to the OWNER's own burst-fire time, not just the squad's global Full Burst window.** `("per_shot_every_during_own_status_window", n, window_duration)` counts shots toward an "every n" tally only within `window_duration` seconds of one of `context.burst_times[slug]` — distinct from the earlier `per_shot_every_during_full_burst` (anchored to `full_burst_windows`, a squad-global instant). Needed whenever a unit's own short self-status window (e.g. Asuka's 9s Annihilation State) starts at HER burst, not at Full Burst start, which is a different instant. See `raid_simulator.py`'s resource fill resolution.
- **`charge_speed_percent`/`attack_speed_percent` are only evaluated once per MAGAZINE BOUNDARY — a short-lived Effect window can silently be inert or over-apply.** Both callables (`attack_rate.py`'s `_at(t)` pattern, threaded through `generate_shot_times`/`generate_charge_shot_times`) are read once at each magazine's start, not per-shot. A speed-change Effect whose window is shorter than a magazine either (a) never lands at all, if granted mid-magazine (no boundary falls inside it — confirmed by `test_one_round_charge_speed_grant_is_inert_mid_magazine`), or (b) slows/speeds the ENTIRE next magazine, if it happens to cover a boundary — neither matches literal "for N seconds"/"for 1 round" semantics. Don't model a short-lived charge/attack-speed grant literally; fold its intended time cost/benefit into a damage-bonus approximation instead (Ada Wong's Special Modification: the ×4 charge-time slowdown that can't land is folded into a reduced net `charge_damage_bonus`, `15/4 − 1 = +2.75` — see `docs/decisions.md`, "Ada Wong: Special Modification's charge-speed half..."). Check this trap before encoding ANY unit that pairs a short-duration charge/attack-speed grant with another buff meant to offset its cost.

- **A magazine-boundary "last bullet" marker is the shot at index `magazine_size - 1`, re-derived from the SAME live `max_ammo_percent_at` callable already used to size each magazine — this is what makes [Max Ammo Up] "just work" with zero extra plumbing.** `attack_rate.magazine_last_bullet_times`/`charge_last_bullet_times`/`last_bullet_shot_times` mirror `generate_magazine_shot_times`/`generate_charge_shot_times`/`generate_shot_times`'s exact 3-tier structure (2 raw-parameter functions + 1 weapon-dispatching wrapper) instead of changing those functions' return shape to carry the marker inline — an additive sibling set avoids breaking any of `test_attack_rate.py`'s existing assertions on a flat list of shot times. General pattern worth reusing: when a new per-shot marker needs to piggyback on existing shot-generation math, mirror the function's tier structure as new functions rather than reshaping its return type. Correctness edge case: a magazine truncated by `fight_duration` ending (not actually emptied) must NOT be marked last — handled by construction, since "is_last" checks the recorded round's INDEX against `magazine_size - 1`, not whether it's the last round appended to the output list. See `docs/decisions.md` ("Magazine-boundary 'last bullet' marker mirrors the existing shot-generation function shape").
- **Attack/charge speed change shot CADENCE, not magazine CAPACITY, so they're structurally irrelevant to any magazine-boundary feature — and neither is wired as a shot-interval modifier anywhere in this engine anyway.** Shot cadence is fixed, computed once from `RATE_OF_FIRE_60FPS`/`charge_time` and never re-read from the registry (both stats are on the "Stats the engine does NOT consume" list). Even if they were modeled, they'd shift WHEN shots land, not HOW MANY rounds fit in a magazine — only `max_ammo_percent` determines magazine size. Confirmed while building the last-bullet marker above: no special-casing needed for attack/charge speed, and none should be added speculatively.
- **A passing unit test that manually calls `fire_trigger("some_name", ...)` doesn't prove `raid_simulator` ever fires that trigger for real.** Helm's Frontline Command last-bullet Crit Rate buff had a passing test built by invoking `fire_trigger("on_last_bullet_hit", ...)` directly — but `on_last_bullet_hit` isn't one of the engine's real trigger names (only `battle_start`/`own_burst_activate`/`ally_burst_activate`/`full_burst_enter`/`full_burst_end` are dispatched by `simulate_raid`'s actual event loop), so the rule silently never fired in any real simulated raid despite its own unit test being green. A test that manually fires a trigger only proves the rule's ACTION logic is correct in isolation, not that anything in the real engine ever calls it with that name. Worth grepping other modules for `fire_trigger("<name>"` calls whose `<name>` isn't in the real trigger list. Fixed by rewiring to `per_shot_rules`' `"last_bullet"` mode instead (a different mechanism entirely — checked directly against per-shot loop state, not dispatched via `fire_trigger` at all). See `skill_rules/helm.py`.
- **A live time-window check against `context.burst_times[caster]` is the fallback when a self-granted status's duration doesn't line up with `own_burst_fired_this_cycle()`'s per-cycle semantics.** `own_burst_fired_this_cycle()` (see Burst rotation, below) works as a status-equivalence trick specifically because the status lasts the WHOLE cycle until the next reset (Asuka/Mana). Privaty's "Designated Target" (set by her burst, lasting a fixed 10s against her own 40s burst cooldown) is a genuine fraction of the cycle, not the whole thing — so it's instead checked as `any(bt <= time < bt + duration for bt in context.burst_times[caster_slug])`, evaluated fresh at the querying shot's own time, inside the per-shot rule's action. Reusable whenever a self-granted status has a real timed window shorter than the caster's own burst cycle. See `skill_rules/privaty.py`.
- **Unconfirmed default: a same-instant self-applied debuff is assumed to affect its own triggering hit's damage, and repeated triggers within the debuff's window are assumed to STACK (not refresh).** Privaty's LD Assault adds its squad Damage Taken debuff via plain `registry.add` (not `add_refreshing`) at the same instant as the hit that triggers it — under the engine's default same-instant-inclusive Effect semantics this means (a) that hit's own damage already reflects the debuff it just applied (same-instant self-reference, like Soda/Cinderella's confirmed precedent, unlike Maiden's confirmed-opposite case), and (b) two last bullets within 10s of each other produce two separate summed debuff instances rather than one refreshed value. Neither is verified in-game — it's just what the engine defaults to absent contrary evidence, the same open-item status Maiden's self-buff-timing question had before Fienn confirmed it in-game. Flag for future in-game verification. See `skill_rules/privaty.py`'s module docstring.
- **A `SkillRule`'s action has no access to the boss's element unless it's threaded onto `SquadContext` — `boss_is_element(element)` is the condition helper for "if the enemy is X Code" bullets.** `raid_simulator` injects `SquadContext.boss_element` from `BossProfile.element` (deck_search already passes this end-to-end); `boss_is_element(element)` (`squad_engine.py`) mirrors the existing `ally_bursted`/`deck_contains` condition-helper pattern rather than gating inside each action (which would duplicate the check across modules). `buff_rule`/`refreshing_buff_rule`/`instant_nuke_pulse_rule` all gained an optional `condition` param so a gated bullet reuses the same builder as an ungated one. First consumers: Brid: Silent Track (Wind debuffs), Helm: Aquamarine, Marciana: Marine Study. See `docs/decisions.md` ("Gap #5: boss_element context...").
- **`boss_is_element` composes with any per-shot mode — a per-shot nuke/buff can be boss-element-gated (and even window-gated) at once.** A per-shot rule's `SkillRule.condition` is honored in every `per_shot_rules` mode (`after`/`every`/`last_bullet`/the window-gated modes), so nothing extra is needed to combine a boss-element gate with a shot-count or window trigger. Marciana's High-Risk 20-normal nuke is a plain `every 20` gated on `boss_is_element("Electric")` (the "High-Risk Target state" is treated as maintained whenever the boss is Electric, so it's NOT windowed — Fienn 2026-07-16).
- **`enemy_def_percent` was fully specified in `damage_formula` but silently inert until gap #5 — `raid_simulator` never read it from the registry.** Wired as `enemy_def_percent=registry.total_for("enemy_def_percent", target, time)` in `_damage_instance`, emitted as a squad-scope enemy debuff exactly like `damage_taken_up`. No DEF=0 floor clamp exists yet — none of the currently-encoded units' debuffs are large enough to need one (boss DEF 31784 stays positive against the largest current DEF-down, Marciana's 10.56%) — add a clamp if a future unit's debuff risks it. First consumer: Marciana: Marine Study's "High-Risk Target" DEF ▼ debuff, but the wire moves damage for every attacker against every deck now that it's live, not just her. See `docs/decisions.md` ("Gap #5...").
- **Solo-raid global assumptions**, adopted encoding Marciana and applicable to any future encoding: Rapture count is always 1 (the boss) — "N or fewer Raptures" conditions are always met, "N or more Raptures" (N>1) bullets never fire; boss DEF = 31784 is the `enemy_def` value to use for solo-raid sims (`BossProfile.enemy_def` defaults to 0.0, so callers must set it explicitly); "Flagged Target" / "highest Max HP enemy" = the boss (the single/highest-HP enemy in a raid). See `docs/decisions.md` ("Gap #5...").

- **The `per_shot_rules` pass runs AFTER `simulate_burst_cycle` has already fired every burst-cycle trigger — so a burst-cycle rule (`battle_start`/`own_burst_activate`/`full_burst_enter`/`full_burst_end`) cannot read a counter or status that a per-shot rule builds.** `raid_simulator.simulate_raid` calls `simulate_burst_cycle` first (firing all four burst-cycle trigger types against the current context), then runs the `per_shot_rules` pass afterward. A burst-cycle rule that tries `context.activation_count(...)`/`context.has_status(...)` for something only a per-shot rule increments will see the pre-per-shot value (typically zero), not the real end-of-cycle count. Concretely: if a buff's VALUE depends on a running normal-attack count AND another burst-cycle rule must read that count (Arcana: Fortune Mate's Keepsake Album, fired on `full_burst_end`, reads the Precious Moments stack that would naturally be built from "6th normal attack" shot-counting), the count must instead be built in the burst-cycle pass — e.g. increment once per Full Burst on `full_burst_enter` via `record_activation`/`activation_count`, not by counting shots directly. This substitution is only valid when the normal-attack threshold is guaranteed reached exactly once per relevant window (an exact per-cycle equivalence, not an approximation onto the wrong trigger) — Fortune Mate's SG fires far more than 6 shots in a 10s Full Burst window, so "6th normal during Making Memories" and "once per Full Burst" coincide exactly. Contrast: the resource-scaled/gated NUKE path (`resource_scaled_nukes`, `resource_gated_buffs`, above) IS deferred into a later resolution pass, so a nuke scaled by a per-shot-built resource count works fine — but a buff added directly to the registry via `registry.add` inside a burst-cycle rule's action does NOT get that deferred resolution; it reads the context synchronously, at the time the burst-cycle pass runs. See `raid_simulator.py` (the `simulate_burst_cycle` call followed by the `per_shot_rules` pass) and `skill_rules/arcana_fortune_mate.py::gain_precious_moments`/`apply_keepsake_album` for the worked example.

## Burst rotation
- **`own_burst_fired_this_cycle()` doubles as an equivalence trick for "on FB enter while in [a self-status my own burst just granted]" — no new status-tracking needed.** Both Asuka's Emergency Repair (Skill 2, "on FB enter while in Annihilation State") and Mana's Metal sigma (Skill 2, "on FB enter while in Metal sigma status, consumed then restored by her own burst") describe a continuous named self-status gating a Full-Burst-entry buff. Because this engine's strict burst1→burst2→burst3→full-burst-enter ordering means a unit's own tier-3 burst always fires immediately before full_burst_enter in the SAME cycle, "her own burst fired this cycle" (the already-existing `own_burst_fired_this_cycle()` condition, previously used by Grave/Arcana for a full_burst_END gate) is exactly equivalent to "her self-granted status is still active" at the instant full_burst_enter checks it — for any deck this engine can simulate (one attacker per burst tier). Reuse this condition directly on a `full_burst_enter` trigger for any future unit with this shape, rather than building real `set_status`/`clear_status` bookkeeping. See `skill_rules/asuka_shikinami_langley_wille.py`, `skill_rules/mana.py`.
- **"Who bursts vs who buffs" = deck left-to-right order.** `burst_cycle` fires the leftmost eligible Nikke per burst tier, so the intra-tier ordering *is* the role assignment. The deck search explores those orderings. See `burst_cycle.py`.
- **Cycle timing waits for the slowest tier's cooldown.** The next Full Burst starts when whichever burst tier's cooldown clears latest (the gauge always charges faster than cooldowns for a raid-viable deck). A cycle is only "missed" when a burst tier is structurally absent from the deck, not when cooldowns lag.
- **`activation_count` starts at 0 — guard alternating-parity statuses against the pre-first-activation state.** A skill that alternates between two statuses each burst (e.g. Mint: Dancing on her 1st burst, Singing on her 2nd, ...) is naturally modeled as `count % 2 == 0` for the "even" status, but count 0 (before she has ever burst) also satisfies that — wrongly treating the unit as already in the even status from t=0. Guard with `count > 0`. See `skill_rules/mint.py::_mint_is_singing`.
- **Precise "highest final ATK" targeting must rank at APPLICATION time, using live buffs — not a static/squad approximation.** `SquadContext.top_atk_slugs` ranks the deck by each unit's ATK as buffed so far, evaluated when the targeting rule fires. This matters because of the same tier-ordering fact above: a Burst-1 unit's own burst (`own_burst_activate`, tier 1) fires before her Full-Burst-enter skill (tier 3), so by the time her FB-enter targeting rule runs, her own burst's ATK buff is already applied and correctly reflected in the ranking — dynamic (not pre-computed) resolution handles this automatically. See `skill_rules/miranda.py`, `nikke-skill-encoding/references/special-mechanics.md` ("Highest-final-ATK top-N targeting").
- **A per-shot/periodic condition sees the FINAL context, not a live one — timestamp alternating statuses instead of checking `has_status`.** Record-then-compute's post-pass evaluates every shot's condition against the whole-fight-final `SquadContext`, so `activation_count`/`has_status` there answer "at the end of the fight," not "at this shot's time." For a status that alternates or gets pinned mid-fight (Mint's Singing), record when it's true instead: `SquadContext.burst_times` (per-unit burst-tier fire times) + `status_since`/`set_status(..., time=...)` (earliest-set timestamp), then compute the status AT a given time (`skill_rules/mint.py::mint_singing_at`) rather than querying it live. This is what let solo Mint's per-cycle Dancing/Singing alternation finally be modeled (previously deferred as untrackable under per-shot).

## Data (lootandwaifus.com primary, dotgg fallback)
- **"Is this stat already folded into the displayed value?" must be asked per source — ShiftyPad answers it differently for cubes vs. overload.** ShiftyPad's shown hp/atk/def already include the equipped cube's contribution (bare character stats if none is equipped), but shows overload option values SEPARATELY from those same stats, additive on top (both confirmed by Fienn — see `docs/decisions.md`, "ShiftyPad's displayed hp/atk/def already include the equipped cube"). Don't assume a UI's convention is uniform across every stat-contributing source it displays; check each one. This mattered far more for automated ingestion than manual entry: a human copying numbers by hand tends to notice something looks off, but a scraper swallows ShiftyPad's displayed numbers wholesale and would silently double-count (or drop) a source's contribution if the fold-in assumption is wrong.
- **NIKKE base stats (ATK/HP) are uniform across all characters of the same class (Attacker/Supporter/Defender) — only DEF varies per-character, and the engine doesn't consume DEF anyway.** blablalink's CDN serves each character's stat table as a `character_level_attack_list`/`_hp_list` array (level 1-1200); byte-for-byte diffing two Attackers (Rapi, Quency) showed the attack and HP arrays are identical, and likewise for Supporter (Mast) and Defender (Moran). Breakthrough/core coefficients (`grade_attack=20`, `core_attack=200`, `grade_hp=3000`, `core_hp=200`, etc.) are also identical across all four characters checked. Collectible-item stats are uniform per rarity tier (R/SR), and a favorite item (SSR) is fixed at "SR collectible at level 15" rather than its own stat curve. Cube flat stats are uniform regardless of cube type. **Practical consequence: a per-character stat manifest is unnecessary** — 3 class stat tables plus the shared breakthrough/core coefficients cover the whole roster (Phase B's collector design leans on this). See `data/blablalink-cdn/NOTES.md` (gitignored local data, not committed) and `docs/decisions.md` ("Phase B redefinition...").
- **Solo Raid is level-400-normalized — the deck-builder must use level-400 stats, not the user's actual account level.** ShiftyPad's main stat display shows the character's actual-level value plus a level-slider delta; the level-400 number is only obtained as (actual + delta at slider=400), never displayed as a clean standalone figure. Confirmed by measurement: the current manual-entry convention (actual level, e.g. 663) gives ATK ~2.9x too high for Solo Raid (Rapi: 418,862 actual vs 143,543 at level 400). See `docs/decisions.md` ("Phase B redefinition...").
- **Neither the ExiaInvasion export nor the authenticated raw API return the one number Phase A/B actually need: final assembled ATK.** The export carries skills/breakthrough/overload rolls but no HP/ATK/DEF and no per-character equipped cube (its `cubes` key is only the account-wide inventory). The authenticated raw API (`GetUserCharacterDetails`) goes further — armor tier/level, cube, skills — but still never returns the final computed ATK; only ShiftyPad computes and displays that, client-side. This is why Phase B's collector reads ShiftyPad's DOM rather than either data source. See `docs/decisions.md` ("Phase A: ExiaInvasion JSON roster import...", "Phase B redefinition...").
- **CDP (`--remote-debugging`) attach to an already-logged-in browser is how a personal tool reaches session-gated blablalink data without storing credentials.** Since ShiftyPad/blablalink don't expose a token-based API for this use case, the Phase B collector attaches to Fienn's own logged-in Chrome via Chrome DevTools Protocol rather than persisting a cookie/token — the browser's own session is the credential store. A per-Nikke ShiftyPad page is reached at `/shiftyspad/nikke?nikke=<resource_id>`, where `resource_id` is available both in blablalink's character-directory data and in the ExiaInvasion export.
- **`data/` is gitignored, so a git worktree does NOT get it — any coverage or loadability measurement taken in a worktree is a false negative until you sync.** Encoding Ein (2026-07-17), a probe said she had no dotgg weapon-stat file, so she was written up as "encoded but not API-loadable, no honest source for her weapon stats". Fienn pointed out `data/dotgg/char_ein.json` plainly exists and her dotgg page is live — she shipped well before the 2026-05 shutdown. The worktree's `data/dotgg/` had 53 files against main's 71: `data/dotgg/` and `data/lootandwaifus/` are in `.gitignore`, and git only ever populates a new worktree from TRACKED files. The 18 missing ones had been collected in main after this worktree was cut. Syncing (`cp -n ../../../data/dotgg/*.json data/dotgg/`) flipped loadable from 50/58 to 54/58 — ein, ark-ranger-black, prika and marciana-marine-study all came back at once, and prika's return is what finally lets the mint+prika Encore synergy matter in a real deck search. **Before measuring anything that reads `data/` from a worktree, run `python3 scripts/sync_worktree_data.py`** (no-op in main, copies only missing files, safe to re-run; `--check` reports drift and exits 1 without copying). Treat "the data isn't there" as a worktree artifact until checked against the main checkout. The same trap applies to `node_modules` and `.venv`.
- **lootandwaifus.com is the primary data source** (switched 2026-07-10) — at least as current as dotgg (which lags ~2 months of releases) and richer listing metadata. Cross-verified exact match against dotgg on Little Mermaid. `api.dotgg.gg` is now a fallback/cross-check. See `references/character-data-sources.md`.
- **Skill values are per level; retain all levels.** Encoding builders take a single-level values dict, so the user's actual skill level selects `levels[level-1]`. Users invest to different levels (Privaty's burst was used at level 7, not 10), so data collection must keep the full level data, never just max.
- **Signature weapon = `dollskills`, and it can add effects.** When `dollskills` is present the character's signature weapon is completed; it changes values and can add entirely new effects/slots, not just bigger numbers. Always check `dollskills` vs `skills`.
- **max_ammo changes apply to base ammo and sum.** An overload ammo increase and a skill's ammo decrease (e.g. Privaty EX Magazine) both compute against BASE ammo and add — the decrease is not taken off the already-increased total. See `attack_rate`.
- **dotgg character-data filenames use dotgg's own slug, not this project's roster slug — locate a unit's file by its JSON `"url"` field, never by constructing a filename from our slug.** Drake's dotgg file is `char_drake-nikke.json`, not `char_drake.json`; a naive filename join silently "not found"s (wrongly excludes) any unit whose dotgg slug diverges from ours. See `backend/app/skill_values.py::_dotgg_path_for`, `docs/decisions.md` ("dotgg data files are indexed by their JSON 'url' field, never by filename").
- **dotgg stopped updating its NIKKE data around 2026-05 — units released after that cutoff need a manual weapon-stats stub (`"source": "manual"`), and an unfilled field in that stub must be OMITTED, never left as an empty string.** `user_roster._weapon_stats` only checks field presence (`field not in dotgg_data`), not value validity — an empty string passes that check and then crashes at `int("")`/`float("")` deeper in the same function, whereas an absent field returns `None` and cleanly excludes the unit (no data yet, not a crash). `scripts/collect_dotgg_weapons.py --stub <slug>` templates leave TODO fields absent (tracked via a `_todo` list) for exactly this reason. See `backend/app/user_roster.py::_weapon_stats`, `docs/decisions.md` ("dotgg's NIKKE data feed stopped updating...").
- **ShiftyPad's tabs (Equipment/Skill/Collection/Cube) are `v-if`, not `v-show` — only the active tab's markup exists in the DOM, and the main stat panel is a SEPARATE DOM branch from all of them, so there is no single container that holds everything.** A pre-implementation manual spike clicked through the tabs and saw them appear to coexist (the SPA caches recently-viewed tab state), which misled the first capture design into assuming one `page.content()` snapshot on the Equipment tab would carry every surface (this claim is still stale in `tools/collect-blablalink/RECIPE.md` section (b) — the shipped `capture.js` overrides it). The robust capture instead visits each of `Equipment`/`Skill`/`Cube` in turn and plucks each surface (stat rows / overload / skill rows / cube) by its own local DOM anchor (e.g. the div whose header child is exactly `Equipment Effects`; a `div` with two `<p>` children labeled HP/ATK/DEF), deduping the stat-panel fragment which repeats on every tab. Skill content in particular only renders after the Skill tab is actually opened, on some units. See `tools/collect-blablalink/capture.js::pluckSurfaces`/`captureUnit`.
- **jsdom's `textContent` has no layout newlines, so `\bATK\b`-style regexes fail against concatenated stat text like `"ATK240903"` — locate the stat panel structurally, not lexically.** `parse.js` finds two-`<p>` rows whose value cell matches `"<number> <signed delta>"` (e.g. `"418862 -275319"`, `"5097 +89718"`) — this pattern is LV-position-independent (works regardless of which level the page happened to render at capture time) and, critically, is what DISTINGUISHES the main stat panel (always has a delta, because the level slider is always off the actual level after stepping to 400) from equipment/cube stat displays (always a bare number, no delta). `raid400 = actual + delta`; delta is negative when the account's real level is above 400 (the common case) and positive when a level-1 uninvested unit is stepped UP to 400.
- **Two ID systems must be joined via a third, rotating-URL source: the game API keys by `name_code`, ShiftyPad's URL keys by `resource_id`.** Join path: the nikke **directory** (a CDN JSON array carrying both `resource_id` and `name_code`, plus `original_rare` and `name_localkey.name` = English name; its URL hash rotates, so discover it at runtime by intercepting whichever JSON response on a ShiftyPad page load is an array whose items have both fields) × `GetUserCharacters` (the owned-roster API, keyed by `name_code`), filtered to `original_rare === 'SSR'` (raid content is SSR-only). **`GetNikkesOrder` is a favourites list only — it is NOT the owned roster and must not be used for enumeration**, a trap because its name suggests otherwise. See `tools/collect-blablalink/RECIPE.md` section (c)/(d), `collect.js`.
- **A name-alias table SHARED by two import paths with different naming conventions is a latent mis-mapping bug — and a silent one, because a wrong slug is still a *valid* slug.** The ExiaInvasion export uses short in-game names, the collector's `roster.json` uses full directory names, and both went through one `resolveSlug` alias table, so the two paths wanted contradictory mappings for the same string. Nothing errored: base `"Soline"` simply resolved to `soline-frost-ticket`, and since drafts merge by `character_slug`, the variant's accurate collected stats got clobbered by the base's. Fixed by giving the collector path its own `resource_id`-keyed table (`frontend/src/lib/resourceIdSlugMap.ts`) and leaving the alias table untouched for ExiaInvasion. Name-based schemes also can't separate the three distinct units that all display as `"Rei"`. See `docs/decisions.md` ("Collector roster units map to slugs by `resource_id`...").
- **When two encodings of the same character share ONE game ID, that ID cannot be the discriminator — identity keys answer "which character", investment/progression state needs its own layer.** A "dual-slot" unit (both `<slug>` and `<slug>-signature` encoded — Drake, Julia) has one `resource_id` for both; whether the signature applies depends on the user owning the in-game Favorite Item, which is per-user and changes over time. So `resourceIdSlugMap` maps id → BASE slug only, and ownership lives in a separate `SIGNATURE_OWNED` set. Merging the two into one table looks tidier and is wrong for everyone but the author, at one moment in time.
- **A guard test can only catch what its source of truth knows — name the blind spot as part of the guard's contract.** `backend/tests/test_resource_id_slug_map.py` cross-checks the hand-authored frontend map against the live `ENCODED_SLUGS`, so it catches typos, stale slugs, missing entries, and newly encoded dual-slots (encoding a new Nikke red-fails the backend suite until the map or `KNOWN_UNMAPPED` is updated — intentional). It cannot catch a wrong-but-VALID `resource_id`, because no committed data maps ids to names; closing that needs a committed public directory snapshot.
- **`data/dotgg/` and `data/lootandwaifus/` are gitignored local data assets — a git worktree does not get them for free.** Data-dependent tests fail broadly in a fresh worktree until both directories are copied over from the main checkout; conversely, deliverables produced while working in a worktree (new/updated data files) are handed off by copying them back to the main checkout, not by committing them (they're gitignored everywhere).
