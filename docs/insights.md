# Insights

Engine gotchas and reusable patterns — the things that surprised us or would
trip up the next person. Grouped by topic. For the encoding procedure and the
full stat/trigger/scope catalog, see the `nikke-skill-encoding` skill.

## Full Burst 보너스의 기준은 **연산 시점**이다 — "추가 대미지" 문구는 그 대리 지표일 뿐

- 확립: 2026-07-26~27 (Fienn). 2026-07-12의 문구 규칙을 **대체하지 않고 감싼다.**
- **원칙:** 대미지 인스턴스가 **연산되는 시각이 Full Burst 창 안이면** 보너스를 받는다.
  문구는 보지 않는다.
- **그럼 "as additional damage" 규칙은 왜 있었나:** B3 유닛의 버스트 스킬에서 그 문구는
  "**캐스트 순간이 아니라 얼마간 딜레이 후에 대미지가 들어간다**"는 뜻이고, 그 딜레이가
  인스턴스를 FB 창 안으로 밀어넣는다. 즉 문구는 시점을 텍스트로 추정하는 **대리 지표**였다.
- **적용 규칙 (판단 순서):**
  1. **연산 시각을 알 수 있으면 문구를 보지 않는다.** 샷·틱·소환물처럼 캐스트 이후의
     구체적 시각에 계산되는 것은 `full_burst_bonus_eligible=True`로 두고, 엔진의
     창 검사(`start <= time < end`, 인스턴스 자기 시각)에 맡긴다. 플래그는 **검사를
     켤 뿐**이라 창 밖 인스턴스는 자동으로 못 받는다 — 근사가 아니라 정확하다.
  2. **시각이 텍스트만으로 모호한 단일 순간 넉에만** 문구 검사를 남긴다.
  3. 여전히 유효한 타이밍 사실: B1/B2가 **자기 버스트 시각에** 터뜨리는 인스턴스는
     `full_burst_start` **이전**이라 자격을 줘도 죽은 코드다(헬름: 아쿠아마린 사례).
     **B3도 마찬가지다** — 사이클이 [3단계 진입 → B3 사용 → **풀버스트 시작**]이므로
     B3의 캐스트-시각 인스턴스도 창이 열리기 **전**이다(Fienn 사격장 측정, 2026-07-27 —
     아래 "★ 진짜 원인" 참조). 창 안에 드는 것은 **캐스트 이후에 연산되는** 인스턴스뿐이다.
- **보너스의 크기는 +0.5다** (Fienn 확인, 2026-07-27). `full_burst_bonus`는 **크기가
  아니라 플래그**다 — `raid_simulator`가 창 안이면 `1.0`을, 밖이면 `0.0`을 넘기고
  `damage_formula._major_modifiers`가 **`full_burst_bonus * 0.5`** 로 major modifier
  버킷에 더한다. **호출부의 `1.0`만 보고 "+100%"로 읽지 말 것** — 실제로 이 착각이
  한 번 나왔다. 크리티컬(`0.5 + 크리 대미지원`)·코어와 **같은 버킷**이라 서로 가산이지
  곱셈이 아니다.
- **이 원칙으로 고친 다섯 곳** — 모두 문구 규칙이 놓치던 자리다:
  - **나유타** Hypocrisy 풀차지 넉(530.46%): 트리거가 풀차지(1.8초)이고 그건 그녀의
    버스트 이후에만 일어난다 → 전부 창 안. 0.79x → 0.85x.
  - **홍련** 단계 넉(283.03/565/848.03%): 각 단계가 **자기 샷의 시각**에 연산된다.
    0.62x → 0.76x.
  - **아니스: 스타** Shooting Stars(40틱): 버스트→FB 발동 **0.2초**, 틱 간격 **0.25초**
    → 첫 틱부터 창 안. 0.748B → 0.816B.
  - **반복 틱 DoT 일반**(기존 Mana 사례): 첫 틱 이후는 구성상 캐스트 이후 → 기본 True.
  - **신데렐라** Flawless Glass 퍼샷 넉(136.6%, 2026-07-27 추가): 풀차지 명중마다
    발동하므로 샷의 시각을 안다. 486발 중 **160발(33%)이 창 안**이고 그 창이 이 소스
    딜의 61%를 갖는다. 넉 +27.9%.
- **함정 1:** 문구 규칙을 그대로 믿고 "as damage니까 자격 없음"으로 적어둔 독스트링이
  여럿 있었다(홍련·아니스). **"보수적 해석"이라 적혀 있으면 대개 미검증 가정이다.**
- **함정 2 — 감사는 유닛이 아니라 불릿 단위로 돌려야 한다.** 2026-07-26의 FB 감사는
  **버스트 넉 경로만** 훑으면서 신데렐라를 "그녀의 additional damage 불릿은 Beautiful
  미러(자원 게이팅 넉)"라며 **유닛 단위로** 기각했다. 그런데 Flawless Glass에 **두
  번째 그런 불릿**(평범한 퍼샷 넉)이 있었고 그것이 1년치 딜의 22~29%였다. 그 감사문
  자신이 남긴 결론이 "유닛 수로 세면 틀리고 불릿 단위로 읽어야 맞는다"였는데, 정작
  그 감사가 유닛 단위로 끝났다. **경로별로 훑을 때는 다른 경로에 같은 문구의 불릿이
  남아 있는지 반드시 되짚을 것.**

## 사격장 한 발이 시뮬 한 시즌보다 낫다 — 볼륨의 에스컬레이션 버프가 처음부터 최대였다

- 조사: 2026-07-27. 신데렐라 과대(덱4 1.48x)의 원인 추적. **실기록(180초 총합)으로는
  못 갈랐고, Fienn의 사격장 단발 측정이 한 번에 갈랐다.**
- 측정 설정(Fienn): 볼륨 · 크라운 · 신데렐라, Lv 665, 표적 작열/우월코드 미적용/DEF 100,
  **전투 개시 1초의 첫 버스트만**. 표기값 — 불릿1 **12,674,307**(논크리) / **20,958,234**(크리),
  불릿2 **513,863** / **737,770**.
- **크리 배율 두 개가 열쇠였다.** 크리는 major modifier에 `0.5 + 크리대미지원`을 **가산**하므로
  `(M+c)/M = r`. 두 불릿의 비를 나누면 **M₂/M₁ = 0.65361/0.43574 = 1.50000** — 소수 5자리까지
  정확히 1.5다. 즉 **M₁ = 1, M₂ = 1.5**이고 이것이 한 번에 세 가지를 확정했다:
  **FB 보너스 = +0.5** · **버스트 불릿1("as damage")은 FB 보너스를 못 받는다**(엔진 정상) ·
  **불릿2("as additional damage")는 받는다**(엔진 **누락**).
- **그리고 크리대미지원을 역산하니 0.65361 − 0.5 = 0.1536이었다.** 신데렐라 오버로드가
  0.0762이므로 스쿼드 기여분은 **0.0774**. 엔진은 **0.2845**를 주고 있었다.
- **원인:** `volume.py`가 Drop the Beat의 크리 대미지를 **세 에스컬레이션 단계의 합**
  (7.74 + 9.42 + 11.29 = **28.45%**)으로 계산해 **전투 시작부터** 건다. 독스트링이 스스로
  "Simplification ... steady-state value is the sum of all three"라고 적어 뒀다.
  게임은 **첫 발동에 1단계 7.74%만** 준다 — `description_value_04`와 실측이 **소수점까지
  일치**한다. 크리 대미지원을 0.1536으로 바꾸면 크리 배율이 **1.6536 = 1.6536**으로
  정확히 맞는다.
- **왜 이게 큰가:** 스쿼드 범위 버프라 **볼륨이 낀 덱 전원**이 초반 사이클에서 부풀어
  오른다. 그리고 이것은 마스트 취기와 **같은 유형**이다 —
  [[prefer-cycle-accurate-escalation]]의 "에스컬레이션 버프는 사이클별로 모델링하라"가
  이미 있는 규칙인데 볼륨에 적용되지 않았다.
- **일반 교훈: 총합 실기록으로는 상쇄되는 오류를 못 가른다.** 180초 5덱 합계는 22개
  유닛 × 여러 버프의 곱이라 어떤 조합으로도 맞출 수 있다. **단일 히트의 표기값 + 크리/
  논크리 쌍**은 major modifier 버킷을 **대수적으로 분리**해 준다 — 앞으로 의심스러운
  버프는 사격장 단발로 재는 게 압도적으로 싸다.
- **★ 진짜 원인 (Fienn, 2026-07-27) — B3의 버스트 대미지는 풀버스트가 열리기 *전에*
  연산된다.** 버스트 사이클은 [1단계 진입 → B1 사용 → 2단계 진입 → B2 사용 →
  **3단계 진입 → B3 사용** → **풀버스트 시작**] 순이다. B3의 버스트 스킬 대미지는
  *자기 캐스팅 시점*에 확정되고, 그 시점은 풀버스트 창이 열리기 **직전**이다. 따라서
  B3의 버스트 넉은 **FB 보너스도, `full_burst_enter`로 붙는 어떤 버프도 받지 못한다.**
  반면 "as additional damage"처럼 **나중에** 연산되는 라이더는 **둘 다** 받는다.
  이것은 이 파일 맨 위의 "**FB 보너스의 기준은 연산 시점**" 원칙과 정확히 같은 말이며,
  그 원칙이 FB 보너스뿐 아니라 **그 순간에 도착하는 모든 버프**로 확장된다는 뜻이다.
- **네 값이 전부 맞는다** (불릿1은 One for All·FB 보너스 **없이**, 불릿2는 **둘 다** 있게):

  | | 모델 | 실측 | |
  |---|---|---|---|
  | 불릿1 논크리 | 12,674,310 | 12,674,307 | **1.0000x** |
  | 불릿1 크리 | 20,958,240 | 20,958,234 | **1.0000x** |
  | 불릿2 논크리 | 511,392 | 513,863 | 0.9952x |
  | 불릿2 크리 | 734,223 | 737,770 | 0.9952x |

- **엔진 결함:** 호출 순서(`on_tier_fire` → `on_full_burst_enter`)는 맞지만 **둘이 같은
  타임스탬프**라, Phase 2가 `applied_at <= time`으로 걷을 때 B3의 버스트가 풀버스트 버프를
  함께 먹는다. 실측 확인: 크라운의 One for All이 t=2.20에 적용되고 신데렐라의 버스트도
  t=2.20에 기록되어, 그녀의 버스트 히트가 `flat_atk` 487,933(= 303,121 + **184,811**)을
  받았다. **파급: `full_burst_enter`로 버프를 주는 유닛이 30기 이상이고, 영향은 모든 덱의
  B3 딜러 자기 버스트에 걸린다.** 이 파일의 낡은 서술("`full_burst_start`가 tier-3 버스트와
  같은 순간이므로 B3의 캐스트-시각 인스턴스는 창 '안'으로 읽힌다")도 **이 실측이 뒤집는다**.
- **한 번 틀렸다가 정정한 가설 — 크라운의 One for All은 정상이다.** "풀버스트 시작 시
  **직전에** 버스트를 사용한 아군"이 B3 본인을 제외한다고 추측해 한때 결함으로 적었으나,
  **Fienn 확인 결과 해당 사이클의 B1·B2·B3 전원을 의미한다**(2026-07-27). 엔진의
  `full_burst_enter` + `burst_used_this_cycle`이 맞다. **교훈: 미지수가 둘인 방정식에서
  "유일해"는 증거가 아니다** — 나머지 하나(아래 불릿1 계수)가 틀려 있었기 때문에 이쪽이
  범인으로 보였을 뿐이다.
- **One for All을 켠 채로 다시 풀면 오차가 한 항에 갇힌다** (offense = 865,986):

  | | 모델 | 실측 | |
  |---|---|---|---|
  | 불릿2(Beautiful 미러) | 511,392 | 513,863 | **0.9952x** |
  | 불릿1(10회 순차공격) | 16,113,521 | 12,674,307 | **1.2714x** |

  **두 불릿은 같은 offense와 같은 `attack_damage_up`을 쓴다.** 불릿2가 0.5% 안에서
  맞는다는 것은 오버로드 ATK(38.79%가 표시 ATK에 **미포함**) · Flawless Glass 303,121 ·
  One for All 184,811 · **FB 보너스 +0.5** · 스택수 1이 **전부 맞다**는 뜻이다.
  따라서 오차는 **불릿1의 계수 하나**에 있다 — 실측이 함의하는 히트당 값은
  **1,074.3%** 이고 스킬 표기는 **1365.92%** 다(비 0.7865). 미해결.

## **"버스트 N단계 진입 시" ≠ "풀버스트 시작 시"** — 한 사이클 안에서 서로 다른 순간이다

- 확립: 2026-07-27 (Fienn 지적). 위 "★ 진짜 원인" 수정을 넣자 **그것이 가리고 있던 두
  번째 오독이 드러났다** — 이 프로젝트에서 반복된 그 패턴이다.
- **두 표현은 B3 캐스트를 사이에 두고 갈라진다:**

  ```
  1단계 진입 → B1 → 2단계 진입 → B2 → [3단계 진입] → B3 사용 → [풀버스트 시작]
                                            ↑                          ↑
                                    캐스트 前 = B3 버스트에 닿음   캐스트 後 = 안 닿음
  ```
- **판별은 오직 원문이다.** 크라운 One for All = *"Activates **at the start of Full
  Burst**"* → `full_burst_enter`(안 닿는다, 정상). 민트 Fantastic Performance =
  *"Activates when **entering Burst Stage 3**"* → `ally_burst_activate` +
  `burst_stage_entered(3)`(닿는다). **엔진은 이 둘을 오래 `full_burst_enter` 하나로
  뭉뚱그려 놨고**, 두 순간이 같은 타임스탬프였을 때는 그 오류가 보이지 않았다.
- **왜 지금 드러났나:** 창을 한 순간 뒤로 밀기 전에는 `full_burst_enter`가 B3 캐스트와
  동시각이라 stage-N 불릿도 **우연히 맞았다**. 창을 옮기자 그 우연이 사라지면서
  잘못된 배선이 노출됐다. **수정이 다른 결함을 드러내는 것은 진전이다.**
- **전수 대조 결과** (원문 표기 ↔ 배선): "at the start of Full Burst"를 쓰는 인코딩
  유닛은 **크라운 하나뿐**이고 올바르게 배선돼 있다. 반면 **"entering Burst Stage N"
  표기인데 `full_burst_enter`로 배선된 유닛이 6기**다 — `mint`(**수정 완료**) ·
  `maiden-ice-rose` · `mast-romantic-maid` · **`mihara-bonding-chain`** ·
  `rei-ayanami` · `snow-white-heavy-arms`. (미하라는 캘리브레이션 표에서 0.70x로
  미달 2위였다 — 유력한 후보다.) 유닛마다 **불릿 단위** 확인이 필요하다.
- **닿는 이유(엔진):** `on_tier_fire`가 `own_burst_activate` → `ally_burst_activate`를
  먼저 쏘고 **그 다음에** 버스트 넉을 기록한다. 셋 다 같은 타임스탬프이고 레지스트리는
  `applied_at <= time`으로 걷으므로, stage-N 버프는 그 캐스트의 버스트 대미지에 들어간다.

## "버스트 N단계 진입 시"를 `own_burst_activate`로 인코딩하면 좌석을 나눌 때 조용히 샌다

- 확립: 2026-07-27 (신데렐라 검증 중 발견). 마스트 취기(1단계)에서 나온 판정과 **같은
  규칙**인데, 그때는 스택 카운터였고 이번엔 트리거 자체다.
- **원칙:** "Activates when entering Burst Stage N"은 **단계**에 대한 서술이지 시전자에
  대한 서술이 아니다. 그 사이클에 **누가** 그 티어 슬롯을 가져가든 일어난다. 따라서
  `ally_burst_activate` + `burst_stage_entered(N)`으로 걸어야 한다. 엔진의
  `squad_engine.burst_stage_entered` 독스트링이 이미 이 문장을 그대로 담고 있다 —
  "Using `own_burst_activate` instead would silently drop those cycles."
- **왜 오래 안 들켰나 — 틀린 근거가 코드에 명시돼 있었다.** `snow_white_heavy_arms.py`가
  선례 검토까지 적어두고 이렇게 결론냈다: *"her Burst Skill is fixed at position 3
  (a game attribute, not a deck-configurable seat), that's every cycle she reaches
  Full Burst."* **이 문장이 틀렸다.** 버스트 위치가 고정인 것과 그 사이클에 그녀가

## 홍련(스칼렛: 블랙 섀도우)의 미해결 가정 두 개는 **실기록이 지지한다**

## "탄약 N발 소모"는 탄창이 아니라 **장부**다 — 실탄은 1발만 나간다

- 발견: 2026-07-19 (신데렐라 스나이프 모드) / 배선: 2026-07-26 (리틀 머메이드 캘리브레이션)
- 벨벳 "파우치에서 300발 소모", 신데렐라 스나이프 "40발 소모" — **실제로 발사되는
  총알은 1발**이다. N은 **소모량 연동 시너지를 먹이기 위한 회계 수치**다. 이걸
  탄창 소모로 읽으면 발사 속도가 틀리고, 반대로 **무시하면 소모량 카운터가 굶는다.**
- 이 장부를 먹는 소비자는 실재한다: 리틀 머메이드 버블 배러지(아군 총 500발마다
  85%×10히트) · 버블 오더(400발마다 버스트 게이지 37%) · 신데렐라 크리스탈 웨이브
  (200발마다 게이지 12%). 즉 **한 유닛의 회계 표기가 다른 유닛의 딜을 결정한다.**
- 규모: 벨벳은 188초에 **129발**밖에 안 쏘지만 장부에는 **약 31,500라운드**를 올린다.
  총알로 세면 카운터에 0.9% 기여, 라운드로 세면 **약 70%** 기여다. 배러지 28회 → 89회.
- 배선 방법: 슬러그 → `(풀버스트 중 라운드, 풀버스트 밖 라운드)` 2튜플
  (`registry._AMMO_ROUNDS_PER_SHOT`). 시뮬레이터가 `context.shot_ammo_rounds`를
  `context.shot_times`와 **평행한 리스트**로 채운다. 창별로 갈리는 이유는 벨벳의
  **파우치 스킬이 두 개**여서다 — 풀버스트 안은 Bullets of Love(300), 밖은
  Sticky Fingers(100). 스칼라 하나로는 표현이 안 된다.
- 함정: 한 샷이 **여러 임계값을 동시에 넘을 수 있다**(1,200라운드 = 500짜리 배러지 2회).
  `while expended >= next_barrage` 루프여야 하고, `for i in range(threshold-1, n, threshold)`
  같은 인덱스 스텝은 총알 카운터에서만 맞는다.
- 전수 조사: 수집된 로스터에서 "expends ... round(s)" 표기를 가진 유닛은
  **벨벳과 신데렐라: 크리스탈 웨이브 둘뿐**이다. 새 유닛을 인코딩할 때 이 문구가
  보이면 레지스트리 테이블에 추가할 것.

## "Damage to Parts"와 "Damage to Interruption Parts"는 **다른 대상**이다 — 이름이 거의 같아서 반드시 오독된다

- 발견: 2026-07-26 (Fienn이 helm 스킬2 "포문 개방"의 한글 원문을 읽다가 지적)
- **"저지 부위 공격 대미지"(Damage to Interruption Parts)** 는 **기믹 수행 시 타격해야 하는
  구역**의 딜을 올린다. **"파츠 대미지"(Damage to Parts)** 는 **파괴 가능 파츠**의 딜을
  올린다. 이름이 거의 같지만 **가리키는 타겟이 아예 다르다.** 한글 표기는 확실히
  구분되는데("저지 부위" vs "파츠") 영문은 `Interruption`이라는 단어 하나 차이라,
  영문 데이터만 보고 인코딩하면 거의 확실히 뭉개진다 — 실제로 뭉개져 있었다.
- 로스터를 원문으로 갈라보면 정확히 반반이다:
  - **Interruption Parts (저지 부위)**: `helm`(Fire Away, 스쿼드 상시) ·
    `noir`(Finale, 스쿼드 10s+30s) · `anis-sparkling-summer`(자기, 10s) ·
    `rapi-red-hood`(자기, 10s)
  - **Parts (파괴 가능 파츠)**: `rosanna-chic-ocean` · `cinderella-crystal-wave`(Destroy
    모드) · `snow-white-heavy-arms` · `raven`(Vital Attack, defer 중)
- 이 오독이 왜 조용했나: 여덟 유닛이 **전부 같은 스탯 `damage_to_parts_up`에 써넣고**
  있었고, 엔진은 그걸 일반 Damage-Up 버킷에 넣어 모든 타격에 곱했다. 두 개념을
  구분하든 안 하든 수치가 같으니 아무도 볼 이유가 없었다. **몸통 딜에서 이 항을
  뺀 뒤에야**(같은 날의 별도 판정) 두 스탯이 서로 다른 미래를 갖게 됐다.
- 해법: 스탯을 분리한다(`damage_to_interruption_parts_up` 신설). **둘 다 몸통 딜에는
  안 붙으므로 지금 수치는 1도 안 변한다** — 이 작업의 가치는 전적으로 "다음 사람이
  파츠를 실제 타겟으로 모델링할 때 잘못된 네 유닛을 합치지 않게 하는 것"이다.
  회귀 테스트 `test_parts_vs_interruption_parts.py`가 유닛별로 어느 쪽인지 고정한다.
- 일반화: **한글 표기가 영문보다 구분이 명확한 경우가 있다.** 인코딩 근거를 영문
  데이터에서만 뽑으면 이런 구분이 통째로 사라진다 — 값이 아니라 **대상**이 의심스러울
  때는 한국 서버 원문을 확인할 것([[korean-service-naming]]와 같은 이유).

## 시뮬레이터를 실측에 대조할 때 판정 기준은 배율이 아니라 배율의 **편차**다 — 그리고 "함의된 파라미터" 역산이 캘리브레이션과 모델 오차를 갈라준다
- Fienn의 두 시즌 전 솔로레이드 실기록 5덱을 그대로 시뮬에 넣었더니 합계 **1.46배 과대**였다. 여기서 "1.46로 나누면 되겠다"로 가면 안 된다 — **덱별 배율이 0.93x~2.00x로 흩어져 있었고**, 순위는 편차만 보기 때문이다. 당시 추천이 주장하던 우위는 +9.9%로 **오차 폭보다 작았다**. 총량 편향은 랭킹에서 상쇄되고 편차는 랭킹을 파괴한다는 것은 `scripts/measure_unmodeled_damage_share.py`가 이미 세워둔 잣대와 같은 원리다.
- **캘리브레이션 오차와 모델 오차를 가르는 방법: 의심되는 파라미터가 데미지에 선형으로 들어간다면 역산하라.** 코어 히트 보너스는 major modifier에 가산되므로 총딜이 코어 히트 비율 f에 선형이다(`total(f) = off + f*(on-off)`). 그래서 각 덱의 실기록이 함의하는 f를 풀 수 있었고 결과는 **52% / 10% / 28% / 2% / 117%**였다. **하나가 100%를 넘는 순간 "전역 노브" 가설은 죽는다** — 어떤 값을 넣어도 다섯 덱이 동시에 맞지 않으므로, 남은 것은 모델 자체가 덱마다 다르게 틀렸다는 결론이다. 노브를 UI에 다는 것은 모델 오차를 유저 입력으로 위장하는 짓이다.
- **부호가 반대인 이상치 하나가 가장 정보량이 크다.** 다섯 덱 중 넷이 과대(1.26~2.00x)인데 하나만 **과소**(0.93x)였다. 그 하나를 파고든 것이 Moran Fervor 쿨감 누락(풀버스트 6회 대 실제 12.5초 사이클)을 잡아냈고, 고친 뒤 그 덱은 1.15x로 **나머지와 같은 방향**으로 정렬됐다. 전부 같은 방향으로 틀린 오차는 투자 드리프트 같은 공통 원인으로도 설명되지만, 방향이 다른 것은 반드시 구조적 결함이다.
- **실측 대조는 유저의 로스터가 그때 이후로 자랐다는 사실을 반드시 같이 적어라.** 여기서 남은 1.08배 중 얼마가 모델 오차이고 얼마가 투자 성장인지는 분리되지 않았다. 분리하지 않은 채로 1.08을 "거의 맞음"이라고 부르면 다음 사람이 그 숫자를 기준선으로 쓴다.
- 재현: 진단 하네스는 실기록 5덱을 `feasible_orderings`로 최적 배치해 채점하고, 같은 덱을 `core_hittable` on/off로 두 번 돌려 f를 역산한다. `docs/decisions.md`의 "코어 데미지는 평타 전용이다" 항목 참조.

## refreshing 버프는 "스킬 불릿" 단위로 묶여야 한다 — 유닛 단위로 묶으면 남의 버프를 지운다

- 발견: 2026-07-21 (Fienn이 Liberalio의 Raging Current 작동 여부를 점검 요청)
- `EffectRegistry.add_refreshing`이 `(stat, source_slug, scope)`가 같은 **모든**
  활성 효과를 truncate했다. 의도는 docstring에 적힌 대로 "한 소스의 재적용을 합치는
  것"이었지만, 키가 **유닛**이라 **같은 유닛의 다른 스킬**까지 잡아먹었다.
- 증상이 지독한 이유: **조용하고, 큰 쪽이 죽는다.** Liberalio는 자기
  `attack_damage_up`을 두 불릿에서 주는데(영구 231% + 매 풀차지 refreshing 20.83%),
  첫 샷에서 231%가 등록되자마자 같은 샷의 20.83%가 그걸 duration 0으로 잘랐다.
  테스트는 전부 통과했다 — 각 불릿을 따로 보면 맞게 동작하기 때문이다. 유닛 단위
  테스트로도 안 잡히고, **두 불릿이 한 시뮬에서 만나야만** 드러난다.
- 해법: `Effect.refresh_group`(옵셔널) — `refreshing_buff_rule` 인스턴스마다 하나.
  `RoundGrant.cap_group`(2026-07-20, Zwei 스택 캡)과 **정확히 같은 형태의 문제이고
  같은 해법**이다. 그룹이 없으면 기존처럼 묶이므로 충돌이 없던 소비자는 불변.
- 파급: 77 슬러그 중 **75개의 딜이 변했다**(전부 상승 — 옛 동작은 살아있어야 할
  버프를 지우는 방향으로만 틀릴 수 있다). Liberalio +132.6%, ark-ranger-black +44%,
  snow-white-heavy-arms +33.6%. 넓은 +4~17% 꼬리는 대부분 **Crown** 때문이다:
  같은 날 추가한 Royal Attire(refreshing 스쿼드 AD)가 그녀 자신의 Last Kingdom
  버스트 버프(36.24%)를 매번 지우고 있었다.
- 교훈: **새 refreshing 버프를 추가할 때, 그 유닛이 같은 (stat, scope)를 다른
  불릿에서도 주는지 반드시 확인할 것.** 안 그러면 새 인코딩이 기존 인코딩을
  조용히 무효화한다.
- **후속 감사 (2026-07-21, 역방향 점검): 옵셔널 그룹으로는 부족했다.** 위 수정은
  `refreshing_buff_rule` 경로만 덮었고, 손으로 쓴 `add_refreshing` 호출부는 전부
  그룹을 안 붙여 **하나의 "무그룹" 양동이**를 계속 공유했다. 게다가 그 양동이에는
  평범한 `registry.add`로 넣은 효과까지 들어간다 — refreshing 불릿이 절대 건드리면
  안 되는 것들이다. **Grave가 Liberalio와 똑같은 버그를 그대로 안고 있었다**:
  Overheat I의 영구 자버프 ATK +15.48%(`add`)를, 창(window) 한정 Overheat II의
  refreshing ATK +20.66%가 첫 발동에서 잘라 없앴다. 기존 테스트가 못 잡은 이유는
  **Overheat I과 II를 서로 다른 registry에서 검증**했기 때문 — 한 registry에 같이
  넣어야만 드러난다.
- 최종 해법: **`add_refreshing`은 이제 `refresh_group`이 없으면 `ValueError`를 던진다.**
  한 사례를 고치는 대신 이 버그 부류 자체를 도달 불가능하게 만든 것 — 불릿 이름을
  붙이는 게 호출자의 명시적 결정이 되고, `add`로 넣은 효과는 group `None`을 유지하므로
  어떤 refresher도 그걸 무너뜨릴 수 없다. 유닛의 연속 버프를 자기 트리거로 **일부러**
  끝내는 경우는 별도의 `truncate_open_ended`를 쓴다.
- 그룹 부여 단위가 중요하다: 헬퍼는 **룰 인스턴스마다**, `escalating_buff_rule`은
  **티어마다**(티어는 누적이므로 같은 stat을 주는 두 티어는 합쳐져야지 서로를 대체하면
  안 된다), `raid_simulator`의 resource-fill 버프는 **spec마다**.
- 영향: 72개 슬러그 스윕에서 **Grave 단독 +1.07%**, 나머지 71개 불변. 수정이 표적만
  건드렸다는 증거다. 이 A/B는 `scripts/sweep_slug_damage.py`로 재현한다(고정 셸에
  대상 유닛 한 명씩 넣어 측정 → `--compare before.json after.json`).

## 버스트가 DPS 손해인 유닛이 있다 — 무기변형 세그먼트를 넣는 게 오히려 부정확할 수 있다

- 발견: 2026-07-21 (Modernia의 New World Destroy Mode 세그먼트 인코딩 시도 중, Fienn 판정)
- Modernia의 버스트(New World)는 **보스전에서 순손해**다: Destroy Mode 평타 2.24%가 base MG
  7.71%보다 훨씬 낮고, 멀티타겟 auto-aim은 "stage target을 파츠 무관 단일 취급"이라 무가치.
  그래서 실전 운용은 **버스트 미사용** — (1,1,3) 맨 오른쪽에 앉혀 평타로만 딜(Fienn).
- 함정: 무기변형 프리미티브가 있다고 Destroy Mode를 세그먼트로 넣으면, 엔진이 버스트를 강제해
  실전에 없는 Destroy Mode를 발동시킨다 → Modernia ~12% 저평가(스윕 확인). **세그먼트가
  "정확한 무기 모델"이지만 "정확한 유닛 운용"은 아니다.**
- 통찰: 버스트 미사용 유닛은 버스트로 발동하는 모든 것(변형·무한탄약·버프)이 실전에서 발동 안
  하므로, **아무것도 안 넣은 base 무기 상태가 오히려 정확한 근사**다. Modernia의 버스트는 이미
  `([], None)`(nuke·버프 전무)이라 현재 상태가 버스트 미사용 딜러에 가깝다.
- 정확한 표현은 `burst_delay`에 `skip_cycles: float("inf")`를 줘 영구 미사용으로 만드는 것.
  실험상 (1,1,3)에서 대상 버스트 0회 + 나머지 B3 2명 로테이션 유지가 확인됐다(B3 ≥2명 보장).
  단 `sweep_slug_damage.py`의 tier3 셸은 대상이 유일 B3라, skip 시 B3 버스트가 없어 Full Burst가
  붕괴 → 측정 불가. 스윕 셸 재설계가 얽힌 아키텍처 작업이라 후속으로 분리.
- 교훈: **엔진 프리미티브가 표현 가능하다는 것과, 그 표현이 유닛의 실제 최적 운용과 맞다는 것은
  별개다.** 무기변형을 넣기 전에 "이 유닛이 실제로 그 변형을 쓰는가"를 먼저 물어라.

## 같은 버스트 bullet이 변형과 데미지타입 변환을 함께 걸면, 변환은 세그먼트에 `damage_type`으로 고정하라 — 별도 효과에 의존하지 말 것
- 발견: 2026-07-22 (Takina Inoue의 Suppression Initiated 인코딩)
- 문제: Takina의 버스트는 한 bullet에서 (a) 무기를 200.64%/발 급사무기로 변형(10초)하고 (b) 그 10초 동안 평타를 진댐으로 변환한다. 이 변형샷이 곧 그녀의 버스트 중 평타이므로, 세그먼트 발사를 기존 self `normal_attacks_deal_true` 효과의 폴백(`normal_attack_type`)에 맡기면 논리적으로 맞아 보인다.
- 함정: 효과 활성 구간은 **우측 배타적** `[applied_at, applied_at+duration)`(effects.py `_is_active`)이다. Fienn 실측 25발을 `until_shots: 25`로 넣으면 마지막 발이 정확히 t=burst+10(=창 끝)에 놓여 변환 창 **밖**으로 떨어진다 → 25발 중 1발이 진댐이 아닌 일반딜로 잘못 타이핑.
- 해결: 세그먼트 프로파일에 `damage_type="true"`를 **직접 고정**한다. 변형과 변환이 같은 bullet·같은 10초라 이 샷들이 진댐인 것은 인과적으로 확실하므로, 경계에 취약한 별도 효과에 기대는 것보다 직접 서술이 정확하다. 변형이 버스트 중 평타를 전부 대체하므로(창 안에 base 샷 없음) 이제 잉여가 된 self `normal_attacks_deal_true` 효과는 제거했다 — "모델된 것처럼 보이나 소비자가 없는 효과"를 남기지 않는다.
- 일반화: **측정 발수가 있으면 `until_shots`(정확), rate×duration 유도는 `end`**. `end` 방식은 `start + k*interval < seg_end` 조건이라 마지막 발이 경계에 딱 걸리면 드랍된다 — Takina를 `end`로 넣었으면 25발이 아니라 24발이 됐다(laplace base가 `end`를 쓴 건 실측 발수가 없어 유도값이었기 때문).

## ShiftyPad 캐릭터 상세 페이로드 — 무기 필드는 고정소수점, 스킬 사다리는 전치 필요, 경로 함정 3개
- 발견: 2026-07-21 ~ 2026-07-22 (무기+기본스킬 데이터원 ShiftyPad 전환, `backend/app/shiftypad_normalize.py`)

- 경로 함정 3개:
  1. `weapon_type`은 `directory.shot_id.element.weapon_type`에 있다(`.element` 아래로 한 단계 깊음, `shot_id.weapon_type`이 아님).
  2. element를 ShiftyPad는 `"Electronic"`으로 부르지만 엔진(`elements.py`)·dotgg는 `"Electric"` — 반드시 리매핑해야 한다(안 하면 전기코드 유닛의 원소 우위 계산이 조용히 깨진다).
  3. `burst`는 `"Step3"` 같은 Step-문자열이고 dotgg는 문자열 `"3"`으로 저장 — `str`로 내야 패리티가 맞는다.
- `dollskills`(시그니처 무기 스킬)는 상세 페이로드에 없다(Julia 페이지의 16개 payload 전문 검색으로 확인). 스킬1·2 쿨다운도 없다(버스트만) — 그 값이 필요한 인코딩은 인게임 UI나 나무위키에서 직접 읽어야 한다(예: julia 스킬1 쿨다운은 dotgg 기준 20초).
- 재사용 패턴: **제3자 페이로드를 기존 내부 포맷(dotgg 모양)으로 정규화해 하위 파싱을 통째로 재사용**하면 로더 변경이 최소화되고 패리티를 필드 단위로 대조할 수 있다.
- 패리티 하니스 패턴: 새 데이터소스의 파서를 기존 소스 정답지에 대해 **백필 없이** 증명한다. 파서 로직이 유닛마다 같으므로 구조 다양성(6무기타입=충전 vs 탄창, 슬롯 수)을 덮는 소수 픽스처로 충분. 함정: `zip()` 기반 레벨 비교는 파서가 레벨을 적게 내면 공허하게 통과 — 비교 전에 `len==len`을 먼저 단언해야 한다(`backend/tests/test_shiftypad_parity.py`).
- 관련 결정: `docs/decisions.md`("무기 + 기본스킬 데이터원을 신규 유닛부터 ShiftyPad로 전환").

## `supported_units()` must resolve a slug's metadata the same way `load_nikke_spec` does
- 발견: 2026-07-22 (draft-based deck allocation, `backend/app/supported_units.py`)
- The palette endpoint's `supported_units()` had its own `MODE_VARIANTS`-only lookup for a slug's weapon/element/tier metadata, instead of reusing `user_roster.load_nikke_spec`'s resolution order: the skill-value manifest's `data_slug` first, then lootandwaifus, falling back to the manifest's declared dotgg/shiftypad weapon-data source when the lootandwaifus file 404s.
- A narrower lootandwaifus-only lookup silently drops real encoded units instead of erroring — `julia-signature`, `drake-signature`, `laplace-signature` (whose `data_slug` lives in their own manifest entry, not in `MODE_VARIANTS`) and `privaty` (no lootandwaifus file exists at all; needs the dotgg fallback) all disappeared from the palette with no error, because a missing/mismatched slug just gets skipped rather than raising.
- Fix (`5e69dce`): mirror `load_nikke_spec`'s resolution order exactly. After the fix, 0/77 `ENCODED_SLUGS` are skipped (previously 4 silently dropped).
- **그리고 2026-07-25에 똑같은 일이 다시 벌어졌다 — "미러링하라"가 틀린 처방이었기 때문이다.** 애장품 4인방을 위해 매니페스트에 `weapon_source` 키가 추가됐을 때 `load_nikke_spec`만 그것을 배웠고, `_load_meta`는 여전히 `manifest["source"]`를 읽어 죽은 dotgg를 찾다 또 조용히 떨어뜨렸다 — 이번에도 정확히 4개(`sugar/flora/rosanna/phantom-signature`), 89/93. 미러링은 **작성 시점에만 참인 불변식**이라 세 번째 키가 추가되는 순간 또 깨진다. 진짜 수정은 분기를 하나로 만드는 것이다: `skill_values.load_weapon_data`가 이제 유일한 정의이고 두 호출자가 그것을 부른다(커밋 `f0273f4`).
- **테스트도 같은 방식으로 실패했다.** 2026-07-22의 회귀 테스트는 그때 사라진 슬러그 4개를 **이름으로** 단언했는데, 그런 테스트는 자기를 만든 사건만 잡고 다음 드리프트는 못 잡는다. 지금 테스트는 목록이 없다 — `set(ENCODED_SLUGS) - {supported_units()의 슬러그}`가 비어 있는지만 본다.
- 교훈: 같은 파생 규칙을 두 곳에서 읽는다면, "둘을 똑같이 유지하라"는 규율이 아니라 **한 곳에서만 정의되게 하라**. 그리고 조용한 누락(`except: continue`)을 감시하는 회귀 테스트는 개별 사례가 아니라 **전수 불변식**으로 쓸 것 — 실패 모드가 크래시가 아니라 침묵이라 아무도 세어보기 전까지 드러나지 않는다.

## 드래프트 완성 비용은 좌석 수에 반비례한다 — 그리고 축소 품질을 검증하는 잣대는 "제약이 적을수록 좋아야 한다"이다
- 발견: 2026-07-25 (`best_completions` 예산화, `backend/app/deck_search.py`)
- **직관과 반대다.** 드래프트가 덜 찰수록 완성 방법이 많아지므로 탐색이 **비싸진다**. 실제 77유닛 로스터(B1 13/B2 17/B3 47) 실측: 좌석 5개 = 4순서, 4개 = 372, 3개 = 10,835, 2개 = 126,513, **1개 = 1,830,670**(8워커 ~6.5시간). 완성 드래프트를 기준으로 성능을 재면 가장 싼 케이스만 보게 되고, 유저가 가장 먼저 닿는 "칩 하나" 경로가 무응답이라는 것을 못 본다. **드래프트 경로 성능은 가장 얇은 드래프트로 재라**(`scripts/measure_thin_draft.py`).
- **축소(프루닝/캐스케이드) 품질을 검증하는 잣대: 드래프트는 제약이므로 좌석이 적을수록 결과가 좋거나 같아야 한다.** 좌석 N개의 답은 좌석 N-1개 문제의 유효한 해이기도 하므로, 좌석 1개가 좌석 2개보다 낮게 나오면 그건 제약의 대가가 아니라 **탐색 결함**이다. `prune_candidate_pool`만 붙였을 때 정확히 이 위반이 나왔다(좌석1 36.73B < 좌석2 42.99B, 14.6% 낮음). 총딜 절대값만 보면 "드래프트를 지켰으니 그럴 수 있다"로 넘어가기 쉽다 — 좌석 수를 늘려가며 단조성을 보는 것이 결함을 드러낸다.
- 왜 얇은 드래프트가 축소에 더 취약한가: 좌석이 적을수록 완성 유닛 5개 중 더 많은 수(좌석 1개면 4개)를 축소 풀에서 뽑는다. `prune_candidate_pool`은 **드래프트가 없는 레퍼런스 덱**에서 한계 기여만 재므로 그 recall 오차에 그만큼 더 노출된다. 캐스케이드(더 넓은 풀 + 덱 전체 랭킹)는 이 노출을 상쇄한다 — 자유 덱에서는 선택이던 것이 완성 경로에서는 필수가 되는 이유.
- 함정: 축소 풀이 **완성을 하나도 못 만들 수 있다**(어떤 티어에 남은 후보가 전부 드래프트된 유닛의 MODE_VARIANTS 형제인 경우 등). 이때 빈 결과를 그대로 반환하면 `allocate_decks`가 `InfeasibleDraft`를 던져 **플레이어가 실제로 낼 수 있는 편성을 "불가능"이라 말한다**. 전수 경로로 되돌아가는 것이 맞다 — 느린 것이 틀린 것보다 낫다.

## Raid decks are unordered — match result decks to a submitted draft by slug overlap, never by array index
- 발견: 2026-07-22 (draft-based deck allocation, `DraftResults` per-deck diff, fixed in `68e5e8f`)
- `recommend_from_draft` (and `allocate_decks` underneath it) picks `_better(scratch, warm)` for the `recommended` tier, and `scratch` may fully repartition the roster into decks that don't correspond 1:1 with the player's submitted deck groupings — deck labels/positions are arbitrary (same boss, same scoring either way), so "deck 1" in the result has no necessary relationship to "deck 1" in the draft.
- 함정: a naive "per-deck diff vs. what the user submitted" that zips result decks against submitted decks by array index will compare unrelated decks whenever the optimizer reshuffles membership across deck boundaries, producing a diff that's nonsensical (e.g. showing a deck's damage change as if it kept the same 5 units when it didn't).
- 해법: match each result deck to the submitted deck it overlaps most with by slug set intersection, not by index, before computing a per-deck diff.

## Damage formula
- **The attack/skill coefficient scales the whole Base Damage, not the ATK stat.** A normal attack's "% of ATK" or a skill's "X% of final ATK" multiplies Base Damage *after* defense is subtracted — pass raw summary ATK plus a separate `attack_coefficient` to `calculate_damage`. Folding the coefficient into ATK mis-scales the defense subtraction and any flat ATK (~14% overstatement against a defended boss, and unevenly across Nikkes since coefficients range from ~5% normal attacks to ~8000% bursts, which would skew deck rankings). See `damage_formula.calculate_damage`.

## Performance (EffectRegistry)
- **`_stat_bundle`-style memos keyed on a global `version` counter are only safe in phase 2 — in phase 1, per-shot mutations churn `version` every call, so every bundle lookup misses and rebuilds, costing more than it saves.** Tried wiring `normal_attack_type` (a phase-1 stat, read while shots are being generated and rules are firing) into the phase-2 `_stat_bundle` memo — Stage 0.5's gain collapsed from 23% to 6% (133.66ms → 125.07ms) because every phase-1 call bumped `registry.version` and invalidated the very bundle it was trying to reuse. Reverted to a direct single-stat `total_for` lookup for `normal_attack_type`, which restored the full 23% gain (→ 103.43ms). Rule: **`_stat_bundle` is phase-2 only** — see the warning comment above `_stat_bundle` in `raid_simulator.py`. Any future stat added to `_BUNDLE_STATS` must be confirmed phase-2-only (read only during damage computation, not during shot/rule generation) before being added.
- **Bit-identical performance refactor pattern: freeze a naive reference implementation, preserve float-addition order, and cross-check with a parity net.** Requiring "bit-identical," not "approximately equal," output from a performance rewrite (Stage 0's segment-table `EffectRegistry.total_for`) needs three things: (a) a frozen copy of the original naive implementation committed with a "do not modernize" comment, so it can't drift out of sync with the fast path it's meant to validate; (b) preserving the ORIGINAL summation order (effect insertion order, not chronological order — float addition is non-associative, so re-ordering can flip the last bit); (c) a parity-net test that runs both implementations against the full test suite plus dedicated mutate/query interleaving cases, not just a handful of hand-picked spot checks. Side benefit: the test suite itself got 3× faster (22s → 6.5s) as a byproduct, since many tests exercise `total_for` heavily. See `docs/decisions.md` ("Stage 0: EffectRegistry rewritten to per-(stat, slug, element) segment tables...").
- **Two mathematically-equivalent float expressions can differ by 1 ULP — a "bit-identical" parity fixture set needs an odd/ugly value, not just round numbers, to catch it.** Unifying every unit's weapon-shot generation onto the new segmented generator (`docs/decisions.md`, "Weapon-mode segments v1...") required rewriting `_base_shot_records`' magazine-shot-time arithmetic from `(i + 1) * effective_charge` to `effective_charge + i * effective_charge`. The two are algebraically identical but not bit-identical under IEEE-754 (float multiplication doesn't distribute over addition in floating point) — the regression was invisible against the existing `SR_BASE`/`AR_BASE` fixtures (`charge_time=1.0`/`0.0`, both exact binary values with nothing to round), and only surfaced once a fixture with no exact binary representation (`SR_ODD`, `charge_time=1.19`) was added specifically to stress it. Rule of thumb: a bit-identical parity net needs at least one "ugly" float per input dimension being refactored, or it can pass while the code underneath is subtly wrong. See `backend/tests/test_attack_rate.py`'s `SR_ODD`, and the "Bit-identical performance refactor pattern" bullet above for the sibling Stage 0 case this generalizes.
- **The epoch superset invariant is what makes bundling multiple stats into one memo safe: the union of every matched Effect's boundaries (`state_epoch`) is itself the superset of each individual stat's own boundaries, so within one epoch ALL bundled stats are simultaneously constant.** `EffectRegistry.state_epoch(target, time)` collapses every stat's own boundary-time set (for effects matching that target) into one combined timeline. Because it's a union (not an intersection or a single stat's own boundaries), any two instants inside the same epoch segment are guaranteed to see identical values for every stat in the bundle — not just the one the epoch happens to be named after. This is the correctness argument for `_stat_bundle` memoizing 17 stats behind one epoch+version key instead of one key per stat. See `docs/decisions.md` ("Stage 0.5: epoch + stat-bundle memo...").

## Crit
- **Crit is expected value, not per-hit RNG.** The major modifier gains `crit_rate*(0.5 + crit_damage_sources)`. Base crit rate is 15%, base crit damage +50%; both buff types are additive. Crit-damage buffs are inert with no crit chance. See `damage_formula._major_modifiers` and `raid_simulator.BASE_CRIT_RATE` (overridable via `base_crit_rate`, set 0.0 for deterministic tests).

- **A resource-scaled nuke's percent must resolve in phase 2, not when the nuke is recorded.** A burst-fired nuke gated/scaled by a named resource's count (Julia's Climax additional hit, Cinderella's mirrored hit, Guillotine's Extermination DoT) is recorded during `on_tier_fire` — but the resource's fills aren't populated until the resolution pass runs, which happens AFTER the whole burst cycle. A repeating DoT tick just records one event per tick, each independently resolved at its OWN time, so a resource still accumulating mid-DoT correctly raises later ticks. - **A burst that "attacks sequentially N times" is N separate damage instances, not one instance at N×percent.** Defense is a FLAT per-hit subtraction (`_base_damage`), so splitting into N hits changes the total whenever `enemy_def > 0` — pre-multiplying the percent would overcount (defense only subtracted once instead of N times). `burst_hit_counts` records N identical events at the same instant. - **A burst-fired BUFF gated on a resource has no "phase 2" to defer to, unlike a nuke — so it must be resolved IN the resolution pass itself, not at `on_tier_fire`.** A resource-scaled/gated NUKE can record now and compute its percent later (`resource_scaled_nukes`, above) because every damage instance in this engine is already record-now/compute-later. A buff has no equivalent second pass: `buff_rule`/`registry.add` mutate the registry immediately when the trigger's action runs, and `on_tier_fire` (where a burst's rules fire) runs BEFORE the resolution pass that populates the resource's fills/resets for that cycle — so a gate check done at `on_tier_fire` time would always see a stale or empty resource. Fix: process `resource_gated_buffs` inside the resolution pass itself, once the resource's full fill/reset schedule for the whole fight is known, iterating `context.burst_times[slug]` for each of the owner's own burst times and adding the Effect directly. - **Same-instant event ordering must be preserved by checking inline against the event log as you walk it, not by merging two independently-sorted lists.** A resource fill mode conditioned on BOTH a global event stream (any squad member's burst-tier fires, Full Burst starts) AND the resource's own running value (Maiden's MP: "+1 if MP==0 on any squad Burst 1", "+1 if MP>=1 on Full Burst enter") needs to know, at each instant, whether the resource's own reset (from its owner's own burst) has already happened relative to that instant's other events. Instead, `_resolve_squad_burst_cycle_resource` walks `simulate_burst_cycle`'s own event log in order and checks the owner's own-burst reset inline against each event as the walk reaches it — so same-instant ordering is exactly what the underlying event log already encodes, not a second-order artifact of the merge. - **A ZERO-LENGTH weapon-mode segment is an INSTANT magazine refill — the same trick as the zero-shot segment below, with the window collapsed to a point.** `_segment_shot_records` returns `cursor = seg["start"]` when `start == end`, and the overlap guard is `seg["start"] < cursor` (strict), so a zero-length segment neither fires a shot nor consumes time nor trips the guard — even two at the same instant are legal. The next stretch then restarts the base weapon with a fresh magazine at that exact time. Scarlet: Black Shadow's Asura ("Reload 100% of the magazine(s)" on Full Burst entry) is encoded this way. - **A "stacks up to N" buff measured in ROUNDS needs an explicit cap — `RoundGrant` has no stack semantics, and the overflow only shows up on charge-weapon recipients.** A round grant becomes one Effect per recipient covering that recipient's next N shots, so concurrent grants simply sum. For a fast magazine ally that is self-limiting (they fire faster than the granter, never holding more than one), but a charge weapon (RL/SR) idles through a reload and its first shot afterwards collects every grant that accumulated meanwhile — Zwei's "stacks up to 3" Pierce Equation was landing 5 on that shot. Two things this teaches beyond the bug: a stack cap expressed in rounds is invisible until a slow-cadence recipient exists, and "grants sum" is only accidentally correct when every recipient outpaces the granter.

- **The `per_shot_rules` pass runs AFTER `simulate_burst_cycle` has already fired every burst-cycle trigger — so a burst-cycle rule (`battle_start`/`own_burst_activate`/`full_burst_enter`/`full_burst_end`) cannot read a counter or status that a per-shot rule builds.** `raid_simulator.simulate_raid` calls `simulate_burst_cycle` first (firing all four burst-cycle trigger types against the current context), then runs the `per_shot_rules` pass afterward. A burst-cycle rule that tries `context.activation_count(...)`/`context.has_status(...)` for something only a per-shot rule increments will see the pre-per-shot value (typically zero), not the real end-of-cycle count. Concretely: if a buff's VALUE depends on a running normal-attack count AND another burst-cycle rule must read that count (Arcana: Fortune Mate's Keepsake Album, fired on `full_burst_end`, reads the Precious Moments stack that would naturally be built from "6th normal attack" shot-counting), the count must instead be built in the burst-cycle pass — e.g. increment once per Full Burst on `full_burst_enter` via `record_activation`/`activation_count`, not by counting shots directly. This substitution is only valid when the normal-attack threshold is guaranteed reached exactly once per relevant window (an exact per-cycle equivalence, not an approximation onto the wrong trigger) — Fortune Mate's SG fires far more than 6 shots in a 10s Full Burst window, so "6th normal during Making Memories" and "once per Full Burst" coincide exactly. Contrast: the resource-scaled/gated NUKE path (`resource_scaled_nukes`, `resource_gated_buffs`, above) IS deferred into a later resolution pass, so a nuke scaled by a per-shot-built resource count works fine — but a buff added directly to the registry via `registry.add` inside a burst-cycle rule's action does NOT get that deferred resolution; it reads the context synchronously, at the time the burst-cycle pass runs. See `raid_simulator.py` (the `simulate_burst_cycle` call followed by the `per_shot_rules` pass) and `skill_rules/arcana_fortune_mate.py::gain_precious_moments`/`apply_keepsake_album` for the worked example.

- **"Every 1 sec for N sec" is N ticks, not N+1** — the established convention (mana's `drop_tokens`/`resource_scaled_nukes` batching) applies unchanged to a repeating DoT elsewhere in the kit: Diesel: Winter Sweets' "63.33% of final ATK every 1 sec for 9 sec" DoT and her burst's 9-tick 1s DoT (`skill_rules/diesel_winter_sweets.py`) are both `tick_count=9`, not 10.
- **A charge weapon (RL/SR) fires a full charge on EVERY shot, so a "on full charge" trigger needs no separate full-charge counter — it's just `per_shot_every 1`.** Diesel's "Full Charge stacks (3s, cap 2)" buff is `("per_shot_every", 1)` feeding a `ResourceSpec(cap=2, lifetime=3.0)`, since every RL shot already IS a full charge. And a stack with both a CAP and a LIFETIME needs `ResourceSpec` specifically — `buff_rule` (infinite stacking) has no cap, `refreshing_buff_rule` (1-stack refresh) has no cap above 1, so any capped-stack mechanic (here: her 1s charge time holds both stacks inside one magazine, and the 2s reload lets one expire) should reach for `ResourceSpec` rather than either buff-rule helper.

## 버스트 사이클에는 "N단계 진입"이라는 별도 이벤트가 없다 — `[버스트 N단계 진입 시]`는 그 티어 유닛의 `own_burst_activate`다

Fienn의 정본 로테이션은 `게이지 충전 → 1단계 진입 → B1 사용 → 2단계 진입 →
B2 사용 → 3단계 진입 → B3 사용 → 풀버스트 10초`지만, 엔진(`burst_cycle.py`)은
"진입"과 "사용"을 하나로 접는다 — `on_tier_fire(tier, slug, time)`이 곧 "BN
사용"이고, 그 뒤 `on_full_burst_enter(tier3_fire_time)`이 호출된다. 즉
**`full_burst_enter` 시각 == tier-3 발동 시각 == B3 버스트 넉 시각**이다.

버프가 넉에 닿는지는 두 가지가 결정한다:
1. `effects.py`의 active-window는 **시작 포함**(`applied_at <= now < applied_at
   + duration`).
2. `raid_simulator`는 record-then-compute라, 넉 데미지는 2단계에서 **넉 시각
   기준 라이브 버프**를 읽는다 — 워크 도중의 등록 *순서*는 무관하고 오직
   버프 시작 시각 vs 넉 시각만 중요하다.

따라서 (`tests/test_burst_cycle_buff_timing.py`가 고정한 결과):
- **B3 유닛의 자기 버스트 넉**: `full_burst_enter` 버프도 `own_burst_activate`
  버프도 **둘 다 닿는다**(동시각 + 시작 포함). 수치적으로 동등.
- **B1/B2 유닛의 자기 버스트 넉**: `auto` 모드는 티어 간 gap이 0이라 동시각 →
  `full_burst_enter` 버프가 닿지만, **`manual` 모드는 티어 간 0.1초 간격이라
  B1 넉이 `full_burst_enter`보다 0.2초 먼저 발생 → 못 닿는다.**

**인코딩 규칙:** 스킬텍스트가 `[버스트 N단계 진입 시]`라고 말하면
`full_burst_enter`가 아니라 **그 유닛의 `own_burst_activate`로 인코딩하라.**
이유는 두 가지다 — (a) B1/B2에서는 manual 모드에서 자기 버스트딜을 놓치고,
(b) 어느 티어든 `full_burst_enter`는 **그 유닛이 버스트하지 않은 사이클에도**
발동해 버프를 과대 지급한다(같은 티어의 다른 유닛이 대신 버스트한 경우).
`full_burst_enter`는 진짜로 "풀버스트 창 진입"이 조건인 효과에만 쓴다.
첫 정정 사례: `laplace_ultimate_hero`의 Over Energy 52.14% (2026-07-24) —
그녀는 B3라 수치는 변하지 않았고, 바뀐 것은 과대지급 방지뿐이다.

**2026-07-24 확장 (Flora 애장품):** 아래 "스코프가 실제 판별 기준" 규칙은
**Stage 3 = Full Burst 진입**이라는 전제 위에 있다(`full_burst_enter`가 정확히
tier-3 발동 시각과 같으므로 "스쿼드 스코프 → `full_burst_enter`"가 성립).
Stage 1/2에는 대응하는 스쿼드 스코프 이벤트가 없어 이 규칙이 적용되지 않는다 —
Flora(B2)의 Petunia 불릿("Burst Stage 2 진입 시", 스쿼드 스코프)이 그 사례다.
`own_burst_activate`는 다른 B2가 슬롯을 가져간 사이클을 놓치고, `full_burst_enter`는
애초에 잘못된 이벤트(Stage 2 ≠ Full Burst)라 둘 다 못 쓴다. 해법은 신규 조건
`burst_stage_entered(tier)` + `ally_burst_activate`(모든 유닛 룰에 발동해 캐스터
자신의 사이클도 커버) — 자세한 내용은 `docs/decisions.md`("Burst Stage N 진입"은
own_burst_activate가 아니라...) 참고.

**스코프가 실제 판별 기준이다** (`snow_white_heavy_arms.py` docstring이 이미

## Burst rotation
- **A state-machine unit's state must be asked "decided by WHAT" before picking a modeling trick — a static mode slug lies the moment the deciding axis is one the engine actually simulates.** If the axis is something the engine does NOT simulate (Bready's Taste: which buff TYPE she receives), a static `MODE_VARIANTS` slug is enough — nothing in the sim depends on it. If the axis IS something the engine simulates (Diesel: Winter Sweets' Intro/Highlight lock depends on whether she bursts into the FIRST Full Burst — a real burst-schedule fact), a static slug is a lie: labelling her "Highlight" while still letting her burst on cycle 1 credits her the Highlight buff (235.03% vs Intro's 60.19%, ~4x) without ever paying the cost of skipping that burst. Fixed by making the Highlight slug actually skip that cycle via `burst_delay: {"skip_cycles": 1}` (see `docs/decisions.md`, "Diesel: Winter Sweets를 Intro/Highlight 2슬러그로 인코딩"), so the state-defining action is really taken, not just claimed. Ask this question first for any future locked-state unit.
- **A per-member burst delay (`burst_cycle.py::_ready_at`) lets a deck-search-driven sim represent a unit the player deliberately holds back, in three shapes that fold into one ready-time calculation:** `{"skip_cycles": N}` excludes the unit from the opening N cycles (returns `float("inf")` until then — Diesel, above); `{"not_before": T}` holds it until wall-clock T (Elegg: Boom and Shock, below); `{"min_interval": S}` stretches its effective cooldown to S whenever a refilling resource is slower than the cooldown itself (also Elegg). All three route through the same `_ready_at`, so tier selection and eligibility keep identical arithmetic regardless of which delay a member carries. A delayed unit left alone in its tier simply never bursts that cycle rather than firing early to "make something happen" — deliberate, since `ALLOWED_SHAPES` (`(1,1,3)`/`(1,2,2)`/`(2,1,2)`) never actually produces a lone-delayed-member tier in Burst 3 (always ≥2 members), so this can't silently zero out a real deck.
- **A resource that refills on WALL CLOCK must be measured from the unit's actual fire time, not the CDR-rewound cooldown timestamp.** `burst_delay`'s `min_interval` (Elegg: Boom and Shock's 13 Ghosts — caps at 13 stacks for a 13-hit branch vs 6-hit below cap; her real cadence is `spend_at_cap * capture_interval` = 54s, which outlasts her 40s cooldown) is measured against a SEPARATE timestamp, `last_fired_at`, that mirrors `last_used_at` but is never rewound by an ally's CDR pulse. Using the CDR-rewound `last_used_at` instead shortened her 54s refill window to 39s across 3 bursts in an early build — allied cooldown reduction speeds up HER cooldown but does nothing to how fast her ghosts actually refill, so the timer that represents the resource must be immune to the timer that represents the cooldown. Both `not_before` (her first cap: `cap * capture_interval` = 78s) and `min_interval` are derived from her own skill values in `skill_rules/elegg_boom_and_shock.py::build_elegg_burst_delay`, not hardcoded measurements — see `docs/decisions.md`.
- **`own_burst_fired_this_cycle()` doubles as an equivalence trick for "on FB enter while in [a self-status my own burst just granted]" — no new status-tracking needed.** Both Asuka's Emergency Repair (Skill 2, "on FB enter while in Annihilation State") and Mana's Metal sigma (Skill 2, "on FB enter while in Metal sigma status, consumed then restored by her own burst") describe a continuous named self-status gating a Full-Burst-entry buff. Because this engine's strict burst1→burst2→burst3→full-burst-enter ordering means a unit's own tier-3 burst always fires immediately before full_burst_enter in the SAME cycle, "her own burst fired this cycle" (the already-existing `own_burst_fired_this_cycle()` condition, previously used by Grave/Arcana for a full_burst_END gate) is exactly equivalent to "her self-granted status is still active" at the instant full_burst_enter checks it — for any deck this engine can simulate (one attacker per burst tier). Reuse this condition directly on a `full_burst_enter` trigger for any future unit with this shape, rather than building real `set_status`/`clear_status` bookkeeping. See `skill_rules/asuka_shikinami_langley_wille.py`, `skill_rules/mana.py`.
- **"Who bursts vs who buffs" = deck left-to-right order.** `burst_cycle` fires the leftmost eligible Nikke per burst tier, so the intra-tier ordering *is* the role assignment. The deck search explores those orderings. See `burst_cycle.py`.
- **Cycle timing waits for the slowest tier's cooldown.** The next Full Burst starts when whichever burst tier's cooldown clears latest (the gauge always charges faster than cooldowns for a raid-viable deck). A cycle is only "missed" when a burst tier is structurally absent from the deck, not when cooldowns lag.
- **`activation_count` starts at 0 — guard alternating-parity statuses against the pre-first-activation state.** A skill that alternates between two statuses each burst (e.g. Mint: Dancing on her 1st burst, Singing on her 2nd, ...) is naturally modeled as `count % 2 == 0` for the "even" status, but count 0 (before she has ever burst) also satisfies that — wrongly treating the unit as already in the even status from t=0. Guard with `count > 0`. See `skill_rules/mint.py::_mint_is_singing`.
- **Precise "highest final ATK" targeting must rank at APPLICATION time, using live buffs — not a static/squad approximation.** `SquadContext.top_atk_slugs` ranks the deck by each unit's ATK as buffed so far, evaluated when the targeting rule fires. This matters because of the same tier-ordering fact above: a Burst-1 unit's own burst (`own_burst_activate`, tier 1) fires before her Full-Burst-enter skill (tier 3), so by the time her FB-enter targeting rule runs, her own burst's ATK buff is already applied and correctly reflected in the ranking — dynamic (not pre-computed) resolution handles this automatically. See `skill_rules/miranda.py`, `nikke-skill-encoding/references/special-mechanics.md` ("Highest-final-ATK top-N targeting").
- **A per-shot/periodic condition sees the FINAL context, not a live one — timestamp alternating statuses instead of checking `has_status`.** Record-then-compute's post-pass evaluates every shot's condition against the whole-fight-final `SquadContext`, so `activation_count`/`has_status` there answer "at the end of the fight," not "at this shot's time." For a status that alternates or gets pinned mid-fight (Mint's Singing), record when it's true instead: `SquadContext.burst_times` (per-unit burst-tier fire times) + `status_since`/`set_status(..., time=...)` (earliest-set timestamp), then compute the status AT a given time (`skill_rules/mint.py::mint_singing_at`) rather than querying it live. This is what let solo Mint's per-cycle Dancing/Singing alternation finally be modeled (previously deferred as untrackable under per-shot).

## Deck search
- **Intra-tier order is a role assignment, not a tie-break — a deck search must score every ordering of a combination, not refine a canonical-order shortlist.** `simulate_burst_cycle` fires the FIRST ready member of each burst tier, so who sits leftmost within a tier decides who actually bursts and who becomes a buffer/normal-attacker that never does (a (1,1,3)'s rightmost Burst 3 commonly never bursts, Prika must precede Mint for her Encore hand-off, Velvet/Helm: Aquamarine are usually seated silent — see "Who bursts vs who buffs" below). Ranking a shape combination on one arbitrary ("canonical") order and only permuting a top-K shortlist by that score therefore mis-ranks the field twice over: once for the combinations scored on their wrong order, and again for any combination whose true value never made the shortlist at all. Measured on real data: up to 78% low, with the true best (1,1,3) landing outside a top-40 shortlist entirely (rank #21 under canonical scoring). `search_best_decks` now scores every intra-tier ordering of every combination (`_all_intra_tier_orderings`); `sim_budget` counts orderings, not combinations, since that's what the sims actually cost. See `docs/decisions.md` ("Deck search now scores every intra-tier ordering per combination...") and `backend/scripts/measure_intra_tier_ordering_impact.py` (reusable — rerun after touching `burst_cycle` or deck-search scoring).
- **`prune_candidate_pool`'s internal reference decks are decks too — they must satisfy the same legality invariants as decks the search actually returns, or the candidate pool they select from is silently wrong.** Landing mode-variant dual slugs (`docs/decisions.md`, "Mode-variant dual-slug expansion...") exposed this the hard way, over four separate follow-up fixes (commits `2eb7490`..`487aa25`): a reference shell could seat two variants of one base (missed because reference-deck construction calls `evaluate_deck` directly, bypassing the real candidate path's `_no_variant_clash` check); a cross-tier variant sibling (a `MODE_VARIANTS` pair spanning `VARIANT_BURST_TIERS`, e.g. Rapi: Red Hood's B1↔B3 pair) could displace the reference's only occupant of a DIFFERENT tier during swap-in, since the swap-in logic only checked same-base clashes, not cross-tier occupancy; and refusing an illegal swap outright silently starved the candidate at a permanent 0.0 score instead of falling back to measuring it against a legal alternative reference. The durable lesson: any new roster-shape rule (a clash constraint, a sole-occupant constraint, a cross-tier tie) must be threaded through the pruning heuristic's OWN internal deck construction, not just the search's real enumeration paths — the two are easy to keep in sync at the time a rule is written and easy to let drift the moment a second rule is added. See `docs/decisions.md` ("Rapi: Red Hood's Combat Assist branch is now a real Burst-1 candidate...") and `backend/app/deck_search.py`'s `_reference_deck`/`_variant_safe_top`/`_swap_slot`.

- **적합 그룹 안에서 어떤 변수가 상수면 그 변수의 효과는 적합값에 흡수되고, 전수 패리티가 통과하는데도 모델이 틀린다 — "설명 안 됨" 예외는 그 흡수가 깨진 자리다.** 스탯 모델은 호감도를 배수 밖에 더했고 159기를 오차 1.0 안에 재현했다. 그게 통했던 이유는 코어 있는 유닛이 적합 그룹마다 **호감도가 단일**했기 때문이다(class 30, PILGRIM/OVERSPEC 40). 호감도가 다양한 그룹은 둘뿐이었고, 그 안의 호감도 10 유닛이 정확히 `CORE_FLAT_*_BY_RESOURCE_ID`의 "NOT explained" 3기(Vesti·Rosanna·Nero)였다. 진짜 규칙은 **호감도가 `(1 + 0.02×코어)`로 스케일된다**는 것이고, 넣어보니 그 3기가 오차 0.01~0.27로 설명되고 **OVERSPEC 계층도 사라졌다**(그것도 호감도 40 대 30의 착각). 진단 순서가 재현 가능하다: ① 같은 조건이어야 하는 관측값이 어긋나면 ② **적합 그룹별로 다른 변수들의 분포를 세어라** — 단일한 변수가 있으면 그게 흡수된 후보다 ③ 두 점으로 적합해 세 번째 점을 **예측**해 검정하라(여기서는 오차 1.11 대 기존 22.3). 그리고 **표를 최대한 줄이려는 유혹을 참으라**: ATK를 2행(PILGRIM 여부)으로 줄여도 159기를 통과하지만 최대 오차가 0.99로 임계값에 붙어 새 유닛 하나에 깨진다.
- **"추측하지 않고 예외를 던진다"는 옳은 판단이지만, 그 예외의 폭발 반경을 정해두지 않으면 데이터 공백 하나가 계정 전체를 못 쓰게 만든다.** `core_flat_atk`/`core_flat_hp`는 측정 안 된 조합(코어 올린 PILGRIM/OVERSPEC **Supporter**)에 대해 class 값으로 폴백하는 대신 `KeyError`를 던진다 — 폴백은 코어당 14~30 틀리므로 **옳은 설계다**. 그런데 그 예외가 엔드포인트까지 올라가 **부계정 첫 싱크가 500**으로 죽었다. 유닛 1기의 공백이 나머지 ~150기를 못 쓰게 만든 것이다. 고친 방향: 전용 예외(`UnmeasuredStat`)를 두고 로스터 조립이 **그 유닛만 빼고 이유와 함께 보고**한다 — `assemble_roster`가 이미 디렉토리 누락·상세 누락·비SSR을 건너뛰는 것과 같은 취급이다. 조용히 빼면 안 된다(그 유닛은 인코딩돼 있어서 그냥 사라진 것처럼 보인다). **진단 함정 둘**: ① `if core:` 가드가 있어서 코어 0이면 호출조차 안 된다 — 그래서 본계정은 같은 유닛(Grave·Nayuta·Little Mermaid)을 갖고도 내내 정상이었고, "부계정이라 투자가 적어서"라는 가설은 **재현으로 반증됐다**(투자 0·연구 0·어피니티 0으로도 200). ② ATK를 고치면 **HP에서 다시 터진다** — `CORE_FLAT_HP_OVERSPEC`에도 Supporter가 없고 PILGRIM은 OVERSPEC로 취급된다. 같은 공백은 표가 나뉘어 있으면 표마다 확인하라. 영향 유닛은 정확히 PILGRIM∩OVERSPEC Supporter 6기(Chime·Dorothy·Grave·Little Mermaid·Nayuta·Rapunzel).
- **실패를 삼키는 별도 호출에서 읽어온 선택적 값은, 저장된 좋은 값을 덮어쓰면 안 된다 — 빈 값은 "없음"이 아니라 "이번엔 못 읽었음"이다.** 계정 닉네임은 로스터와 다른 blablalink 호출(`GetUserProfileBasicInfo`)에서 오고, 북마클릿이 그 호출을 `.catch(()=>null)`로 감싸 실패해도 싱크는 성공한다. 그런데 `upsertProfile`이 `nickname: args.nickname`으로 무조건 덮어써서, 그 호출이 한 번 실패한 재싱크가 **잘 저장돼 있던 닉네임을 지우고** Account 드롭다운을 원래 open_id로 되돌렸다. 증상이 "코드 회귀"처럼 보이지만 코드(`ProfileSwitcher`의 `nickname || openId`)는 멀쩡하고 **데이터가 비어 있는 것**이다. 그리고 앱이 매 렌더에 북마클릿 href를 새로 만들어도 **유저 북마크바에 저장된 복사본은 그 시점에 얼어 있다** — 닉네임 지원이 들어오기 전에 저장한 북마클릿을 계속 쓰면 매 싱크가 빈 닉네임을 보낸다. 일반화: 값의 **출처가 본체와 다른 호출**이고 그 실패가 조용하면, 저장 계층에서 `new || stored`로 방어하고 못 읽었다는 사실을 사용자에게 보이게 하라.
- **어떤 유닛을 화면에서 "빼서" 문제를 피할 때는, 그 화면이 다른 기능도 겸하고 있는지 보라 — 드래프트 팔레트는 제외 토글까지 겸한다.** 드래프트로 앉힐 수 없는 유닛(소유 슬러그가 구체적 spec이 아닌 경우)을 드래프트 팔레트에서 걸러내 422를 피했는데, 드래프트 모드에서는 풀 팔레트가 **아예 렌더되지 않아**(`mode !== 'draft'`) 그 유닛이 **보이지도·제외되지도** 않게 됐다. "raid 모드와 동일하니 회귀 없음"이라는 판단이 모드별로 렌더 트리가 다르다는 사실에서 깨졌다. 일반화: **필터로 문제를 회피하기 전에, 그 리스트를 소비하는 컴포넌트가 몇 가지 역할을 하는지 세라.** 또 하나 — 이런 유닛을 "유저가 직접 고르게" 하는 우회는 **선택의 주체가 도메인마다 다를 때 거짓이 된다**: Cinderella의 MG/Snipe는 플레이어가 고르지만 Bready의 모드는 덱의 버퍼가 결정한다. 결국 엔진이 후보별로 덱을 완성해보고 고르는 쪽(`_seed_choices`)이 정답이었다. 그리고 **잠금·대조는 반드시 같이 base 키로 옮겨야 한다**: 잠금을 슬러그로 비교하면 `bready` 잠금이 실제 앉은 `bready-lingering`에 안 걸려 조용히 풀리고, 결과 대조를 슬러그로 하면 "하나 빼고 하나 넣음"으로 읽히며 슬러그 겹침 기반 덱 짝짓기는 그 덱을 못 짝지을 수 있다. `docs/decisions.md`("드래프트도 소유 슬러그로 받는다...") 참조.
- **한 개체가 "소유 단위"와 "엔진 후보 단위"로 서로 다른 이름을 가지면, 그 둘을 교집합하는 화면이 조용히 유닛을 잃는다 — 카탈로그가 두 어휘를 다 말해야 한다.** 동기화된 로스터는 플레이어가 **소유한** 것(`bready`)을 이름하고, 결과 덱은 엔진 **후보**(`bready-lingering`)를 이름한다. `/api/supported-units`가 후보만 반환했으므로 "owned ∩ supported"로 팔레트·로스터 그리드·풀 카운트를 만드는 프론트가 3명을 탈락시켰고, 그 3명을 백엔드는 내내 출전시키고 있었다 — 화면이 "아직 지원 안 됨"이라 적은 유닛이 추천 덱에 앉아 있는 상태. **증상이 카운트로 먼저 드러난다**: `70/70`(실제 77유닛/73캐릭터)과 `89`(백엔드 excluded는 86)가 3만큼 어긋났고, 그 3이 정확히 문제의 캐릭터 수였다. 산술로 검산하라 — 배치+벤치+제외가 로스터 크기와 안 맞으면 어휘가 어긋난 것이다(25+52+86=163=159+확장 4). 해법은 후보 엔트리를 **대체**하지 말고(결과 화면이 후보로 조회한다) 소유 슬러그 엔트리를 **추가**하는 것이며, 같은 규칙이 초상화 매니페스트에도 적용된다(한쪽 어휘만 키로 두면 다른 쪽이 빈 박스를 그린다). 그리고 **어휘를 늘리면 그 어휘를 좁게 받는 경로를 반드시 같이 점검하라**: 팔레트에 base가 등장하면 드래프트로 끌어놓을 수 있게 되는데 `api.py`는 드래프트 좌석을 구체적 spec으로만 해석해 422를 준다 — 새 엔트리가 새 버그를 만들 뻔했다(`canSeatInDeck`으로 드래프트 팔레트만 걸러냄). `docs/decisions.md`("`supported-units`가 두 어휘를 다 말하게...") 참조.
- **"한 덱 안에서 안 겹친다"는 규칙은 레이드 할당에서 부족하다 — 동시 출전하는 5덱 전체가 하나의 배타 범위다.** `MODE_VARIANTS`는 한 소유 캐릭터를 여러 후보 슬러그로 부풀리고, 그 규칙을 `_no_variant_clash`가 **덱 단위로** 지켰다. 레이드 할당은 덱을 슬러그로만 서로소로 유지했으므로 통과했고, 실제 로스터에서 `rapi-red-hood`(Deck 2)와 `rapi-red-hood-b1`(Deck 4), `cinderella-crystal-wave-mg`(Deck 2)와 `-snipe`(Deck 4)가 동시에 앉은 결과가 나왔다 — 게임에서 만들 수 없는 편성이고 합계 데미지도 과대평가였다. 일반화하면: **어떤 개체가 "여러 후보로 부풀려진 하나"라면, 배타 범위는 그 후보들이 함께 소비되는 가장 넓은 단위여야 한다.** 여기서는 덱이 아니라 할당 전체다. 두 번째 함정은 **불변식을 언제 세우느냐**였다 — peel에서 캐릭터 단위로 걸러도 두 후보가 **모두 벤치에 남는** 경우(실측: `bready-lingering`·`bready-recommended` 동시 벤치)가 있어서, 힐클라임이 하나씩 서로 다른 덱으로 끌어올려 같은 버그를 재생산한다. `_try_swaps`의 "후보 목록은 절대 낡지 않는다"는 불변식에서 **유일하게 낡는 필터**가 이것이므로, 채택 시점에 아직 안 본 꼬리만 걷어낸다(전체 재계산은 스캔 순서를 바꿔 "첫 개선 채택" 규칙을 깬다). 배타 키는 `deck_search.variant_base` 하나로만 두라 — 같은 분기를 두 곳에 복제하면 `supported_units`/`user_roster` 때처럼 한쪽만 갱신된다("`supported_units()` must resolve a slug's metadata..." 참조). `docs/decisions.md`("레이드 할당의 배타 단위를 슬러그에서 소유 캐릭터로...") 참조.
- **The peel+swap hill-climb only ever accepts a strictly-improving swap, so a weak/uninvested unit can never win a seat away from the field — a pool-reduction lever (letting the user exclude units from the search) buys speed and preference, not result quality.** Peeling and the same-tier swap phase (see "Five-deck allocation algorithm" below) both only take moves that raise the summed score, so a unit that would lower it never gets picked regardless of whether it's in the searched pool or not — excluding it from the pool changes how long the search takes and whether irrelevant units even get shown, not which units the recommender would have chosen. Keep this in mind before reaching for a pool-shrinking feature as a *quality* fix — it's a speed/preference lever, and the algorithm's own monotone-improvement property already keeps weak units out of results without one. See `docs/decisions.md` ("유저 주도 '사용할 니케' 풀 선택...").

- **A deck's damage lives in timeline-dependent nukes, so a fit-free static scorer cannot rank decks — measured, not assumed.** `backend/app/closed_form.py` fires a deck's skill rules once against a real `EffectRegistry` (the encodings are thin closures over `Effect(stat, value, scope, duration)`, so this harvests the whole buff table with no timeline and no shot loop) and estimates damage off that snapshot, mirroring `raid_simulator._damage_instance` term for term. It is ~140x faster than a simulation (0.79 ms vs 110 ms per deck) and skips zero skill bullets — and it still only reaches **Spearman 0.54** against real damage, with the true-best deck landing at rank 157 of 300 and its own top pick delivering **64% of the best damage** (a random pick averages 33%). The reason is structural and quantified (`scripts/measure_unmodeled_damage_share.py`, 60 decks, 40-unit roster): only **60% of damage comes from normal attacks + burst nukes**, the two sources a static snapshot can see. The rest is per-shot nukes (17.6%), resource-scaled nukes (7.1%), periodic (5.9%), scheduled (5.0%), instant (3.2%) and dynamic-hit-count (1.0%) — and the unseen share swings from **6% to 62% per deck**, so it is deck-dependent noise, not a constant bias that would cancel out of a ranking. Two rounds of fixing the obvious errors (only the tier's leftmost unit bursts; the cycle length derived from the bursters' cooldowns minus the deck's own CDR instead of a fixed 20s) moved Spearman by −0.02, i.e. nothing: the ceiling is the unmodeled 40%, not the modeling of the visible 60%. Before reaching for "just use a cheap formula like the other tools do" (Genshin Optimizer et al. — see `docs/decisions.md`), note that those tools' damage IS their formula, whereas here the formula is 60% of the answer. See `docs/decisions.md` ("캐스케이드 대리모델: 표본 회귀 vs 닫힌 수식...").

- **A pair bonus with a FIXED partner is representable by a per-unit additive model — so it proves nothing about synergy blindness. Use a cancelling pair instead.** Written while building the cascade's quality regression test, where the first fixture planted "`{A,B}` together = +100" believing a unit-only ridge could not express it. It can: `A` co-occurs with the bonus in every sampled deck that contains it, so the fit simply absorbs the bonus into `A`'s coefficient. Measured, the effect is not merely weak but *inverted* — raising the bonus 40 → 100 moved `A` from third to first in its tier's coefficient ranking and made the cascade return the optimum at **every** shortlist width, i.e. the test became unable to fail. The fix is a synergy whose sign depends on the partner: `{A,B}` = **+100** and `{A,C}` = **−100**, so `A`'s coefficient averages toward neutral and the additive model genuinely cannot tell the good partner from the bad one. Only then did the fixture expose real behaviour. The general rule for testing any additive surrogate: a term is representable if it correlates with a single feature — to defeat it you need one that cancels across that feature's occurrences. See `backend/tests/test_deck_allocation.py`.
- **The cascade's `prune_candidate_pool` seat is load-bearing, not belt-and-braces — measured at 100% vs 90.6% of optimal.** `widened_pool` seats prune's picks before filling the rest by surrogate coefficient, and that ordering is what rescues a unit whose value lives entirely in a synergy the surrogate cannot see: such a unit ranks LAST by coefficient (correctly — its solo value is low), so the coefficient-ranked pass drops it at the tier cap before `top_k` is ever consulted. `prune_candidate_pool` measures marginal contribution by actually simulating a reference deck, so it *does* see the synergy and pulls the unit in. With the safety net the cascade returned the true optimum; with prune stubbed out it returned **90.6%**. The two filters are worth keeping precisely because their blind spots differ — a cheap ranker's failure mode is not a reference-deck heuristic's. See `docs/decisions.md` ("캐스케이드 Phase 2 착지...") and the paired tests in `backend/tests/test_deck_allocation.py`.

- **A uniform-investment roster is not a neutral perf fixture — it changed the measured value of a change by 2.6x, in the direction nobody predicted.** Every deck-builder perf number up to 2026-07-25 came from "the first N supported slugs, all at ATK 60,000 / skills 10/10/10 / no overload". The real synced roster differs on every axis a swap verdict touches: ATK 82,895-144,793 (1.75x spread), 23 distinct skill-level combinations, 0-6 overload rows per unit. The prediction going in was that uniform stats make same-tier units nearly interchangeable, maximizing near-tie verdicts, so the synthetic fixture would OVERSTATE the hill-climb's difficulty. Half right and wrong where it counted: the real roster does converge sooner (22.2s / 2,363 sims vs 31.3s / 3,734), but the damage the old serial cut-off was throwing away is **10.5% of the allocation total on the real roster against 4.0% on the synthetic** — the fixture was understating the fix's worth, not overstating its cost. Real rosters have clearly-better units, so greedy peeling's mistakes are *larger* and concentrated where swap arrives late. Do not reason about which direction a synthetic fixture biases a perf number; measure on the real roster (`scripts/roster_fixture.py` loads it, and reports which one a run used).
- **A serial hill-climb parallelizes without changing its answer if you batch SPECULATIVELY and re-batch on acceptance — the trick is proving the candidate LIST is invariant even though the scores are not.** The swap phase looked unparallelizable ("each accepted swap changes the state the next candidate is judged against", `docs/decisions.md` 2026-07-17) and was deferred twice for that reason. But the dependency is only on the *scores*: the candidate list — (seat, partner) pairs surviving the same-tier and not-locked filters — cannot change, because a same-tier swap leaves both seats' tiers untouched and a locked unit is never a swap source on either side. So the whole list can be scored ahead of the walk, and the walk keeps the serial rule (accept the FIRST improvement, in the original order); only when it accepts does the rest of that batch become stale, and then it re-batches from the next candidate. The result is bit-identical to the serial version — pin that with a test that runs the same fixture at several batch widths and asserts one outcome, plus one where the second candidate improves on the ORIGINAL deck but not the accepted one (a naive implementation trusting stale scores seats the worse unit). Waste is bounded by the acceptance rate, which was under 1% of candidates on a 78-unit roster. General shape: before declaring a sequential loop unparallelizable, separate what the iteration *reads* from what it *decides* — often only the former is order-dependent.
- **A threshold that guards creating an expensive resource must not also gate reusing it.** `SimPool.SPAWN_THRESHOLD = 32` ran small batches inline, which is right when the cost in question is starting a `ProcessPoolExecutor` (spawning processes, pickling the roster into each). Applied to *every* batch, though, it silently refused an executor that was already warm — and the swap hill-climb's deck-to-deck candidates arrive ~22 at a time, so they all fell through to the serial path. First measurement of the batched phase came back at 1.9x instead of the workers' worth; the 282 inline sims were ~29s of a 45s budget while the pooled leftover batches did twice the work in ~4s. Fix was one condition (`len(decks) < threshold and self._executor is None`). Watch for this shape wherever a lazily-created resource has a "is it worth it?" guard — the guard's cost model is about creation and stops being true the moment the resource exists.
- **A real scoring bias can still be worth leaving in: the swap hill-climb judges candidates on ONE canonical ordering — a method this codebase measures as up to 78% low — and fixing it buys ≤0.47%.** `_swap_pass` scores a deck in the order the search returned it, then replaces one seat and re-scores in that same order. The decks arriving from `search_best_decks` are already at their BEST ordering while the unit swapped in may want a different seat in its tier, so the error does not cancel between incumbent and challenger — it is biased *against* the challenger, and the hill-climb rejects swaps that would have won. All true, and measured worthless to fix: judging every candidate on its best ordering, run to convergence on the real 77-unit roster, gained **+0.02% (Water/180s), +0.47% (Fire/180s), +0.14% (Electric/90s)** while making the whole allocation 3.3-5.4x slower (`scripts/audit_swap_ordering.py`). **The reason is that the objective is flat near its optimum** — the Water run's two methods produced *completely different* five-deck compositions whose totals differed by 0.02%. A mis-ranked swap does flip the verdict; it just lands on another local optimum of the same value. The durable lesson: a demonstrable bias in a heuristic's judgment is not the same as a loss in its output, and on a flat objective the two can differ by two orders of magnitude — measure the output, not the bias. (Revisit if shells grow, raising orderings per deck, or if synergies become far more order-sensitive.) See `docs/roadmap.md`.

- **jsdom `<details>` test trap: default a collapsible open (`<details open>`) if a test needs to find content inside it.** jsdom keeps a closed `<details>`'s content out of the accessibility tree, so RTL/Testing-Library queries for controls inside it fail as if they don't exist. jsdom's handling of a `<summary>` click toggling `open` is also flaky — avoid writing a test that depends on that toggle; default the element open in tests (or in the component, if there's no product reason to default-collapse) instead of simulating the click.
- **A non-interactive `<span>` cannot carry a meaningful `aria-label`.** A `<span>` has the generic ARIA role, which screen readers ignore any `aria-label` on — the accessible name computation only honors `aria-label` on elements with a non-generic role (or an interactive one). If the visible text already names the element, an `aria-label` duplicating it is both useless and dead weight; drop it (found while wiring the unit-pool palette's per-unit `<span>`, commit `6309514`).
- **Deterministic engine ⇒ exact result caching, but the cache key must include EVERY result-affecting input, not just the "obvious" ones.** `evaluate`/`recommend` are RNG-free pure functions of (ordered specs, boss), so caching `(inputs) -> result` client-side (`frontend/src/lib/inputHash.ts`, FNV-1a over a canonicalized snapshot) is exact, not a staleness heuristic. A self-caught bug before ship: the first hash omitted `num_decks`, so a 3-deck and a 5-deck allocation of the identical roster collided onto the same cache entry and served the wrong result. See `docs/decisions.md` ("Per-profile recommendation result persistence...").
- **Per-profile UI isolation needs a `key={activeProfileId}` remount, not just swapping the data underneath a persistent component.** A shared async hook (e.g. `useRecommendRaid`) living inside a panel component that ALSO persists its result on completion can leak across profiles: a slow request submitted under profile A can resolve after the user has already switched to profile B, and its persist callback — closed over whatever "current profile" means at call time — writes A's result into B's slot (or displays it). Fix: give the stateful panel a React `key` bound to the active profile ID, so switching profiles remounts it with fresh hook state and orphans the old in-flight request's effects on unmount (React drops results delivered to an unmounted component's closures). - **React 19 hard-blocks a `javascript:` URL passed through a JSX `href` prop, even in the production bundle — a bookmarklet's install link can't be set that way.** `react-dom`'s `sanitizeURL` replaces any string matching its javascript-protocol regex with `"javascript:throw new Error('React has blocked a javascript: URL as a security precaution.')"`; confirmed against react-dom 19.2.7's `cjs/react-dom-client.production.js`, so this is not a dev-only warning. See `frontend/src/components/SyncRosterPanel.tsx`'s `ref={(el) => { el.href = buildBookmarklet(...) }}`.
- **A blablalink re-sync REPLACES a profile's roster wholesale — it must not merge with what was there before.** A sync response is the account's full current roster as of now, so applying it as a merge (the old `mergeCollectorDrafts` helper, now deleted) would retain units the player no longer owns (sold/never-had entries left over from a stale prior sync). Overwrite the profile's roster entirely on every re-sync.
- **Keep account identifiers off the backend even though the client needs them for profile keying/labeling.** `open_id`/`nickname` are captured client-side (during blablalink sync, for `nikke-profiles` keying and nickname display) but are destructured out of the request body before it reaches `/api/assemble-roster` — see `frontend/src/api/assembleRoster.ts`'s `const { open_id, nickname, ...rosterPayload } = payload`. Only the anonymous per-browser `clientId` (`X-Client-Id` header, `frontend/src/lib/clientId.ts`) ever reaches this project's backend, and neither `open_id` nor `nickname` is ever sent to blablalink either. This keeps the multi-account feature's account identifiers a purely client-side (localStorage) concern.
